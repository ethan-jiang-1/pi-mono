## 现象是什么

pi-mono 提供了两个文件修改工具：

- **edit**：精确的字符串替换引擎。模型给出 `oldText`（要替换的内容）和 `newText`（替换成什么），工具在文件中定位 `oldText` 并替换。支持一次调用中的多个 disjoint edits。
- **write**：创建或覆盖文件。自动创建父目录。内容可以是任意文本。

这两个工具在 TUI 中会渲染 diff 预览（edit 工具渲染在实际执行前的 preview），让用户在工具调用参数完成时就能看到将要发生的改动。

## 核心矛盾是什么

文件修改是 agent 系统中最危险的操作，因为它的副作用是**持久化的**。（解释）核心矛盾围绕以下几点：

1. **Read-then-write 一致性**：LLM 可能在"读文件"和"写文件"之间得到过时的文件内容（用户手动修改了文件，或者另一个工具修改了文件）
2. **并发修改冲突**：多个工具调用可能同时操作同一个文件（特别是在 `toolExecution: "parallel"` 模式下）
3. **Whitespace 和 BOM 处理**：LLM 不理解文件中的 BOM（字节序标记），也可能在匹配时因为换行符（CRLF vs LF）而失败
4. **匹配精度**：edit 工具的 `oldText` 必须精确匹配文件中的文本，包括缩进、空行、空白字符

## 实现思想是什么

### 两套实现

和 bash 一样（见 4.5），v0.84.2 有两条平行实现，共享同一套 edit-diff 算法语义：（硬事实）

- **harness 线**：`packages/agent/src/harness/tools/edit.ts`（127 行）、`write.ts`（39 行）——纯 `ExecutionEnv`，`createEditTool<TContext>()`（edit.ts:77）/ `createWriteTool<TContext>()`（write.ts:15）**不带 options**；可插拔性来自 `ExecutionEnv` 本身
- **产品线**：`packages/coding-agent/src/core/tools/edit.ts`（443 行）、`write.ts`（274 行）——`createEditToolDefinition(cwd, options?)`（edit.ts:316）/ `createWriteToolDefinition(cwd, options?)`（write.ts:187），带 `EditOperations`（edit.ts:96）/ `WriteOperations`（write.ts:31）可插拔接口和 TUI 渲染回调

### Edit 工具

**参数结构（两线一致）：**

```typescript
const editSchema = Type.Object({
  path: Type.String(),                           // 文件路径（相对或绝对）
  edits: Type.Array(Type.Object({
    oldText: Type.String(),                      // 要替换的精确文本
    newText: Type.String(),                      // 替换后的文本
  })),
});
```

**执行流程（harness 线，edit.ts:89-125）：**

1. `prepareEditArguments()`（L48）：处理 legacy 格式——某些模型（源码注释点名 Opus 4.6、GLM-5.1）把 `edits` 发成 JSON string 而不是 array；或用顶层 `oldText`/`newText` 字段而非 `edits[]` 数组，两种都自动转换
2. `validateEditInput()`（L66）：验证至少有一个 edit
3. `resolveToolPath(env, path)` 异步解析绝对路径
4. **通过 file mutation queue**：`withFileMutationQueue(env, absolutePath, () => ...)` 确保同一文件的操作串行
5. 读文件（`env.fileInfo` 校验 kind）→ `stripBom()` → `detectLineEnding()` → `normalizeToLF()` → 应用 edits → `restoreLineEndings()` + 重新前置 BOM → 写文件。每步之间检查 `signal.aborted`

**Edits 应用算法：**

```typescript
const { baseContent, newContent } = applyEditsToNormalizedContent(
  normalizedContent,  // 已转为 LF 的文件内容
  edits,              // oldText/newText 对
  path,               // 用于错误报告
);
```

每个 `edits[].oldText` 都在**原始文件**上匹配（不是在之前 edit 的结果上），且要求唯一、互不重叠。（硬事实）这避免了编辑顺序带来的歧义。（解释）如果两个修改触及同一个代码块或邻近行，模型应该把它们合并成一个 edit。返回的 `details` 包含 `diff`（展示用）、`patch`（标准 unified patch）和 `firstChangedLine`（编辑器跳转用）（edit.ts:115-122）。

**Diff 生成和渲染（产品线）：**

- 预执行 diff：`computeEditsDiff()` 在工具调用参数完成后生成 preview diff，`renderCall()`（edit.ts:369）异步加载——LLM 和用户都能在实际执行前看到将要发生的改动
- 执行后 diff：`generateDiffString()` 基于实际 `baseContent`/`newContent` 生成

### Write 工具

**参数结构：**

```typescript
const writeSchema = Type.Object({
  path: Type.String(),
  content: Type.String(),
});
```

**执行流程：**

- harness 线（write.ts:26-36）：`resolveToolPath` → mutation queue → `env.writeFile()`。"创建父目录"是 `FileSystem.writeFile` 契约的一部分（"Create or overwrite a file, creating parent directories when supported"，`harness/types.ts:248`），不需要单独 mkdir
- 产品线（write.ts:210-224）：queue 内先 `ops.mkdir(dir)`（`recursive: true`）再 `ops.writeFile()`，两步之间检查 abort。注释明确说明**不在 abort listener 里 reject**——那样会在文件系统操作还在飞行中时就释放队列锁；改为在每个 await 之后检查，观察到同样的 abort 同时保持队列锁定直到当前操作 settle

**语法高亮渲染（产品线）：**

Write 工具实现了增量语法高亮：`rebuildWriteHighlightCacheFull()`（write.ts:82）初次全量高亮；`updateWriteHighlightCacheIncremental()`（L96）在参数流式传入时增量更新——只有新增部分需要高亮，未完成的首行重新算，其余行单独高亮。这在 TUI 中提供近乎实时的文件预览。

**可插拔操作（产品线）：**

```typescript
interface EditOperations {
  readFile: (path: string) => Promise<Buffer>;
  writeFile: (path: string, content: string) => Promise<void>;
  access: (path: string) => Promise<void>;   // R_OK | W_OK 检查
}
interface WriteOperations {
  writeFile: (path: string, content: string) => Promise<void>;
  mkdir: (dir: string) => Promise<void>;
}
```

默认本地文件系统（`fs/promises`），可被 extensions 替换为远程文件操作。harness 线没有这层接口——换实现就是换 `ExecutionEnv`。

### File Mutation Queue（file-mutation-queue.ts）

这是保证文件修改一致性的关键基础设施。（解释）**harness 线**（`agent/src/harness/tools/file-mutation-queue.ts`，56 行）：

```typescript
// per-env 隔离：WeakMap 保证每个 ExecutionEnv 实例独立、env 被 GC 时队列自动清理
const states = new WeakMap<ExecutionEnv, MutationQueueState>();

export async function withFileMutationQueue<T>(env, path, fn): Promise<T> {
  // 1. key 计算本身也被串行化（state.registration 链），
  //    避免两个并发调用在 canonicalPath 解析期间插队
  // 2. key = canonicalPath(absolutePath(path))；
  //    not_found / not_supported 时回落到 absolutePath（新文件还没有 realpath）
  // 3. 链式追加：currentQueue.then(() => nextQueue)，fn 执行完 releaseNext()
  // 4. 队尾自清理：state.queues.get(key) === chainedQueue 时 delete
}
```

**设计要点：**

1. **Per-env 串行化**：同一个 env 内同一文件的操作串行；不同文件并行；不同 env 互不影响（多 session/多租户场景）（硬事实）
2. **realpath 去重**：符号链接和相对路径解析为相同 canonical key，防止绕过；尚不存在的路径（新 write 目标）回落到绝对路径 key（硬事实）
3. **注册串行化**：v0.84 的实现把"解析 key + 占位入队"放进 `registration` promise 链（L31-48），并发调用不会因为 async canonicalPath 而交错建队（硬事实）
4. **队列链式追加**：没有 mutex/lock。新操作追加到 promise 链上，前一个完成时自动触发下一个；异常路径由 finally 保证 `releaseNext()` 一定执行（硬事实）
5. **自清理**：最后一次操作完成后从 map 删除，防内存泄漏（硬事实）

**产品线**（`coding-agent/src/core/tools/file-mutation-queue.ts`，61 行）是同一算法的全局版：`Map<string, Promise<void>>` 全局 key 空间（`realpath` 去重，ENOENT/ENOTDIR 回落 resolved path），同样有 registration 串行化；签名是 `withFileMutationQueue(filePath, fn)`（无 env 参数）。

### 权限集成

Edit 和 Write 的权限拦截与 bash 相同，在 AgentSession 层通过 `agent.beforeToolCall` → `ExtensionRunner.emitToolCall()` 完成（见 4.4/4.5）：（硬事实）

```typescript
// extension: my-permissions.ts
export default function (api: ExtensionAPI) {
  api.on("tool_call", (event) => {
    if (event.toolName === "edit" || event.toolName === "write") {
      const resolvedPath = resolve(event.input.path);
      if (!resolvedPath.startsWith(allowedDir)) {
        return { block: true, reason: "Cannot modify files outside project directory" };
      }
    }
  });
}
```

## 在 Agent 能力面里的影响是什么

1. **File Mutation Queue 保证了不会出现竞态条件**。（解释）即使在 parallel tool execution 模式下，同一文件的 edit/write 操作也是串行的。

2. **Read-then-write 不是工具的责任**。（解释）权限 hook 是 LLM 层面的，工具只负责单次执行。一致性由 LLM 的调用顺序（先 read 再 edit）加 per-file 串行化共同保证。

3. **Edit 的 "在原始文件上匹配" 语义减少了复杂性**。（解释）不需要处理 edit 之间的交错影响，模型侧的规则（不重叠、就近合并）写进了工具 description。

4. **BOM 和换行符的透明处理对 LLM 友好**。（解释）LLM 不需要理解 BOM 或换行差异——读时剥、写时原样恢复。

5. **Abort 语义与队列锁一致**。（硬事实）abort 检查发生在 await 边界而不是事件回调里，队列锁总是等到当前操作 settle 才释放。

## 最小例子是什么

```typescript
// harness 线：从 pi-agent-core 主入口导入（不再有 "./harness" 子路径导出）
import { createEditTool, createWriteTool } from "@earendil-works/pi-agent-core";
// withFileMutationQueue 未从包导出（tools/index.ts 只导出工具 factory），
// 仓库内引用模块路径：agent/src/harness/tools/file-mutation-queue.ts

// 1. 创建工具（harness 线无 options —— ExecutionEnv 就是扩展点）
const editTool = createEditTool();
const writeTool = createWriteTool();

// 2. LLM 调用格式
// edit:   { path: "src/main.ts", edits: [
//            { oldText: "const x = 1;", newText: "const x = 2;" },
//            { oldText: "console.log(x)", newText: "logger.info(x)" }
//          ]}
//         —— 两个 oldText 都在原始文件上匹配，必须互不重叠且各自唯一
// write:  { path: "src/new-file.ts", content: "export const foo = 'bar';\n" }

// 3. 直接执行（context 提供 ExecutionEnv）
const result = await editTool.execute(
  "call_1",
  { path: "src/main.ts", edits: [{ oldText: "const x = 1;", newText: "const x = 2;" }] },
  undefined, undefined,
  { env: myExecutionEnv },
);
// 观察到的信号：result.details.diff 是统一 diff，result.details.patch 是标准 patch，
// result.details.firstChangedLine 指向第一处变更行

// 4. File mutation queue 也可以单独使用（harness 线签名带 env）
await withFileMutationQueue(myExecutionEnv, "/path/to/src/main.ts", async () => {
  await myExecutionEnv.writeFile("/path/to/src/main.ts", newContent);
});

// 5. 产品线自定义 EditOperations（远程文件编辑）
import { createEditTool as createProductEditTool } from "@earendil-works/pi-coding-agent";
const remoteEditTool = createProductEditTool("/remote/project", {
  operations: {
    readFile: async (path) => Buffer.from(await sshReadFile(path)),
    writeFile: async (path, content) => await sshWriteFile(path, content),
    access: async (path) => await sshStat(path),
  },
});
```

关键要点：**edit 和 write 通过 file mutation queue 保证同一文件的串行修改（harness 线按 ExecutionEnv 隔离、产品线全局），通过 tool_call hook 暴露权限控制点，通过 BOM/换行符透明处理降低 LLM 的使用难度。**
