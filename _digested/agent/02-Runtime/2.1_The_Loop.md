## 现象是什么

当用户发送一条消息给 pi-mono Agent 时，Agent 不会只做一次 LLM 调用就结束。它会反复进行"调用模型 → 解析 tool call → 执行工具 → 注入结果 → 再次调用模型"，直到模型不再请求工具后才返回。（解释）更重要的是，即使这次"思考-行动"链路已完成，用户还可以通过 follow-up 队列注入新消息，让 Agent 在不重新创建上下文的情况下继续工作。（硬事实）一层回答可能被拆分成多个 turn，而一个 turn 内部可能包含多次 LLM 往返。

核心入口在 `agentLoop()` 和 `agentLoopContinue()` 两个函数，它们共享同一个 `runLoop()` 实现。（硬事实）

**源码位置：** `/packages/agent/src/agent-loop.ts`

## 核心矛盾是什么

Agent 运行时需要在两种不同的循环动力源之间做优先级仲裁：（解释）

- **内层动力源（tool calls）：** 模型返回 `tool_use` 后，Runtime 必须等待工具执行完毕、将结果注入上下文、再次请求模型，这是一个"单步执行-反馈"的紧耦合循环。（解释）
- **外层动力源（用户介入）：** 用户可能在工具执行过程中通过 `steer()` 发送修正指令，也可能在 Agent 完成所有工具调用后通过 `followUp()` 追加新任务。（解释）

两种动力源的触发时机和调度策略完全不同，必须在同一个循环体中有序编排，同时还要支持"优雅停止"（**v1.0.0 起为 `finishTurn` 返回 `{action:"end"}`**，`shouldStopAfterTurn` 已删）和"回合间状态切换"（prepareNextTurn）。（解释）

## 实现思想是什么

`runLoop()` 用一个**双层循环**来解决这个矛盾：（解释）

```
runLoop 入口：poll getSteeringMessages → 初始 pending（用户等待期间键入的消息）
外层 while(true)                 // follow-up 驱动
  内层 while(hasMoreToolCalls    // tool calls 驱动
            || pendingMessages > 0)
    若存在上一 turn 快照（lastCompletedTurn，首 turn 没有）：
      prepareNextTurn（可替换 context/model/thinkingLevel）
      prepare 后补 poll getSteeringMessages（仅当先前 poll 为空）
      emit turn_start（首 turn 的 turn_start 由 runAgentLoop 发出）
    注入 pending 消息（含 system message 的 tool placement）
    prepareRequest（v1.0.0 新增：每次 provider 请求前，含第一次）
    streamAssistantResponse()
    stopReason === "error"|"aborted" → finishTurn（决策被忽略）→ turn_end + agent_end，直接返回
    stopReason === "length" → failToolCallsFromTruncatedMessage()
    否则 executeToolCalls()
    记录 lastCompletedTurn 快照
    finishTurn（在 turn_end 之前调用，决策在其后生效）
    emit turn_end
    决策生效：{action:"end"} → emit agent_end 退出（不轮询队列，prepareNextTurn 不再运行）
              {action:"continue"} → 保证一次下一请求；undefined → 常规调度
    poll getSteeringMessages → 补充 pending
  poll getFollowUpMessages → 决定继续外层还是退出
```

具体的边界规则：

1. **内层循环的进入条件有两个：** `hasMoreToolCalls`（上一轮助理消息包含 tool call 且未被 terminate）或 `pendingMessages.length > 0`（有排队中的 steering/follow-up 消息）。（硬事实）此外 `runLoop()` 在进入循环前先 poll 一次 steering 队列（agent-loop.ts:176），保证 prompt 提交与 run 启动之间键入的消息不丢失。（解释）

2. **turn 边界：** 一个 turn = 一次 assistant 响应 + 该响应触发的所有 tool call 执行及结果。（硬事实）首个 turn 的 `turn_start` 由 `runAgentLoop()` 在 prompt 消息 emit 之前发出；此后 `turn_start` 在内层循环顶部、`prepareNextTurn` 之后 emit（`if (lastCompletedTurn)` 块，agent-loop.ts:185-207）——`runLoop()` 用 `lastCompletedTurn` 快照是否存在来区分"这是延续 turn"。（硬事实）每个内层迭代以 `turn_start` 开头、`turn_end` 结束。

3. **prepareNextTurn（v0.84.4 时序重排；v1.0.0 判定链改写）：** 只在**循环确认将继续**（`finishTurn` 未返回 `{action:"end"}`、且仍有 pending 消息或 tool calls——v0.87.0 之前这一步是 `shouldStopAfterTurn` 返回假）之后、下一 turn 开始前，在内层循环顶部调用。它可以返回新的 `context`、`model`、`thinkingLevel`，用来替换下一轮 LLM 调用的运行时状态。**final/terminating turn 不触发 prepare**——上一轮 turn 结束后若 `finishTurn` 返回 end 或无后续消息，循环退出，prepare 不运行，收尾工作应挂 `agent_end`。（硬事实）此外 prepare 完成后若先前 steering 轮询为空，会补 poll 一次（agent-loop.ts:204-206）。（硬事实）

4. **finishTurn（v1.0.0，替代 `shouldStopAfterTurn`）：** 在 assistant + 全部 tool result 定型后、**`turn_end` 之前**，用刚记录的 completed-turn 快照调用（agent-loop.ts:286）。（硬事实）返回 `{action:"end"}`：`turn_end` 照常发出，随后 emit `agent_end` 退出——不 poll steering/follow-up 队列、不再 prepare（:289-292）。返回 `{action:"continue"}`：保证一次下一 provider 请求，若 tool-result/steering/follow-up 调度已满足则不多发，否则做一次 context-only 请求（:294、:310-314）。返回 `undefined`：保持常规调度。**error/aborted 响应上 finishTurn 也会运行**（:252）但决策被忽略（硬退出）——迁移 `shouldStopAfterTurn` 时需守卫这两种 stopReason（官方迁移代码块见 `packages/agent/CHANGELOG.md` 0.87.0 段）。这是一种"优雅停止"——当前回合的结果仍然完整保留。（解释）

5. **terminate 机制：** `executeToolCalls()` 返回的 batch 带 `terminate` 标志。当且仅当批次非空且**所有** finalized tool call 的结果都设置了 `terminate: true`（含被 `beforeToolCall` block 并显式带 `terminate` 的调用）时，`hasMoreToolCalls` 被设为 `false`，内层循环结束。（硬事实）

6. **提前终止路径：** assistant 消息 `stopReason` 为 `"error"` 或 `"aborted"` 时，先调用 `finishTurn`（决策被忽略，v1.0.0 起），再 emit `turn_end`（空 toolResults）和 `agent_end` 并返回，不再执行工具；（硬事实）`stopReason === "length"`（输出被 token 上限截断）时所有 tool call 走 `failToolCallsFromTruncatedMessage()` 变为 error result 而非执行（见 2.2）。（硬事实）

7. **外循环的出口条件：** 内层循环自然结束（无更多 tool calls 且无 pending steering 消息）后，poll `getFollowUpMessages`。如果有 follow-up，将其设为 pending 并 `continue` 外层；如果没有，`break` 退出，emit `agent_end`。（硬事实）

8. **system message 的注入（v0.86.1，#9548）：** system prompt 是 transcript 的一部分而非循环外的固定头。`initialState.systemPrompt` 只用于 seed 首条 system message（agent.ts:85 `createInitialSystemMessage`）；之后改 prompt/tool 集合的方式是 append 一条带 `content`/`sections` 或 tool 变更字段的 system message，loop 在准备下一请求时把 pending system message 插到首个非 system pending message 之前、并把 tool 增删合并进它（`declareToolChanges()`，v1.4.0 `agent-loop.ts:342`，由 runLoop :220 调用；v0.86.1 时为 :284-325 内联逻辑）。由于状态随 transcript 携带，run 恢复与分支导航天然还原当时的 prompt/tool 前缀（保住 provider prompt cache）。（硬事实）

## 在 Agent 能力面里的影响是什么

- **多轮工具链式调用：** 模型可以像 "read → edit → write → bash" 这样链式调用多个工具，Runtime 不需要任何特殊处理，双层循环自然地实现了这个模式。（解释）
- **用户中途介入：** `steer()` 可以在工具执行过程中排队消息，下个 turn 开始时注入。这意味着用户可以在 Agent "忙"的时候修正方向，而不需要等待 Agent 完全停止。（解释）
- **优雅退出：** v1.0.0 起 `finishTurn` 返回 `{action:"end"}` 让上层可以在上下文过满时请求停止，不会强行中断正在执行中的工具调用（`shouldStopAfterTurn` 已删除，迁移需守卫 error/aborted）。（解释）
- **模型/推理热切换：** `prepareNextTurn` 允许在每个 turn 之间切换模型或 thinking level，这对于不同阶段需要不同能力（规划用强模型、执行用便宜模型）的场景非常有用。（解释）

## 最小例子是什么

以下是一个概念性的最小使用示例，演示双层循环的关键行为：

```typescript
import { Agent } from "@earendil-works/pi-agent-core";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const agent = new Agent({
  streamFn: streamSimple, // v0.83 起必传（coding-agent 的 sdk.ts 会把它设为全局默认）
  initialState: {
    model: claudeSonnet,
    tools: [readTool, writeTool, bashTool],
    systemPrompt: "You are a coding assistant.",
  },
});

// 订阅事件观察循环行为（listener 同时收到当前 run 的 abort signal）
agent.subscribe((event, signal) => {
  switch (event.type) {
    case "turn_start":
      console.log("新回合开始");
      break;
    case "turn_end":
      console.log(`回合结束，${event.toolResults.length} 个工具结果`);
      break;
    case "agent_end":
      console.log(`Agent 结束，共产生 ${event.messages.length} 条消息`);
      break;
  }
});

// 发送 prompt - 这会触发内层循环
await agent.prompt("Read package.json and explain the dependencies");

// 如果 Agent 仍在运行，可以通过 steer 中途介入
agent.steer({
  role: "user",
  content: "Also check for outdated versions",
  timestamp: Date.now(),
});

// Agent 停止后，followUp 会触发外层循环的下一轮
agent.followUp({
  role: "user",
  content: "Now write a summary to SUMMARY.md",
  timestamp: Date.now(),
});

// agent.continue() 会消费 followUp 队列
await agent.continue();
```

这个例子演示了：一次 `prompt()` 触发内层 tool call 循环 → `steer()` 在 mid-run 注入 → Agent 完成后 poll followUp → `continue()` 触发 outer loop 的新一轮。
