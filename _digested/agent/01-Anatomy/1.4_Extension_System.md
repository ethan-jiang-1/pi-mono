## 现象是什么

pi-mono 的扩展系统允许第三方程代码在 agent 生命周期的几乎所有关键点注入行为：

- **事件订阅**：30 余种事件类型，从 `session_start` 到 `agent_end`/`agent_settled`，从 `tool_call` 到 `tool_result`，从 `before_provider_request` 到 `after_provider_response`
- **工具注册**：通过 `pi.registerTool()` 注册 LLM 可调用的工具（ToolDefinition）
- **命令 / 快捷键 / CLI flag 注册**：扩展可以添加 slash commands、键盘快捷键、命令行参数
- **消息注入**：`pi.sendMessage()` 发送自定义消息，`pi.sendUserMessage()` 发送代理用户消息
- **模型和 provider 控制**：运行时注册/注销 provider，切换模型和 thinking level
- **UI 定制**：设置 footer、widget、editor component、theme 等 TUI 元素

这些扩展以 TypeScript 模块的形式存在，通过 **jiti**（即时编译）在运行时加载。在 Bun 编译的二进制模式下，通过 virtual modules 把预打包的 `@earendil-works/pi-*` 包注入给扩展代码使用。

## 核心矛盾是什么

**矛盾一：扩展需要访问丰富的运行时上下文，但加载发生在系统初始化早期。** 扩展通过 `ExtensionAPI`（即 `pi` 对象）调用的某些方法（如 `sendMessage`、`setModel`）依赖于 SessionManager、ModelRegistry 这些在扩展加载时尚不存在的对象。解决方式是两阶段绑定：Loader 创建 ExtensionRuntime 时所有 action 方法都是 throwing stub，Runner 的 `bindCore()` 在系统初始化完成后替换为真实实现。（解释）

**矛盾二：多个扩展可能注册冲突的快捷键、命令或 provider。** 快捷键有内置保留字（如 `app.interrupt`、`app.exit`）不可被扩展覆盖；（硬事实）扩展之间的同名快捷键按"后覆盖前"原则处理，产生 warning diagnostic。命令名冲突时自动加后缀（`:1`、`:2`）。（解释）Provider 注册也是"后来覆盖先来"——这允许扩展覆盖内置 provider 的 baseUrl。（解释）

**矛盾三：扩展在 session 切换或 reload 后会变 stale。** 如果扩展在 `session_before_switch` 事件中保存了对 ExtensionContext 的引用，session 切换后这个 context 指向旧 session。`ExtensionRuntime.invalidate()` 在 session 替换时打上 stale 标记，后续对 stale context 的任何调用都会抛出错误，防止数据写入错误 session。（解释）

## 实现思想是什么

### 加载流程（Loader）

`packages/coding-agent/src/core/extensions/loader.ts` 负责扩展的发现和加载。

**发现优先级：**
1. 项目本地扩展：`cwd/.pi/extensions/`
2. 全局扩展：`~/.pi/agent/extensions/`
3. 显式配置的路径

**模块加载（jiti）：** v0.84.2 是三种运行环境三种配置，**v0.84.3 变四种**（`loadExtensionModule()`，`extensions/loader.ts:78-82/503`）：
- Bun 二进制模式：jiti 的 `virtualModules` 注入预打包模块，`tryNative: false`
- **Node SEA 二进制**（`process.features.sea`）与 **bundled Node**（`PI_BUNDLED_NODE`）：v0.84.3 新增，同样 `virtualModules` + `tryNative: false`（#8237、#8474）
- TypeScript 源码运行（开发 monorepo）：同样用 `virtualModules`，外加 `tsconfigPaths: true`
- 构建后的 Node.js：使用 jiti 的 `alias` 选项把 `@earendil-works/pi-*` 映射到 monorepo 的编译产物（dist）

`VIRTUAL_MODULES` 包含 `typebox`（含 `@sinclair/typebox` 兼容别名）、`@earendil-works/pi-agent-core`、`@earendil-works/pi-tui`、`@earendil-works/pi-ai`（解析到 compat 入口，兼容旧全局 API）、`@earendil-works/pi-ai/oauth`、`@earendil-works/pi-ai/providers/all`、`@earendil-works/pi-coding-agent`，以及一套 `@mariozechner/pi-*` 旧包名别名。

这让扩展可以 `import { ... } from "@earendil-works/pi-coding-agent"` 而不管运行环境是开发还是二进制。（解释）

**npm 包支持：** 如果扩展目录有 `package.json` 且包含 `pi.extensions` 字段，Loader 尊重这个字段的声明；否则查找 `index.ts` 或 `index.js`。（硬事实）

**Extension 数据结构：** 每个加载成功的扩展产生一个 `Extension` 对象：
```typescript
interface Extension {
  path: string;                         // 扩展路径
  resolvedPath: string;                 // 解析后绝对路径
  hidden?: boolean;                     // 从启动 Extensions 列表隐藏（inline 扩展用）
  sourceInfo: SourceInfo;               // 来源元数据
  handlers: Map<string, HandlerFn[]>;   // 事件 -> 处理器数组
  tools: Map<string, RegisteredTool>;   // 注册的工具
  messageRenderers: Map<string, MessageRenderer>;  // 自定义消息渲染器
  markdownTransformer?: MarkdownTransformer;      // user/assistant Markdown 渲染前变换
  entryRenderers?: Map<string, EntryRenderer>;    // CustomEntry（不进 LLM context）渲染器
  commands: Map<string, RegisteredCommand>;        // 注册的命令
  flags: Map<string, ExtensionFlag>;               // 注册的 CLI flag
  shortcuts: Map<KeyId, ExtensionShortcut>;        // 注册的快捷键
}
```

### 运行时管理（Runner）

`packages/coding-agent/src/core/extensions/runner.ts` 的 `ExtensionRunner` 管理扩展的运行时生命周期。

**bindCore()** 是关键的初始化步骤：（解释）
1. 把真实的 action 实现（`sendMessage`、`setModel` 等）写入共享的 `runtime` 对象
2. 把 context action 实现（`isIdle`、`abort`、`getContextUsage` 等）绑定到 Runner 自身的函数引用
3. 清空 pending provider registrations（在扩展加载期间排队的 provider 注册，含 `ProviderConfig` 按名注册和原生 `Provider` 注册两个队列），现在 ModelRegistry 已经可用，逐一执行真正的注册
4. 从此之后 `runtime.registerProvider()` / `runtime.registerNativeProvider()` 和 `runtime.unregisterProvider()` 直接调用 ModelRegistry（或宿主注入的 providerActions），无需再排队

**事件扇出（emit 系列方法）：**
Runner 对每种事件类型提供专用的 `emitXxx()` 方法（类型安全 + 合并逻辑），通用的 `emit()` 处理简单事件。（硬事实）

- `emitContext(messages)`：structuredClone 后遍历所有扩展的 `context` 处理器，允许每个处理器修改消息数组（chain），返回最终消息
- `emitBeforeProviderRequest(payload)`：遍历处理器，允许替换 request payload（chain）
- `emitBeforeProviderHeaders(headers)`：处理器原地修改 headers（返回值被忽略，`null` 值删除 header）
- `emitBeforeAgentStart(...)`：systemPrompt 链式替换（后面的 handler 看到前面改过的值），message 注入逐个收集
- `emitToolCall(event)`：遍历处理器，任何 handler 返回 `{block: true}` 就停止（还可返回 `terminate` 提前终止本批工具）
- `emitToolResult(event)`：遍历处理器，合并对 content/details/isError/usage 的修改
- `emitMessageEnd(event)`：遍历处理器，允许替换整个 message（必须保持原 role）
- `emitInput(text, images, source, streamingBehavior?)`：遍历处理器，支持 `transform`（修改文本/图片）和 `handled`（完全消费输入）两种结果
- `emitResourcesDiscover(cwd, reason)`：收集扩展提供的额外 skill/prompt/theme 路径

**Session before 事件的可取消性：**
`session_before_switch`、`session_before_fork`、`session_before_compact`、`session_before_tree` 四种事件都支持 `cancel: true` 返回值——第一个返回 cancel 的处理器会阻止操作继续。

### ExtensionAPI 设计

`ExtensionAPI`（即扩展代码中看到的 `pi` 参数）的接口分组：

| 分组 | 方法 | 说明 |
|---|---|---|
| 事件订阅 | `on(event, handler)` | 类型安全的事件订阅（重载匹配每种事件类型） |
| 工具 | `registerTool(tool)` | 注册 LLM 可调用工具 |
| 命令/快捷键/Flag | `registerCommand`, `registerShortcut`, `registerFlag`, `getFlag` | 交互和 CLI 扩展 |
| 消息/条目渲染 | `registerMessageRenderer`, `registerMarkdownTransformer`, `registerEntryRenderer` | 自定义消息、Markdown 变换、自定义条目的 TUI 渲染 |
| 消息发送 | `sendMessage`, `sendUserMessage`, `appendEntry` | 向会话注入消息或持久化数据（sendMessage 支持 `triggerTurn`/`deliverAs: steer/followUp/nextTurn`；sendUserMessage 支持 `deliverAs: steer/followUp` 和 `expandPromptTemplates`） |
| 会话控制 | `setSessionName`, `getSessionName`, `setLabel` | 会话元数据 |
| 执行 | `exec(command, args)` | 执行外部命令 |
| 工具管理 | `getActiveTools`, `getAllTools`, `setActiveTools`, `getCommands` | 查询和控制工具集 |
| 模型控制 | `setModel`, `getThinkingLevel`, `setThinkingLevel` | 运行时模型切换 |
| Provider | `registerProvider`, `unregisterProvider` | 运行时 provider 注册/注销 |
| 通信 | `events` (EventBus) | 扩展间通信总线（订阅随 runtime invalidate 自动退订） |

### Provider 注册的特殊性

`registerProvider()` 是最特殊的能力——它在扩展加载阶段的效果是"排队"（因为 ModelRegistry 还不存在），在 `bindCore()` 之后才真正生效。（解释）有两个重载：按名注册 `ProviderConfig`，或直接传入原生 pi-ai `Provider` 对象。`ProviderConfig` 支持的注册内容：
- 为 provider 注册新模型（替换该 provider 下所有现有模型），可用 `refreshModels()` 提供动态模型目录
- 覆盖 baseUrl（用于代理转发）
- 注册 OAuth provider（用于 `/login`）
- 注册自定义 `streamSimple` handler（完全接管 LLM 调用）

`unregisterProvider()` 删除该 provider 的所有模型，并恢复被覆盖的内置模型。

## 在 Agent 能力面里的影响是什么

1. **扩展是 pi-mono 内部能力 harness 的唯一入口。** 不像 OpenCode 有 Skill/MCP/ACP 等多条协议通道，pi-mono 的扩展系统是统一的能力注入点——工具、命令、快捷键、provider、system prompt 修改都走同一个加载和事件系统。（推测）

2. **两阶段绑定让扩展可以在系统完全就绪前安全加载。** 这在 library-first 的集成场景中很重要——外部宿主可能在 createAgentSession 之前就准备好了扩展路径，但 session 内部的 ModelRegistry 和 SessionManager 尚未创建。两阶段绑定保证了不会因为初始化顺序而出错。（解释）

3. **Stale context 保护防止了 session 替换后的数据损坏。** 当扩展在 `session_before_switch` 中保存了 context 引用，然后 `newSession()` 或 `fork()` 替换了 session，旧的 context 调用会抛出明确的错误，而不是静默写入错误 session。（解释）

4. **运行时 provider 注册让扩展可以动态切换模型后端。** 扩展在命令处理器中（比如一个 `/switch-proxy` 命令）调用 `pi.registerProvider("anthropic", { baseUrl: "https://proxy.corp.com" })`，立即生效——不需要 `/reload`。这对企业代理切换、多 region failover 等场景很有用。（推测）

5. **事件扇出不是 pub/sub 广播——有 chain 和 merge 两种模式。** Chain 模式（`emitContext`、`emitBeforeProviderRequest`、`emitBeforeAgentStart` 的 systemPrompt 部分）让扩展按加载顺序依次修改数据，后面的 handler 看到前面的结果；Merge 模式（`emitToolResult`、`emitBeforeAgentStart` 的 message 注入、`emitResourcesDiscover`）让所有扩展的修改被合并收集；Cancel 模式（`session_before_*` 和 `emitToolCall`）让第一个返回 block/cancel 的处理器终止流程；此外 `emitBeforeProviderHeaders` 是原地修改模式（mutate in place）。（硬事实）

## 最小例子是什么

### 例子 1：创建一个最小扩展

```typescript
// my-extension.ts
// 扩展入口：导出一个接收 ExtensionAPI 的工厂函数
export default function(pi) {
  // 订阅 agent 生命周期
  pi.on("agent_start", (event, ctx) => {
    // ctx 是 ExtensionContext，可以访问 session、model、UI 等
    if (ctx.hasUI) {
      ctx.ui.setStatus("my-ext", "Agent is thinking...");
    }
  });

  pi.on("agent_end", (event, ctx) => {
    if (ctx.hasUI) {
      ctx.ui.setStatus("my-ext", undefined);  // 清除状态
    }
  });

  // 注册一个工具
  pi.registerTool({
    name: "hello",
    label: "Hello",
    description: "Say hello",
    promptSnippet: "- hello: say hello to the user",
    parameters: t.Object({
      name: t.String({ description: "Who to greet" }),
    }),
    execute: async (toolCallId, params, signal, onUpdate, ctx) => {
      return {
        content: [{ type: "text", text: `Hello, ${params.name}!` }],
        details: {},
      };
    },
  });

  // 注册一个 slash command
  pi.registerCommand("my-status", {
    description: "Show extension status",
    handler: async (args, ctx) => {
      const usage = ctx.getContextUsage();
      ctx.ui.notify(`Context: ${usage?.tokens ?? "?"} / ${usage?.contextWindow ?? "?"} tokens`);
    },
  });

  // 注册一个键盘快捷键
  pi.registerShortcut("ctrl+g", {
    description: "Show greeting",
    handler: async (ctx) => {
      ctx.ui.notify("Hello from extension!");
    },
  });
}
```

### 例子 3：Provider 注册

```typescript
// 在扩展中注册一个代理 provider
pi.registerProvider("anthropic", {
  baseUrl: "https://anthropic-proxy.internal.company.com",
  // 不提供 models——保留现有的 Anthropic 模型列表，只改 URL
});

// 或在命令处理器中动态注册
pi.registerCommand("switch-proxy", {
  description: "Switch to corporate proxy",
  handler: async (args, ctx) => {
    pi.registerProvider("openai", {
      baseUrl: "https://openai-proxy.internal.company.com",
      headers: { "X-Custom-Auth": "corp-token" },
    });
    ctx.ui.notify("Switched to corporate proxy", "info");
  },
});
```

你会观察到的信号：
- 扩展加载时的 `registerProvider` 在 `bindCore()` 后才生效——ModelRegistry 在那时才可用
- 命令处理器中的 `registerProvider` 立即生效——之后的 LLM 请求会走新的 baseUrl
- 如果同时注册了多个 provider，后来的覆盖先来的
