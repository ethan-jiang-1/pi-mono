## 现象是什么

v0.85.1 的 agent 包 session 存储把"执行历史"拆成**两类 durable 数据 + 一套 bound 地址系统**：（解释）

1. **Entry**（4 种）——不可变、write-once 的对话树节点：`message`、`compaction`、`branch_summary`、`custom`（`session/types.ts:16`）
2. **UsageRow**——append-only 的成本账本行，只增不改不删（`session/types.ts:378`）
3. **bound values / lists**——**唯一可变**的存储，按 `value<T>(namespace, key)` / `list<T>(namespace, key)` 这样的**绑定类型化地址**寻址（`session/values.ts:98,103`）

旧模型的失败点是**表示法本身**：（解释）v0.84 用"7 种 entry + 9 种 LaneRecord + Facts + 一个全局严格连续 seq"来表达所有东西——模型/思考级别/工具集的变化各占一种 entry 类型，operation 的生命周期是一串 record 对，name/label 是 set 语义的 Facts，三类写入共享一条**不允许有 gap** 的会话级序列号（**已删除的** `session/state.ts:104`：一旦 `seq !== sequence + 1` 即抛 "has non-consecutive seq"）。（硬事实）这套表示法把"每一次 phase 迁移"都变成一行新 record，于是**崩溃恢复要重放整条流水**，而且任何"跳过/丢弃一行"的修复都会破坏 seq 连续性。（解释）

新模型的核心取舍是**把"状态"与"日志"分开**：（解释）

- **不可变部分**（entry / usage）继续 append-only，但它只承载"确实发生过的对话事实"；
- **可变部分**（bound values）承载"当前是什么"——operation 当前停在哪个 leaf、lane 当前的 model/thinkingLevel/工具集、session 的名字。**每次 transition 是整体替换一个值**，旧值不留历史（`harness.md:300`）；（硬事实）
- 于是恢复不再"重放流水"，而是**读少量精确地址**（每个 lane 读 `branchTip`/`laneConfig`/`laneState`，有 open operation 再读 `op.meta`/`op.state`），状态空间可枚举。（解释）

结果：**崩溃状态是"事务之间可枚举"的，永远不在事务内部**（`harness.md:425`）。（硬事实）

> **一个数字对照**：v0.84.4 的 `session/testing/conformance.ts` 单文件 1016 行一致性套件，v0.85.1 拆成 `conformance/storage.ts`（920 行）+ `conformance/session-repo.ts`（846 行）+ `benchmark/` + 三个 decorator；同时 `harness/reducer.ts`（667 行）被删。（硬事实）

## 接口分层

旧版的三大接口（`SessionStorage` / `SessionTree` / `SessionRepo`）在 v0.85.1 **全仓零命中**。新分层**按能力切**，而不是按"存储/树/仓库"切：（解释）

| 接口 | 位置 | 职责 |
|------|------|------|
| `Storage` | `session/types.ts:454` | 后端契约：`commit(writes)` + `getEntries` + `getValue`/`scanValues`/`readList` + `scanBranch`/`scanBranchStructure`/`scanEntries`/`scanUsage` + `getStats` + `close`，共 10 个方法 |
| `SessionReader` | `session/types.ts:493` | 只读能力：`getEntries`、`getStats`、`getValue`、`scanValues`、`readList`、`scanBranch`（6 个） |
| `SessionMutation extends SessionReader` | `session/types.ts:508` | reader + `commit(writes)` + `end()` |

| `Branch` | `session/types.ts:520` | lane 数据面：`name`、`getTipId`、`findEntries`/`findEntry`、`appendMessage`/`appendCustomEntry` |

`Storage` 实例**只服务一个 session**；仓库发现与生命周期在它之外。（硬事实）

## 并发原语：keyless 独占屏障

旧模型的串行化靠 append-only record log 天然排队。v0.85.1 的替代品是两个东西：（解释）

**`SessionMutation`——"keyless 独占屏障"**（`session/types.ts:507-513`）。doc comment 原文：

```ts
/** Exclusive keyless mutation barrier for one Session. */
export interface SessionMutation extends SessionReader {
	/** Exactly zero or one commit attempt. A second attempt rejects. */
	commit(writes: Write[], context: Context): Promise<CommitResult>;
	/** Wait for any commit attempt, invalidate the capability, and release the barrier. */
	end(context: Context): Promise<void>;
}
```

三点硬约束：（硬事实）

1. **`commit` 至多一次**：第二次调用直接 reject，实现体是 `StorageBackedSessionMutation.commit()` 里的 `if (this.commitResult !== undefined) return Promise.reject(...)`（`session/session.ts:109`）；
2. **`end()` 才释放屏障**：`end()` 等待已受理的 commit 落地，把 capability 置为失效（之后所有读都会抛 `"SessionMutator cannot be used outside its mutation callback"`，`session/session.ts:179`），然后 resolve 那个让 `MutationLine.run` 得以继续的 `finished` promise；
3. **每一条受支持的 mutation 都走这一条线**：lane 命令、lane 获取、进度写、Branch 创建/append、metadata/value 写、一致的 restore/watch 捕获全部如此。代价是**故意牺牲 lane 之间的准备并行度**，换更简单的所有权模型（`harness.md:953`）。

**`MutationLine`**（`session/mutation-line.ts:2`）是这把锁的实现：`run(operation)` 把闭包接到 `tail` promise 链上做**完整 read-modify-write 的串行化**；`seal(error)` 让后续 `run` 全部以该 error reject，并等待尾部排空——`Session.close()` 就是靠它实现"封闸、排空、再放后端资源"。（硬事实）

`Session.mutate(callback)` 是便利包装：`beginMutation` → 执行回调 → `finally { end() }`（`session/session.ts:263-270`）。（硬事实）

> **易错点（spec 明写）**：`mutate()` 的回调**必须**只用传入的 mutator 做有界读和它那唯一一次 commit。在回调里调用 Session 的公开 writer（如 `setName()`）会把那次写**排在当前回调之后**——`await` 它必然死锁（`harness.md:955`）。（硬事实）派生自：那些公开 writer 内部也调 `mutate()`，而 `mutate()` 又要抢同一条线。

## seq 语义：完整替代规范

> 这是本版最需要重新取证的一条。结论：**替代规范存在，且在 spec 与源码中都完整**，不是"规范缺口"。

**旧规则**：全局严格连续——`state.ts:104` 校验 `seq !== this.sequence + 1` 时报 "has non-consecutive seq"，不允许 gap。

**新规则**（`harness.md:297` §1.4 规则 2，原文）：

> Writes receive **strictly increasing** `seq` in the order given; **gaps are legal within and between transactions**; `seq` is monotonic session-wide across all lanes and write kinds. A value `set` stamps the stored value with its assigned `seq`.

拆成四条可核对的硬事实：

1. **分配点是 commit**：`prepareStorageCommit(writes, firstSeq, timestamp)` 把一次事务里的第 i 条 write 赋成 `firstSeq + i`（`session/commit.ts:82-88`），`firstSeq` 就是存储当前的 `nextSeq`。（硬事实）`EntryBase.seq`、`UsageRow.seq`、`StoredValue.seq`、`ListElement.seq`、`CommitResult.seqs` 全部来自这一次分配。（硬事实）
2. **跨 lane、跨 write kind 单调**：entry、usage、value set/delete、list append/delete **共用同一条序列**，`nextSeq` 是**会话级**高水位。（硬事实）
3. **事务内严格递增，且仍被校验**：`validateCommittedWrites()` 以 `previousSeq = firstSeq - 1` 起步，逐条要求 `write.seq > previousSeq`，否则抛 `Non-monotonic storage sequence: ${seq}`（`session/commit.ts:95-100`）。（硬事实）这条是**每事务**的局部单调校验，**不是**旧的会话级连续性校验——它允许 gap，只是不允许回退。
4. **高水位可以显式抬高**：`InMemoryStorageState.applyValidated()` 每条 write 后置 `this.nextSeq = write.seq + 1`（`in-memory-storage-state.ts:143`）；`advanceNextSeq(n)` 取 `max`（`:148-153`）；JSONL open 时若 header 带 `nextSeq` 就 `advanceNextSeq(header.nextSeq)`（`jsonl/storage.ts:209`）。（硬事实）

**gap 从哪来**（解释）：三个来源——(a) **fork**：copied entry/value 保留源 `seq`，目的端 `nextSeq` 直接取源高水位（`fork.ts:40` 的 `Math.max(...entry seq) + 1`，JSONL 写进 header：`jsonl/storage.ts:166`，SQLite 同理）；(b) **v3→v4 升级**：`upgradeLegacyV3ToV4` 先塞一条内部 usage 调整行，再把 `nextSeq = firstSeq + writes.length` 写进新 header（`jsonl/storage.ts:284-285`）；(c) **spec 未来的 J1 snapshot compaction**：保留行**沿用原 `seq`**，明确"不重编号"（`harness.md:365`）。（硬事实）

**JSONL 侧的持久化校验**：open replay 时逐行调用 `replayCommitted` → `validateCommitted`，因此整个文件的 seq 必须**严格递增（gap 合法）**；spec 的措辞是 "Open verifies persisted sequence monotonicity (strictly increasing, gaps legal)"（`harness.md:361`）。（硬事实）

**仍有一条"连续"的残留**：单事务内因为是 `firstSeq + i` 稠密分配，所以事务内部**实际是连续的**——但这是分配方式的副作用，**不是**被强制的不变量：只要调用方（fork / 升级）自己带 `seq` 进来，`validateCommittedWrites` 只要求递增。（解释）旧文档"不允许 gap"那句据此作废。

> **未取证**：spec 没有给出 `nextSeq` 在**同一会话被多个并发 backend 实例打开**时的归属规则（harness.md 反而明说 ownership 是 host-authoritative、后端不检测第二个进程，`harness.md:403`）。这一点属"未取证/不确定"。

## bound values / lists：取代 Facts 与三种 change entry

### 地址模型

公开的存储抽象是**绑定类型化地址**：`value<T>(namespace, key = "")` 命名一个可替换的 durable 值，`list<T>(namespace, key = "")` 命名一个 append-only 的 durable 列表（`session/values.ts:98,103`）。地址一旦构造，namespace/key 就绑死；没有全局类型表、没有 token catalog、没有 declaration merging、没有独立的 application-state 存储机制（`harness.md:214`）。（硬事实）

铁律：（硬事实）

- `namespace` 非空；两个分量都不许含 `\u0000`（`values.ts:92-96`）；
- `pi` 与一切 `pi.*` namespace **按契约保留给内建**，内建一律以 `pi.` 开头；应用使用 `pi.*` 是 trusted-programming 缺陷——构造函数**不做**所有权检查，靠"精确构造器测试"而非运行时权限检查来约束（`harness.md:219`）；
- 空 key 合法，寻址"整个 session 一个值"；
- 对象身份**没有** durable 含义，`(kind, namespace, key)` 三元组相等即同一位置；
- value 地址与 list 地址**不得共用**同一 `(namespace, key)`；存储不做跨 kind 冲突检查。

### 三种 change entry → `LaneConfiguration`

旧模型的 `model_change` / `thinking_level_change` / `active_tools_change` 三种 entry **全部消失**，收进一个 bound value：（硬事实）

```ts
// session/types.ts:69
export interface LaneConfiguration {
	model: { provider: string; modelId: string };
	thinkingLevel: ThinkingLevel;
	activeToolNames: string[];
}
```

- **地址**：`laneConfig(lane)` → `pi.lane.config` / `<lane 名>`；
- **读**：`session.getValue(laneConfig(lane), context)` 拿 `StoredValue<LaneConfiguration> | undefined`；`undefined` 说明这条 lane 既可能是"只有 tip 的 **data-only Branch**"，也可能根本不存在——**必须与 `branchTip`/`laneState` 一起读**才能分类（这正是 `classifyLaneStorage` 做三分类的原因，见下文）（`harness.md:481`）；
- **写**：`session.setValue(laneConfig(lane), next, context)`——**整体替换**，latest-wins，不留历史；
- **上层门面**：`AgentLane.getModel/setModel`、`getThinkingLevel/setThinkingLevel`、`getActiveTools/setActiveTools`（`agent-harness.ts:572-577`）。

为什么这是"换模型"而不是"换个字段名"：（解释）旧表示法里"换了模型"是**往树里插一个节点**，于是它天然成为对话历史的一部分、影响 tree 遍历和 fork 的 entry 选择；新表示法里它只是 lane 的一个当前值，**不进树**——`LaneConfiguration` 因此也不参与 context 投影，除非 lane 在做 branch 导航时被 `OperationMeta`/`state` 捕获。

### Facts → `sessionName` / `entryLabel`

旧 `Facts`（latest-wins 的 name/label）被两个 bound value 取代：（硬事实）

```ts
// session/values.ts:194-195
export const sessionName = value<string>("pi.session.name");
export const entryLabel = (entryId: string) => value<string>("pi.entry.label", entryId);
```

**读写方式**（`session/session.ts:310-316, 394-401`）：

- `getName(ctx)` ≡ `(await getValue(sessionName, ctx))?.value`；`getLabel(id, ctx)` ≡ `(await getValue(entryLabel(id), ctx))?.value`；
- `setName(undefined)` **不写 null**，而是 `deleteValue(sessionName)`；`setLabel(id, undefined)` 同理。删除一个不存在的 key 是 **no-op**（`harness.md:300` 规则 5），所以"清一个本来就没设的 label"合法；
- 这两类值**在树之外**（`harness.md:489`），写入**立即提交且永不移动 tip**。

> **语义差异（易踩）**：`pi.session.name` 的空 key 表示"一个 session 一个名字"；`pi.entry.label` 用 entry id 当 key，所以 label 数量随 entry 数增长——spec 明确 `pi.result` 与 `pi.entry.label` 是"随写历史线性增长"的类别（`harness.md:367`），J1 落地前物理字节不会回收。（硬事实）

### 一句话对照

旧模型的四类"表示法"全部被 bound value / 精确状态值吸收：三种 change entry → `LaneConfiguration`；`Facts` → `pi.session.name` + `pi.entry.label`；9 种 `LaneRecord` → 删除（operation 状态改由 `pi.op.state` 的 13 个 leaf 承载）；record 对 → `OperationMeta` + `OperationResultRecord` 夹一个可变的 `OperationState`。本节的地址与读写方式是这三条替代关系的展开。完整逐条对照见 [0006 change log](../../_change_log/0006-v0.84.4-to-v0.85.1.md)。

## 事务与 Entry

`Write` 只有 4 种（`session/types.ts:387-397`）：

```ts
interface EntryWrite { kind: "entry"; entry: NewEntry }
interface UsageWrite { kind: "usage"; row: Omit<UsageRow, "seq"> }
type Write = EntryWrite | UsageWrite | ValueWrite | ListWrite;
// ValueWrite = ValueSetWrite | ValueDeleteWrite（values.ts:89）
// ListWrite  = ListAppendWrite | ListDeleteWrite（values.ts:90）
```

**写入口只走构造函数**：`insertEntry(entry)` / `insertUsage(row)`（`session/commit.ts:53,57`）+ values 的 `setValue`/`deleteValue`/`appendList`/`deleteList`（`values.ts:108,118,127,137`）。`NoInfer<T>` 让**地址**而不是 `T` 成为权威（`harness.md:285`）。（硬事实）

`NewEntry<TEntry>` 是**不带 `seq`/`timestamp`** 的 entry（`types.ts:67`）——这两项由存储补齐，这正是旧的 `ProvisionedEntry` 的替代物（旧符号已零命中）。（硬事实）

**事务规则**（`harness.md:296-303`，逐条硬事实）：

1. **全有或全无**——不存在"一半 write 生效"的可观测状态；
2. 按给定顺序拿**严格递增** `seq`；gap 合法；会话级跨 lane 跨 kind 单调；`set` 把分配的 `seq` 盖在被存值上；
3. **事务内按序生效**：一个 entry 可以引用**同一事务里更早创建**的 parent；一个 stored value 可以引用同一事务更早创建的 entry/usage id。placement 事务把"插入完整 entry"与"删除它的 `pendingEntry(id)`"放在一起，**两者永不同时存在**；
4. **entry id 与 usage id 共用一个会话级 id 空间**，在任一已存在的 id 上写任一 kind 都是 **corruption**（不是 update）：`validateCommittedWrites` 抛 `Duplicate entry or usage id`（`commit.ts:102-104`）；
5. `set` 替换、`delete` 移除、之后 `set` 可重建；**不留历史**；delete 不存在的 key 是 no-op；
6. 一次 list `append` 只带一个元素、**从不读已有元素**；元素提交后不可变，按分配的 write `seq` 排序；没有 per-element 的 update/delete/insert/truncate；
7. list `delete` 删掉 `(namespace, key)` 下的**全部**元素；同一事务里 delete 后 append = 原子地建一个新列表；
8. 一个 session 上的事务**串行化**：一个 writer、一条队列。

> **失败即 fault**：一个**已受理**的 commit 失败会 fault 整个 harness——所有 effect 停止、所有调用 reject `HarnessFault`、**要求重启进程**，而不是返回一个可预期的 `Err`（`harness.md:305,1011`）。（硬事实）原因是"部分应用的事务不可容忍"，而宿主无法从"存储内部到底写没写成功"里恢复出确定答案。

### 4 种 Entry 的完整字段

```ts
// session/types.ts:18-64
interface EntryBase { id; parentId; seq; timestamp; type: EntryType; customType? }

interface MessageEntry      { type: "message"; message: AgentMessage; terminate?: true }
interface CompactionEntry   { type: "compaction"; summary: string; retainedTail: AgentMessage[];
                              tokensBefore: number; details?: JsonValue; usage?: Usage; fromHook: boolean }
interface BranchSummaryEntry{ type: "branch_summary"; fromId: string | null; summary: string;
                              details?: JsonValue; usage?: Usage; fromHook: boolean }
interface CustomEntry       { type: "custom"; customType: string; data?: JsonValue }
```

要点（`harness.md:454`，硬事实）：`type`/`customType` 是**结构字段**（分支查询按它过滤，SQLite 分支索引对它做反规范化）；assistant entry **永远**装 `SettledAssistantMessage`——写 `pending` 会被拒（`session/session.ts:117` 抛 `SessionPendingAssistantMessageError`）；`terminate?: true` 只出现在 tool-result entry 上；每个 compaction 都存**完整的** `retainedTail`（空就是 `[]`），**context 永不读过 compaction**；只有 custom entry 可以没有 `data`；payload 内联，两个 entry **永不共享**存储内容，没有去重层。

### placement 与 staging

spec 把 entry 的生命周期讲得很清楚（`harness.md:456-477`）：（硬事实）

- **Born placed**：assistant 回复、空闲 lane 上的直接 append——内容与位置在同一事务到达（`TX[ insert entry, upsert pi.branch.tip ]`）；
- **Content first（排队输入）**：`steer`/`followUp`/`nextRun`/deferred write 在**入队时**就铸造 entry id 并构造 `pendingEntry(id)`；队列状态用这个 id 引用内容；两个事务可能相距很远。崩溃在 placement 前 = 仍在队列里，之后 = 已落在树里、pending 值消失；
- **Content first（并行工具结果）**：结果 id 先是 `pi.op.state` 里的一个"预留字符串"，`outcome_ready` 时完整 `ToolResultMessage` 落进 `pendingEntry(resultEntryId)`，只有**源码顺序上更早的兄弟都 ready** 之后才进树。effect 按**完成序**结算，entry 按 **assistant 源码序**物化；
- **Id 先于内容预留**：assistant 响应、工具结果、usage 的 id 都先在 operation state 里当字符串出现——这在 effect 窗口内让"预留 id 到底有没有落地"变成可判定问题。

## operation 状态机：OperationMeta + 13 leaves

旧模型用一个 `operation_started`/`operation_finished` **record 对**表示一个操作，intent 只分 `run`/`compaction`/`navigation` 三种，而"操作现在到哪一步了"要靠扫描 `LaneRecord` 流水推出来。v0.85.1 换成**一份受理元数据 + 一个完整的当前状态值**：（解释）

	operationId: string;
	lane: string;
	sourceTipId: string | null;          // 受理前的 lane tip
	startedAt: number;
	intent:
		| { kind: "run"; promptEntryIds: string[] }

		| { kind: "navigation"; targetId: string | null; summarize: boolean;

`OperationMeta` 是**不可变的受理数据**：写一次，与一个完整的 `operationState(operationId)` 配对，由终态事务删除（`harness.md:602`）。（硬事实）

推论（硬事实）：由 Session mutation line 提供的 `Lane.state` **就是控制权威**；drive 过程**永不**为了决定下一步去重读 `laneState`/`operationMeta`/`operationState`/`branchTip`/`laneConfig`/`operationResult`；存储读只用于"解引用当前状态点名的 id"或"枚举 operation 自己的清理地址"（`harness.md:668`）。（硬事实）取消（cancellation）与状态机**正交**：并发的 inbox 调用只改 `LaneState.inbox`，`requestAbort` 只改 `control`。（硬事实）

## Lane 持久状态与恢复语义

新模型里 lane 的持久状态**只剩三个字段**（`session/types.ts:343-347`）：

```ts
interface LaneState {
	currentOperationId: string | null;
	lastOperationId: string | null;
	inbox: Array<{ entryId: string; kind: InboxItemKind }>;   // steer | followUp | nextRun | write
}
```

这与旧模型形成鲜明对比：旧版要靠 `findOpenOperations(lane, {limit: 2})` 数出 0/1/2 条 record 来判断"空闲 / suspended / corruption"（硬事实：该符号与整个 record 流水都已删除）。（解释）新模型把"有序 inbox"和"当前/上一个 operation id"直接写成字段，判定变成**纯集合运算 + 三分类**。

### `classifyLaneStorage()`：absent / branch / lane

`packages/agent/src/harness/runtime/restore.ts:63` 是一个**闭集三分类器**，对一条 lane 读到的三个值做判定：（硬事实）

| tip | config | state | 分类 | 含义 |
|---|---|---|---|---|
| `undefined` | `undefined` | `undefined` | `absent` | 这条 lane 根本不存在 |
| 有 | `undefined` | `undefined` | `branch` | **data-only Branch**——只有一条路径，不是 AgentLane |
| 有 | 有 | 有 | `lane` | 完整配置的 AgentLane |
| 其它任意组合 | | | **抛 `SessionInvariantError`** | 缺 tip / 缺 config / 缺 state 一律 corruption |

注意实现细节：`tip === undefined` 但 config/state 存在 → 抛"missing branch.tip"；`branch` 分支要求 config 与 state **同时**缺失——只要一个有一个没有就是 corruption（`restore.ts:65-75`）。（硬事实）

### `stateMatchesIntent()`：意图与状态的闭集一致性校验

`restore.ts:26` 是恢复的关键校验器，**取代了旧的 `findOpenOperations` 计数规则**：（硬事实）

- `intent.kind === "compaction"` → 状态必须是**某个 `summary.*` leaf** 且 `task.boundary.kind === "finish"`；
- `intent.kind === "navigation"` 且未摘要 → 状态必须是 `navigation.ready_to_commit`，且 `targetId`/`label` 与 intent **逐字段相等**；
- `intent.kind === "navigation"` 且摘要 → 状态必须是 `summary.*`，`boundary.kind === "commit_navigation"`，`targetId`/`label`/`customInstructions` 逐字段相等；
- `intent.kind === "run"` → 状态**不得**是 `navigation.ready_to_commit`，且若是 `summary.*` 则 boundary 必须是 `resume_checkpoint`。

不匹配 → 抛 `Operation ${id} intent ${kind} does not match state ${at}`（`restore.ts:156-160`）。（硬事实）

### 恢复到底读什么

`restoreSession()`（`restore.ts:92`）在**一次连贯的 Session read**（就是 `session.mutate`）里做三件事：（硬事实）

1. 三个 `scanValues` 分别扫 `branchTipInventoryPrefix()`、`laneConfig("")`、`laneState("")`——即"清点 lane 的并集"；
2. 对每条 lane 做 `classifyLaneStorage`，**跳过非 `lane` 的**（`absent`/`branch`/idle 不进 `open` 数组）；
3. 对有 `currentOperationId` 的，读 `op.meta` + `op.state`，校验 `meta.operationId === operationId`、`meta.lane === lane`、`stateMatchesIntent`，组装成 `LaneState`。

`restoreLaneState` 返回的进程内投影是 `{tipId, configuration, inbox, lastOperationId, operation}`（`restore.ts:164-170`），由一个**进程内**的 `LaneState` 类型（`runtime/types.ts`）承载，与 durable 的同名类型是两回事。（硬事实）

spec 明确了边界（`harness.md:662`）：**attachment 不解引用** transcript、inbox payload、deferred source、frames、tool args/checkpoint/memo、preparation、staged outcome——`watch` 和 drive 过程在**消费**这些引用时才校验；缺失的可选 frame list 与 tool checkpoint **合法**，矛盾的必需内容 fault 它的消费者。（硬事实）base restore **从不读 list**（`harness.md:335`）。（硬事实）

崩溃位置的可枚举性（`harness.md:982-989`，硬事实）：因为事务没有内部前缀，每个"重复敏感"的 effect 只有四个 durable 崩溃位——(a) intent commit 前 → 当作什么都没发生；(b) intent 后、effect 受理前 → `effect_pending`；(c) effect 期间/之后、settlement 前 → 同一 unknown-outcome 策略；(d) settlement commit 后 → 继续，**永不重结算**。孤儿 `assistant.effect_pending` 的恢复方式是从 `pendingAssistantFrames` 分页读、用 pi-ai 的 frame reducer 归约、然后**在预留 id 下**提交一条合成的 zero-usage `error` 响应，并附"请求被中断、前面内容是最后已提交的部分、更新的活输出可能缺失、外部结局未知"的显式警告（`harness.md:975`）。（硬事实）

## Fork 契约

旧版 `fork` 的 `branch` 参数默认 `main`、无 scope 校验。v0.85.1 是**强制 discriminated union**（`session/types.ts:561-589`）：（硬事实）

```ts
type ForkOptions =
	| { scope: "branch"; branch: string; entryId?: string;
	    position?: "before" | "at"; id?: string }
	| { scope: "tree"; id?: string };
```

- **branch scope** 要求源 Branch 是**完整配置的 AgentLane**（tip + configuration + lane state 三者齐全）。缺 tip = unknown Branch；data-only Branch **拒绝**；config/state 只有一半、或有 lane 值却没 tip = corruption。`entryId` 若给了，必须在**当前 tip 的祖先链上（含自身）**；省略则选当前 tip。`position` 默认 `"at"`，`"before"` 选目标的 parent，可能在根 entry 之前产生 `null` 目的 tip。`null` 源 tip **只能在没给 `entryId` 时**出现（`harness.md:541`）。
- **tree scope** 复制**每一个**不可变 entry（包括从所有当前 tip 都不可达的），每一条 Branch tip，每个完整 lane 的 configuration + 新的 idle lane state，以及每个 data-only Branch **保持 data-only**（`harness.md:543`）。
- **两个 scope 共同**：复制 session name 与"仅限被复制 entry 的"label；**排除** usage ledger、`pi.result`、所有 `pi.op.*`、所有 `pi.pending.*`；目的端 usage 从 0 起算，`messageCount` 只数被复制的 message entry；**entry 保留原 id**（`harness.md:545`）。

### 闭集分类器 `classifyForkAddress`

`session/fork-policy.ts:10` 对**每一个当前存活的 scalar/list 地址**做闭集判定，返回 `copy | exclude | reconstruct`（`fork-policy.ts:7`）：（硬事实）

| namespace | 处置 |
|---|---|
| `pi.session.name` | `copy` |
| `pi.entry.label` | 看该 entry 是否被复制：是 `copy`，否 `exclude` |
| `pi.branch.tip` / `pi.lane.config` / `pi.lane.state` | `reconstruct`（lane 处理会发射一个一致的新值，所以**不复制原行**） |
| `pi.result` | `exclude` |
| 任何 `pi.op.*` / `pi.pending.*` | `exclude` |
| 精确的 `pi` 或其它未声明的 `pi.*` | **抛 `Unknown reserved fork namespace`** |
| 其它（应用 namespace） | `scope === "tree"` → `copy`，否则 `exclude` |

注意最后两行：**未知保留 namespace 只有在"当前仍有存活 scalar/list 状态"时才 reject**；已被替换或删除的历史不存在，本身不能成为拒绝的理由（`harness.md:549`）。（硬事实）应用状态按 **scope** 走而不是按"历史 seq 截断"：tree scope 复制每一条当前应用 scalar 与每一个存活的应用 list 元素，branch scope 一个都不复制——因为当前状态里**没有**"被替换的值"或"被删掉的 list 元素"可供重建历史点，所以按 `seq <= selectedTipSeq` 过滤是**被禁止的**（`harness.md:547`）。（硬事实）

`createForkSnapshot()`（`session/fork.ts:30`）是共享的纯函数构造器：先 `validateForkSourceSnapshot`（`fork.ts:127`，校验"有 lane 值必有 tip"、"config 与 state 必须同现"、"branch scope 的源必须是完整 AgentLane"、"tip 必须能在 entry 集合里找到"），再 `selectForkContents`（`fork.ts:86`，branch scope 沿 parent 链走到 `requested`，`position === "before"` 取 parent），最后为每个目的 branch 发射 `branchTip` + `laneConfig`（拷贝源值）+ `laneState`（**新的 idle 三元组**，`fork.ts:53`），其余按 `classifyForkAddress` 走。（硬事实）

> **⚠️ spec/实现不一致之一：tree scope 不复制应用 list（本轮新发现，硬事实）** —— 这一条与"之二"同处 `harness.md:547-551` 这一段：该段似乎整体描述了一个比 `session/fork.ts` 更丰富的 fork。`harness.md:547` 明确说 tree scope "copies ... every surviving application list element"，但三后端的实现都**不复制 list**。证据：`ForkSourceSnapshot` 只有 `{entries, scalarValues, entriesComplete}`（`fork.ts:6-11`），`createForkSnapshot` 只遍历 `source.scalarValues`；`InMemoryStorageState.snapshotEntriesAndValues()` 也只返回 `{entries, scalarValues}`（`in-memory-storage-state.ts:258`）；SQLite 的 `ForkSnapshot` 同样只有 entries + scalarValues（`sqlite-node/src/sqlite/repo.ts:72-77`）。一致性套件里 **tree scope 用例（`conformance/session-repo.ts:613`）只断言 scalar 被复制、根本没 append 过 list**，branch scope 用例则断言 `readList(...) === []`（`:467`、`:609`）。**结论：tree scope 复制应用 list 是"仅 spec 未落地"，且当前没有测试覆盖。** 应用若依赖 fork 保住 list 状态会踩坑。

> **⚠️ spec/实现不一致之二：目的端 seq 规则（本轮新发现，硬事实）**：

- **spec（`harness.md:551`）**：被复制的 entry/value/list 元素**保留源 `seq`**；被重写的 tip 和新的 idle lane state **复用源行的当前 seq**；目的端 `nextSeq = 源高水位`，因此**没有 seq 可以被复用**。
- **实现（`fork.ts:39-65`）**：只有**被复制的 entry** 保留源 `seq`。所有 value（无论 copy 还是 reconstruct）都由本地 `store()` **重新稠密分配**：`nextSeq` 从 `max(被复制 entry 的 seq) + 1` 起，每写一个值 `nextSeq++`；返回的 `nextSeq` 因而已被这些值推高。`forkSnapshotWrites` 按 `seq` 排序后把这些**已带 seq** 的 write 直接交给后端（`fork.ts:70-84`），JSONL 把它写进 header 的 `nextSeq`（`jsonl/storage.ts:166`）、SQLite 写进 session 行（`sqlite-node/src/sqlite/repo.ts:352`）。**没有一处"复用源行 seq"**。
- 后果（解释）：目的端**自身**是自洽的——所有被分配的 seq 严格递增、值排在 entry 之上、不会重复；但 spec 那句"目的端 `nextSeq = 源高水位`、没有 seq 可以被复用"**不成立**——若源的高水位来自 value/usage/list 写入（典型：`pi.op.state` 反复替换），它可能**高于**目的端算出的 `nextSeq`。由于 fork 不复制 list、usage 也不复制，这个差异目前不产生可观测的错读；但**跨 session 的 seq 引用**（如 cursor 持久化到别处）会踩到。这一条建议 upstream 澄清。（推测）

三后端的实现路径（`harness.md:551`，与源码一致）：Memory 直接在 commit-queue 边界构造目的状态；JSONL 抓一个固定只读文件前缀；SQLite 建独立只读快照、流进临时 staging 库、关掉源 reader、再在目的端一个事务里发布。

## JSONL 后端

`JSONL_FORMAT_VERSION = 4` **没变**，`JSONL_STORAGE_VERSION = 1`（`session/jsonl/types.ts:4-5`）。upstream 对"为什么不用迁移"的原话（`docs/runtime-simplification.md:7`，硬事实）：

> Format 4 is still work in progress, so the durable type replacement required no migration or compatibility representation.

即 **v4 的 payload 被原地重写，没做 v4 内部迁移**；也没有任何 v4 迁移机制（`harness.md:360`、`:397`）。（硬事实）

### 文件即"重放配方"

spec 的措辞很精确：**文件是 Memory maps 的重放配方，不是状态本身**（`harness.md:358`）。（解释）

- **一行一个 `commit()`**：存储先分配 seq/timestamp，再把**一条** write 编码成一个 JSON 对象行，或把**多条**编码成**一个数组行**（`serializeTransaction`：`writes.length === 1 ? writes[0] : writes`，`jsonl/storage.ts:79-81`）；（硬事实）
- **行 kind 只有 4 种**：`entry` | `usage` | `value` | `list`（`parseCommittedWrite`，`jsonl/storage.ts:47-67`）。旧版的 `entry|record|lane|fact` **全部消失**。（硬事实）
- **header**：`{"v":4,"kind":"header","id":…,"storageVersion":1,"createdAt":…,"cwd":…}`，外加可选的 `parentSessionId`、`legacyParentSessionPath`，以及由 fork 目的端与 v3 归一化写下的 `nextSeq` 高水位（`jsonl/types.ts:7-18`）；（硬事实）
- **open = 按序 replay 进内存**：entries/usage 累积；后面的 value `set` 覆盖、`delete` 移除；list `append` 加 `{seq, value}`、`delete` 移除整个 key。spec 强调这是 **decoding，不是恢复逻辑**（`harness.md:361`）。（解释）

### torn tail 与原子发布

- `splitCompleteLines()`（`jsonl/storage.ts:87`）：内容以 `\n` 结尾 → 完整；否则**最后一行判为 torn**，整行（**含数组行的每一个元素**）丢弃；
- open 时若发现 torn，就把有效前缀**原子重写**：`publishFileAtomically` = 写 `<path>.tmp` + `renameFile` 到目标（`jsonl/storage.ts:94-114`，在 `:210` 被调用）。（硬事实）
- **中间行**损坏或 framing 非法 → 抛 corruption（`storage.ts:201-208` 的循环把行号带进错误里）。（硬事实）
- 常规写只 `appendFile` 一行（`storage.ts:256`），所有 commit 经 `commitQueue` 链串行化（`storage.ts:241-245`）。（硬事实）
- 这就是 v0.84.0 给 `FileSystem` 加**必需 `renameFile()`** 的原因（同文件系统替换语义）。该方法的行号已从旧文档的 `harness/types.ts:252` 漂到 **`harness/types.ts:284`**。（硬事实）

### v3 → v4：只读 backing + 写入即升级

`JsonlBacking = {kind:"v4"} | {kind:"v3"; importedUsage; baselineWrites}`（`jsonl/storage.ts:116-122`）。（硬事实）

- v3 文件（header `{type:"session",version:3,...}`，由 `isLegacyV3SessionHeader` 识别，`jsonl/codec.ts:21`）走 `openLegacyV3`：用 `normalizeLegacyV3Records` 把 v3 records 归一化成 **v4 的 CommittedWrite 序列**，用 `normalizeLegacyV3Header` 造 v4 header（带 `nextSeq`），然后 `replayCommitted(baselineWrites)`；（硬事实）
- **v3 backing 是只读的**：`commit()` 只要收到**非空** writes，就直接走 `upgradeLegacyV3ToV4`——把 `baselineWrites` + "一条 `adjustment: true`、`details: {source: "v3-import"}` 的 usage 聚合行" + 调用方 writes 一起原子发布成 v4 文件，再翻转 backing。**第一次写入即完成升级。**（硬事实）
- 返回值有一处细节：`firstSeq` 与 `seqs` 都**剥掉了那条内部 usage 行**（`storage.ts:296-301`），调用方看到的 seq 只对应自己的 writes。（硬事实）
- v3 导入的 usage 在升级前靠 `withImportedUsage()` 直接替换 stats 里的 usage（`storage.ts:353-355`）。（硬事实）

相关文件：`session/jsonl/legacy-v3.ts`（539 行，导出面是 `metadataFromLegacyV3Header:135`、`normalizeLegacyV3Header:154`、`normalizeLegacyV3Records:519`）；测试 `packages/agent/test/harness/jsonl-v3-migration.test.ts`（2013 行）。（硬事实）

> v3 归一化的细节（`custom_message` 怎么投影、`firstKeptEntryId` 怎么物化成 `retainedTail`、保留 id 怎么重铸）超出本篇范围，`legacy-v3.ts` 有完整的 `LegacyV3*Entry` 联合与 `RetainedIdResolver` 机制，值得单独一篇。（推测）

## context 投影：branch → provider 消息序列

`session/context.ts`（64 行）是无状态纯函数层：（解释）

1. **`buildContextEntries(pathEntries)`**（`context.ts:10`）：**从尾向头**找最新一个 `compaction`，返回 `[compaction, ...其后的所有 entry]`；找不到就整段返回。这正是"**context 永不读过 compaction**"的实现点——compaction 是自包含的检查点，不是指向历史的指针。（硬事实）
2. **`sessionEntryToContextMessages(entry)`**（`context.ts:31`）：`message` 若 `isContextMessage` 则原样；`compaction` 展开成"`createCompactionSummaryMessage` + `retainedTail.filter(isContextMessage)`"；`branch_summary` 展开成一条 branch summary message（**summary 为空串时不产生消息**）；`custom` **恒返回 `[]`**。（硬事实）
3. **`buildSessionContext(...)`**（`context.ts:47`）：非 custom entry 直接展开；custom entry 只在 `entryProjectors[customType]` 注册了投影器时才可能进 context，否则**永不进入**。（硬事实）

丢弃规则（`isContextMessage`，`context.ts:24-29`）：`stopReason` 为 `error`、`aborted`、`deferred` 的 assistant 消息被丢；**真正的 output-limit `length` 被保留**。（硬事实）注意与旧文档的差异：**溢出响应不再需要专门的省略规则**——它以 `stopReason: "error"` 落盘，被同一条规则丢掉（`harness.md:516`）。（解释）

spec 还点明了一条**成本级不变式**（`harness.md:518`）：跨同一 lane 的多次请求，provider context **只允许在尾部增长**——在上一请求尾部之前插入内容会作废 provider 的 KV cache 并放大成本。这正是"运行中的写要 defer 到 checkpoint"的原因，也解释了为什么 compaction 是**唯一被有意接受的 cache 失效**。（解释）

`EntryProjector`（`types.ts:59`）签名是 `(entry: CustomEntry, context: Context) => AgentMessage[] | undefined | Promise<...>`；spec 明确"从 `toProviderMessages` 或 `entryProjector` 抛出的异常会 fault harness"（`harness.md:1013`）。（硬事实）
