## 现象是什么

当 LLM API 返回 "overloaded_error"、"rate limit exceeded"、502、503 等错误时，pi-mono 会自动等待一段时间后重试，用户会看到 "auto_retry_start" 和 "auto_retry_end" 事件。重试行为在两个层次独立运作（硬事实）：pi-ai 的 provider 级别（HTTP 层面的客户端重试）和 coding-agent 的 AgentSession 级别（Agent 生命周期层面的可重试错误处理）。

**源码位置：**
- `/packages/ai/src/types.ts`（`ProviderRequestOptions` 中的 maxRetries / maxRetryDelayMs）
- `/packages/ai/src/utils/retry.ts`（`isRetryableAssistantError`、`RetryPolicy`、`retryAssistantCall`）
- `/packages/coding-agent/src/core/agent-session.ts`（`_handlePostAgentRun`、`_prepareRetry`、`_isRetryableError`、`autoRetryEnabled`）

## 核心矛盾是什么

两个层次的重试有不同的语义和范围：

- **Provider 级重试（pi-ai）：** 发生在单次 HTTP 请求层面（硬事实）。SDK（如 `@anthropic-ai/sdk`、`openai`）自带重试逻辑（硬事实），pi-ai 通过 `maxRetries` 和 `maxRetryDelayMs` 控制。这种重试对上层 Agent Runtime 是透明的——重试发生在流开始产生事件之前（解释）。
- **Agent 级重试（coding-agent）：** 发生在 Agent 完成一个完整回合（`agent_end`）之后（硬事实）。`AgentSession._runAgentPrompt()` 在 `agent.prompt()` 返回后循环调用 `_handlePostAgentRun()`（硬事实）：检查最后一个 AssistantMessage 是否为"可重试错误"，如果是，则移除该错误消息、等待指数退避、通过 `agent.continue()` 重新进入 loop（硬事实）。

两种重试需要协调（解释）：
- Provider 级重试不应掩盖本应由 Agent 级处理的错误（如 context overflow 不应重试，应触发 compaction）。（解释）
- Agent 级重试需要可中断（用户可能在等待重试期间 abort）。（解释）
- 重试不能无限进行：`maxRetries` 在两层都是硬限制。（硬事实）

## 实现思想是什么

### Provider 级重试

在 `ProviderRequestOptions`（`StreamOptions` 继承它）中定义：

```typescript
interface ProviderRequestOptions {
  maxRetries?: number;        // 最大重试次数，默认 2（OpenAI/Anthropic SDK 默认）
  maxRetryDelayMs?: number;   // 重试延迟上限，默认 60000ms，0 表示不设上限
}
```

这些参数直接传递给 SDK（Anthropic SDK 的 `maxRetries`，OpenAI SDK 的 `maxRetries` 等）（硬事实）。`maxRetryDelayMs` 的语义是：如果服务端要求的等待超过此值，请求立即失败并携带所要求的 delay 信息，让上层 Agent 级重试以用户可见的方式处理（解释）。coding-agent 侧对应 SettingsManager 的 `retry.provider.{timeoutMs,maxRetries,maxRetryDelayMs}`（硬事实）。

### Agent 级重试

重试不发生在事件回调里，而是在 run 的驱动循环中（硬事实）（`_runAgentPrompt`，agent-session.ts:1106-1119）：

```
agent.prompt(messages) 完成（agent_end 已发出）
  → while (await _handlePostAgentRun()) { await agent.continue(); }
      _handlePostAgentRun:
        取本 run 最后一条 assistant 消息 (_lastAssistantMessage)
        → _isRetryableError(msg)?
          → 排除 context overflow (由 _checkCompaction 处理)
          → isRetryableAssistantError(msg) 匹配正则
        → 可重试且 _prepareRetry(msg) 成功 → 返回 true → agent.continue()
        → 否则若 stopReason === "error" 且 _retryAttempt > 0:
            emit auto_retry_end(success: false, finalError)，_retryAttempt = 0
        → _checkCompaction(msg) 触发压缩续跑 → 返回 true
        → agent.hasQueuedMessages() → 返回 true（消费 agent_end 后排入的队列）
  → finally: _emitAgentSettled()（agent_settled 事件 + idle 解锁）
```

`agent_end` 事件本身经 `_willRetryAfterAgentEnd()`（agent-session.ts:726-739）计算后带上 `willRetry: boolean`（硬事实），UI 可以在事件流上直接看到"这个 error 会不会被自动重试"（解释）。

关键设计点：

1. **可重试错误的判定**（`_isRetryableError`，agent-session.ts:2846-2850）：先排除 context overflow（`isContextOverflow(message, contextWindow)`，ai/utils/overflow.ts:134），再交给 `isRetryableAssistantError`（ai/utils/retry.ts:223-228）正则匹配。覆盖 `overloaded`、`rate limit`、429/500/502/503/504/524、`service unavailable`、`network error`、`connection lost`、`websocket closed`、`fetch failed`、`timeout`、流早断（`stream ended before message_stop`）等（硬事实）；**明确排除** quota/billing 类（`insufficient_quota`、`out of budget`、`billing` 等）——它们 deterministic，重试没有意义（硬事实+解释）。

2. **`retry.enabled` 开关：** 通过 SettingsManager 的 `retry` 设置控制（默认 enabled=true，maxRetries=3，baseDelayMs=2000，settings-manager.ts:821-827）（硬事实）。disabled 时 `_prepareRetry` 直接返回 false，可重试错误不发起重试（硬事实）。

3. **错误消息的清理：** 在发起重试前，若 `agent.state.messages` 末条是 assistant，则从 state 中移除（session 历史仍保留）。（硬事实）Agent 的 state 保持干净，`continue()` 从上一个有效状态继续。（解释）

4. **重试期间的 abort：** `_prepareRetry` 中每次退避都新建 `_retryAbortController`，`sleep(delayMs, signal)` 可被中断（硬事实）。`abortRetry()` 方法 abort 该 controller，触发 sleep 的 catch 分支：重置计数、emit `auto_retry_end(success: false, finalError: "Retry cancelled")`、返回 false 不再 continue。（硬事实）

5. **重试成功的重置：** `_handleAgentEvent` 的 `message_end` 分支（agent-session.ts:705-712）：assistant 消息 `stopReason !== "error"` 且 `_retryAttempt > 0` 时立即 emit `auto_retry_end(success: true)` 并把计数清零，防止同一个 run 内多次 LLM 调用导致计数累积（硬事实）。

6. **summarization retry（第三层）：** compaction / branch-summary 的摘要 LLM 调用走 `retryAssistantCall()`（ai/utils/retry.ts:163，bounded attempts + 指数退避 + abort 归一化为 aborted AssistantMessage）（硬事实），复用同一份 `settings.retry` 预算（硬事实）；`_summarizationRetryCallbacks`（agent-session.ts:2858-2881）把它映射为 `summarization_retry_scheduled / attempt_start / finished` 事件，与 agent turn 重试的 `auto_retry_*` 事件分开渲染（硬事实）。

### 两层重试的协调

Provider 级重试先发生（因为它在单个 HTTP 请求的上下文中）（硬事实）。当 Provider 的重试也耗尽时，SDK 抛出的错误被转换成 `stopReason: "error"` 的 AssistantMessage，然后 Agent 级重试接管（硬事实）。

当 `maxRetryDelayMs` 限制了 SDK 的等待时间时，即使 SDK 本可以继续等待，也会让 Agent 级重试来处理更长的退避周期（硬事实）。这种设计让上层有更大的控制权（例如显示"正在重试，第 3 次..."的 UI 提示）（解释）。事实上 `isRetryableAssistantError` 的正则特意匹配 `"retry delay"` 文本，让被 cap 掉的请求 fail-through 到外层策略（硬事实）。

## 在 Agent 能力面里的影响是什么

- **对用户透明的恢复：** 瞬态错误（如服务暂时过载）在几秒内自动恢复，用户感知到的只是短暂的 "busy" 状态。（解释）
- **可观测性：** `auto_retry_start/end` 事件让 UI 层可以展示重试进度（"第 2 次重试，等待 5 秒..."）。（硬事实）
- **可取消性：** 用户可以在重试等待期间 abort，不会留下损坏的 Agent 状态。（硬事实）
- **与 compaction 的分工：** Context overflow 走 compaction 路径（压缩 → retry），overloaded/rate-limit 走 retry 路径，不会混淆。（硬事实）

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent-core";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const agent = new Agent({
  streamFn: streamSimple,
  initialState: {
    model: claudeSonnet,
    tools: [readTool],
    systemPrompt: "You are a file reader.",
  },
  // Agent 级重试的预算在 AgentSession 的 SettingsManager（settings.retry：
  // enabled/maxRetries=3/baseDelayMs=2000）里配置，不在 Agent 构造参数里。
  // Provider 级重试通过 retry.provider.maxRetries / maxRetryDelayMs（settings）
  // 或逐请求 SimpleStreamOptions 控制。
});

// 监听重试事件（coding-agent 级别）
const unsubscribe = session.subscribe((event) => {
  switch (event.type) {
    case "auto_retry_start":
      console.log(
        `[重试] 第 ${event.attempt}/${event.maxAttempts} 次，` +
        `等待 ${event.delayMs}ms，原因: ${event.errorMessage}`
      );
      break;
    case "auto_retry_end":
      if (event.success) {
        console.log("[重试] 成功恢复");
      } else {
        console.log(`[重试] 失败，最终错误: ${event.finalError}`);
      }
      break;
    case "agent_end":
      // agent_end 带 willRetry：这个 error 会不会被自动重试
      console.log(`agent_end, willRetry=${event.willRetry}`);
      break;
  }
});

// 如果 API 返回 overloaded_error:
// → provider SDK 先做 HTTP 级重试（默认 maxRetries=2）
// → 如果全部失败 → agent_end 携带 error（willRetry=true）
// → _handlePostAgentRun 判定可重试 → _prepareRetry 指数退避
// → agent.continue() 重新进入 loop
// → 如果 continue 成功 → message_end(stopReason!=="error") → auto_retry_end(success: true)

// 用户也可以在重试过程中取消
// session.abortRetry();  // 取消退避等待，停止重试
// await session.abort(); // abortRetry + agent.abort + waitForIdle
```

这个例子展示了双层重试的工作流：Provider 级重试对上层透明，Agent 级重试提供用户可见的进度和可取消性。
