# 4.1 AgentHarness v3：`Drive` + 13-leaf 扁平状态的真实现

> **⚠️ 版本史 / 本文已整体重写**：本文最初写于 v0.75.3 的泛型 `AgentHarness<TSkill,TPromptTemplate,TTool>`；v0.84.0 重写为"零泛型的 `AgentLane` 骨架"（每个操作抛 `HarnessNotImplemented`）；**v0.85.1 该骨架被整体替换为真实现**——`HarnessNotImplemented` 在 `packages/` 源码树里已零命中（只剩两处历史 CHANGELOG 文字）。**如果你手上是 v0.84 的旧版 4.1，它的每一条机制断言、每一个锚点、每一个例子都已失效，请整篇废弃。** 变更全景见 [`_change_log/0006-v0.84.4-to-v0.85.1.md`](../../_change_log/0006-v0.84.4-to-v0.85.1.md)。
>
> **结论先行**：`AgentHarness` 现在**是真实现，能跑完整 turn**——它由 `Drive`（一次进程本地执行 pass）+ effect gate + 13 个扁平 durable `OperationState` leaf + 直接 async procedure 组成，配套约 8.4k 行聚焦运行时测试（含 faux provider 的整 turn 驱动）。**但产品级集成仍然不要走它**：这条线只被 `coding-agent/src/experimental/` 下的 experimental 路径使用（`session-worker.ts`、`mini/`），`watchSession()` 仍是唯一的 `SliceNotImplemented` stub，且它与产品路径的 `AgentSession` 是**两套互不 import 的并列实现**。产品集成继续走 `AgentSession` / SDK（`createAgentSession()`，`packages/coding-agent/src/core/sdk.ts:173`）——那是逐字节未变的稳定面。

## 现象是什么

`Agent`（`packages/agent/src/agent.ts`）只做最纯粹的 LLM 对话循环：收消息、调 LLM、执行 tool call、吐事件。它不知道 session 的存在，不管 compaction，也没有 hook 机制。（解释）

因此 `Agent` 之上需要一层 harness：管持久化、拼 context、实现 steer/followUp 队列、在 crash 后从 durable 状态继续。**这层需求从 v0.75 到 v0.85 从未变过，变的是"由谁实现、以及实现得如何"**：

- **产品现实**：coding-agent 的 `AgentSession`（`packages/coding-agent/src/core/agent-session.ts:310`）是这层包装的活实现。（硬事实） 它有 `prompt()`（L1159）、`steer()`（L1387）、`followUp()`（L1407）、`abort()`（L1619）、`compact()`（L1946）、`navigateTree()`（L3113），权限拦截在 `_installAgentToolHooks()`（L486）。TUI/RPC/SDK 都建立在它上面。
- **产品路径与 harness 路径互不相干**（硬事实，很容易误判）：`packages/coding-agent/src/core/agent-session.ts` 全文 **grep `harness` 零命中**，`sdk.ts` 同样不 import harness。两者是并列实现，不是"harness 在下、AgentSession 在上"的堆叠关系。
- **upstream 在建工程已落地**：`packages/agent/src/harness/agent-harness.ts` 从 v0.84.4 的 508 行骨架变成 v0.85.1 的 622 行公开面 + `harness/runtime/`（约 7.5k 行，其中 `lane.ts` 2012 行、`drive/structural.ts` 1221 行）。**唯一的 consumer 是 experimental 线**：`packages/coding-agent/src/experimental/session-worker.ts:805` 的 `createCodingAgentHarness()`（`:834` 调 `AgentHarness.create()`）、`experimental/mini/worker/run.ts:66`、以及经 chord facet 暴露 `AgentLane` 的 `experimental/services/worker.ts`。（硬事实）

## 核心矛盾是什么

老矛盾仍然成立：**循环的核心逻辑不应该知道 session，但产品功能必须依赖 session。**（解释） `Agent` 保持纯净，session 感知/权限/compaction/队列由上一层负责——`AgentSession` 一直在证明这个分层可行。harness 换了三轮实现，这条轴线一次都没动过。

v0.85.1 的 harness 又在老矛盾上加了两条新的、互相拉扯的轴线，这才是这次重写真正的动机（依据 `docs/work-packages/00-runtime1-removal.md` 与 `05-direct-durable-drive.md`，硬事实）：

1. **"执行器拥有 pass" vs "宿主拥有调度权"**（解释）。runtime1（`harness/runtime/` 首版，从未进过任何 v0.84.x tag，被 `877c2d0ea` 整体删除）的形状是 `run-driver.ts` / `transitions.ts` / `operation-task.ts`——一个 "installer-owned drive + 手动步进" 的模型：调用者通过 `peekAction()` / `executeAction()` / `runToCompletion()` 一步步驱动图。WP00 判它不可用，整体删除。新模型反转过来：**一个 lane 同时只有一个进程本地 `Drive`，第一个匹配的调用者"安装"它、其余调用者只是观察同一个 completion；第一个调用者不是 owner，Lane 才是**（`runtime/types.ts:85`、`runtime/lane.ts:921`）。（硬事实）
2. **"可推断的持久化" vs "便宜的进程内行为"**（解释）。每个操作都要能落进 bound value、能在 crash 后从扁平状态直接恢复、能在 durable 取消后完整对账。upstream 为此把原来 22 个按 family 前缀区分的 durable leaf 折叠成 **13 个 family-neutral 的扁平 `OperationState`**，`compaction` / `navigation` 复用同一套 summary 四元组，靠一个封闭的 `ResultBoundary` 三分支决定结果落到哪（WP05 §1/§8，硬事实）。这比 v0.84 那种"在回调里随手改状态"严格得多，所以 `AgentSession` 那套活实现**不能**直接搬进来。

## 实现思想是什么

### 1. `AgentHarness` 从 class 变成工厂对象

这是最容易踩的一脚：**`AgentHarness` 不再是 class，而是一个只有一个方法的对象字面量**。

```typescript
export interface AgentHarnessConstructor {
	create<TContext extends object | undefined = object | undefined>(
		options: AgentHarnessOptions<TContext>, context: Context,
	): Promise<{ harness: AgentHarness<TContext>; open: OpenOperation[] }>;
}
/** Runtime constructor for attaching the durable harness to one open session. */
export const AgentHarness = { create: createAgentHarness } satisfies AgentHarnessConstructor;
```

（`agent-harness.ts:614-622`，硬事实）

同时 `agent-harness.ts:586` 还导出一个 **同名 interface `AgentHarness<TContext>`**（type 与 value 合并，所以 `AgentHarness` 既能当类型用、也能当值用）。真实现是 `runtime/harness.ts:29` 的 `class Harness<TContext> implements AgentHarness<TContext>`，**不从 `src/index.ts` 导出**——`runtime/index.ts` 只导出 `createAgentHarness`，公开面唯一的取到实现的路径就是 `AgentHarness.create()`。（硬事实）

另一个结构变化：**`AgentHarness` 自己不是 lane**（旧版是 `implements AgentLane` 且 `name = "main"`）。它管理 lane，自己不是 lane：`runtime/harness.ts:28` 的注释原文即 "The harness manages lanes but is not itself a lane."。（硬事实）

### 2. `AgentLane` 公开面：四个原语 + 一层便利组合

`AgentLane`（`agent-harness.ts:538`）现在是**分支门面 + 执行门面**。每个 async 方法都多了一个尾参 `context: Context`（这是全轮最大面积签名变更）。（硬事实）

- **Branch 五件套**：`getTipId`（`lane.ts:266`）、`findEntries`（`:1900`）、`findEntry`（`:1909`）、`appendMessage`（`:1916`）、`appendCustomEntry`（`:1920`）
- **四个原语**：`accept(request: OperationRequest)`（`:480`）durable 地创建一次操作，不安装进程 owner；`drive(options: DriveOptions)`（`:921`）安装或加入一次 pass；`requestAbort(operationId)`（`:1006`，公开别名 `:1102`）是**唯一的 durable 取消原语**；`getResult(operationId)`（`:271`）/ `inspectExecution()`（`:1106`）做观察
- **便利组合**：`prompt`（`:1133`）/`skill`（`:1147`）/`promptFromTemplate`（`:1154`）≡ accept + drive；`compact`（`:1200`）/`navigateTree`（`:1232`）在 A 落定后**可能再接受并驱动一个空 prompt 的普通 run B**（见下）；`resume`（`:1327`）≡ inspect + drive 当前操作，并给这个 pass 一张 deferred-poll 许可（`pollDeferred: true`）；`abort`（`:1373`）≡ inspect + requestAbort + 观察一次对账 pass
- **队列**：`steer`/`followUp`/`nextRun`（`:1418`/`:1422`/`:1430`）是一个 enqueue 的三个 tag 糖，**永远 admit**；`cancelQueued`（`:1518`）
- **其他**：`recordUsage`（`:1553`）、`waitForIdle`（`:1588`）、`runWhenIdle`（`:1608`）、`getModel`/`setModel`（`:1648`/`:1653`）、`getThinkingLevel`/`setThinkingLevel`、`getActiveTools`/`setActiveTools`、`watch`（`:1705`）

**便利 = 原语的可复现组合**（解释）：这是 upstream 明确承诺的等价性——`compact()` 带 continuation ≡ `accept(A); drive(A); accept({kind:"prompt", prompt:""}); drive(B)`，写与事件逐字节可复现（WP05 §10）。B 是一个**普通 run**，有自己的 `run_start`，不享受任何 continuation 特判；如果并发 accept 抢到了那个 idle 窗口，B 就失败（`InvalidMessage` 或 `LaneBusy`），便利调用只返回 A。**绝不 auto-start、reopen 后也绝不自动续跑**。（硬事实）

**`setModel` 接身份而不是对象**（硬事实）：`setModel(model: ModelIdentity, ...)`，`ModelIdentity = { provider, modelId }`（`agent-harness.ts:142`）。live `Model` 对象是进程本地注册表的事；一个未注册的身份是**合法配置**，会在真正发起请求时像任何 registry 缺失一样 in-band 失败（`harness.test.ts:61` "persists model identity without requiring a local registration" 就是在钉这条）。

### 3. `Drive`：一次 pass 的进程本地延续

`Drive`（`runtime/types.ts:85`）是这套执行模型的中心。它的形状很小：

```typescript
class Drive {
	readonly operationId: string;
	readonly completion: Promise<DriveOutcome>;
	readonly gate: Gate;                 // 程序面：{ signal, admit }
	readonly context: Context;           // 安装者的 abortSignal 已被剥离
	readonly waitForRetry: boolean;
	deferredPermits: number;             // pollDeferred 时 = 1
}
```

（硬事实）

三条不变量（解释 + 硬事实混合，都有源码锚点）：

- **一个 lane 同时只有一个 Drive**。`lane.drive()` 在 Session mutation line 上做一次 claim（`lane.ts:926-960`）：当前操作 id 匹配且无活动 Drive → **安装**；已有匹配的 Drive → **加入**（观察同一个 `completion`）；已有不匹配的 Drive → `occupied`，等它结束再重试整段循环。已有 result record 的操作 → 直接 `{ kind: "settled", outcome: record }`（**`drive` 对已落定操作是全函数**）；两者都不是 → `OperationMismatch`。（硬事实）
- **第一个调用者不是 owner**。所有调用者都是观察对等体，执行由 Lane 拥有；每个调用者只用自己的 `context.abortSignal` 与**自己的观察**赛跑——安装前 signal 赢了就什么都不启动，安装后赢了只拒绝那一个调用者的 invocation，**绝不移除、替换或取消 Drive**（`drive-public.test.ts:522/534`）。（硬事实）
- **唯一的顶层状态推进写者**。inbox 方法只改 inbox 字段，`requestAbort` 只改 `control`，close 只封住 mutation admission——所以活动 procedure 的操作身份和 `at` leaf 不可能被并发改动，procedure 因而**不需要反复校验操作存在性、id、kind、Drive 身份或预期的 `at`**（`runtime/types.ts:60-82` 的 `LaneCommand` / `OperationCommand` 类型设计就是这个"唯一写者"假设的编码）。（解释）

`Drive.context = withoutAbortSignal(context)`（`runtime/types.ts:101`）——**pass 的 Context 不继承安装者的取消信号**，否则一个调用者退出会连带杀掉整条 pass。

### 4. Effect gate：同步准入边界

`runtime/drive.ts:34-45` 与 `execution/effect-gate.ts` 一起定义了一个"检查与调用之间不许 yield"的准入点。（硬事实）

`GateState = open | aborting(cancellation) | closed(error)`；`Gate.admit(invoke)` 做**唯一一次**检查然后**立即同步**返回 `invoke()`：aborting → 抛 `AbortRequested(cancellation)`；closed → 抛封门错误（`effect-gate.ts:35-47`）。（硬事实）

为什么必须同步（解释）：`requestAbort` 的顺序是 (1) 同步 `beginAbort`，(2) 提交 `control = cancel_requested`，(3) `signalAbort` 拔掉已准入操作的信号（WP05 §9）。如果 preparation 自己也被包进 `admit`，abort 就可能在 preparation await 的窗口里抢赢，从而出现"已准入但语义上不该跑"的效应。

准入目录有明确边界（硬事实）：**hook 聚合**（一次 `admit` 包住整条注册管线，不是每个 handler）、**provider 操作**（一次 `Models.streamSimple`、每个结构摘要请求、一次 `Models.streamDeferred` 轮询）、**其他**（一次真实 `tool.execute`、每个重试计时器的创建）。commit、公开队列/配置/树写、纯分类、合成结果、已准入的 promise、对账过程、被动监听器**都不走 gate**（harness.md §4.2）。

### 5. 13 个扁平 leaf + 一个直接 switch

`OperationState`（`session/types.ts:315`）现在是**一个 `at` 判别式 + 13 个 family-neutral 的直接 leaf**，没有 `run.` / `compaction.` / `navigation.` 前缀，没有 per-family scope 类型，没有交叉类型动物园：

```text
starting · checkpoint · assistant.ready · assistant.effect_pending · assistant.retry_wait
tools · deferred.suspended · deferred.effect_pending
summary.deciding · summary.ready · summary.effect_pending · summary.retry_wait
navigation.ready_to_commit
```

（硬事实）

四个 `summary.*` leaf 携带一个 `SummaryTask`，其 `boundary` 是一个**封闭三分支 union**（`resume_checkpoint` / `finish` / `commit_navigation`）：摘要算法种类（compaction vs branch summary）**由 boundary 推导、不落盘**，所以"kind 与 boundary 矛盾"这个状态根本不可表示。（硬事实）

执行侧对应的是 `runtime/drive.ts:48-105` 的一个 `for (;;)` 里**一个直接 `switch (state.at)`，13 个 case 全部有直接实现**（不是图解释器，也不是 action 调度器）：（硬事实）

| leaf | procedure |
|---|---|
| `starting` | `startRun`（`drive/checkpoint.ts`） |
| `checkpoint` | `runCheckpoint` |
| `assistant.ready` / `assistant.retry_wait` | `runGeneration`（`drive/generation.ts`） |
| `assistant.effect_pending` | `recoverAssistantGeneration`（`drive/recovery.ts`） |
| `tools` | `runTools`（`drive/tools.ts`） |
| `deferred.suspended` / `deferred.effect_pending` | `runDeferred`（`drive/deferred.ts`） |
| `summary.deciding` | `runStructuralDecision` |
| `summary.ready` | `runStructuralGeneration` |
| `summary.effect_pending` | `recoverStructuralGeneration` |
| `summary.retry_wait` | `runStructuralRetryWait` |
| `navigation.ready_to_commit` | `commitNavigation` |
| （`control.status === "cancel_requested"` 时） | `reconcileOperation`（`drive/reconcile.ts`），**在普通 dispatch 之前** |

**兜底是一条不变量断言**（硬事实，`:102-104`）：如果一轮 procedure 之后 `currentOperation` 的 `state` **对象引用没变**且控制状态不是 `cancel_requested`，就抛 `SessionInvariantError("Drive procedure made no progress from ...")`。`continue` 结果必须对应一次 `Lane.state` 投影替换或一个当前可观察的 `cancel_requested`；任何一种"没变化的 continue"都是不变量缺陷。这把"图跑不动了"从静默挂死变成了硬故障。

`ProcedureResult` 只有三态（`runtime/types.ts:143-146`）：`continue` / `waiting(outcome)` / `settled(outcome)`。一次 pass 要么以 terminal result 结束，要么以 durable wait 结束；pass 结束后清掉 `activeDrive`，**进程内不替换活动 pass**。

### 6. 结果即记录：`OperationResultRecord`

旧的 outcome 家族（`RunOutcome` / `CompactionOutcome` / `NavigationOutcome` / `ResumeOutcome` / 各 `*Rejected` union / `OptionalFinalAssistant`）**全部消失**。（硬事实）

现在 terminal transaction 只写一条不可变的、lane 生命周期的记录：

```typescript
export type TerminalStatus = "completed" | "declined" | "aborted" | "failed";
export interface OperationResultRecord {
	operationId: string; kind: "run" | "compaction" | "navigation";
	status: TerminalStatus; error?: OperationError;
	fromTipId: string | null; tipId: string | null;   // 转录段 (fromTipId, tipId]
	startedAt: number; endedAt: number;
}
```

（`session/types.ts:105-118`，硬事实）

它是**处置 + 一个转录段指针**，从不列举中间工作（compaction、turn、tool），从不内嵌 entry（WP05 §7）。（解释）这个设计买来三件事：terminal planner 做**零次** outcome 读取；观察路径**不可能**因为 entry 缺失而 fault（旧设计里 hydration 里的 `getEntries` 抛错会升级成 harness fault，为一个只读便利值付出代价）；未来的协议帧就是一个 8 字段的平面对象。

另一条重要不变量（硬事实，WP05 §7 "terminal-control invariant"）：**在 durable `cancel_requested` 下执行的 terminal transaction 必须记 `aborted`**；等价地，任何非 aborted 的 terminal status 都蕴含当时控制状态是 running。这让"要不要续跑"这个判断可以**仅凭记录本身**做出。

唯一的非终态观察是 `SuspendedRun`（`agent-harness.ts:78`）：`{ operationId, status: "suspended", deferred: DeferredHandle }`，**只出现在便利返回值上，永不落盘**。

### 7. 恢复、abort、close

**恢复（硬事实）**：`createAgentHarness()`（`runtime/harness.ts:375-408`）在一条 keyless Session mutation 里，用 `restoreSession()`（`runtime/restore.ts:92`）把**所有完整的 lane** 一次性读出来，返回 `{ harness, open }`。`open` 是"有 durable 当前操作"的 lane 的清单（`OpenOperation = { lane, operationId, kind, startedAt, aborting? }`，`agent-harness.ts:211`），idle lane 和数据-only Branch 不在里面，`aborting: true` **只**从 durable 取消控制拷贝过来。**`create` 不驱动任何东西**——不启动 hook、provider、tool、timer、Drive 或应用回调。（硬事实）

`restoreLaneState()`（`runtime/restore.ts:131`）做的是严格校验而不是宽容解释：操作 meta/state 缺失 → `SessionInvariantError`；meta 的 `operationId` 与 key 不符、或 `meta.lane` 不是这个 lane、或 `stateMatchesIntent()`（`:26-45`）判定 intent 与 `at` 不匹配 → 全部 fault。"半个 lane"（只有 tip 没有 config/state）**也 fault**（`harness.test.ts:321`）。数据-only Branch（只有 tip）是合法的，可以被 `lane(name, {createAt})` 挂上 agent 状态而不移动 tip（`harness.test.ts:201`）。（硬事实）

崩溃后的孤儿恢复按 leaf 分派（硬事实，harness.md §4.5 表 + `drive/recovery.ts`）：assistant 生成停在 `effect_pending` → 读已提交的 frame 前缀、用 `reduceAssistantMessageFrames` 还原出一个带警告的合成 `error` 响应（**provider 流从不重新附着**）；工具停在 `effect_pending` → 只有存取两处声明都是 `replay: "safe"` 才删掉旧 checkpoint 并用同一 invocation memo/id 重跑，否则合成一个"已中断"的非终止错误结果；deferred 轮询停在 `effect_pending` → 有许可且 model 可解析就用新 id 替换未知轮询再取一次，没有许可就继续挂起。**恢复不是第二个端到端驱动。**

**abort 与 close 是两件事**（硬事实）：

- `requestAbort` 的顺序已如 §4 所述；同一个仍打开的取消操作重复请求返回 `newlyRequested: false`、空 drain、无重复事件；陈旧 id 返回 `OperationMismatch` 且**不能**取消别的操作。drained 的 steer/followUp 消息**只存在于返回值与事件里**，没有 durable 字段——commit 之后进程崩溃或响应丢失就**永久丢失那些 payload**，这是 upstream 明确承认的产品取舍（spec §4.6）。
- `close()`（`runtime/harness.ts:322`）**不写任何取消或终态**——它封住 harness 与 Lane 的 mutation admission、用 `HarnessClosed` 拒绝调用者观察、把已准入的 mutation 排干、然后关 Session，**不替换 Drive、不改 durable 操作状态**，所以重新打开看到的重启点和进程死亡完全一样（spec §4.7 "Close — a controlled crash"）。
- `fault`（`runtime/harness.ts:309`）是一条不归路：一次失败的已准入存储 commit 会封掉所有 Drive gate、用 `HarnessFault` 拒绝当前与未来的调用、要求进程重启——**绝不退化成某个可预期的 `Err` 结果**。（硬事实）

### 8. hooks / events / reducer

**hooks 从"任何注册即 throw"变成真注册表**（硬事实）：`hooks.ts:15` 的 `HookRegistry implements Hooks`，`on(name, handler, {id?})` 返回退订函数。`HookMap`（`agent-harness.ts:430`）有 11 个 hook：

```text
before_run · before_drive(新) · before_run_end · transform_context ·
before_request · before_payload · after_response ·
before_tool · after_tool · before_compaction · before_navigation
```

**`before_resume` 已删除**（旧版的持久化 resume 契约一并消失）。（硬事实）

聚合语义有明确分类（硬事实，`hooks.ts`）：

- `before_run`（`:128`）：handler 追加 messages，**后一个 handler 看到 prompt + 之前所有注入**，由 `starting → checkpoint` 那次 commit 一次性消费
- `before_drive`（`:409` `invokeAllFailClosed`）：**fail-closed**——handler 抛错就注册 `handler_error` 然后**重新抛**，整条 pass 被拒（但**不** fault harness、不写 durable 进度）
- `before_tool`（`:156`）：args 替换逐个 chained 且**重新校验**；第一个 `block` 是终态的、后续 handler 不再跑；handler 抛错也 fail-closed 成 block
- `before_tool` / `after_tool` 是**唯一带 telemetry span 的 hook**（`:376` `startHarnessSpan("pi.harness.hook", ...)`），span 上带 `pi.hook.outcome: completed | blocked | failed`
- `before_compaction` / `before_navigation`（`:337` `firstStructural`）：在第一个 `decline` 或提供的 result 处停止；`decline` 与 result 同时返回算 handler error（注册 `handler_error` 后被忽略）
- `before_run_end` 取**最后一个**定义的 followUp

**events**：`HarnessEventPayload`（`agent-harness.ts:255`）是一大族 discriminated union，operation / terminal / suspended-retry / transcript / tools-turns / replicated-state / metadata-faults 七组。`HarnessEvent` 在 lane 作用域的 payload 上加 `lane`，孤儿恢复/重放时可加 `recovery: true`。（硬事实）

**reducer 是远端消费者的唯一受支持 fold**（硬事实）：`runtime/reducer.ts:22` 的 `reduceLaneSnapshot(snapshot, event): LaneSnapshotReduction`。注意**这跟旧的 `harness/reducer.ts` 不是同一个东西、也不是移动**——旧的 667 行 `harness/reducer.ts`（durable record-log 重放与 `RecordLogCorruption`）**已整体删除**；新的是 232 行的**纯视图 fold**，从 `src/index.ts:77` 导出。（硬事实）

它的关键约定是 `navigation_end` **返回 `"rebase"`**（`:220-221`）：导航后移到的 tip 可能落在副本之外，reducer 无法自己算出来，所以消费者必须调 `WatchHandle.resnapshot(context)`（`agent-harness.ts:184`）重新抓一份快照——**不需要拆订阅再重订**。其他几个约定：in-run 的 `compaction_start`/`compaction_end` 是**段括号**，**不能**清掉 `operation`（fold 知道当前操作的 kind，所以事件里不需要 phase 字段）；`run_suspend` 让 `operation` 保持非 null 并挂上 `deferred`；只有 `run_end`、`navigation_end`、以及 compaction-kind 操作的 `compaction_end` 是操作终态（spec §5.4）。

## 在 Agent 能力面里的影响是什么

1. **"harness 跑不起来"这条判断彻底作废**（硬事实）。v0.84 的旧结论是"绝大多数操作抛 `HarnessNotImplemented`"——现在源码树里该符号零命中。`AgentHarness.create()` 真的做 restore，13 个 leaf 全部可驱动可对账，hooks 全部接线，runtime 自己的聚焦测试约 8.4k 行（`test/harness/runtime/` 14 个文件，其中 `drive-structural.test.ts` 1451 行、`drive-tools.test.ts` 763 行），并用 pi-ai 的 `fauxProvider` / `fauxAssistantMessage` 驱动整 turn。

2. **但产品集成路径没有变，也不该变**（硬事实 + 解释）。`AgentSession` / `createAgentSession()` 仍是 TUI/RPC/SDK 的入口，且 `sdk.ts`、`modes/rpc/rpc-types.ts`、`modes/rpc/rpc-mode.ts`、`modes/json-event.ts` 在 v0.84.4 → v0.85.1 之间**逐字节未变**。三条具体理由：（a）`AgentHarness` 在 coding-agent 里只被 `src/experimental/` 与 test fixture 引用；（b）`watchSession()` 仍是唯一 stub，抛 `SliceNotImplemented`（`runtime/harness.ts:305-307`）；（c）experimental 整条线**不在 npm 包和 standalone binary 里**（0006 主题 7），只能在 repo checkout 里跑。

3. **面向接口编程仍然是对的，但契约换了**（解释）。集成方应依赖 `AgentLane` / `AgentHarness` 这两个 **interface**（`agent-harness.ts:538` / `:586`），而不是 `class Harness`——后者不导出，只经 `AgentHarness.create` 暴露。而且**入口本身被当成成本契约守住**：`packages/agent` 的 exports map 把 `./harness/context` 单列成一个入口（在 `scripts/check-entry-graphs.mjs` 的 `BUDGETS` 表里它有 `maxFiles: 6` 且 `forbid` 掉 `harness/runtime/`、`harness/execution/`）。（硬事实）这从构建侧确认了 `runtime/` 不是公开面。

4. **错误处理范式继续是"失败是值"**（硬事实）。`Result<TValue, TError>`（`harness/types.ts:9`）+ `TaggedError`（`result.ts:18-88`）承载可预期失败，`matchError`（`:111`）按 `_tag` 穷尽匹配。v0.85.1 的错误集变成了：`Closed` / `LaneBusy` / `InvalidMessage` / `InvalidNavigation` / `InvalidLane` / `UnknownSkill` / `UnknownTemplate` / `UnknownTarget` / `NothingToCompact` / `NothingToResume` / `NoActiveOperation` / `OperationMismatch`；**新增** `OperationMismatch` / `InvalidNavigation` / `SliceNotImplemented`，**删除** `HarnessNotImplemented` / `MissingIdentities` / `LaneExists` / `UnknownQueueItem`。throw 留给 `HarnessFault` / `HarnessClosed`（`result.ts:90`/`:100`，非 TaggedError）这类基础设施错误。

5. **`suspended` 仍然是一等结局**（解释）：`prompt()` 在 run defer 时返回 `SuspendedRun` 而不是 record（`lane.ts:1186-1192`），`resume()` 会给 pass 一张 deferred-poll 许可。这为跨进程/跨重启的 agent 运行铺路（推测）——`AgentSession` 目前没有这个能力（硬事实）。

6. **一个操作可能产生两条记录**（硬事实）：`CompactionResult` / `NavigationResult` 的形状是 `{ compaction|navigation: OperationResultRecord; run?: OperationResultRecord | SuspendedRun }`（`agent-harness.ts:88-95`）——structural 操作落定后若还有排队的对话输入，会再跑一个**普通 run**，于是返回两条 record。
