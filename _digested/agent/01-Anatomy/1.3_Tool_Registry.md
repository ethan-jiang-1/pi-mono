## 现象是什么

pi-mono 的工具不是单一类型——它们跨三个包定义了三层结构：

1. **`Tool`**（`packages/ai`）：最底层，只有 `name`、`description`、`parameters`（TypeBox schema）和可选的 `constrainedSampling`（provider 侧 JSON schema/grammar 约束采样请求）。这是 LLM 看到的工具定义——纯粹的 JSON Schema 描述。（硬事实）
2. **`AgentTool`**（`packages/agent`）：中间层，扩展了 `Tool`，加上 `label`、`execute()`、`prepareArguments?`、`executionMode?`。这是 agent 循环实际调用的接口。（硬事实）
3. **`ToolDefinition`**（`packages/coding-agent`）：最外层，扩展了 AgentTool 的语义，加上 `promptSnippet`、`promptGuidelines`、`renderCall()`、`renderResult()`、`renderShell` 和 `ExtensionContext`。这是面向产品（UI 渲染 + 扩展注册）的完整工具定义。（硬事实）

另外 `packages/agent` 的 harness 层还有第四个形状 `AgentHarnessTool`（`agent/src/harness/types.ts`）：在 `AgentTool` 基础上换掉 `execute()`。v0.85.1 起是**六参**签名 `(toolCallId, params, onUpdate, toolContext, invocation, context)`——`onUpdate` 提到 `toolContext` 之前，新增 `invocation: AgentHarnessToolInvocation` 与尾参 `context: Context`，并**删掉了旧的 `signal?` 参数**（取消信号改从 `context.abortSignal` 取）。`agent/src/harness/tools/` 提供 read/bash/edit/write 四个 factory（详见 [4.7_Harness_Tools.md](../04-Harness/4.7_Harness_Tools.md)）。（硬事实；v0.85.1 重写签名描述）

如果你只看 `packages/agent`，工具就是一个 `execute()` 函数。但如果你看 `packages/coding-agent`，工具还携带了如何在 TUI 中渲染调用和结果、如何在 system prompt 中描述自己、如何与扩展系统交互的信息。（解释）

而且 pi-mono 只有 8 个内置工具：`read`、`bash`、`edit`、`write`、`grep`、`find`、`ls`、`powershell`。比 OpenCode 少得多——没有 web_search、web_fetch、notebook 等复杂工具。默认激活的是 coding 四件套：`read`、`bash`、`edit`、`write`。只读场景用 `grep`、`find`、`ls`；`powershell` 是 v0.84.3 新增的 Windows-only 工具（默认不激活）。（硬事实）

## 核心矛盾是什么

**矛盾一：LLM 只需要 JSON Schema，但产品需要 execute + render + prompt。** 如果只在 AgentTool 上堆字段（把所有 UI/prompt 相关的都塞进去），AgentTool 会变得非常臃肿，而且引入了对 UI 框架的依赖。pi-mono 的解决方式是保留两层——AgentTool 保持纯运行时职责，ToolDefinition 承载产品层附加信息。`wrapToolDefinition()` 和 `createToolDefinitionFromAgentTool()` 是两个方向的转换桥。（解释）

**矛盾二：工具执行的安全性需要分层控制，但内核不应该硬编码安全策略。** pi-ai 层只有 `validateToolArguments()`（参数校验），pi-agent 层有 `beforeToolCall` / `afterToolCall` 钩子（可 block 可修改），coding-agent 层通过扩展系统的 `tool_call` / `tool_result` 事件再加一层拦截。安全策略完全由上层注入，内核只提供"在哪拦截"的锚点。（解释）

**矛盾三：工具允许列表需要灵活，但要防止配置错误导致无工具可用。** `allowedToolNames` 是精确数组——传了 `["read", "bash"]` 就只有这两个。`noTools` 提供了一种"禁用模式"：`"all"` 禁用全部，`"builtin"` 只禁用内置四件套但保留扩展工具。当 `tools` 未提供且 `noTools` 未设置时，先取 settings 的 `defaultTools` 配置，没有配置才落到默认 `["read", "bash", "edit", "write"]`。`excludeTools` 是作用在以上结果之后的 denylist。（硬事实）

## 实现思想是什么

### 三层类型定义

**Layer 1: Tool（pi-ai）**
```typescript
// packages/ai/src/types.ts
interface Tool<TParameters extends TSchema = TSchema> {
  name: string;
  description: string;
  parameters: TParameters;  // TypeBox schema
  constrainedSampling?: false | ConstrainedSamplingConfig;  // provider 侧约束采样（json_schema strict / grammar）
}
```
只有 LLM function calling 需要的信息。（解释）

**Layer 2: AgentTool（pi-agent）**
```typescript
// packages/agent/src/types.ts
interface AgentTool<TParameters, TDetails> extends Tool<TParameters> {
  label: string;                                 // UI 显示名
  prepareArguments?: (args: unknown) => TParams;  // 参数前处理（兼容性 shim）
  execute: (toolCallId, params, signal?, onUpdate?) => Promise<AgentToolResult<TDetails>>;
  executionMode?: ToolExecutionMode;             // 按工具覆盖全局执行模式
}
```
AgentTool 是 agent-loop 实际调用的接口。`execute()` 接收一个 `onUpdate` 回调用于流式输出部分结果。`AgentToolResult<TDetails>` 包含 `content`（发给 LLM 的文本/图片）、`details`（结构化数据，用于 UI 渲染或日志）、可选的 `usage`（工具自身的 token 消耗）、可选的 `addedToolNames`（deferred tool loading 的加载点）和可选的 `terminate` 标记。（硬事实）

**Layer 3: ToolDefinition（coding-agent）**
```typescript
// packages/coding-agent/src/core/extensions/types.ts
interface ToolDefinition<TParams, TDetails, TState> {
  name: string; label: string; description: string; parameters: TParams;
  promptSnippet?: string;      // 在 system prompt 的 Available tools 节中展示的一行描述
  promptGuidelines?: string[]; // 追加到 system prompt Guidelines 节的指引
  renderShell?: "default" | "self";  // TUI 渲染模式
  constrainedSampling?: false | ConstrainedSamplingConfig;
  prepareArguments?: (args: unknown) => TParams;
  executionMode?: ToolExecutionMode;
  execute: (toolCallId, params, signal, onUpdate, ctx: ExtensionContext) => Promise<AgentToolResult<TDetails>>;
  renderCall?: (args, theme, context) => Component;     // 工具调用的 TUI 渲染
  renderResult?: (result, options, theme, context) => Component;  // 工具结果的 TUI 渲染
}
```
`ToolDefinition.execute()` 比 `AgentTool.execute()` 多了一个 `ctx: ExtensionContext` 参数——这让工具实现可以访问 UI、session、model 等上下文。`wrapToolDefinition()` 负责把这个额外的 ctx 参数适配掉，生成 `AgentTool.execute()` 签名。（解释）

### 转换桥

**AgentTool -> ToolDefinition（降级包装）：** `createToolDefinitionFromAgentTool()` 从 AgentTool 合成一个最小 ToolDefinition——只复制 name/label/description/parameters/constrainedSampling/prepareArguments/executionMode，execute 适配掉 ctx 参数，不提供 promptSnippet/renderCall/renderResult。（硬事实）

**ToolDefinition -> AgentTool（升级包装）：** `wrapToolDefinition()` 把 ToolDefinition 包成 AgentTool，核心是 `execute` 的适配（同时透传 constrainedSampling）：
```typescript
execute: (toolCallId, params, signal, onUpdate, ctx?) =>
  definition.execute(toolCallId, params, signal, onUpdate, ctx ?? (ctxFactory?.() as ExtensionContext))
```

### 第四种形状：`AgentHarnessTool.execute()`（v0.85.1 重写）

`packages/agent/src/harness/types.ts` 的 `AgentHarnessTool<TContext, TParameters, TDetails>`（行 108-122）本轮换了 `execute()` 签名。旧版是"五参、第 5 参是应用上下文 `context: TContext`、第 3 参为 `signal?`"；新版是六参：

```typescript
execute(
  toolCallId: string,
  params: Static<TParameters>,
  onUpdate: AgentHarnessToolUpdateCallback<TDetails>,  // 提到 toolContext 之前（旧版在 signal 之后）
  toolContext: TContext,                              // 旧版第 5 参（原写作 context）
  invocation: AgentHarnessToolInvocation,             // 新增
  context: Context,                                   // 新增：chord 的 Context，含 abortSignal
): Promise<AgentToolResult<TDetails>>;
```

三处语义变化（硬事实）：
- **旧的 `signal?: AbortSignal` 参数被删除**——取消信号改从尾参 `context.abortSignal` 取。
- 新增 `invocation: AgentHarnessToolInvocation`（行 96-105）：`{ invocationId, operationId, turnId, getMemo(name), setMemo(name, value) }`。这是**一次 tool call 的 durable replay 身份**——`invocationId` 等于该次调用预留的 result-entry id，`getMemo`/`setMemo` 读写 invocation 作用域的持久 memo，安全重放时身份不变。
- 新回调类型 `AgentHarnessToolUpdateCallback<TDetails>`（行 90-93）：`(partialResult, options?: AgentHarnessToolUpdateOptions) => void`，其中 `options.checkpoint === true` 表示"请求替换本次 invocation 的 durable recovery checkpoint"（行 84-87）。注意它是**同步全量快照**回调，与 `AgentTool.execute` 的 `AgentToolUpdateCallback` 不是同一个类型。

### 有界 shell 输出捕获：`ShellOutput*`（v0.85.1 新增）

同一文件（行 318-388）新增了一族"有界 shell 输出"类型——shell 输出不再无限累积，而是由调用方声明上限、越界后按保留端丢弃、并用增量回调交付：

| 类型 | 行号 | 角色 |
|------|------|------|
| `ShellOutputRetention` | 318 | `"head" \| "tail"`——越界后保留哪一端（`ShellOutputLimits.retain` 默认 `"tail"`） |
| `ShellOutputLimits` | 321-326 | `{ maxBytes, maxLines, retain? }` 源侧限制 |
| `ShellOutputCaptureOptions` | 329-334 | `{ limits, spill? }`；`spill` 把完整输出落到执行环境本地文件 |
| `ShellOutputTruncation` | 336 | `Omit<TruncationResult, "content">`——不带重复文本的截断元数据 |
| `ShellOutputMetadata` | 339-344 | `{ truncation, spillPath?, lastLineBytes? }` |
| `ShellOutputView` | 346-349 | `ShellOutputMetadata & { text }` 完整视图 |
| `ShellOutputUpdate` | 351-355 | 增量变更 union：`replace` / `append` / `slide`（丢弃 N 行）/ `metadata` |
| `ShellExecResult` | 358-361 | `ShellOutputMetadata & { exitCode }`（输出文本经 `ShellExecOptions.onUpdate` 交付） |
| `ShellExecOptions` | 363-377 | `{ cwd?, env?, inheritEnv?, timeout?, capture?, onUpdate? }`；`onUpdate(update, context)` |
| `Shell`（`exec` 返回类型变更） | 379-388 | `exec(command, options, context): Promise<Result<ShellExecResult, ExecutionError>>` |

即 `Shell.exec()` 现在返回 `Result<ShellExecResult, ExecutionError>`（旧版是裸结果），并把 `capture`（源侧有界捕获）+ `onUpdate`（`ShellOutputUpdate` 增量）作为输出交付通道。把增量折叠回视图的函数是 `applyShellOutputUpdate(view, update)`（`harness/utils/output-capture.ts`，由 `agent/src/index.ts:146` 导出）。

### 8 个内置工具

所有内置工具都在 `packages/coding-agent/src/core/tools/` 下，每个工具有一个 `createXxxTool()`（生成 AgentTool）和一个 `createXxxToolDefinition()`（生成 ToolDefinition）。工具创建函数接收 `cwd` 和可选的 tool-specific options。（硬事实）

| 工具 | 文件 | 类型 |
|---|---|---|
| `read` | `read.ts` | 文件读取 |
| `bash` | `bash.ts` | Shell 命令执行 |
| `edit` | `edit.ts` | 精确字符串替换编辑 |
| `write` | `write.ts` | 创建/覆盖文件 |
| `grep` | `grep.ts` | 正则搜索 |
| `find` | `find.ts` | 文件名搜索 |
| `ls` | `ls.ts` | 目录列表 |
| `powershell` | `powershell.ts` | PowerShell 命令执行（v0.84.3 新增，Windows-only，基于 bash 工具定义 + UTF-8 输出 shim） |

预置的工具集合（在 `tools/index.ts`，AgentTool 版和 ToolDefinition 版各一套）：
- `createCodingTools(cwd)` — `[read, bash, edit, write]`
- `createReadOnlyTools(cwd)` — `[read, grep, find, ls]`
- `createAllTools(cwd)` — 全部 8 个（返回 `Record<ToolName, Tool>`，按名字索引）
- `createCodingToolDefinitions(cwd)` / `createReadOnlyToolDefinitions(cwd)` / `createAllToolDefinitions(cwd)` — 对应的 ToolDefinition 版本；另有按名单个创建的 `createTool(name, cwd)` / `createToolDefinition(name, cwd)`

### 工具允许列表

在 `CreateAgentSessionOptions` 中：
- `tools?: string[]` — 精确指定哪些工具激活。传了就只激活这些。
- `noTools?: "all" | "builtin"` — 当 `tools` 未提供时的禁用模式。`"all"` = 全部禁用，`"builtin"` = 只禁用内置四件套（扩展/自定义工具保持可用）。
- `excludeTools?: string[]` — denylist，在 `tools`/默认集合确定后再剔除（两者同时给定时也生效）。
- 默认（`tools`/`noTools` 都未设置）— 取 settings 的 `defaultTools` 配置，未配置则激活 `["read", "bash", "edit", "write"]`。
- `customTools?: ToolDefinition[]` — 扩展/自定义工具总是被注册，但受 allowlist/denylist 影响。

### 执行模式

`ToolExecutionMode = "sequential" | "parallel"`：

- **全局配置**：`AgentLoopConfig.toolExecution`（默认 `"parallel"`）（硬事实）
- **按工具覆盖**：`AgentTool.executionMode` / `ToolDefinition.executionMode`（硬事实）
- **优先级**：如果助手的 tool_calls 中有一个工具的 executionMode 是 `"sequential"`，整批工具串行执行（硬事实）
- **并行模式行为**：preflight（参数验证 + beforeToolCall）串行，execute 并发，`tool_execution_end` 按完成顺序发出，但 tool-result message 按 assistant 消息中 tool_call 的顺序发出（硬事实）
- **批次提前终止**：`beforeToolCall` 返回 `{block, terminate}`、`afterToolCall`/工具结果带 `terminate: true` 时，只有当批内**所有**已 finalize 的结果都 terminate 才会停止本批后的继续循环（`shouldTerminateToolBatch()` 要求全真）（硬事实）
- **截断保护**：assistant 消息 `stopReason === "length"` 时，其中的 tool calls 可能参数被截断，loop 直接把整批标记为 error tool result（`failToolCallsFromTruncatedMessage()`），不执行（硬事实）

## 在 Agent 能力面里的影响是什么

1. **三层类型让关注点分离。** pi-ai 的工具定义可以独立于 agent 和 UI 使用（纯 LLM 调用场景）。pi-agent 的工具定义可以独立于 coding-agent 的 UI 使用（被其他产品嵌入时）。coding-agent 的 ToolDefinition 提供了完整的 TUI 集成能力但不强制——`createToolDefinitionFromAgentTool` 可以把外部 AgentTool 带进来。（解释）

2. **工具允许列表是安全边界。** 通过 `tools: ["read", "grep"]` 可以把 agent 限制为只读模式——不需要修改 system prompt 或工具实现。这是外部宿主控制 agent 能力范围的最直接手段。（解释）

3. **executionMode 影响并发安全。** 默认 `"parallel"` 意味着 `bash` 和 `write` 可能同时执行——如果两个工具操作同一文件，可能出现竞争。把文件操作工具设为 `"sequential"` 可以避免这个问题。`withFileMutationQueue()` 工具包装器提供了另一种解决方案：对文件修改操作排队。（解释）

4. **工具是可扩展的。** 扩展系统通过 `pi.registerTool()` 注册 ToolDefinition，宿主通过 `customTools` 选项注入 ToolDefinition。两者最终都通过 `wrapToolDefinition()` 转成 AgentTool 进入 agent 循环。（解释）

## 最小例子是什么

### 例子 1：注册一个自定义工具

```typescript
import { createAgentSession } from "@earendil-works/pi-coding-agent";
import { t } from "typebox";  // TypeBox schema builder

const { session } = await createAgentSession({
  model: myModel,
  tools: ["read", "bash", "my_counter"],  // 激活自定义工具 + 两个内置工具
  customTools: [{
    name: "my_counter",
    label: "Counter",
    description: "Get or increment a counter value",
    promptSnippet: "- my_counter: get or increment a persistent counter",
    parameters: t.Object({
      action: t.String({ description: "'get' or 'increment'" }),
    }),
    execute: async (toolCallId, params, signal, onUpdate, ctx) => {
      const value = params.action === "increment" ? count++ : count;
      return {
        content: [{ type: "text", text: `Counter is now ${value}` }],
        details: { value },
      };
    },
  }],
});

// 向 agent 发送 prompt
await session.prompt("Increment the counter and tell me the new value");
```

你会观察到的信号：
- Agent 调用 `my_counter` 工具时，参数被 TypeBox 校验（如果 action 不是 "get" 或 "increment" 会失败）
- LLM 能在 system prompt 的 Available tools 节中看到 `my_counter` 的描述（通过 promptSnippet）
- `tool_execution_start` / `tool_execution_end` 事件包含 toolName: "my_counter"

### 例子 2：串行执行控制

```typescript
// 这个工具标记为 sequential——如果 LLM 同时请求它和 bash，
// 整批工具会串行执行而不是并发
const sequentialTool = {
  name: "critical_write",
  label: "Critical Write",
  description: "Write to a file that must not race with other operations",
  parameters: t.Object({ path: t.String(), content: t.String() }),
  executionMode: "sequential" as const,  // 强制串行
  execute: async (toolCallId, params, signal, onUpdate, ctx) => {
    // 关键写入逻辑
  },
};
```

你会观察到的信号：
- 当 LLM 返回的 tool_calls 包含 `critical_write` 和 `bash` 时，两个工具按顺序执行（先处理 critical_write，再处理 bash）
- 如果两个工具都是默认 "parallel" 模式，它们会并发执行
