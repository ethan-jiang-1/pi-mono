# 2.5 声明式资源轴：不写代码的扩充

> 前四条轴（2.1-2.4）都是 **TypeScript 代码轴**——写扩展、注册、渲染、持久化。但 pi 官方的扩充面还有另一半：**声明式资源**（skills / prompt templates / themes / agent 定义）。它们不进扩展 loader、没有执行入口，却和代码扩展共享同一套发现、打包、分发机制。本篇讲这条"不写代码"的轴。

## 现象是什么

pi 的四种可分享资源里，只有 extension 是代码；其余三种都是**纯声明**：

| 资源 | 形态 | 入口 | 机制锚点 |
|------|------|------|----------|
| **Skill** | `SKILL.md` + frontmatter | 模型按需加载（description 匹配任务时）或 `/skill:name [args]` | docs/skills.md:5/:69/:76 |
| **Prompt template** | `.md` 片段 | 编辑器 `/name` 展开成完整 prompt | docs/prompt-templates.md:5 |
| **Theme** | `.json` | UI 配色 | docs/packages.md:165 |
| **Agent 定义**（subagent 生态） | `.md` frontmatter（如 pi-subagents 的 scout/worker/reviewer） | 委派工具按名调用 | 04-Ecosystem/2 |

发现位置高度一致：全局（`~/.pi/agent/`）、项目（`.pi/`，**需 project trust**）、包（`pi` manifest 条目或约定目录）、settings 数组、CLI flag——五层来源对四种资源全部同构（docs/skills.md:24、docs/prompt-templates.md:11-15）。

## 核心矛盾是什么

**代码扩展给出精确性，声明式资源给出扩散速度。**

- 写一个 extension：要会 TS、要懂接缝、要发 npm——门槛高，但行为精确可测。
- 写一个 skill：一个 Markdown 文件、一段 frontmatter、贴到哪里都行——**不会编程的人也能发布能力**。
- 代价在安全模型上：extension 的风险是"代码执行"（docs/packages.md:20），skill 的风险更隐蔽——"**skill 可以指挥模型执行任何操作，包括调用可执行文件**"（docs/skills.md:22）。声明式不等于无害，它把"代码"换成了"对模型的指令"。

## 扩充思路是什么

### 判断一：skills 是 pi 对开放标准的押注，不是私有格式（硬事实）

pi 实现的是 [Agent Skills 标准](https://agentskills.io/specification)（docs/skills.md:7），且**故意宽于标准**——允许 skill 名与父目录名不同，理由写在源码注释里：这条标准规则"对跨多个 agent harness 共享的 skill 目录不友好"（docs/skills.md:7）。方向与 chord 包（非 Pi 依赖）一致：**生态资产要可携带，不锁定在 pi 一家**。

### 判断二：skill 的加载是"目录广告 + 按需 read"，不是启动注入（硬事实）

模型可见的只有 name+description 广告（进 `<available_skills>`，见 harness/4.4）；正文 `SKILL.md` 在任务匹配时才用 read 工具加载——模型不总是自觉，所以保留 `/skill:name` 强制入口（docs/skills.md:69）。这个设计和 MCP adapter 的"代理工具省 context"（04-Ecosystem/2）是同一个经济学：**能力目录常驻，能力本体按需付费**。

### 判断三：发现规则对"人来维护"做了特化（硬事实）

根目录裸 `.md` 只在 `~/.pi/agent/skills/` 和 `.pi/skills/` 被当作独立 skill（要求合法 frontmatter + 非空 description）；`~/.agents/skills/` 则**忽略**根裸 `.md`、只认分组文件夹里的嵌套 skill——因为前者是 pi 用户手工放文件的地方，后者是跨 harness 共享目录（docs/skills.md:37-39）。同一机制对不同目录有不同礼貌。

### 判断四：资源轴与代码轴在包层合流（硬事实 + 解释）

一个 pi 包可以同时携带四类资源（`pi` manifest 的 `extensions`/`skills`/`prompts`/`themes` 数组，支持 glob 与 `!` 排除，docs/packages.md:118-133；约定目录 fallback :160-165）。pi-subagents 就是合流样本：TS 代码注册 `subagent` 工具，agent 行为却是 `.md` frontmatter 声明。**代码做机制，声明做内容**——这是生态包的标准形状。

## 影响是什么

- 扩充 pi 能力**不要求会编程**：生态的广度（5300+ 包里 skill 类占比可观，如 bigpowers 的 73 个 skill）主要靠这条轴。
- 声明式资源同样进 trust/审计模型：项目级 `.pi/prompts`、`.pi/skills` 都在 project trust 闸门后面（docs/prompt-templates.md:12）。
- 对扩展作者的组合技：像 pi-mcp-adapter 那样"代码注册工具 + 捆绑 manual-only skill 教模型用"（见 04-Ecosystem/2）。

## 最小例证是什么

一个 skill 的全部：

```markdown
---
description: Review staged git changes
---
Review the staged changes (`git diff --cached`). Focus on correctness.
```

放进 `~/.pi/agent/skills/review.md`——没有构建、没有 npm、没有代码执行入口，但模型从此多了一项可被发现、可被 `/skill:review` 强制触发的能力。（硬事实，机制见 docs/skills.md:37）
