## 现象是什么

pi-mono 的 bash 工具让 LLM 可以执行 shell 命令（硬事实）。从 LLM 的视角看，它跟其他工具一样：一个 `command` 参数加可选的 `timeout`。但从实现视角看，bash 是 pi-mono 中最复杂的工具——它涉及进程管理、流输出、取消、输出截断、权限控制、渲染优化（解释）。

用户在 TUI 中看到的是：命令执行时输出**增量出现在工具卡片中**（100ms throttle），不是等命令结束后一次性刷出来。如果输出太长，会被截断并把全量写入 temp 文件。如果按了 interrupt，进程树会被清理。

## 核心矛盾是什么

Bash 工具的核心矛盾来自**长生命周期进程 vs 短生命周期事件循环**（解释）：

1. `execute()` 是 async 函数，但 bash 命令可能运行几分钟甚至无限
2. 输出在命令执行过程中持续产生，UI 需要增量渲染
3. 取消（abort）需要杀死整个进程树，不能留下孤儿进程
4. 输出可能非常大（GB 级），不能全放在内存中的字符串
5. 超时（timeout）需要可靠的进程终止

## 实现思想是什么

### 两套实现：harness 线与产品线

v0.84.2 有两条平行的 bash 实现，共享同一套截断常量（2000 行 / 50KB，两边的 `truncate.ts` 各自定义）（硬事实）：

**harness 线（`packages/agent/src/harness/`）—— 纯 `ExecutionEnv` 抽象，无 Node 依赖（硬事实）：**

- `createBashTool(options?)`（`tools/bash.ts:51`）：工具 factory，只接受 `commandPrefix` 和 `prepare`（`BashToolOptions`，L36）——没有可插拔 operations，可插拔性来自 `ExecutionEnv` 本身
- `executeShellWithCapture(env, command, options)`（`utils/shell-output.ts:51`）：进程输出捕获层，最终调 `env.exec()`（`Shell` 接口，`types.ts:304`）
- 错误路径全部返回 `Result` / `ExecutionError`（`code: "aborted" | "timeout" | ...`），工具层用 `getOrThrow()` 解包

**产品线（`packages/coding-agent/src/core/`）—— TUI 耦合，`BashOperations` 可插拔（硬事实）：**

- `createBashToolDefinition(cwd, options?)`（`tools/bash.ts:529`）/ `createBashTool(cwd, options?)`（L536）：工具定义（含渲染回调）+ AgentTool 包装
- `createLocalBashOperations()`（L158）：默认本地执行后端（Node `spawn`）
- `bash-executor.ts` 的 `executeBashWithOperations()`（L50）：给 **AgentSession 用户主动执行 bash**（TUI 的 `!command` / RPC bash，`agent-session.ts:2900`）用的执行器。注意 v0.84.2 中 **bash 工具本身不再经过它**——工具的 `execute()` 直接调 `ops.exec()` 并用自己的 `OutputAccumulator` 管理输出

### BashOperations 接口（产品线）

bash 工具的执行不是硬编码的。通过 `BashOperations` 接口（`coding-agent/src/core/tools/bash.ts:63`），可以替换底层执行实现（硬事实）：

```typescript
interface BashOperations {
  exec(command, cwd, options: {
    onData: (data: Buffer) => void;  // 流输出回调
    signal?: AbortSignal;            // 取消信号
    timeout?: number;                // 超时秒数
    env?: NodeJS.ProcessEnv;         // 环境变量
  }): Promise<{ exitCode: number | null }>;
}
```

默认实现 `createLocalBashOperations(options?: { shellPath? })` 使用 Node.js 的 `spawn()`。`BashToolOptions`（L192）还提供 `commandPrefix`（前缀注入）、`shellPath`、`exposeSessionEnvironment`（默认 true，暴露 `PI_SESSION_ID`/`PI_MODEL` 等 env）、`spawnHook`。

### 进程生成和信号取消（createLocalBashOperations）

1. **Shell 选择**：`getShellConfig()`（`utils/shell.ts:67`）确定 shell 路径和参数；Windows 上支持通过 stdin 传命令（`commandTransport === "stdin"`，L102-113）（硬事实）

2. **Detached 进程**：`spawn()` 使用 `detached: process.platform !== "win32"`（L105）——子进程在自己的进程组中运行，可以整组 kill（解释）；pid 同时被 `trackDetachedChildPids` 登记，宿主退出时可统一清理（硬事实）

3. **信号取消**（`killProcessTree`，`utils/shell.ts:200`）：
   - Unix：直接向进程组发 **SIGKILL**（`process.kill(-pid, "SIGKILL")`），失败则回落杀单个 pid——**没有 SIGTERM→SIGKILL 升级过程**（硬事实）
   - Windows：`taskkill /F /T /PID`（硬事实）
   - 触发源：`AbortSignal` abort（L117-119、L133-136）或 timeout 到期（L123-128）都走 `killProcessTree`（硬事实）
   - `waitForChildProcess()`（`utils/child-process.ts:49`）等待进程退出，并处理 detached 子进程持有继承 stdio 句柄导致的不退出问题（解释）

4. **stdout/stderr 合并**：`child.stdout` 和 `child.stderr` 都接到同一个 `onData`（L130-131）（硬事实）

### 输出捕获与截断

harness 线的 `executeShellWithCapture()`（`utils/shell-output.ts:51`）（硬事实）：

1. **滚动缓冲**：内存里只保留尾部 `DEFAULT_MAX_BYTES * 2`（100KB），用 `trimToLastUtf8Bytes()` 按 UTF-8 边界裁剪；同时维护 `completedLines`/`hasOpenLine` 计数，供截断信息使用（硬事实）
2. **清洗**：每个 chunk 先 `sanitizeBinaryOutput()`（剥掉除 `\t\n\r` 外的控制字符，L30）再删 `\r`。注意 harness 线**不剥 ANSI 颜色码**（硬事实）；产品线会先 `stripAnsi()` 再 sanitize（`bash-executor.ts:82`）（硬事实）
3. **Temp 文件**：总输出超过 50KB 或 2000 行时，通过 `env.createTempFile({prefix: "bash-", suffix: ".log"})` + `env.appendFile()` 把全量写盘——全部走 `ExecutionEnv` 抽象，写入用 promise `writeChain` 串行化（L70-91）。**先前的 chunk 也会补写进 temp 文件**，所以全量完整（硬事实）
4. **截断**：`truncateTail()` 保留最后 `DEFAULT_MAX_LINES`（**2000 行**）或 `DEFAULT_MAX_BYTES`（50KB），先到者为准（硬事实）；截断信息（`truncatedBy`/`totalLines`/`outputBytes`/`lastLinePartial`）随 `TruncationResult` 返回（硬事实）
5. **取消**：`env.exec` 返回 `aborted` 或 signal 已 aborted 时，返回已有输出（不丢失），`exitCode: undefined`、`cancelled: true`；timeout 则以 `ExecutionError("timeout")` 随输出一起返回（`returnExecutionErrors: true` 模式，L173-181）（硬事实）

产品线的 `OutputAccumulator`（`tools/output-accumulator.ts:35`）是同一思想的 Buffer 版：`append(Buffer)` / `finish()` / `snapshot({ persistIfTruncated })` / `closeTempFile()`，同样滚动缓冲 + 超限落盘 + 行/字节统计（硬事实）。**100ms throttle（`BASH_UPDATE_THROTTLE_MS`）不在 accumulator 里，而在工具的 `execute()` 中**——`scheduleOutputUpdate()` 把 UI 刷新节流到 100ms 一次（`tools/bash.ts:374-387`；harness 版同款逻辑在 `agent/harness/tools/bash.ts:92-105`）（硬事实）。

### BashSpawnHook 与 PI_* 环境（产品线）

命令执行前，`resolveSpawnContext()`（`coding-agent/src/core/tools/bash.ts:164`）构建 `{ command, cwd, env }`（硬事实）：

- 先从 shell env 中删掉 `PI_SESSION_ID`/`PI_SESSION_FILE`/`PI_PROVIDER`/`PI_MODEL`/`PI_REASONING_LEVEL`（硬事实）
- `exposeSessionEnvironment`（默认 true）且有 extension context 时再注入当前的这些值——这就是 LLM 能"inspect PI_* environment variables"的机制（解释），对应 bash 工具的 system prompt guideline（`bashToolSystemPromptContribution`，L46-49）（硬事实）
- `spawnHook?: BashSpawnContext => BashSpawnContext`（L162）最后可改写命令/cwd/env，例如给所有命令加 `set -euo pipefail`（解释）

### 工具定义中的渲染（产品线）

Bash 工具实现了两个渲染回调（硬事实）：

- `renderCall(args, _theme, context)`（L464）：显示 `$ command` 的样子（硬事实）
- `renderResult(result, options, _theme, context)`（L474）：显示输出内容（折叠/展开）、截断警告、完整输出路径、耗时（硬事实）；未展开状态用 `BASH_PREVIEW_LINES = 5` 行预览（`truncateToVisualLines`）；耗时由一个 1s 的 `setInterval` 驱动重绘（L477）（硬事实）

### 错误信息拼装

两条线共享同一套"输出 + 状态行"的报错格式（harness 版 `agent/harness/tools/bash.ts:144-154`）（硬事实）：

- 取消 → `Command aborted`
- 超时 → `Command timed out after N seconds`
- 非零退出码 → `Command exited with code N`
- 截断时输出尾附 `[Showing lines X-Y of Z. Full output: <temp path>]`

这些都以 Error 形式抛出（agent tool 的 isError 路径），同时保留已捕获的输出文本（硬事实）。

### Permission 集成

权限拦截在 AgentSession 层：`_installAgentToolHooks()` 把 `ExtensionRunner.emitToolCall()` 挂到 `agent.beforeToolCall`（`agent-session.ts:479`）（硬事实），extension handler 可以返回 `{ block: true, reason }` 阻止命令执行（v0.84 起还支持 `terminate`，见 4.4）。handler 抛异常会 fail-close 地阻断执行（解释）。

## 在 Agent 能力面里的影响是什么

1. **Bash 是 LLM 访问执行环境的主要通道**（硬事实）。read/edit/write 之外的文件搜索、构建、测试都靠它。

2. **流输出是良好 UX 的基础**（解释）。100ms throttle 的增量更新让用户看到命令正在运行，而不是卡住等待。

3. **可插拔性有两层**（硬事实）。harness 线换 `ExecutionEnv`（整个文件系统+shell 一起换，可指向 Docker/远程）；产品线换 `BashOperations`（只换命令执行，TUI/截断逻辑保留）。

4. **Cancellation 是安全的**（解释）。进程组 SIGKILL + detached pid 追踪确保没有孤儿进程残留。

5. **有界内存**（解释）。滚动缓冲 + temp 文件意味着 GB 级输出不会撑爆进程。

## 最小例子是什么

```typescript
// harness 线：纯 ExecutionEnv，不需要 Node —— 从 pi-agent-core 主入口导入
import { createBashTool } from "@earendil-works/pi-agent-core";

const bashTool = createBashTool({
  commandPrefix: "set -euo pipefail", // 每条命令前注入
});

// 直接执行（也可作为 AgentHarnessOptions.tools 交给 harness —— 但 v0.84.2 的
// AgentHarness 骨架还不能跑 turn，见 4.1；产品集成用 AgentSession）
const result = await bashTool.execute(
  "call_1",
  { command: "ls -la", timeout: 30 },  // timeout 可选，单位秒
  undefined,                            // signal
  undefined,                            // onUpdate
  { env: myExecutionEnv },              // ExecutionToolContext
);
// 观察到的信号：result.content[0].text 是输出文本；
// 跑 `seq 1 100000` 时输出尾会出现 "[Showing lines 99801-100000 of 100000. Full output: /tmp/bash-xxx.log]"

// 产品线：本地 cwd + 自定义 BashOperations（例如远程执行）
import { createBashTool as createProductBashTool } from "@earendil-works/pi-coding-agent";

const remoteBashTool = createProductBashTool("/remote/project", {
  operations: {
    exec: async (command, cwd, { onData, signal }) => {
      const ssh = spawn("ssh", ["remote-host", `cd ${cwd} && ${command}`]);
      ssh.stdout.on("data", onData);
      ssh.stderr.on("data", onData);
      signal?.addEventListener("abort", () => ssh.kill());
      return new Promise((resolve) => ssh.on("close", (code) => resolve({ exitCode: code })));
    },
  },
});

// 权限拦截（产品线）：在 extension 里注册，而不是在 harness 上（harness 的 hooks.on 目前会 throw）
// my-extension.ts:
// api.on("tool_call", (event) => {
//   if (event.toolName === "bash" && event.input.command === "sleep 999") {
//     return { block: true, reason: "Suspiciously long sleep" };
//   }
// });
```

关键要点：**bash 工具的复杂度不在"跑一条命令"，而在有界内存地捕获无限输出、可取消地管理进程树、以及在两条实现线（ExecutionEnv / BashOperations）上保持同一套截断与错误语义。**（解释）
