## 三个必须先建立的判断

### 1. durable 的 ToolPark 不是"又一个任务状态"，而是把"等待"变成一等公民

因果链（读 durable changelog 顺序即可，但理解要按这条线）：

- **工具可以 park**：`execute()` 返回 `{ sleep: { checkpoint?, until?, signals? } }` 或 `{ wait: { checkpoint?, on, policy } }`，被唤醒后带 `api.wake`/`api.checkpoint` 重跑。写法在 v1.6.0 还是嵌套形式（`{ sleep: {...} }`），**v1.6.1 立即改成 tagged flat 形式**（0015 记录）——引用示例时用 1.6.1 形式。
- **信号**：`defineSignal({ name, version, schema, migrate? })` 定义类型化 JSON 值；`harness.signal(taskId, token, key, value, context)` 或 `tx.signal()` 从外部投递给活任务。睡眠可只等信号（`until` 变可选，sleeping 状态的 `until` 可能不存在——Breaking）；wait 可 `policy: "any"`（`on` 里任一任务结束即醒）。
- **组合件**：`executeTool(..., { wait: false })` 返回 `{ taskId, result(context) }` 让工具 park 在嵌套调用上；`api.createTask()` 带 `key` 复用；`SubmissionDraft.notify: { taskId, key }` 在提交结算的 commit 里投递内建 `SubmissionSettled` 信号（subagent 工具 park 等待的基础件）；`beforeTool` 可返回 `{ sleep }` 把调用在运行前 park 住（审批 gate 的实现位），每次唤醒**整个 `call` 阶段重跑**。
- **hooks 升级**：`afterTools`/`onYield` 可返回 `{ tasks }` 派生为 generation 子任务（`afterTools` 任务可 `{ terminate: true }` 结束整个 run）；`RunEndTask`/`runEndTask` 因此改名 `HookTask`/`hookTask`（Breaking，迁移就是改 import）。
- **代价与边界**：`pi.tool` schema v4、`pi.generation` v3——**数据库不可被旧 Harness 打开**（会 `task_too_old` 阻塞这些任务、把无 `until` 的睡眠当错误）；`durationMs` 语义变为"从工具任务第一次 run 到结果"（跨 park 的总时长，不是单次执行时长）。示例 38–46（signals、问一个人、等 webhook 的工具、轮询工具、并行嵌套调用、等待的 subagent、审批 gate、yield 时 review、afterTools 任务）随 release 入库。

对 `_digested` 的含义：`harness`/`orchestration` 专题里"工具调用 = 一次 execute"的模型需要重写为"execute → park → wake → 再 execute"的状态机；"长任务 = sleep 状态的任务"要扩成"sleeping（可无 until）+ parked tool + gate"。

### 2. chord slice 14 的准入（admission）把"谁能用什么"从代码习惯升为协议

- contract 可声明 `admission: schema`——factory 收到的关于 caller 的值；`host.serve(Type, fn, { admit })` 的 `admit(params, principal, self)` 拒绝时请求失败 `forbidden`；`host.route(Kind, { authorize, resolve, admit })` 与 `createWorkers(host, Kind, { admit })` 在**解析/转发之前**做每 principal+address 一次的决定——**被拒的 caller 不会启动 worker**。
- `telemetryIngestFacet` 现在要求 `admit(principal)`（Breaking）：未 admit 的 principal 的 hold 直接 `forbidden`；app kit 对每个已登录页面 admit。
- `createWorkers` 现在要求 `store`（Breaking）：worker 退出前排队 commit 的提交落定才发布退出；app kit 自传。
- `HostError` `query_failed` 携带 `query`（named query 的 label / `self.query` 的表名）替代 `table`（Breaking）。
- 数据面：named queries 声明在 `local` contract（`queries(Item, { name: argsSchema })`）、owner 用 `self.queries(table, { map, reads?, partnerReads? }, builders)` 实现；`self.list(name, [[namedQuery, args]], { first })` 返回 `{ value, more }`——固定书签之间分页、行移动不产生空洞/重复；column sets（`defineColumns` + `exists(Set, match, ...)`/`query(Table).join(Set, match)`）让另一插件的查询可测/可 join 本表的列；live query 重跑按索引判断（commit 的写不可能影响该 read 就跳过）；telemetry 计数 `chord.query.probes/skips/rows`。
- 杂项：worker base 压缩（裸 worker 每个约省 0.4 MiB 源文本，p3 测量）；`links.opened(request, principal, close)` 第三参 `close`（吊销凭证时掐断链接）；`memberNames(contract, variant)`、`Method`/`LiteralsSchema`/`HostKeyed` 类型导出（给生成声明文件的包用）；`useVariant`/`TuiScope.variant`；`WorkerState.incarnation`；`appInfoFacet`/`workerInfoFacet` 导出。

### 3. p3 的工程结构已经"像模像样"——研究 pi 未来架构应以 p3 为样本

`apps/p3/docs/README.md` 的结构：五篇强制顺序指南（process/chord-practices/testing/performance/names）+ Linear 一包一 issue + slices brief + 两个 walkthrough（slice 1 base-and-sessions、slice 26 release/`p3` 命令）。代码分层：`plugins/<name>/`（内置插件，`sessions` 是 model plugin）、`src/api/v1/`（插件 import 的 `@earendil-works/p3/v1` 三出口）、`src/`（bin/server/worker/supervisor + 数据目录）、`test/`（自带 harness 与测试插件根）、`bench/`（每 slice/package 一个 benchmark）。**p3 在 chord 上的分层（host/objects/admission/queries/lists）就是 chord v2 的"reference application"**——`architecture-next` 若要写"chord v2 如何被真实使用"，样本是 p3，不是 p2（p2 被明确标注为灵感而非来源）。
