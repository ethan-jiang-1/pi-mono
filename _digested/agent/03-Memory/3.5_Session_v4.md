# 3.5 Session v4: lane-based 会话存储

> **基线 v0.84.2**（2026-08-17，本仓库工作树实测）。本文取代 [3.4 Session Tree](./3.4_Session_Tree.md) 中关于 agent 包 session 模型的描述——旧模型（`SessionTreeEntry` + legacy JSONL/in-memory repo）在 v0.84.0 被**整体删除**。（硬事实）

## 现象是什么

v0.84.0 把 agent 包的 session 存储换成了一个显式建模"执行历史"的系统：一个 session 不再只是"一棵 entry 树"，而是**三种 durable 数据 + 一个全局序列号**：（解释）

1. **Entry**（7 种）——不可变的对话树节点：`message`、`model_change`、`thinking_level_change`、`active_tools_change`、`compaction`、`branch_summary`、`custom`
2. **LaneRecord**（9 种）——lane 归属的操作流水：`operation_started`、`abort_requested`、`operation_finished`、`step_attempt`、`tool_started`、`queue_enqueued`、`queue_cancelled`、`write_deferred`、`usage`
3. **Facts**——session 级、latest-wins 的名字/标签（set 语义，不是 append）

三类写入共享**同一个严格连续的单调 seq**（`state.ts:104` 校验 `seq !== this.sequence + 1` 时报 "has non-consecutive seq"，不允许 gap）。（硬事实）**Lane** 是指向 entry 树某个 leaf 的具名游标，每个 session 必有 `main`；每个 lane 同时至多一个 open operation。（硬事实）

这个设计的核心矛盾是**崩溃可恢复性 vs 写入简单性**：（解释）所有写路径都是单行 append（快、简单、天然日志化），恢复靠重放（慢、但完整）；（解释）只有 torn-tail 修复和 fork 两处例外走"临时文件 + rename"的原子发布。（硬事实）

## 与周边系统的关系（避免误读）

- **coding-agent 没有接入**。`packages/coding-agent/src/core/session-manager.ts` 仍是自己的 JSONL 持久化（`SessionManager`），TUI/RPC/SDK 路线的 session 恢复走的还是它。session v4 目前是 agent 包内 **harness v2 演进的地基**，不是运行时事实。（硬事实）
- **`AgentHarness` 是骨架**。v0.84.2 的 `AgentHarness` 去掉了 v0.83 的全部四个泛型参数，改为非泛型类 `implements AgentLane`（`agent-harness.ts:305`）；（硬事实）`create()` 只要发现已有 record 就抛 `HarnessNotImplemented("create.restore")`（`agent-harness.ts:350`），绝大多数 lane 操作返回 unavailable。（硬事实）真正在跑的还是 `Agent` + `AgentLoop`（02-Runtime 各篇）。（硬事实）
- **官方 spec 描述的是另一个未来**。[`packages/agent/docs/harness.md`](../../../packages/agent/docs/harness.md) 讲的是 registers-based 存储 + SQLite 第三后端 + JSONL array-line 事务，并在 :496 明说当前源码的 format-4 "unfinished and is replaced in place"。（硬事实）**读 API 以 `src/harness/session/` 代码为准，spec 只当目标态设计书。**（解释）

## 三大接口的分工

| 接口 | 位置 | 职责 |
|------|------|------|
| `SessionStorage<TMetadata>` | `session/types.ts:290` | 后端契约：lanes 管理、`appendEntry(entry, lane)` / `appendRecord(record)`、全部查询、facts、`getLog()` |
| `SessionTree` | `session/types.ts:328` | tree-scoped 只读视图 + facts + `appendMessage`/`appendCustomEntry`（不含 record） |
| `SessionRepo` | `session/types.ts:361` | 仓库级生命周期：`create` / `open` / `list` / `delete` / `fork` |

`Session`（`session/session.ts:102`）是门面类，自身就是 `main` lane 的视图；`session.view(lane)` 返回绑定其他 lane 的 `SessionTree` 投影（`session.ts:115-132`）——branch 查询的 `start` 缺省解析为该 lane 的当前 leaf。

调用方写入时给 **`ProvisionedEntry`**（只带 id + payload），`parentId`/`seq`/`timestamp` 三项由 storage 补齐（`session/types.ts:76`）——**append 必须链到 lane 当前 leaf**，否则报 "does not chain to the lane leaf"（`state.ts:109-121`）。（硬事实）这就是树的 append-only 纪律的 enforcement 点。（解释）

## lane 与 operation：恢复语义

`operation_started` / `operation_finished` record 对（intent 分 `run` / `compaction` / `navigation` 三种）定义了一个 lane 上的工作单元。恢复规则（`session/types.ts:311-317` 的 doc comment）：

- `findOpenOperations(lane, { limit: 2 })` 返回 **0 条** → lane 空闲（硬事实）
- **1 条** → suspended（有 operation_started 无 operation_finished）——恢复流程的输入（解释）
- **2 条** → corruption（同一 lane 不允许开第二个 operation，storage 层硬拒，`jsonl/storage.ts:175-181`）（硬事实）

这套 record 流水让"agent 崩在半路"从不可判定变成可查询：（解释）重放 entries + records 即可重建到崩溃前的一致状态。（解释）`usage` record（6 种 cause）顺带把 token 消耗累积进 session stats。（硬事实）

## JSONL 后端：append-only + 两处原子发布

[`session/jsonl/`](../../../packages/agent/src/harness/session/jsonl/) 的写路径：

- **常规写**：每个 mutation 一行 `fs.appendFile`，行格式是带 `kind: "entry" | "record" | "lane" | "fact"` 的单 JSON 对象（`jsonl/codec.ts:203`）；（硬事实）所有写经 tail-promise 链**串行化**（`jsonl/storage.ts:259` 的 `this.tail`）（硬事实）
- **先 append 后 apply**：durable 先行，内存状态随后（`jsonl/storage.ts:171` 的 `appendRecord` 链）——保证崩溃不会导致已生效的脏状态，只有 torn tail 曾丢失最后一行。（解释）
- **torn-tail 修复**：load 时逐行解析；只有"最后一行 + syntax 级错误"判为 torn tail（`jsonl/storage.ts:84`），丢弃该行并把有效前缀**原子重写**（`publishFileAtomically`：写 `.tmp` + `renameFile`，`jsonl/storage.ts:38-41, 88-91`）；（硬事实）内部行损坏直接抛 corruption（硬事实）
- **fork**：临时文件上写 header + 逐条 fork mutation，然后原子 rename 发布（`jsonl/storage.ts:110-120`）（硬事实）——这就是 v0.84.0 给 `FileSystem` 加**必需的 `renameFile()`** 的原因（同文件系统替换语义）（解释）

fork 语义（repo 级，`state.ts:260-299`）：（硬事实）branch scope 的 fork 目标**必须是 message entry**；（硬事实）`scope: "tree"` 复制全部 entries + 所有 lane 指针；（硬事实）facts 里 name 总是复制；（硬事实）**records 不复制**（操作流水属于源 session）；（硬事实）目标端 seq 从 1 重编。（硬事实）

## context 投影：branch → provider 消息序列

`session/context.ts` 是无状态纯函数层：（解释）沿 lane leaf → root 的路径推导 `{ messages, thinkingLevel, model, activeToolNames }`（last-wins，assistant message 本身也会更新 model）。（解释）两个关键规则：

- **截到最新 compaction**：路径上最新的 `compaction` entry 之前的条目一律不进 context（`defaultContextEntryTransform`，`context.ts:45`，经 `buildContextEntries` :59 调用）（硬事实）
- **丢弃项**：`stopReason === "deferred"` 的 assistant message 被丢弃；（硬事实）`custom` entry 只有注册了 `entryProjectors[customType]` 才可能进 context，否则永不进入（硬事实）
