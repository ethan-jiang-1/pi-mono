# 2.5 Session Service: 会话的树形状态模型

> **⚠️ v0.83.0**：`session-manager.ts`(18 commits, +682 lines)。`buildSessionContext` 分解为 `buildSessionPath`+`buildContextEntries`+`sessionEntryToContextMessages`；`firstKeptEntryId` 变 optional；文件 I/O 改为 chunked read；新增 `assertValidSessionId`。行号全部失效。

## 现象是什么

pi-mono 的会话不是一个简单的消息列表，而是一个 append-only 的树形结构。用户可以随时从历史中的任意一点"分叉"出一个新的对话分支，在不同的分支间导航，也可以在分支之间跳转时自动生成分支摘要。所有这些能力都建立在一个统一的 Session tree 模型之上。

**源码位置：**
- `/packages/agent/src/harness/session/session.ts`（Session 类与 `buildSessionContext()`）
- `/packages/agent/src/harness/types.ts`（SessionTreeEntry、SessionStorage 接口）
- `/packages/coding-agent/src/core/session-manager.ts`（JSONL 存储实现、迁移逻辑）

## 核心矛盾是什么

一个可导航、可分叉的对话系统必须解决三个矛盾：

1. **追加 vs 修改：** 对话历史一旦产生就不应被修改（append-only），但用户需要"回到之前的状态"的能力。不能靠删除消息来实现导航，必须在旧分支上追加新节点。

2. **存储 vs 重建：** 树形结构在磁盘上需要高效的序列化格式（JSONL），但在内存中需要支持从任意节点到 root 的路径遍历以构建 LLM 上下文。

3. **状态追踪 vs 表达力：** 对话中的状态变化（模型切换、thinking level 变更、compaction 事件）需要像消息一样被记录在树中，但它们不是 LLM 可消费的消息，需要在上下文重建时特殊处理。

## 实现思想是什么

### 核心数据结构

Session tree 由 `SessionTreeEntry` 的 discriminated union 组成，每个 entry 都有 `id`、`parentId`、`timestamp`：

```typescript
type SessionTreeEntry =
  | MessageEntry          // type: "message" — 用户/助理/工具结果消息
  | ThinkingLevelChangeEntry  // type: "thinking_level_change" — 推理等级切换
  | ModelChangeEntry      // type: "model_change" — 模型切换
  | CompactionEntry       // type: "compaction" — 上下文压缩点
  | BranchSummaryEntry    // type: "branch_summary" — 分支摘要
  | CustomEntry           // type: "custom" — 扩展自定义数据（不进入 LLM 上下文）
  | CustomMessageEntry    // type: "custom_message" — 扩展自定义消息（进入 LLM 上下文）
  | LabelEntry            // type: "label" — 用户标签/书签
  | SessionInfoEntry      // type: "session_info" — 会话元数据（如名称）
  | LeafEntry             // type: "leaf" — 当前活动指针
```

每个 `MessageEntry` 包含一个 `AgentMessage`（pi-mono 的超集消息类型，支持 `bashExecution`、`branchSummary`、`compactionSummary`、`custom` 等额外 role）。

### Session 类

`Session<TMetadata>` 包装一个 `SessionStorage<TMetadata>` 后端，提供面向业务的 API：

| 方法 | 作用 |
|------|------|
| `getBranch(fromId?)` | 从给定节点（默认 leaf）走到 root，返回路径上的所有 entry |
| `buildContext()` | 调用 `getBranch()` + `buildSessionContext()` 重建 LLM 可消费的消息列表 |
| `appendMessage(msg)` | 在 leaf 下追加一条消息节点 |
| `appendModelChange(provider, modelId)` | 追加模型切换节点 |
| `appendThinkingLevelChange(level)` | 追加推理等级切换节点 |
| `appendCompaction(summary, firstKeptEntryId, tokensBefore)` | 追加压缩节点 |
| `moveTo(entryId, summary?)` | 导航到任意历史节点（设置新的 leaf），可选生成分支摘要 |
| `appendLabel(targetId, label)` | 给某节点添加标签 |
| `appendCustomEntry(customType, data)` | 扩展自定义数据（不进入 LLM 上下文） |
| `appendCustomMessageEntry(customType, content, display)` | 扩展自定义消息（进入 LLM 上下文） |

### buildSessionContext()：从树到线性上下文的转换

这是 Session 模型最核心的算法。给定从 leaf 到 root 的路径，它需要重建出 LLM 可以消费的 `{messages, thinkingLevel, model}` 三元组：

1. **沿路径扫描：** 从 root 到 leaf，提取最后出现的 `thinkingLevel`（来自 `ThinkingLevelChangeEntry` 或 AssistantMessage）、最后出现的 `model`（来自 `ModelChangeEntry` 或 AssistantMessage）、以及所有的 `CompactionEntry`。

2. **Compaction 边界处理：** 如果路径中存在 `CompactionEntry`：
   - 生成一条"压缩摘要消息"（`compactionSummary` role），告知模型早期对话的摘要。
   - 在 compaction entry 的 `firstKeptEntryId` 处截断历史：只保留该 ID 之后的 entry，之前的被摘要替代。
   
3. **消息提取：** `MessageEntry` 直接提取 message；`CustomMessageEntry` 转换为前缀 user message；`BranchSummaryEntry` 转换为 `branchSummary` role 消息。

### JSONL 存储（coding-agent 层的 SessionManager）

`SessionManager` 实现了 `SessionStorage` 接口，使用 **JSONL 文件**（每行一个 JSON 对象）存储整个 session tree：

- **Header 行：** 文件第一行是 `SessionHeader`，包含 `type: "session"`、`version`（当前为 3）、`id`、`timestamp`、`cwd`、`parentSession`。
- **Entry 行：** 后续每行是一个 `SessionEntry`（`SessionTreeEntry` 的超集，加上 `SessionHeader`）。
- **Leaf 追踪：** `LeafEntry`（type="leaf"）记录当前活动的 tree tip。`setLeafId(null)` 表示导航到 root 之前（返回空上下文）。
- **版本迁移：** 支持 v1→v2（添加 id/parentId tree 结构）、v2→v3（重命名 hookMessage role 为 custom）的就地迁移。
- **内存后端备选：** 虽然编码上主要使用 JSONL，但 `SessionStorage` 接口使得内存后端（用于测试或临时会话）成为可能。

## 在 Agent 能力面里的影响是什么

- **分支与导航：** `moveTo(entryId)` 让用户可以在不同版本的回答之间自由切换，每次切换可以自动生成分支摘要以便后续理解。
- **Compaction 是树的一部分：** CompactionEntry 不仅影响当前上下文构建，还作为树的节点存在，使得后续从 compacted 点 fork 的对话能正确理解被压缩的历史。
- **扩展的持久化通道：** `CustomEntry` 和 `CustomMessageEntry` 让扩展可以在会话树中持久化任意数据，并在会话重新加载时恢复状态。
- **重放与调试：** Append-only JSONL 格式使得会话完全可以被重放——只需从 header 开始逐行重建树结构。

## 最小例子是什么

```typescript
import { Session, SessionStorage } from "@earendil-works/pi-agent";

// 使用内存存储后端（仅示意，实际使用 SessionManager 的 JSONL 后端）
const storage: SessionStorage = new InMemorySessionStorage({
  id: "session-001",
  createdAt: new Date().toISOString(),
});

const session = new Session(storage);

// 追加用户消息
await session.appendMessage({
  role: "user",
  content: "Write a hello world program in Python",
  timestamp: Date.now(),
});

// 追加模型响应
const msgId = await session.appendMessage({
  role: "assistant",
  content: [{ type: "text", text: "I'll write a Python hello world." }],
  api: "anthropic-messages",
  provider: "anthropic",
  model: "claude-sonnet-4-5-20250929",
  usage: { input: 100, output: 50, cacheRead: 0, cacheWrite: 0, totalTokens: 150, cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 } },
  stopReason: "stop",
  timestamp: Date.now(),
});

// 追加工具调用结果
await session.appendMessage({
  role: "toolResult",
  toolCallId: "tool-001",
  toolName: "write",
  content: [{ type: "text", text: "File written successfully" }],
  details: {},
  isError: false,
  timestamp: Date.now(),
});

// 追加模型切换
await session.appendModelChange("openai", "gpt-5");

// 重建 LLM 上下文
const ctx = await session.buildContext();
// ctx.messages = [user, assistant, toolResult]
// ctx.thinkingLevel = "off"
// ctx.model = { provider: "openai", modelId: "gpt-5" }

// 导航到历史上第一条消息之后
await session.moveTo(msgId, {
  summary: "Explored Python hello world alternative implementation",
});
// moveTo 设置 leaf 到 msgId，并生成 BranchSummaryEntry 记录原分支的摘要
```

这个例子展示了 Session tree 的核心操作：消息的追加、模型状态的追踪、上下文的线性重建、以及分支导航。
