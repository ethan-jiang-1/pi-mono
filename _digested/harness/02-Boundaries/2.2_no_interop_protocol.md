# 2.2 MCP 采纳与互操作(v1.0.0 转向)

## 版本史

| 版本 | 状态 |
|---|---|
| v0.86.1 及以前 | **无任何 MCP/ACP 实现**(源码 grep 仅子串误配)。本文旧版的核心论断"pi 无 MCP 实现 → 统一注入点的另一面是生态锁定"在当时成立。 |
| v1.0.0(MCP 于 0.99.0 落地,commit 8562bcf66) | **pi 采纳 MCP 客户端**:独立包 `packages/mcp` + coding-agent 内置扩展 `src/extensions/mcp/` + `mcp.json` + OAuth + CI 官方 conformance 套件。外部 MCP server 从"每人写适配"变为"配置即用"。本文整篇重写。 |
| v1.0.0 | **ACP 仍缺席**(已在 v1.0.0 工作树重新核实,见判断三)。 |

## 现象是什么

v1.0.0 的 MCP 支持是三层结构,职责各不相同:

1. **协议层**:`packages/mcp`(`@earendil-works/pi-mcp`)是独立 MCP 客户端。README 首句自述"不依赖官方 MCP SDK,也不依赖其他 pi 包"(`packages/mcp/README.md:3`),运行时依赖只有 `cross-spawn` 一项(`packages/mcp/package.json:53-55`)。形态是传输中立核心 + stdio + Streamable HTTP + in-memory 测试传输;OAuth 子集改编自官方 MIT TS SDK v1.29.0(`packages/mcp/LICENSES/modelcontextprotocol-typescript-sdk.txt` 附带其许可证)。协议面:LATEST `2025-11-25`,向下兼容 `2025-06-18`/`2025-03-26`/`2024-11-05`(`src/protocol/types.ts:4`、`:9`);batch JSON-RPC、legacy HTTP+SSE、sampling、tasks 明确不在初始核心内(`README.md:132`)。
2. **消费层**:coding-agent 的 `src/extensions/mcp/`(9 个实质文件 + 2 个 lazy 桩,共约 3,900 行)import 前者(`runtime.ts:29-30`),负责:mcp.json(全局 + 受信项目,`config.ts:4-5`、`:117-118`)与 `pi.registerMcpServer()`(`core/extensions/types.ts:1839`)、`/mcp` 命令(`index.ts:1097`)与 `pi mcp add|remove|list|login|logout`、OAuth(含 RFC 9207 iss 校验与 step-up scope;v1.0.1 起两个增量:CIMD 改为选择性启用——coding-agent 侧 `oauth.clientRegistration: "cimd"`,用 pi.dev 上的 Client ID Metadata Document 替代 dynamic client registration;DCR 请求体按 MCP SEP-837 从 redirect_uris 推导 `application_type`,loopback 主机/自定义 scheme 即 `native`,缺省时 OIDC 服务器按 web client 拒绝 loopback 回调)、工具命名与 exposure 装配、系统提示 `mcp_servers` 段(`index.ts:149`)。
3. **验证层**:CI 有独立 `mcp-conformance` job(`.github/workflows/ci.yml:44-62`),用 pinned 官方 conformance 套件跑三个协议版本的 client 场景,对照 committed baseline(`test/mcp-conformance/baseline.json`)fail-on-regression。

官方用户文档是 `packages/coding-agent/docs/mcp.md`(272 行；v1.0.3 时为 248):Quick setup 三行命令、OAuth、tool exposure、逐客户端的配置迁移表。

## 核心矛盾是什么

旧版的矛盾是"统一注入点 vs 跨 harness 通用口子,两者互斥"。v1.0.0 之后矛盾换了形式:

1. **authoring 与 consumption 分成了两个面。** 写代码注册能力(tool/command/provider/事件)仍然只有 ExtensionAPI 一个口子([1.2](../01-Architecture/1.2_single_injection.md));消费外部生态现成 server 新增了 mcp.json 这条声明式入口。两条来源汇入同一套工具注册表:MCP 工具注册成 `mcp__<server>__<tool>`,走 pi 自己的 tool 管线——"Every call runs through pi's tool pipeline, so `tool_call`/`tool_result` hooks and permission extensions apply to MCP tools the same way they do to built-in tools"(`src/extensions/mcp/index.ts:20-21`)。
2. **方向性。** `packages/mcp` 是 client,不是 server:pi 消费 MCP 生态(pi 的模型够得着外部工具),pi 的扩展生态没有被 MCP 消费(extension、provider、slash command 都不经 MCP 暴露,pi 也不含 MCP server 端实现)。

## 设计判断是什么

### 判断一:"适配层税"没有消失,是被内化为中心化的一次性投资(修订旧论断)

旧论断:"一个 MCP 工具要进 pi,得有人为它写一个 pi extension 的适配层;每个 server 都要写一遍,这是适配层税。" v1.0.0 改变了这笔税的征收方式:pi 自己写了一遍,写成两份中心化资产(独立协议客户端 + 内置装配扩展),此后外部 server 的接入成本从"每人一个 extension"降到"一段 mcp.json 或一条 `pi mcp add`"(`docs/mcp.md` Quick setup:三行命令)。

值得注意的是落点。旧版"影响"一节预言:"如果要补互操作,落点是 extension 系统里的协议 adapter,而不是另起一套协议——这保持统一口子不破。" v1.0.0 正是这么落的:agent 核心(pi-agent-core)零改动、零 MCP 依赖;`packages/mcp` 自己也不依赖任何 pi 包;消费方是一个普通内置扩展(`export default createMcpExtension()`,`index.ts:1181`),可禁用、可被第三方扩展整体顶替(`docs/mcp.md:240-243`)。预言兑现,且兑现方式验证了预言本身。

severity 修订:自用/团队 = 无感(不变);吸纳外部工具生态 = 从"高(每 server 一税)"降到"低(配置即用)",但出现新税种(判断四)。

### 判断二:MCP 是"受控的客户端侧消费面",不是第二条 authoring 通道(与 1.2 的重新表述)

[1.2](../01-Architecture/1.2_single_injection.md) 的"统一注入点"在 v1.0.0 之后要读得更准:

- **authoring 面仍只有一个口子。** ExtensionAPI 仍是唯一写代码注入能力的地方;MCP 侧没有任何反向通道——不能通过 MCP 给 pi 写 extension、拦事件、改 system prompt。`packages/mcp` 的 API 面只有连接/工具/资源/OAuth(`client.ts:153` 起)。
- **MCP 消费面是从统一注入点内部长出来的。** MCP 支持本身就是一个 ExtensionFactory(`index.ts:273`、`:1181`),`registerMcpServer` 也挂在同一个 `pi` 对象上(`types.ts:1839`)。MCP 工具最终注册回 pi 的工具注册表,带 exposure 五档(`direct|model-only|codemode|deferred|hidden`,`types.ts:509`)、annotations、namespace。MCP server 在 pi 眼里相当于"一个不能写代码、只能声明工具的 extension 作者"。
- **消费面可整体顶替。** 装一个注册 `/mcp` 的扩展(如 pi-mcp-adapter)即顶替内置 MCP 支持,或 `"extensions": ["-builtin:mcp"]` 禁用(`docs/mcp.md:240-243`)。统一口子没有破口。

所以 1.2 的"一个口子进"仍然成立,但含义收窄为"**一套管线**"而非"一个文件入口":tool 来源现在有两条(extensions、mcp.json),而生命周期/护栏/exposure 只有一套。

### 判断三:ACP 仍缺席——采纳的是"工具互操作",不是"agent 间协议"(v1.0.0 已核实)

在 v1.0.0 工作树重新 grep `acp`(`packages/coding-agent/src`、`packages/agent/src`、`packages/mcp/src`):命中仅两处,均为 llamaCpp* 子串误配(`interactive-mode.ts:341` `llamaCppPostLoginGuidance`、`extensions/llama/provider.ts:12` `llamaCppClassifyApi`)。旧版结论原样存活。

MCP 解决的是"模型够得着的工具"的横向复用;ACP 这类 agent 客户端协议解决的是"把另一个 agent 当宿主前端"的复用。pi 对后者的答案仍是自家的 extension subagent(`examples/extensions/subagent/` 仍在,仍是 registerTool + 隔离 context 的扩展实现,无任何外部协议)。pi 采纳 MCP ≠ pi 走向通用互操作,它采纳的只是工具这一层。

### 判断四:仍是可辩护的取舍,但押注变了——记新的代价清单(评价)

pi 押的东西没变:自洽平台 + 自家扩展生态;变的是它愿意为"白嫖外部工具生态"付一份中心化客户端投资。这份投资不是免费的,新代价是真实约束(升级时是 de facto breaking):

| 新代价 | 机制 | 锚点 |
|---|---|---|
| 工具名规范化 | MCP 工具/命名空间名 `-`→`_`(`mcp__my-server__x`→`mcp__my_server__x`),同 server 内碰撞加 sha256 hash 后缀,仅 `-`/`_` 之差的 server 名被拒 | `tools.ts:77-90`、`mcp-servers.ts:114-116`;#10239 |
| 首 prompt 不等待 | 连接后台跑;第一个 prompt 只等有 direct 工具的 server,且最多 10s(`startupWaitMs`) | `index.ts:87-90`、`:996-1013` |
| OAuth 存储布局 | 凭据按 server name+URL 双键(`mcp__<name>|<url>`),纯 URL 旧键由首个加载者迁移 | `oauth.ts:120-124`;#10252 |
| 默认不见 | MCP 工具默认 exposure=codemode,不进模型声明;要模型直接看见须显式 direct/deferred | `docs/mcp.md:167-172`、`types.ts:509` |

另外,协议面是 pi 自维护的子集(非官方 SDK 全量:不做 batch/legacy SSE/sampling/tasks),"兼容 MCP 生态"承诺的上限由 pi 自己的客户端能力决定——这是内化适配层的对价。

**结论**:旧版说"两个定位不可兼得,pi 明确选了前者"。v1.0.0 的答案是兼得了一半:authoring 的统一口子原样保留,消费侧加了受控闸门。仍然可辩护,但要知道它现在押的是"**消费别人生态可以,别人插手我的 harness 不行**"。

## 影响是什么

1. **评价必须与 [1.2](../01-Architecture/1.2_single_injection.md) 一起读**:统一注入点是 authoring 面,MCP 是 1.0 新增的客户端消费面,分工而非替代。只夸"统一口子"或只夸"支持 MCP"都会失真。
2. **旧预言已兑现且给出了方法论**:补互操作的正确落点是"独立包 + 内置扩展消费",agent 核心不动。将来若补 ACP,大概率同构。
3. **升级迁移看判断四的表**:命名、时序、OAuth 布局、exposure 默认值四处是真实行为变化,依赖旧行为的自动化需要逐条核对。

## 最小例证是什么

**例证 1(独立客户端,零 pi 依赖):** 打开 `packages/mcp/package.json`——dependencies 只有 `cross-spawn: 7.0.6`,没有 `@earendil-works/pi-*`,没有官方 MCP SDK。旧版用 grep 证明"无实现";现在反着读同一个证据面:实现存在,且是独立包,不是 agent 内的胶水。

**例证 2(官方文档即产品承诺):** 打开 `packages/coding-agent/docs/mcp.md`——"Migrate configuration from another client"一节逐客户端(Claude Desktop/Claude Code/Cursor、VS Code、Codex、OpenCode)给出 `mcpServers` 条目的转换表(`mcp.md:94-103`)。文档在教用户把别家配置抄进来,这是"配置即用"成立的最直接文本证据。

**例证 3(`pi mcp list` 的语义):** 跑 `pi mcp list`——连接所有 enabled server 并打印状态、工具、错误;entry 非法或 enabled server 未连上时 exit 1(`docs/mcp.md:86`)。注意 shell 命令不加载扩展(`docs/mcp.md:82`):管理面与扩展面分离——"配置即用"的管理路径不经过 ExtensionAPI,但 server 的运行时装配仍是内置扩展。

可观察信号:例证 1 → 采纳是结构性的(独立包),不是顺手胶水;例证 2 → 消费姿态是开放的(教迁移);例证 3 → 管理面可用且可验证。三者同看,才能说"1.0 采纳 MCP"是产品决策而非实验性 flag;同时判断四的代价表说明它不是无代价的采纳。
