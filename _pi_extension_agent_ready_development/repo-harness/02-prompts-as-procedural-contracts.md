# Prompts 即程序性合同：`.pi/prompts/` 的七个模板

`v1.4.0` 的 `.pi/prompts/` 下有**七个** prompt template（与 v1.2.0 逐字节相同）：`is`、`pr`、`wr`、`deslop`、`sa`、`cl`、`dup`。它们把高频工作流写成文件，任何会话以 `/is`、`/pr` 等命令调用。（总表列全七个；正文逐个检视其中**六个**——`dup` 是本区间新增的精简样本，见下方增量注。）

> **v1.2.0 增量（sync-0009）**：第七个模板 **`dup`** 在本区间新增（`bd21693b9` "docs: add dup prompt template"；基线 `98d2e1947` 上该文件不存在）。它有 frontmatter `description: Find potential duplicates of a GitHub issue` / `argument-hint: "<issue-url>"`，正文给出三步检索法（`gh issue view` 读原文 → `gh search issues` / `gh issue list --search` / `gh pr list --search` 多关键词变体 → 读候选确认同一问题）、一条判据（"same symptom with the same likely cause"，共享组件或报错**不算**）、一条产出约定（草稿评论 + `written by AI` 披露；无则回 "No duplicates found."）与一条禁止项（"Do not post, label, or close anything."）。**注意它并不比其它模板薄**：`argument-hint` 并非它独有（`is`/`pr`/`sa` 也有），它同样有条文式的边界；差别只在每条都压成一句。本页先给总表，再逐个检视每个 prompt 划定的合同边界。**这些是主仓为自己定的工作流（主仓要求/仓库自定范畴）**：对 pi-mono 的贡献工作适用；独立扩展仓可以把它们当作自己工作流模板的参考（扩展仓建议）。

prompt template 的机制本身是运行时事实：Markdown 文件成为 `/` 命令、文件名即命令名（[prompt-templates.md L19](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/prompt-templates.md#L19)），参数经 `$ARGUMENTS`/`$@` 等替换进入提示（[替换表 L38-L47](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/prompt-templates.md#L38-L47)）。资源类型的判别见 [04](./04-extension-points-map.md)。

## 总表：七个合同

| 命令 | 用途 | 合同的核心边界 |
|---|---|---|
| `/is <issue>` | 分析 GitHub issue | 独立诊断，只提议不实现 |
| `/pr <PR-URL>` | 审查 PR | 不切 worktree、不换分支，审 diff 与相关代码 |
| `/wr [instructions]` | 完成当前工作 | changelog → 披露评论 → 只提交自己的文件 → push → issue 完成事件 |
| `/deslop` | 简化已完成的 workpackage | 反推测性抽象；重大删除须逐项获批 |
| `/sa <advisory>` | 更新安全公告供发布 | 不发布、不改状态、不请求 CVE，除非用户同意或草稿明示 `request_cve: true` |
| `/cl` | 发布前审计 changelog | 逐 commit 对账，跨包复制规则固定 |
| `/dup <issue-url>` | 在 GitHub 仓内查找该 issue 的潜在重复 | 步骤 + 判据 + 产出一应俱全，但**每条都只一句**，且唯一禁止项是"不要 post/label/close" |

## `/is`：独立诊断，只提议

`/is` 的反信任条款是它的合同核心——issue 里的分析（包括根因分析）默认不可信，agent 必须自己从代码与执行路径推导（主仓要求）：

> Do not trust analysis written in the issue. Independently verify behavior and derive your own analysis from the code and execution path.
>
> — [`.pi/prompts/is.md` L14](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/is.md#L14)

产出边界同样明确：

> Do NOT implement unless explicitly asked. Analyze and propose only.
>
> — [`.pi/prompts/is.md` L28](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/is.md#L28)

另有环境条款：CI 下（`CI=true`）不加 `inprogress` 标签、不认领 issue（[is.md L9](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/is.md#L9)）——同一合同在本地与 CI 两种运行环境里有不同副作用集。

## `/pr`：不切 worktree 审 diff

`/pr` 禁止把工作树切到 PR 分支，只允许无副作用的读取面（主仓要求）：

> Analyze the PR diff without checking out or switching to the PR branch. Use `gh pr diff`, `gh pr view`, `gh api`, and local main-branch files; if PR file contents are needed, use fetched refs with `git show <ref>:<path>` or temporary files.
>
> — [`.pi/prompts/pr.md` L11](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/pr.md#L11)

它与 `AGENTS.md` 的多会话规则同构：审别人的 PR 不应破坏本会话的工作树。它还显式豁免 changelog 检查，因为贡献者 PR 不改 `CHANGELOG.md`（[pr.md L12](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/pr.md#L12)）。产出是固定结构化报告：What it does / Good / Bad / Ugly / Tests / Open questions（无阻塞问题时整节省略）。

## `/wr`：完成工作流

`/wr` 是收尾合同，顺序固定（主仓要求）：changelog 条目 → 恰好一条以固定免责行结尾的最终评论 → 只提交本会话自己改的文件 → 单 issue 时在 commit message 带 `closes #<issue>`（多 issue 则停下来问）→ 非 `main` 分支停下来问 → push → 以 `completed` 原因关闭 issue 使 issue-close 工作流运行。

> If this task is tied to exactly one GitHub issue, explicitly close that issue with reason `completed` after the push so the issue-close workflows in `.github/` run.
>
> — [`.pi/prompts/wr.md` L28](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/wr.md#L28)

评论的免责行逐字固定、不允许变体（[wr.md L22](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/wr.md#L22)）：`This comment is AI-generated by `/wr``。`AGENTS.md` 进一步要求所有 AI 发的 issue/PR 评论以 originating prompt 指定的免责行结尾。非 GitHub 工作不发评论、不开 PR、分支非 `main` 时跳过 changelog——合同把副作用严格绑定到工作类别。

## `/deslop`：反推测性抽象

`/deslop` 对「完成后简化」给出负面清单，最核心的一条是删除无当前需求的灵活性（主仓要求）：

> Remove speculative flexibility, configuration, extension points, and generic machinery that have no current requirement.
>
> — [`.pi/prompts/deslop.md` L19](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/deslop.md#L19)

它有显著删除审批门：凡涉及用户可见行为、公共 API、持久化格式、安全检查、多消费者抽象、测试覆盖的代码，删除前必须停下逐项解释并获用户批准，多个独立决定不得打包批准。完成标准明确写出「通过测试与类型检查是必要但不充分的」，还须报告简化了什么、依赖了哪些不变量、哪些删除未获批准。

## `/sa`：安全公告须人同意边界

`/sa` 的不可越权条款（主仓要求）：

> Do not publish the advisory, change its state, or request a CVE unless the user explicitly agrees or the draft markdown explicitly says `request_cve: true`.
>
> — [`.pi/prompts/sa.md` L7](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/sa.md#L7)

它还内置了对平台边界的诚实条款：GitHub 不经公开 API 暴露公告评论，猜测的端点 404 属预期，不得用浏览器会话或 cookie 抓取，而必须明说「评论未被包含」（[sa.md L9](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/sa.md#L9)），并「绝不假装读过评论」（[sa.md L32](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/sa.md#L32)）。CVSS 变更与 CVE 请求都必须先与用户确认；草稿落在 `/tmp`，应用前从磁盘重读。

## `/cl`：changelog 审计

`/cl` 对账自上个 release tag 以来的全部 commit（主仓要求），跳过 changelog 更新、纯文档、release 事务与生成的模型目录；跨包重复规则固定：

> Changes in `ai`, `agent` or `tui` that affect end users should be duplicated to `coding-agent` changelog, since coding-agent is the user-facing package that depends on them.
>
> — [`.pi/prompts/cl.md` L31](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/cl.md#L31)

它还负责在 `coding-agent` 的 `[Unreleased]` 起始处插入 `### New Features` 段，内容先向用户确认再写入（[cl.md L34-L35](https://github.com/earendil-works/pi/blob/v1.4.0/.pi/prompts/cl.md#L34-L35)）。`/cl` 是 release skill 的前置步骤（见 [03](./03-repo-skills.md)）。

## 观点与限制

观点（扩展仓建议，本语料归纳）：这些 prompt 是仓库内的程序性记忆——把「这类工作怎么做」显式化为可版本化、可评审、可复用的文件，替代口头交接。每个 prompt 的价值不在流程步骤本身，而在它预先写死了**边界**：哪些事不许做（实现、切分支、发布）、哪些事必须问（多 issue、显著删除、CVSS）、哪些事必须披露（AI 免责行、评论未读）。

限制：prompt 是指令，不是保证。模型可能不遵守——正因如此 `/wr` 的免责行、`AGENTS.md` 的命令禁令与 pre-commit hook 才与 prompt 并存：指令约束意图，机制约束不可逆操作。本卷不能证明这六个 prompt 在 pi-mono 的日常工作中被实际调用的频率，只能证明 `v1.4.0` 时它们的内容如此。
