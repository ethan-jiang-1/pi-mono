# 2.2 Processor: 消息流的处理管线

>
> **✅ v0.84.2**：v0.84 无 processor 级 breaking（`harness/reducer.ts`/`messages.ts` 为 session v4 新增旁路，见 3.5）。2026-08-17 已对照 v0.84.2 复核，正文已修正至 v0.84.2。

## 现象是什么

在双层循环的每个内层迭代中，有两段核心处理管线：`streamAssistantResponse()` 和 `executeToolCalls()`。前者负责将 Agent 消息上下文发给 LLM、流式接收响应、实时 emit 事件；后者负责解析助理消息中的 tool call、逐一（或并行）执行、将结果格式化为消息条目。两者的衔接构成了一个 turn 的完整生命周期。（解释）

**源码位置：** `/packages/agent/src/agent-loop.ts`（`streamAssistantResponse` 和 `executeToolCalls` 函数）

## 核心矛盾是什么

pi-mono 存在两个层次的消息格式：（解释）

- **AgentMessage**：pi-mono 内部的超集消息类型，可以包含 `bashExecution`、`branchSummary`、`compactionSummary`、`custom` 等非原生 LLM 消息类型。
- **Message**（LLM 原生）：标准的 `user` / `assistant` / `toolResult` 三元组。

Processor 必须在每次 LLM 调用前完成 AgentMessage → Message 的转换（通过 `convertToLlm`），同时保持流式输出期间的事件粒度足够细，让 UI 可以逐 token、逐 thinking chunk、逐 tool_call 地渲染。（解释）

此外，工具执行有并行/串行两种模式：多个独立的工具可以并发执行以提高吞吐，但某些有副作用的工具（如 bash）可能需要按 assistant 返回的顺序串行执行。（解释）

## 实现思想是什么

### streamAssistantResponse 管线

```
AgentMessage[] (context.messages)
  → transformContext (可选，AgentMessage 级别裁剪/注入)
  → convertToLlm (AgentMessage → Message)
  → 构建 Context {systemPrompt, messages, tools}
  → getApiKey (resolve 可能过期/接近过期的 token，fallback 到 config.apiKey)
  → streamFunction(config.model, llmContext, {...config, apiKey, signal})  // 委托 pi-ai（AgentLoopConfig extends SimpleStreamOptions，types.ts:149，apiKey 来自基类 ProviderRequestOptions）
  → for await (const event of response)  // 消费 AssistantMessageEventStream
    → case "start": partialMessage 初始化，push 到 context，emit message_start
    → case "text_start"/"text_delta"/"text_end": 更新 context.messages 最后一项
    → case "thinking_start"/"thinking_delta"/"thinking_end": 同上
    → case "toolcall_start"/"toolcall_delta"/"toolcall_end": 同上
    → case "done"/"error": 取 response.result() 得到最终 AssistantMessage，emit message_end
  → 返回包含 usage + stopReason 的完整 AssistantMessage
```

关键细节：

- **getApiKey 动态解析：** 对于 GitHub Copilot 等 OAuth token 场景，token 可能在长工具执行期间过期。`getApiKey` 在每个 LLM 请求前被调用，确保每次请求都有有效 token。（解释）
- **transformContext 先于 convertToLlm：** 这意味着上层可以在 AgentMessage 层面做 compaction 或其他上下文操作，在下层转换发生之前。（解释）
- **streamFn 可替换：** 通过 `streamFn` 参数传入（v0.83 起 required），允许上层在测试或特殊场景中 mock 流式函数；未传时 `runLoop` 回落到 `getDefaultStreamFn()`（coding-agent 的 `sdk.ts` 用 `setDefaultStreamFn(streamSimple)` 预先安装）。（硬事实）

### executeToolCalls 管线

```
assistantMessage.content 中提取所有 toolCall block
  → 串行判定：config.toolExecution === "sequential"
              或任一 toolCall 命中的 tool.executionMode === "sequential"
  → 否则并行模式（默认 "parallel"）

串行模式：for each toolCall
  emit tool_execution_start
  → prepareToolCall()
    → 查找 tool 定义（未找到 → immediate error result）
    → prepareArguments (兼容性参数转换)
    → validateToolArguments (schema 校验)
    → beforeToolCall hook (可以 block，返回 error result；可带 terminate)
    → signal.aborted → immediate "Operation aborted" error result
  → executePreparedToolCall()
    → tool.execute(toolCallId, args, signal, onUpdate)
    → onUpdate → emit tool_execution_update（acceptingUpdates 门控）
  → finalizeExecutedToolCall()
    → afterToolCall hook (可以 override content/details/usage/isError/terminate)
  → emit tool_execution_end
  → createToolResultMessage (ToolResultMessage 格式)
  → emit message_start/message_end (注入 transcript)

并行模式：
  → 先对所有 tool 做 prepareToolCall（preflight 阶段是串行的，immediate 结果就地 finalize）
  → 对所有 prepared 的 tool 发起 Promise.all(execute + finalize + emit tool_execution_end)
    （tool_execution_end 按完成顺序发出）
  → 完成后按 assistant 消息中的 tool call 顺序创建 toolResultMessage
  → emit message_start/message_end（tool result 按源顺序发出）
```

另有两条进入管线前的旁路：

- **stopReason === "length"：** 整批 tool call 不执行，`failToolCallsFromTruncatedMessage()` 对每个调用 emit `tool_execution_start/end` 并生成 error tool result（"arguments may be truncated, re-issue"），`terminate: false`，循环继续让模型重发。
- **abort：** preflight/串行循环中每个调用后检查 `signal?.aborted`，立即 break，已完成的调用照常产出 result。

### beforeToolCall 与 afterToolCall 钩子

这两个钩子是 tool 安全策略的核心：（解释）

- **beforeToolCall：** 在参数校验之后调用，可以返回 `{ block: true, reason, terminate }` 阻止工具执行。Runtime 会为此 tool call 创建一个 error 类型的 ToolResultMessage；`terminate: true` 让被 block 的调用也参与批次的早停判定。钩子收到 `(context, signal)`，负责自行尊重 abort。
- **afterToolCall：** 在 `tool_execution_end` 和 tool-result 消息事件之前调用，可以逐字段覆盖 `content`、`details`、`usage`、`isError`、`terminate`（省略的字段保持原值，无深合并；钩子抛错则整个 result 变为 error）。这是"脱敏"（redact 不应返回给模型的内容）和"终止"（所有工具完成且都标记 terminate 时停止循环）的实现点。

## 在 Agent 能力面里的影响是什么

- **流式渲染体验：** `message_update` 事件携带 `assistantMessageEvent` 的完整 `contentIndex` 和 `partial` 快照，UI 可以逐 token 渲染文本、逐行展开思考过程、逐字段构建 tool call 参数。（硬事实）
- **Tool Safety：** beforeToolCall/afterToolCall 钩子让嵌入方可以在不修改 tool 实现的前提下添加安全策略层（如文件路径白名单、输出内容脱敏）。（解释）
- **并行执行优化：** 多个独立工具（如同时 read 三个文件）可以并发执行，只有标记了 `executionMode: "sequential"` 的工具才强制串行。（硬事实）
- **终止语义：** `terminate` 标志让 tool 可以优雅地告诉 Runtime "我完成了，不要再调用其他工具"。（解释）

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent-core";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const agent = new Agent({
  streamFn: streamSimple,
  initialState: {
    model: claudeSonnet,
    systemPrompt: "You are a file reader.",
    tools: [
      {
        name: "read",
        label: "Read File",
        description: "Read file contents",
        parameters: { type: "object", properties: { path: { type: "string" } } },
        execute: async (id, params) => ({
          content: [{ type: "text", text: "file contents..." }],
          details: { path: params.path },
        }),
      },
    ],
  },
  beforeToolCall: async (ctx) => {
    // 安全检查：block 对 /etc 目录的访问
    if ((ctx.args as { path?: string }).path?.startsWith("/etc")) {
      return { block: true, reason: "Access to /etc is denied" };
    }
  },
  afterToolCall: async (ctx) => {
    // 对工具结果脱敏（content 是 (TextContent | ImageContent)[]，逐字段整体替换）
    if (ctx.result.content.some((c) => c.type === "text" && c.text.includes("secret"))) {
      return { content: [{ type: "text", text: "[REDACTED]" }] };
    }
  },
});

// 订阅事件观察管线
agent.subscribe((event) => {
  if (event.type === "message_update") {
    // event.assistantMessageEvent.type 可能是 text_delta, thinking_delta 等
    const ae = event.assistantMessageEvent;
    if (ae.type === "text_delta") {
      process.stdout.write(ae.delta); // 逐 token 输出
    }
  }
  if (event.type === "tool_execution_start") {
    console.log(`\n[执行工具: ${event.toolName}]`);
  }
});

await agent.prompt("Read /etc/hosts and /tmp/readme.txt");
// /etc/hosts → beforeToolCall block → error result
// /tmp/readme.txt → execute → afterToolCall redact if needed
```

这个例子展示了 Processor 管线的完整路径：流式输出通过 `message_update` 事件实时推送 → beforeToolCall 做访问控制 → afterToolCall 做结果脱敏。
