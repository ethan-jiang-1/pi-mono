# 2.7 Cancellation: 运行中的取消与信号传播

> **⚠️ v0.83.0**：`AgentEvent`→`AgentSessionEvent`；`agent_end`→`agent_settled`；abort signal 检查增强（`executeToolCallsSequential/Parallel` 中新增 `signal?.aborted` 检查）。
>
> **⚠️ v0.84.2**：v0.84 无 cancellation breaking；全仓 auth/refresh 路径补齐 abort signal 传递（见 5.2）。注意 `AgentHarness.abort()` 在 v0.84 的 lane 骨架中是 `HarnessNotImplemented`（见 4.1），扩展取消走 coding-agent 的 runtime context。
>
> **✅ 复核**：2026-08-17 已对照 v0.84.2 复核，正文已修正至 v0.84.2。

## 现象是什么

当用户按下 Ctrl+C 或点击 "Stop" 按钮时，pi-mono Agent 会优雅地中止当前运行：正在进行的 LLM 流式请求会被取消，正在执行的工具调用会被中断，Agent 状态回到 idle，并且 emit 一个携带 `stopReason: "aborted"` 的 `agent_end` 事件来表示此次运行的非正常终止。整个过程不会留下损坏的 Agent 状态。

**源码位置：**
- `/packages/agent/src/agent.ts`（`Agent.abort()`、`Agent._runWithLifecycle()`、`signal` 生命周期）
- `/packages/agent/src/agent-loop.ts`（signal 在 runLoop 中的传播）
- `/packages/agent/src/types.ts`（`AgentEvent` 中的 aborted 相关语义）

## 核心矛盾是什么

Agent 运行过程中有三个并发执行路径，取消信号需要传递到每一个：

1. **LLM 流式请求：** 一个正在等待服务端响应的 HTTP streaming 连接（在 provider 层）。
2. **并发工具调用：** 多个 `tool.execute()` 正在运行（可能是文件 I/O、shell 命令、网络请求等）。
3. **重试等待：** Agent 级重试中的一个 `sleep(delayMs)` 正在等待退避时间。

取消操作必须满足：
- 所有三个路径都能被中断（不能有"卡住"的取消）。
- 取消后的 Agent 状态必须干净（`isStreaming` 变为 false，`pendingToolCalls` 清空）。
- 取消后的事件协议必须完整（最终仍 emit `agent_end`）。

## 实现思想是什么

### AbortController 生命周期

`Agent` 在 `runWithLifecycle()` 中为每次 run 创建一个新的 `AbortController`（agent.ts:486-509）：

```typescript
private async runWithLifecycle(executor: (signal: AbortSignal) => Promise<void>): Promise<void> {
  if (this.activeRun) {
    throw new Error("Agent is already processing.");
  }
  const abortController = new AbortController();
  let resolvePromise = () => {};
  const promise = new Promise<void>((resolve) => { resolvePromise = resolve; });
  this.activeRun = { promise, resolve: resolvePromise, abortController };

  this._state.isStreaming = true;
  this._state.streamingMessage = undefined;
  this._state.errorMessage = undefined;
  try {
    await executor(abortController.signal);
  } catch (error) {
    await this.handleRunFailure(error, abortController.signal.aborted);
  } finally {
    this.finishRun(); // 清理 isStreaming, streamingMessage, pendingToolCalls
  }
}
```

关键点：
- `AbortController` 在 executor 开始前创建，在整个 run 过程中存活；事件 listener 也通过 `processEvents` 拿到同一个 signal（`agent.subscribe((event, signal) => ...)`）。
- `signal` 通过 `executor` → `runAgentLoop` → `streamFunction(options: { signal })` 的路径传递给 provider。
- `signal` 也传递给 `tool.execute(toolCallId, params, signal, onUpdate)`，工具实现负责检查 `signal.aborted`。
- `runWithLifecycle` 包装 executor 的异常：如果运行正常完成或抛出异常，都走 `finishRun()` 清理（resolve `waitForIdle()` 的 promise 并清空 `activeRun`）。

### Agent.abort()

```typescript
abort(): void {
  this.activeRun?.abortController.abort();
}
```

调用后，`abortController.signal.aborted` 变为 `true`，所有持有此 signal 的操作都会感知到。coding-agent 层的封装是 `AgentSession.abort()`（agent-session.ts:1550-1554）：`abortRetry()`（取消重试退避）→ `agent.abort()` → `await waitForIdle()`。

### 在 runLoop 中的取消处理

`runLoop()` 在 `streamAssistantResponse()` 返回后检查 stopReason（agent-loop.ts:196-200）：

```typescript
if (message.stopReason === "error" || message.stopReason === "aborted") {
  await emit({ type: "turn_end", message, toolResults: [] });
  await emit({ type: "agent_end", messages: newMessages });
  return;
}
```

这意味着如果 abort 发生在 LLM 调用期间，当前 turn 仍然完整 emit `turn_end` 和 `agent_end`，不会有挂起的 turn。工具执行阶段则更细粒度：`prepareToolCall` 在 beforeToolCall 之后、每个 tool call 之间都检查 `signal?.aborted`（返回 "Operation aborted" error result 或直接 break 出循环）。

### 错误表面

当 abort 发生时：

1. Provider 层的 HTTP 请求被取消，SDK 抛出 `AbortError`。
2. Provider 将此转换为 `stopReason: "aborted"` 的 AssistantMessage，通过 `error` 事件在流中发出。
3. `streamAssistantResponse()` 的 `done`/`error` case 捕获此消息。
4. Loop 检查 `stopReason === "aborted"` 并提前退出。
5. 如果 abort 发生在 `runWithLifecycle` 的 executor 抛异常时（而非 stream 内部处理），`handleRunFailure` 创建一个合成的助手消息（`stopReason: "aborted"`），emit message_start/end、turn_end、agent_end。

两种路径最终都产生完整的 agent_end 事件，只是 aborted 消息的内容不同（一个是 provider 返回的真实错误消息，一个是合成的空消息）。

### 扩展的 abort 支持

扩展钩子（`beforeToolCall`、`afterToolCall`、`shouldStopAfterTurn` 等）接收 `(context, signal)`，可以传播给内部的异步操作。coding-agent 的扩展 runtime context 额外提供 `getSignal()`（返回 `agent.signal`）和 `abort()`（agent-session.ts:2419-2426）：如果扩展注册了 `abortHandler` binding 则优先调用它（扩展自行决定如何收敛自己的工作），否则落到 `AgentSession.abort()`。注意 v0.84 的 `AgentHarness.abort()` 是 lane 骨架的 `HarnessNotImplemented` 桩（agent-harness.ts:383-385），不是可用的取消通道。

bash 工具是工具级取消的参考实现：signal abort 时 kill 整个进程树（tools/bash.ts 的 `onAbort` listener），`bash-executor.ts` 把被取消的执行归一为 `{ exitCode: undefined, cancelled: true }` 的 BashResult 而不是抛错。

## 在 Agent 能力面里的影响是什么

- **优雅取消体验：** 取消不会导致 Agent 状态损坏。用户可以立即在取消后发送新 prompt，Agent 状态干净。
- **事件协议的完整性：** 即使是取消，`agent_end` 事件仍会 emit，UI 层可以可靠地依赖这个事件来处理渲染清理和状态重置。
- **工具执行的中断：** 工具实现如果检查 `signal.aborted`，可以在取消时优雅地关闭文件句柄、终止子进程、回滚部分操作。
- **重试取消：** 如果取消发生在退避等待期间，`_retryAbortController.abort()` 终止 sleep，emit `auto_retry_end(success: false)`。

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent-core";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const agent = new Agent({
  streamFn: streamSimple,
  initialState: {
    model: claudeSonnet,
    systemPrompt: "You are a task runner.",
    tools: [
      {
        name: "long_running_task",
        label: "Long Running Task",
        description: "A task that takes a long time",
        parameters: { type: "object", properties: {} },
        execute: async (id, params, signal) => {
          // 工具实现检查 signal 以支持取消
          for (let i = 0; i < 100; i++) {
            if (signal?.aborted) {
              throw new Error("Task cancelled");
            }
            await new Promise(resolve => setTimeout(resolve, 1000));
          }
          return { content: [{ type: "text", text: "Done!" }], details: {} };
        },
      },
    ],
  },
});

// 监听事件，即使是 abort 也能看到完整的生命周期
agent.subscribe((event) => {
  switch (event.type) {
    case "agent_start":
      console.log("Agent 启动");
      break;
    case "agent_end":
      console.log(`Agent 结束 (共 ${event.messages.length} 条消息)`);
      const lastMsg = event.messages[event.messages.length - 1];
      if (lastMsg.role === "assistant" && lastMsg.stopReason === "aborted") {
        console.log("--- 运行被取消 ---");
      }
      break;
  }
});

// 启动运行
const promptPromise = agent.prompt("Run the long running task");

// 2 秒后取消
setTimeout(() => {
  console.log("取消中...");
  agent.abort();
}, 2000);

await promptPromise;

console.log("Agent isStreaming:", agent.state.isStreaming); // false
console.log("Agent pendingToolCalls:", agent.state.pendingToolCalls.size); // 0
// Agent 状态干净，可以立即发新 prompt
await agent.prompt("Try a different task");
```

这个例子展示了完整的取消生命周期：signal 从 Agent 传播到 tool → tool 检查 `signal.aborted` → stream 以 `stopReason: "aborted"` 结束 → agent_end 事件仍正常 emit → 状态清理干净，可以立即开始新运行。
