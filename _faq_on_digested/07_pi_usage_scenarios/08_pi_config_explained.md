# Pi-mono 项目 `.pi/` 配置详解

> 本文说明 `/Users/bowhead/pi-mono/.pi/` 目录的结构、每个文件干什么、以及"接线"逻辑——即这些配置如何被 pi agent 发现、加载、生效。

---

## 一句话

`.pi/` 是 pi agent **项目层的配置目录**。它放在项目根，被 pi 的启动扫描发现（前提是项目已被 trust）。它不负责"配置 pi 的行为参数"——那种事在 `~/.pi/agent/settings.json`——它负责的是"给 agent 注入项目特定的知识和方法"。

pi 的启动加载链（三层，从宽到窄）：

```
全局层 ~/.pi/agent/         → 个人纪律、全局技能、全局扩展
父目录链 AGENTS.md          → 各目录自顶向下合并
项目层 .pi/                 → 本项目的 prompts / skills / extensions
```

## 文件总览

```
.pi/
├── prompts/              # 5 个 prompt template（slash 命令）
│   ├── cl.md
│   ├── is.md
│   ├── pr.md
│   ├── sa.md
│   └── wr.md
├── extensions/           # 4 个 TypeScript 扩展
│   ├── tps.ts
│   ├── redraws.ts
│   ├── import-repro.ts
│   └── prompt-url-widget.ts
├── skills/               # 1 个 Agent Skills 标准 skill
│   └── add-llm-provider.md
├── git/.gitignore        # 预留 git 子目录，锁全忽略
└── npm/.gitignore        # 预留 npm 子目录，锁全忽略
```

`.git/` 和 `.npm/` 是两个占位子目录，内容全被 `.gitignore` 忽略（`*` + `!.gitignore`）。它们的目的是让未来可能的 per-project git hooks 或 per-project npm 缓存留在项目 `.pi/` 下而不是全局，但当前未使用。

## Prompts：5 个 slash 命令

每个 prompt template 是 `.pi/prompts/*.md` 格式，pi 启动后注册为 `/命令名`。

### `/cl` — Changelog 审计（cl.md）

**用途**：发布前审计所有包的 changelog entry 是否完整。

**设计焦点**：
- 自己找上一次 release tag（`git tag --sort=-version:refname | head -1`）
- 三个包的 CHANGELOG.md 逐个过
- 设有交叉包重复规则（ai/tui 的改动用户可见的要复制到 coding-agent）
- 专门绕过 `models.generated.ts` 的变更（生成文件不算产品改动）

这是这个项目**最常被调用的 prompt 之一**，因为 release 流程里它的步骤固定、容易被遗漏步骤。

### `/is` — Issue 分析（is.md）

**用途**：分析 GitHub issue（bug / feature request），不实现，只分析。

**设计焦点**：
- **显式不信任 issue 里的分析**："Ignore any root cause analysis in the issue (likely wrong)"
- 要求读完整相关代码，不截断
- 区分 bug（追踪代码路径找根因）vs feature request（给实现方案但不动手）
- CI 环境自动跳过 label 操作（防止 CI 污染 label 状态）

这条 prompt 的设计哲学是这个项目贯穿的：**先独立验证，再建信任**。

### `/pr` — PR 审查（pr.md）

**用途**：审查 GitHub PR，输出结构化 review。

**设计焦点**：
- 没有多余的检查点锁——`-e` 扩展里的 `prompt-url-widget.ts` 会在 PR 启动时抓取元数据（title、author）在 TUI 顶部显示
- 明确定义不查 changelog（CONTRIBUTING.md 说贡献者不写 changelog，维护者合入时加）
- 审查维度固定：What / Good / Bad / Ugly / Tests / Open questions
- 安全护栏：`Do not check out or switch to the PR branch`——只读审查，不进脏工作树

### `/sa` — Security Advisory 发布（sa.md）

**用途**：把 GitHub Security Advisory 从 draft 状态更新到发布就绪。

**设计焦点**：
- 163 行——项目里最长的 prompt，因为安全发布涉及大量一次性规则。
- 核心约束链：获取 advisory JSON → 独立验证漏洞事实 → 讨论 CVSS → 写 draft markdown → 用户批准后才 PATCH API
- 明确定义 GitHub API 的限制（报告中不会包含 advisory comments，因为 API 不暴露）
- 禁止从浏览器获取数据（cookie/会话）

这条是复杂单任务 focus 的好例子——一条 prompt 的复杂度等于整个子任务的安全约束。

### `/wr` — End-to-end 收尾（wr.md）

**用途**：当前任务收尾：changelog → commit → push → close issue。

**设计焦点**：
- 上下文感知：如果会话源自 `/is` 或 `/pr`，复用已有的 issue/PR 引用
- 显式的 git 纪律：只加自己改的文件、不用 `git add -A`/`git add .`、不 push 到非 main 分支
- issue close 逻辑细致：查 state→看 stateReason→如果是 COMPLETED 且无 inprogress label 就不动它——避免重复触发 GitHub close 事件
- 最后一行 AI 声明 `This comment is AI-generated by /wr` 是组织的审计要求

这 5 条 prompt 覆盖了这个项目的**四个核心重复工作流**：发布检查（cl）、问题分析（is）、代码审查（pr）、安全发布（sa）、收尾闭环（wr）。它们没有覆盖"写代码"本身——那由 agent 的对话语境和 AGENTS.md 来管。

## Extensions：4 个 TypeScript 文件

Extension 是 pi 的"真·插件"。prompt 只影响 agent 的 initial prompt，extension 可以注册命令、挂钩事件、操作 TUI。

### `tps.ts` — Tokens Per Second 监控

**作用**：每次 agent 回复结束时，在 TUI footer 显示一条指标通知（不会打断对话）：
```
TPS 12.3 tok/s. out 1,234, in 5,678, cache r/w 2,100/900, total 7,778, 15.2s
```

**接线**：挂 `on("agent_end")` 事件，统计所有 assistant 消息的 usage 字段。

**为什么存在**：这个项目的 owner 需要跨 provider 观察推理速度（特别是 deepseek-v4-flash 的 thinking token vs output token 比例）。这条信息在 UI 中的位置（notify，非阻塞）比 TUI 内置的状态栏更及时。

### `redraws.ts` — TUI 重绘统计

**作用**：注册 `/tui` 命令，显示当前会话的 TUI 全量重绘次数。

**接线**：通过 `ctx.ui.custom()` 从 TUI 实例读取 `fullRedraws` 计数器。

**为什么存在**：调试 TUI 性能的工具。当 TUI 出现闪烁或响应慢时，owner 用 `/tui` 检查是否触发了过多的全量重绘（正常情况下应该少）。这是一个**调试用扩展**，不为日常流程服务。

### `import-repro.ts` — Issue 再现会话导入

**作用**：`/ir <gist-id | gist URL | pi.dev/session URL | issue URL>` — 从 CI 输出的 gist 导入 issue 分析会话并切换到它。

**接线**：CI 的 issue-analysis workflow 在分析完成后把会话 JSONL 上传为 GitHub Gist。本地开发者用 `/ir` 一键导入同一个会话，自动重写路径（CI 的高熵 checkout 目录 → 本地目录），然后切换到那个会话，像是在那个 CI 环境里继续工作。

**为什么存在**：这是**"reproducible debugging"** 的关键组件。issue 报告者说"这里出错了"，CI 自动运行分析并把完整上下文（读过的文件、调试轨迹、agent 的推理步骤）做成可导入的 session 发给开发者。开发者不用自己复现一遍问题。

**代码量**：351 行（`.pi/extensions/` 里最大的文件）。功能复杂：
- 支持 6 种输入格式（gist ID、URL、share URL、issue URL、HTML 文件、JSONL 文件）
- 跨平台路径重写（CI 跑在 Ubuntu 但本地是 macOS）
- HTML 中 base64 JSON 的解码
- 通过 GitHub API 从 issue comments 反向查找 gist
- 重写所有记录中出现的 CI 路径为本地路径

### `prompt-url-widget.ts` — Prompt URL Widget

**作用**：当 prompt 以 GitHub PR/Issue/Advisory URL 开头时，在 TUI 顶部显示结构化信息卡。

**接线**：挂 `on("before_agent_start")` 和 `on("session_switch")` 事件。如果 prompt 匹配已知模式（`You are given one or more GitHub PR URLs: ...` 等），则：
1. 立即显示原始 URL
2. 异步抓取 GitHub metadata（title、author）
3. 更新 widget 显示 title + author + URL
4. 自动设置会话名称为 `PR: <title> (<url>)` 格式

**为什么存在**：在终端里同时管理多个 PR/issue 分析会话时，会话列表中有序号 + title + URL，可以快速定位。否则你从会话列表里看到的只有 `pi session 2025-06-17 14:23:05`。

## Skills：1 个 checklist skill

### `add-llm-provider.md`

**用途**：给 `packages/ai` 添加新 LLM provider 的 checklist。

**格式**：Agent Skills 标准的单 Markdown 文件（带 frontmatter + 分步骤 Markdown 内容）。

**覆盖的改动点**（7 个维度，42 步）：Core types → Provider implementation → Lazy registration → Model generation config → Tests → Coding agent wiring → Documentation。

**为什么是 skill 而不是 prompt**：因为添加 provider 不是一个"问号回答"任务，而是一个**跨 7 个子系统、42 个具体操作点的面包屑追踪**。Skill 格式允许（且期望）agent 逐条读 checklist、标记进度、逐条确认。

**参考来源**：如果你在 `packages/ai/src/providers/` 下看实际 provider 实现（openai.ts、anthropic.ts...），每一个都对应了这个 checklist 中的步骤。这个 skill 是将散落在多个文件中的"注册一个新 provider 需要改什么"显式化为 agent 可跟踪的路径。

## 整体的"接线"逻辑

理解这个 `.pi/` 的关键在于了解它**不是什么**和**是什么**：

**不是**：
- 不是 pi 的配置文件（`settings.json` 才管默认 provider、model、UI 主题、tool 白名单）
- 不是 AI 配置中心（models.json / auth.json 在 `~/.pi/agent/` 全局层）
- 不是 CI 配置（`.github/` 才是）

**是**：
- 一个**模块化的工作流库**，按"这个项目需要什么能力"来组织
- prompts = "固定流程的初始指令"
- extensions = "运行时能力注入"（命令、widget、事件处理）
- skills = "可跟踪的 checklist 执行器"
- git/ 和 npm/ = "能力预留插槽"

一套典型的工作流会在多个层级之间跳转：

```
你        → `/is <issue-url>`
           prompt-url-widget.ts  → 显示 issue title + author
           自动设置会话名称为 "Issue: <title> (<url>)"
           agent 启动，读 is.md 作为初始 prompt
agent     → 分析 issue（不实现）
你        → "实现了"
agent     → 写代码 → 跑检查 → 跑 verify skill 到绿
你        → `/wr`
           agent 读对话历史发现来自 issue #123
           → 改 changelog → 显式路径 commit → push → close issue #123
```

四条 prompt、四个扩展、一条 skill，在这个流程里只参与了两次"显式调用"（`/is` 和 `/wr`）和一次"隐式触发"（`prompt-url-widget` 自动注册 session 名称）。其他文件（`/cl`、`/pr`、`/sa`、`tps`、`redraws`）在它们自己的使用场景里才激活。

这就是 pi 的设计哲学在这个 `.pi/` 上的体现：**不预装全家桶，每个能力在对应的场景里被按需发现和激活**。
