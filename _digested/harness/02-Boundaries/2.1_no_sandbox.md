# 2.1 无默认沙箱：扩展以宿主进程同等权限运行——"吸纳陌生人"的第一道闸是敞开的

## 现象是什么

扩展跑在宿主进程里，拥有**完整系统权限**，可以执行任意代码。这是 pi 自己写明的：`docs/extensions.md` 警告 "Extensions run with your full system permissions and can execute arbitrary code"；`docs/packages.md` 对 pi packages 同样警告 "full system access"。

沙箱存在，但**只作为可选 example**，不是默认：`examples/extensions/sandbox/`（`@anthropic-ai/sandbox-runtime` 的 OS 级沙箱）和 `gondolin/`（把工具路由进 micro-VM）。

![无沙箱的威胁模型](figures/threat_model.svg)

## 核心矛盾是什么

1. **自用扩展要的是"全功率、零摩擦"**：给自己写个扩展，加一道沙箱只是碍事。所以默认无沙箱对"自用"是合理的。
2. **吸纳陌生人要的是"隔离、可审计"**：`pi install` 一个第三方 npm/git 包，等于执行它仓库里的任意代码，且没有隔离。默认无沙箱对"吸纳"是攻击面。

**同一个默认值，对两种诉求的 severity 完全相反**——这正是本节 README 要求"先分诉求再下结论"的原因。

## 设计判断是什么

### 判断一：无沙箱是刻意的自用优化，不是遗漏（解释）

扩展的定位是"你自己的全权限代码"（`docs/extensions.md` 的 Security 警告紧跟在"Extensions are TypeScript modules"之后）。给自用扩展默认套沙箱，会立刻杀掉它最大的价值——直接 `fs`、`child_process`、任意 npm 依赖。pi 把"信任"放在了"谁装了它"而不是"它是什么代码"上。

### 判断二：但信任边界在"分发"处断裂（硬事实 + 评价）

`pi install npm:@foo/bar` 的模型是**信任即安装**：装进 `~/.pi/agent/extensions/` 后，下次启动 `loadExtensions` 就执行它的 factory 函数。这里没有"安装前审计""权限声明""运行时隔离"任何一环。对"像 npm 一样开放地吸陌生插件"这个目标，这等价于**让陌生代码直接进主进程**。

**severity 分层**：自用 = 无风险；团队内部包 = 中（靠 code review 兜）；公开分发、陌生安装 = 高（信任完全转移到用户自己的警觉，harness 不给任何护栏）。

### 判断三：缓解路径存在但都是 opt-in，且都不是"插件沙箱"（硬事实）

- `examples/extensions/sandbox/`：用外部 `@anthropic-ai/sandbox-runtime` 做 OS 级隔离——但这是**示例**，作者要自己写整个扩展，pi 不提供"把这个扩展跑进沙箱"的开关。
- `gondolin/`：把内置工具和 `!` 命令路由进 micro-VM——沙的是**工具执行**，不是**扩展代码本身**。

**关键结论（就 `core/extensions` 而言）**：pi 有"沙箱执行 bash/工具"的思路（gondolin），但**没有"沙箱运行扩展代码"的机制**。前者的威胁模型是"模型跑危险命令"，后者的威胁模型是"扩展代码本身是恶意的"——对 `~/.pi/agent/extensions/` 里用户自己写的 extension factory（`loadExtensions` 直接执行它），pi 只防了前者，没防后者。

**scope 限定（v0.85.1 补）**：这条结论对 `core/extensions` 仍然成立，但对 pi 正在长的**第二条扩展轴**（facet 投递路径）**已不再成立**——那条轴的隔离机制已经选定。详见下文判断四。

### 判断四：第二条扩展轴（facet 投递）已选定隔离机制——但这是**规格 + PoC，不是产品**（硬事实 + 评价）

`core/extensions` 之外，pi 正在长第二条扩展轴：**facet**——经 wire 投递、按 host 拆 bundle 的插件单元（载体是新包 `packages/chord`）。这条轴的隔离问题**已经答了**，答案是 `isolated-vm` isolate + 只传字符串的膜（string-only membrane）；但答案写在 spec 和一个依赖未安装的 PoC 里，**不在产品路径上**。

**硬事实（规格侧）**：`packages/agent/docs/mobile-handoff/02-plugins/01-facets/facets.md` §14 是**按 sandbox PoC 重写过**的隔离章：

- 旧稿把威胁模型限定为 "a careless plugin author, not a hostile one"，spec 自己判为**错的**（`:1431-1433`：**"That was wrong"**、"The attacker is hostile, **the delivery is remote**, and the target is a workstation."）。
- §14.2 选定 `isolated-vm` isolate + string-only membrane（`:1443-1448`），并明确**否决** SES / `lockdown()`（`:1457`，guest 与 host 同 VM，正是 Figma Realms 的逃逸类别）、Node `worker_threads`（`:1464`）、Deno workers（`:1470`）。
- §14.3 承认**封闭面不均匀**：session / server / TUI facet 可闭（把 ambient authority 收成 endowment 独占面），**web 不可闭**——DOM 是 "ambient mutable graph"，从任一节点都能走到 `ownerDocument`/`window`（`:1567-1571`），`lockdown()` 帮不上。结论写得很直白：**"make the safe path the easy path, and do not pretend the escape is closed."**（`:1601-1602`）
- §14.4 把隔离落成三条 API 约束（绑定自带 disposer、绑定返回的每个对象也是绑定、跨界不可变 JSON 强制冻结；`:1618-1651`），并明确 endowment 极简、`fetch`/`Buffer`/`require`/`process.exit` 永不 endowed。

**硬事实（PoC 侧）**：`mobile-handoff/02-plugins/02-sandbox/` 是一个 "working PoC"，`02-sandbox/README.md:17-38` 给出**结构性**安全论证（作者用语："by construction, not by care"，不是"小心使用"）：`encode()` 只产字符串、host callable 只以整数 id 进入 guest、全程只给 guest **一个** `Reference`（`__invokeRef`）、`derefInto()` 只用一次且作用于 guest **自己的** global——"The guest's entire view of the host is `{ number, string }`. There is no object graph, so there is nothing to walk."（`:36-37`）

**但必须同时说清三点，否则会写出比原文更错的结论：**

1. **这是 PoC + 规格，不是产品。** `mobile-handoff/README.md:22` 自己写着 "Three units ship working code. Four are specifications."；`:47` 把 facets 标为 `SPEC ONLY ... not built`，`:48` 把 sandbox 标为 `working PoC`。`02-sandbox/` 自 `9e1aa8b44`（2026-08-31 一次性加入 handoff）以来**零提交**，`isolated-vm` 依赖**未安装**（该目录内无 `node_modules`）——所以**审计数字与"412 assertions"是文档转述，本仓库未经独立复现**。
2. **沙箱针对的是"从 wire 投递过来的 presentation facet"，不是 `~/.pi/agent/extensions/` 里用户自己写的 extension factory。** 判断三那条结论在 `core/extensions` 上**没有被消除**。
3. **封闭面不均匀是 spec 自认的结论**（web 不可闭）；两条真能闭合它的机制（每 facet 一个 iframe、纯声明式组件）spec 自己评估为"costs more than the problem is currently worth"（`:1578` 起）。

**解释（设计判断）**：这条轴的价值不在"pi 终于有沙箱了"，而在**它把沙箱问题问对了**——旧稿的错不在机制选型，在威胁模型（careless 作者 → hostile 远端投递）。威胁模型改对之后，机制选择（isolate vs SES vs worker）才变得可判定。用 `codebase-design` 的词汇：这是**先定 seam 的信任语义，再选 adapter**。

**severity 分层**：`core/extensions` 路径 = 不变（判断二）；facet 路径 = **未落地**（spec 有结论、PoC 有审计数据，但产品路径不存在，给不出任何运行期承诺）。

**引用限制**：引用 `02-sandbox/README.md` 的性能数字（300 组件 70/108/419 ms、"~1.8× native"、crossing 4.5 µs）时**必须标明是文档转述、未经复现**。该 README 自己还记了未闭环的限制：`isolated-vm` 的 ABI 矩阵很窄（darwin-x64 无 prebuild；`isolated-vm@7` + Node 22 落回源码构建并失败，`:103-117`）、"budgets do not nest"（外层 50 ms 预算下，被 host 回调的 guest 函数跑了 5005 ms，`:92-96`）、引用依赖懒回收（`:125-129`）。

## 影响是什么

1. **这是四条短板里最硬的一条**，因为它直接决定"开源吸纳"的上限：没有扩展级沙箱，pi 就永远到不了"npm 式随便装插件"的开放度，只能停在"装你信得过的插件"。**v0.85.1 的精确化**：这条说的是 `core/extensions` 轴；第二条轴（facet 投递）正在用 isolate 解同一个问题，但只到 spec + PoC（判断四）。
2. **与 [1.4](../01-Architecture/1.4_lifecycle_guards.md) 互为因果**：正因为无沙箱，两阶段绑定、stale 保护、fail-close 这些**进程内护栏**成了唯一防线。它们防的是"时序陷阱"和"权限钩子崩溃"，防不了"扩展主动 rm -rf / 偷 env"。
3. **评价要诚实**：不能说"pi 有 sandbox example 所以安全"。example 是"给你看怎么做"，不是"帮你做了"；同样的标准也适用于 facet 的 PoC——**PoC 有审计数据 ≠ 产品有隔离**。

## 最小例证是什么

**例证 1（无沙箱）：** 写一个扩展，`pi.on("session_start", () => require("child_process").execSync("touch /tmp/owned-by-extension"))`，放 `~/.pi/agent/extensions/` 启动 pi——文件被创建，无任何确认或隔离。证明"扩展 = 宿主进程同等权限"不是文档措辞，是物理事实。

**例证 2（沙箱是 opt-in 且沙的是工具不是代码）：** 读 `gondolin/` 的用途——它把 `bash` 工具的执行路由进 micro-VM，但扩展的 factory 代码本身仍在宿主进程跑。证明"扩展代码级沙箱"缺位，现有沙箱只覆盖"模型跑命令"这一半。

**例证 3（severity 分层）：** 对同一个扩展，走"自用"（自己写、放自己机器）和走"分发"（`pi install npm:@evil/pkg`）——前者安全、后者等于执行陌生代码，但**代码路径完全一样**（都是 `loadExtensions` 执行 factory）。证明"信任在谁装"这个模型下，分发就是信任的断裂点。

可观察信号：例证 1 → 无沙箱是事实；例证 2 → 缓解路径只覆盖一半威胁模型；例证 3 → severity 随"自用/分发"翻转。三者同成立，才能下"吸纳陌生插件这道闸是敞开的"的结论。
