# 4.7 Harness Tools：factory 模式工具架构

> **⚠️ v0.84.0**：`FileSystem` 接口新增**必需的** `renameFile()` 操作（JSONL session 的原子发布依赖同文件系统替换语义，见 [3.5 Session v4](../03-Memory/3.5_Session_v4.md)）——自定义 `ExecutionEnv`/`FileSystem` 实现必须补这个方法，否则 v0.84 编译不过。工具 factory 结构本身无变化（2026-08-17 已对照 v0.84.2 复核：目录仍为 10 文件，全部路径锚点有效；`DEFAULT_MAX_LINES`/`DEFAULT_MAX_BYTES` 截断常量为 2000 行 / 50KB）。

## 现象是什么

v0.83.0 新增了 `packages/agent/src/harness/tools/`（10 个文件），把 bash、read、write、edit 四个内置工具从 `coding-agent/src/core/tools/` 的 TUI 耦合实现，重写为纯 `AgentHarnessTool` 的 factory 函数。这些新工具不依赖 `node:fs`、不引用 React Ink、不含任何渲染组件——它们只通过 `ExecutionEnv` 抽象接口与外界交互。

## 核心矛盾

**工具需要两件事：执行能力和上下文。** 执行能力（读文件、跑 shell）是平台相关的——本地文件系统 vs Docker 容器 vs 浏览器沙箱的实现完全不同。上下文（cwd、env vars、用户身份）是每次调用都可能变化的。如果工具直接 `import { readFile } from "fs/promises"`，你就被锁死在 Node 本地文件系统上了。

pi-mono 的解法：**factory 函数 + 泛型 context + ExecutionEnv 抽象**。

## 实现思想

### Factory 模式

每个工具由一个 `create*Tool<TContext>(options?)` 函数产生，返回 `AgentHarnessTool<TContext, TParameters, TDetails>`：

```ts
createBashTool<TContext>(options?)   → AgentHarnessTool<TContext, ...>
createReadTool<TContext>(options?)   → AgentHarnessTool<TContext, ...>
createWriteTool<TContext>()          → AgentHarnessTool<TContext, ...>
createEditTool<TContext>()           → AgentHarnessTool<TContext, ...>
```

泛型 `TContext extends ExecutionToolContext` 让同一个工具定义可以被不同 harness 复用——只要 context 满足 `{ env: ExecutionEnv }` 即可。

### ExecutionEnv：平台抽象

`ExecutionEnv` 是 `FileSystem` + `Shell` 的 union（`harness/types.ts:315`），16 个 FileSystem 操作 + Shell：

- **FileSystem**：`absolutePath`、`joinPath`、`readTextFile`、`readTextLines`、`readBinaryFile`、`writeFile`、`appendFile`、`renameFile`（v0.84 新增）、`fileInfo`、`listDir`、`canonicalPath`、`exists`、`createDir`、`remove`、`createTempDir`、`createTempFile`，外加 `cleanup()`
- **Shell**：`exec(command, options)` + `cleanup()`

所有方法返回 `Result<T, Error>`（`ok | error` union），永不 throw。工具内部用 `getOrThrow()` 解包。

这意味着同一套工具代码可以跑在：
- 本地 Node 进程（标准 `ExecutionEnv` 实现）
- Docker 容器（`exec` 包装为 `docker exec`）
- 浏览器沙箱（`readFile` → OPFS, `exec` → Web Worker）

### File Mutation Queue：per-env 串行化

`write` 和 `edit` 通过 `withFileMutationQueue(env, path, fn)` 保护并发安全：

1. `WeakMap<ExecutionEnv, MutationQueueState>` — 每个 `ExecutionEnv` 实例独立的队列，env 被 GC 时队列自动清理
2. 先 resolve canonical path（async，通过 `env.canonicalPath`），再入队
3. 同路径的操作串行执行——避免 edit 读到 write 的中间状态

相比旧实现的全局 `Map<string, Promise<void>>`，新设计支持多 session/多租户场景。

### Bash 的扩展点

`createBashTool` 接受 `BashToolOptions`：
- `commandPrefix?: string` — 注入命令前缀（如 `docker exec container-id`）
- `prepare?: (execution, context, signal) => ...` — 在 exec 前改写 execution 配置

这使外部集成可以用同一个 bash tool 定义 + 不同的 commandPrefix 实现沙箱化。

## 在 Agent 能力面里的影响

- **工具定义与执行环境解耦**。同一个 tool 定义，切换 `ExecutionEnv` 即可切换执行后端。
- **context 是 per-turn 的**。harness 每轮 resolve 一次 `toolContext`，工具拿到的是当前快照。
- **concurrent bash**。v0.83.0 中 `_bashAbortController` 从单例改为 `Set<AbortController>`，支持并发 bash。

## 最小例子

用 `createReadTool` + 最小 `ExecutionEnv` 读一个文件：

```ts
const readTool = createReadTool()
const result = await readTool.execute(
  "call_1", 
  { path: "/tmp/test.txt", offset: 0, limit: 100 },
  undefined,  // signal
  undefined,  // onUpdate
  { env: myExecutionEnv }  // context
)
// result: { content: [{ type: "text", text: "..." }], details: { path, totalLines, ... } }
```

你可以观察到的信号：tool 调用完全不需要 `import "fs"` —— 它通过 `myExecutionEnv.readTextFile()` 读取，你的 `ExecutionEnv` 实现决定了文件从哪里来。
