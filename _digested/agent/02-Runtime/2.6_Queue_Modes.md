# 2.6 Queue Modes: 双队列并发控制

> **⚠️ v0.83.0**：AgentSession idle tracking 从 `_agentEventQueue` 改为 `_isAgentRunActive` + `_idleWaitPromise`；新增 `agent_settled` 事件。行号全部失效。

## 现象是什么

当用户在 Agent "正在思考"或"正在执行工具"时发送新消息，pi-mono 不会直接注入该消息，也不会丢弃。它会将消息放入 steering 或 follow-up 队列，等待合适的时机（turn 边界或 agent 完成）再注入上下文。用户会看到一条 "busy" 提示，但也可能看到 Agent 在当前 turn 结束后自动消费排队消息。

**源码位置：**
- `/packages/agent/src/types.ts`（`QueueMode`、`steering`/`followUp` 相关类型定义）
- `/packages/agent/src/agent.ts`（`Agent.steer()`、`Agent.followUp()`、`PendingMessageQueue`）
- `/packages/agent/src/agent-loop.ts`（`runLoop` 中的队列消费）

## 核心矛盾是什么

Agent 运行时的并发控制面临三个相互矛盾的需求：

1. **Busy 保护：** Agent 不能同时运行两个 prompt——这会导致状态不一致。但用户期望在 Agent 忙碌时仍然可以"说话"。
2. **时机选择：** 用户的消息有两种语义：一种是"修正当前方向"（应在当前 turn 结束后立即注入，不等 agent 完成），另一种是"追加新任务"（应等 agent 完全停止后才注入）。
3. **批量 vs 逐个：** 如果用户连续发了多条消息，是一次性全部注入（"all"），还是一次一条地逐个处理（"one-at-a-time"）？前者快但可能混淆模型，后者慢但更可控。

## 实现思想是什么

### 双队列模型

pi-mono 使用两个独立的 `PendingMessageQueue` 实例来区分两种注入语义：

| 队列 | 方法 | 注入时机 | 消费位置 |
|------|------|---------|---------|
| steering | `Agent.steer(msg)` | 当前 turn 结束后、下一 turn 开始前 | 内层循环每次迭代末尾 poll |
| followUp | `Agent.followUp(msg)` | Agent 完成所有 turn 并停止后 | 外层循环 poll |

### PendingMessageQueue 实现

`PendingMessageQueue` 是一个带 `QueueMode` 参数的内存队列：

```typescript
class PendingMessageQueue {
  private messages: AgentMessage[] = [];
  constructor(public mode: QueueMode) {}

  enqueue(message: AgentMessage): void { this.messages.push(message); }
  hasItems(): boolean { return this.messages.length > 0; }

  drain(): AgentMessage[] {
    if (this.mode === "all") {
      // 一次性取出所有消息
      const drained = this.messages.slice();
      this.messages = [];
      return drained;
    }
    // "one-at-a-time": 只取第一条
    const first = this.messages[0];
    if (!first) return [];
    this.messages = this.messages.slice(1);
    return [first];
  }
}
```

默认模式：steering 为 `"one-at-a-time"`，followUp 也为 `"one-at-a-time"`。这意味着默认情况下每个 turn 最多注入一条排队消息，给予模型逐条处理的空间。

### 在双层循环中的消费

回顾 2.1 中的双层循环，队列在以下位置被消费：

```
外层 while(true):
  内层 while(hasMoreToolCalls || pendingMessages > 0):
    turn_start
    注入 pendingMessages (来自 steering 或 followUp)
    streamAssistantResponse()
    executeToolCalls()
    turn_end
    → pendingMessages = getSteeringMessages()  // 消费 steering 队列
  → followUpMessages = getFollowUpMessages()     // 消费 followUp 队列
  → 如果有 followUp: pendingMessages = followUpMessages; continue 外层
  → 否则: break, emit agent_end
```

注意：`getSteeringMessages` 在内层循环**每次迭代后**都被 poll，`getFollowUpMessages` 只在**内层循环完全结束**后才被 poll。

### SingleFlight / Busy Gate

`Agent.prompt()` 和 `Agent.continue()` 都检查 `this.activeRun`：

```typescript
async prompt(input: string | AgentMessage | AgentMessage[]): Promise<void> {
  if (this.activeRun) {
    throw new Error(
      "Agent is already processing a prompt. " +
      "Use steer() or followUp() to queue messages, or wait for completion."
    );
  }
  // ...
}
```

这意味着：
- 任何时候只有一个 run 在活跃。
- 如果 Agent 正在运行，`prompt()` 会 throw，迫使调用方使用 `steer()` 或 `followUp()`。
- `continue()` 在遇到最后一条消息是 `assistant` 时，会先尝试消费 steering/followUp 队列，只有在无排队消息时才 throw。

### 流式交互中的特殊处理

当用户在 Agent 正在流式输出（`isStreaming === true`）时发送消息，coding-agent 层的逻辑会：
- 如果配置为使用 steering：将消息放入 steering 队列（`Agent.steer(msg)`）
- 如果配置为使用 followUp：将消息放入 followUp 队列（`Agent.followUp(msg)`）

这里涉及配置决策：对大多数交互，使用 steering 让消息在当前 turn 后被处理更自然；但对于某些场景（如用户想先看完整回答再追加任务），followUp 更合适。

## 在 Agent 能力面里的影响是什么

- **迭代式对话：** 用户可以在 Agent 执行长工具链时"中途说话"（steer），而不需要等待 Agent 完全停止。Agent 会在当前 turn 结束后读入 steering 消息。
- **批量处理控制：** `QueueMode.all` 适用于"用户粘贴了一段多行内容，可以一次性处理"；`QueueMode.one-at-a-time` 适用于"用户边看边补充，逐句处理更安全"。
- **并发安全：** SingleFlight 模式保证了 Agent 状态的完整性——不可能出现两个 prompt 同时修改 `messages` 数组。
- **流式响应中的交互：** 当模型正在流式输出时，用户消息可以排队到 followUp，等当前回答完整显示后再处理。

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent";

const agent = new Agent({
  initialModel: claudeSonnet,
  tools: [readTool, writeTool, bashTool],
  systemPrompt: "You are a coding assistant.",
  steeringMode: "one-at-a-time",  // 默认模式
  followUpMode: "one-at-a-time",  // 默认模式
});

// 启动第一个 prompt
agent.prompt("Write a Python script that processes CSV files")
  .catch(err => console.error(err));

// Agent 正在执行工具...此时用户发送修正指令
agent.steer({
  role: "user",
  content: "Actually, make it process JSON instead of CSV",
  timestamp: Date.now(),
});
// → 消息进入 steering 队列
// → 当前 turn 结束后 poll，注入到上下文
// → Agent 在下一个 turn 会读到 "Actually, make it process JSON"

// Agent 仍在运行，用户再发一条
agent.steer({
  role: "user",
  content: "Also add error handling",
  timestamp: Date.now(),
});
// → 因为 mode 是 "one-at-a-time"，这条消息要等再下一个 turn

// 如果尝试 prompt() 而 agent 正在运行
try {
  await agent.prompt("Add logging"); // throw!
} catch (e) {
  // "Agent is already processing a prompt"
  // 只能用 steer() 或 followUp()
}

// Agent 完成所有 tool call 后
// followUp 中的消息会触发外层循环的新一轮
agent.followUp({
  role: "user",
  content: "Now write tests for the script",
  timestamp: Date.now(),
});
await agent.continue(); // 消费 followUp 队列，继续 run

// 检查是否有排队消息
if (agent.hasQueuedMessages()) {
  console.log("还有消息等待处理");
}
```

这个例子展示了：`prompt()` 的 busy gate 保护 → `steer()` 在当前 turn 后注入 → `followUp()` 在 agent 停止后触发新一轮 → `QueueMode` 控制注入频率。
