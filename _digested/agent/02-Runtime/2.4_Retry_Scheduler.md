# 2.4 Retry Scheduler: 双层重试调度

> **⚠️ v0.83.0**：`agent_end`→`agent_settled`；新增 summarization retry（`summarization_retry_scheduled/attempt_start/finished`），独立于 agent turn retry。行号全部失效。

## 现象是什么

当 LLM API 返回 "overloaded_error"、"rate limit exceeded"、502、503 等错误时，pi-mono 会自动等待一段时间后重试，用户会看到 "auto_retry_start" 和 "auto_retry_end" 事件。重试行为在两个层次独立运作：pi-ai 的 provider 级别（HTTP 层面的客户端重试）和 coding-agent 的 AgentSession 级别（Agent 生命周期层面的可重试错误处理）。

**源码位置：**
- `/packages/ai/src/stream.ts`（StreamOptions 中的 maxRetries / maxRetryDelayMs）
- `/packages/coding-agent/src/core/agent-session.ts`（`_handleRetryableError`、`_isRetryableError`、`autoRetryEnabled`）

## 核心矛盾是什么

两个层次的重试有不同的语义和范围：

- **Provider 级重试（pi-ai）：** 发生在单次 HTTP 请求层面。SDK（如 `@anthropic-ai/sdk`、`openai`）自带重试逻辑，pi-ai 通过 `maxRetries` 和 `maxRetryDelayMs` 控制。这种重试对上层 Agent Runtime 是透明的——重试发生在流开始产生事件之前。
- **Agent 级重试（coding-agent）：** 发生在 Agent 完成一个完整回合（`agent_end`）之后。此时 AgentSession 检查最后一个 AssistantMessage 是否为"可重试错误"，如果是，则移除该错误消息、等待指数退避、通过 `agent.continue()` 重新进入 loop。

两种重试需要协调：
- Provider 级重试不应掩盖本应由 Agent 级处理的错误（如 context overflow 不应重试，应触发 compaction）。
- Agent 级重试需要可中断（用户可能在等待重试期间 abort）。
- 重试不能无限进行：`maxRetries` 在两层都是硬限制。

## 实现思想是什么

### Provider 级重试

在 `StreamOptions` 中定义：

```typescript
interface StreamOptions {
  maxRetries?: number;        // 最大重试次数，默认 2（SDK 默认）
  maxRetryDelayMs?: number;   // 重试延迟上限，默认 60000ms
}
```

这些参数直接传递给 SDK（Anthropic SDK 的 `maxRetries`，OpenAI SDK 的 `maxRetries` 等）。`maxRetryDelayMs` 的语义是：如果服务端返回的 Retry-After 超过此值，立即失败而非等待，让上层 Agent 级重试来处理。

### Agent 级重试

AgentSession 的核心重试逻辑在 `_handleAgentEvent` 的 `agent_end` 分支中：

```
agent_end 事件到达
  → 检查消息是否为可重试错误 (_isRetryableError)
    → 排除 context overflow (应触发 compaction)
    → 匹配 overloaded / rate limit / 5xx / network error / timeout 等正则
  → 如果可重试且 autoRetry.enabled:
    → _retryAttempt++
    → 如果 _retryAttempt > maxRetries: 放弃，emit auto_retry_end(success: false)
    → 否则:
      → emit auto_retry_start (包含 attempt, maxAttempts, delayMs)
      → 从 agent state 中移除最后一条错误消息
      → sleep(delayMs = baseDelayMs * 2^(attempt-1))  // 指数退避
      → setTimeout 中调用 agent.continue() → 重新进入 loop
```

关键设计点：

1. **可重试错误的判定**（`_isRetryableError`）：通过正则匹配 `errorMessage`。覆盖的场景包括 `overloaded_error`、`rate limit`、429/500/502/503/504、`service unavailable`、`network error`、`connection lost`、`websocket closed`、`fetch failed`、`timeout` 等。**明确排除 context overflow**（由 compaction 处理）。

2. **`autoRetry: false` 关闭：** 通过 SettingsManager 的 `autoRetry` 设置控制。当 disabled 时，可重试错误直接失败，不发起重试。

3. **错误消息的清理：** 在发起重试前，最后一条 error 类型的 assistant 消息从 `agent.state.messages` 中移除。Agent 的 state 保持干净，`continue()` 从上一个有效状态继续。

4. **重试期间的 abort：** `_retryAbortController` 允许在退避等待期间取消重试。`abortRetry()` 方法 abort 该 controller，触发 sleep 的 catch 分支，emit `auto_retry_end(success: false)`。

5. **重试成功的重置：** 当 `message_end` 事件到达且 `stopReason !== "error"` 时，`_retryAttempt` 立即重置为 0，emit `auto_retry_end(success: true)`。

### 两层重试的协调

Provider 级重试先发生（因为它在单个 HTTP 请求的上下文中）。当 Provider 的重试也耗尽时，SDK 抛出的错误被转换成 `stopReason: "error"` 的 AssistantMessage，然后 Agent 级重试接管。

当 `maxRetryDelayMs` 限制了 SDK 的等待时间时，即使 SDK 本可以继续等待，也会让 Agent 级重试来处理更长的退避周期。这种设计让上层有更大的控制权（例如显示"正在重试，第 3 次..."的 UI 提示）。

## 在 Agent 能力面里的影响是什么

- **对用户透明的恢复：** 瞬态错误（如服务暂时过载）在几秒内自动恢复，用户感知到的只是短暂的 "busy" 状态。
- **可观测性：** `auto_retry_start/end` 事件让 UI 层可以展示重试进度（"第 2 次重试，等待 5 秒..."）。
- **可取消性：** 用户可以在重试等待期间 abort，不会留下损坏的 Agent 状态。
- **与 compaction 的分工：** Context overflow 走 compaction 路径（压缩 → retry），overloaded/rate-limit 走 retry 路径，不会混淆。

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent";

const agent = new Agent({
  initialModel: claudeSonnet,
  tools: [readTool],
  systemPrompt: "You are a file reader.",
  // Provider 级重试通过 stream options 控制
  maxRetries: 2,
  maxRetryDelayMs: 30000,
});

// 监听重试事件（coding-agent 级别）
agentSession.onEvent((event) => {
  switch (event.type) {
    case "auto_retry_start":
      console.log(
        `[重试] 第 ${event.attempt}/${event.maxAttempts} 次，` +
        `等待 ${event.delayMs}ms，原因: ${event.errorMessage}`
      );
      break;
    case "auto_retry_end":
      if (event.success) {
        console.log("[重试] 成功恢复");
      } else {
        console.log(`[重试] 失败，最终错误: ${event.finalError}`);
      }
      break;
  }
});

// 如果 API 返回 overloaded_error:
// → provider SDK 先尝试 maxRetries=2 次 HTTP 重试
// → 如果全部失败 → agent_end 携带 error
// → _isRetryableError 匹配 "overloaded"
// → 指数退避 sleep → agent.continue() 重新进入 loop
// → 如果 continue 成功 → 对用户透明地恢复

// 用户也可以在重试过程中取消
// agentSession.abortRetry(); // 取消退避等待，停止重试
```

这个例子展示了双层重试的工作流：Provider 级重试对上层透明，Agent 级重试提供用户可见的进度和可取消性。
