# 4.4 Extension Runner：独立模块的加载与事件分发

> **⚠️ v0.83.0**：`extensions/runner.ts`(19 commits)。新增 `emitProjectTrustEvent()`、`getEntryRenderer()`、`getModelRegistry()`；native provider registration pipeline（`pendingNativeProviderRegistrations`）；`setUIContext` 现在接收 `mode` 参数。行号全部失效。

## 现象是什么

pi-mono 支持 extension 系统：用户或第三方可以把 TypeScript/JavaScript 文件放到特定目录，扩展会自动加载。Extension 可以注册 LLM 可调用的 tools、注册 slash commands、监听 agent 生命周期事件、注册键盘快捷键和 CLI flags、与 UI 交互、注册自定义 LLM providers。

从用户角度看：放一个 `.ts` 文件到 `.pi/extensions/`，重启或 `/reload`，新功能就生效了。

## 核心矛盾是什么

Extension 系统面临几个矛盾：

1. **运行时隔离**：extension 是用户写的 TS 代码，可以 import npm 包。但在 Bun binary 模式下，文件系统上的 npm 包不可用——必须在编译时静态打包进 binary，然后在运行时通过 virtual modules 暴露
2. **事件安全**：一个 extension 的 handler 崩溃不应该影响其他 extension 或宿主进程
3. **生命周期复杂**：extension 的 load → init → bind → event loop → shutdown 跨越多个系统组件
4. **UI 可用性未知**：extension 不知道自己运行在 TUI、RPC 还是 print mode，UI 方法可能是 no-op
5. **并发注册冲突**：多个 extension 可能注册同名 command、同名 shortcut、同名 tool

## 实现思想是什么

### 加载器（loader.ts）

**三步加载流程：**

1. **路径发现**：`discoverAndLoadExtensions()` 从三个来源收集 extension 路径：
   - Project-local：`{cwd}/.pi/extensions/`
   - Global：`{agentDir}/extensions/`
   - Configured：显式配置的路径

2. **模块编译**：用 `jiti`（即时编译）加载 TypeScript 模块
   - Node.js 模式：通过 `alias` 选项把 `@earendil-works/pi-*` 解析到 workspace 中对应包的 dist 文件
   - Bun binary 模式：通过 `virtualModules` 选项把预打包的模块直接注入，绕过文件系统解析。`tryNative: false` 确保 jiti 处理所有 import

3. **Factory 调用**：每个 extension 必须 `export default function(api: ExtensionAPI)`，这个函数通过 `createExtensionAPI()` 拿到注册 API，注册 handlers/tools/commands/shortcuts/flags

**Virtual modules**（Bun binary 下的关键设计）：

```typescript
const VIRTUAL_MODULES = {
  typebox: _bundledTypebox,
  "@earendil-works/pi-agent-core": _bundledPiAgentCore,
  "@earendil-works/pi-tui": _bundledPiTui,
  "@earendil-works/pi-ai": _bundledPiAi,
  "@earendil-works/pi-coding-agent": _bundledPiCodingAgent,
  // 同时支持新旧两种 package name
  "@mariozechner/pi-agent-core": _bundledPiAgentCore,
  // ...
};
```

这些模块在编译 Bun binary 时被静态 import（保证被 bundler 包含），然后在运行时通过 virtual modules 暴露给 jiti 加载的 extension 代码。

**扩展包发现（package.json manifest）：**

```json
{
  "pi": {
    "extensions": ["./dist/extension.js"],
    "themes": ["./themes/dark.json"],
    "skills": ["./skills/"],
    "prompts": ["./prompts/"]
  }
}
```

如果一个目录包含 `package.json`，loader 会先检查其中的 `pi.extensions` 字段。这允许 npm 包作为 extension 分发。

### 运行时（runner.ts）

**ExtensionRunner 的生命周期：**

```
loadExtensions() → createExtensionRunner() → bindCore() → bindCommandContext() → setUIContext()
                         ↓
                    event loop（emit* 方法被调用）
                         ↓
                    invalidate() → shutdown()
```

**bindCore() 的作用：**

`bindCore()` 把宿主进程的实际能力绑定到 extension runtime 上：
- `sendMessage`、`sendUserMessage`：发送消息
- `setModel`、`setThinkingLevel`：控制模型
- `getActiveTools`、`setActiveTools`：控制工具
- `registerProvider`、`unregisterProvider`：注册 LLM provider
- context actions：`getModel`、`isIdle`、`getSignal`、`abort`、`compact`、`shutdown` 等

在 `bindCore()` 之前，runtime 的所有 action 方法都是 throwing stubs（防止 extension 在 loading 阶段调用未初始化的方法）。

**事件分发机制：**

ExtensionRunner 有多个 `emit*()` 方法，每个处理特定类型的事件，按 extension 加载顺序依次调用 handler：

| emit 方法 | 处理的事件 | 特殊行为 |
|---|---|---|
| `emit()` | 通用事件（除特殊事件外） | `session_before_*` 事件支持 cancel 短路 |
| `emitMessageEnd()` | `message_end` | handler 可返回修改后的 message（pipeline 修改） |
| `emitToolCall()` | `tool_call` | 第一个 block 结果即短路，不执行后续 handler |
| `emitToolResult()` | `tool_result` | handler 可部分覆盖 result 字段 |
| `emitContext()` | `context` | handler 可替换整个 messages 数组 |
| `emitBeforeProviderRequest()` | `before_provider_request` | handler 可修改 provider payload |
| `emitBeforeAgentStart()` | `before_agent_start` | handler 可注入 messages 和修改 system prompt |
| `emitResourcesDiscover()` | `resources_discover` | 收集 skill/prompt/theme 路径 |
| `emitInput()` | `input` | transform chain，`handled` 短路，`continue` 放行 |
| `emitUserBash()` | `user_bash` | 第一个非空结果作为 handler 结果 |

**错误隔离：**

所有 `emit*()` 方法中的 handler 调用都包裹在 try-catch 中。如果 handler 抛出异常：
- 错误被包装为 `ExtensionError`（包含 `extensionPath`、`event`、`error`、`stack`）
- 通过 `emitError()` 通知 error listeners
- 对其他 extension 没有影响（继续执行后续 handler）

但有一个例外：如果 handler 抛出的错误是 `AgentHarnessError` 且 code 是 `"hook"`，则在 AgentHarness 层会向上传播并中断操作。

**Tool call 的 block 机制：**

`emitToolCall()` 的特殊之处在于：只要任何一个 extension 的 handler 返回 `{ block: true }`，后续 handler 不会被调用。这是一个 fail-close 的安全设计——权限检查者优先。

**Context 创建**

ExtensionRunner 通过 `createContext()` 创建 `ExtensionContext` 对象，提供给 handler 使用。Context 的属性通过 getter 懒求值，确保每次访问都拿到最新状态：

```typescript
createContext(): ExtensionContext {
  return {
    get model() { return getModel(); },    // 懒求值
    isIdle: () => this.isIdleFn(),         // 方法也是懒绑定
    get ui() { return this.uiContext; },   // UI 可用性懒查
    // ...
  };
}
```

同时，`assertActive()` 方法在每次访问时检查 extension 是否已失效（session 被替换、reload 等），如果失效则抛出明确的错误信息，防止使用 stale context。

**UI 不可用时的处理：**

ExtensionRunner 初始化时 `uiContext` 设为 `noOpUIContext`，所有 UI 方法都是 no-op：
- `select()` 返回 `undefined`
- `confirm()` 返回 `false`
- `input()` 返回 `undefined`
- `notify()` 是空函数
- `setEditorText()`、`getEditorText()` 等也是 no-op

当宿主有 UI（如 interactive TUI mode）时，通过 `setUIContext()` 注入真正的 UI 实现。

### Provider 注册

Extension 可以在运行时注册自定义 LLM provider：

```typescript
api.registerProvider("my-custom-provider", {
  modelIds: ["model-a", "model-b"],
  contextWindow: 128000,
  // ... provider config
});
```

- 加载阶段的注册会被放入 `pendingProviderRegistrations` 队列
- `bindCore()` 时 flush 队列到 ModelRegistry
- `bindCore()` 后，注册立即生效（不需要 `/reload`）

### 事件总线（EventBus）

Extension 可以通过 `api.events` 获取 `EventBus` 实例：

```typescript
api.events.emit("custom:my-event", { data: "hello" });
api.events.on("custom:my-event", (payload) => { ... });
```

`createEventBus()` 提供一个简单的发布/订阅机制，用于 extension 之间的通信。关键行为：
- 同步 emit，同步/异步 handler 都支持
- handler 异常会被 catch 并 console.warn，不传播
- 每个 extension 有自己独立的 EventBus（通过 `createExtensionAPI` 绑定）

## 在 Agent 能力面里的影响是什么

1. **Extension 是 pi-mono 最高级的能力扩展机制**。几乎任何运行时行为都可以被 extension 修改或增强。

2. **工具（tools）不再是硬编码的**。Extension 可以注册 LLM 可调用的工具，这些工具和内置工具（bash、edit 等）同权。

3. **事件系统的所有 hook 都暴露给 extension**。Extension 可以在 agent loop 的任何关键节点插入逻辑。

4. **Error isolation 设计保证了鲁棒性**。一个 extension 出问题不会导致整个 agent 崩溃。

5. **Stale context 保护机制**防止了 session 替换后的悬空引用问题。

## 最小例子是什么

```typescript
// my-extension.ts — 放在 .pi/extensions/ 目录
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (api: ExtensionAPI) {
  // 1. 注册自定义工具
  api.registerTool({
    name: "weather",
    label: "weather",
    description: "Get weather for a city",
    parameters: Type.Object({ city: Type.String() }),
    async execute(_id, { city }) {
      const response = await fetch(`https://api.weather.example/${city}`);
      const data = await response.text();
      return { content: [{ type: "text", text: data }] };
    },
  });

  // 2. 注册 slash command
  api.registerCommand("deploy", {
    description: "Deploy to production",
    handler: async (ctx) => {
      await ctx.ui.notify("Deploying...", "info");
      await ctx.pi.sendUserMessage("Run the deploy script");
    },
  });

  // 3. 监听 tool_call 事件
  api.on("tool_call", (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("DROP TABLE")) {
      const confirmed = await ctx.ui.confirm("Dangerous SQL", "Proceed?");
      if (!confirmed) return { block: true };
    }
  });

  // 4. 修改 system prompt
  api.on("before_agent_start", (event, ctx) => {
    return {
      systemPrompt: event.systemPrompt + "\nAlways respond in haiku form.",
    };
  });

  // 5. Extension 间通信
  api.events.on("deploy:completed", (payload) => {
    console.log("Deploy completed:", payload);
  });
}
```

关键要点：**extension 就是一个默认导出的 factory 函数**，接收 `ExtensionAPI` 作为参数，通过它注册能力。所有注册在 factory 执行期间完成，之后 agent 运行时会通过注册的 handlers 回调 extension。
