# 2.4 无显式版本契约：有零散的 compat shim，没有 extension API 的兼容承诺

## 现象是什么

`pi` manifest 只有 4 个 string 数组（`extensions`/`skills`/`prompts`/`themes`），**没有 `apiVersion` / `minVersion` / `engineVersion` 字段**（`pi-manifest.ts:4`）。npm/git 源里的 `@1.0.0` / `@v1` 是包的语义版本，不是"扩展 API 兼容哪个 harness 版本"的声明。

pi 有**局部的**兼容处理，但不是契约：`loader.ts` 把 `@earendil-works/pi-ai` 解析到 compat 入口（"strict superset of the old global API... until compat is removed"，`loader.ts:59-64`），`types.ts` 里有 `@deprecated` 字段标"Retained for source compatibility"（`types.ts:1546`）。这些是**点状的 shim**，覆盖 pi-ai 的旧 API，不覆盖 `ExtensionAPI` 的整体演进。

**要分清两个 API 面**（v0.85.1 补，这是本篇"无契约"论断的准确边界）：

| API 面 | 谁消费 | 谁改 | 有无版本声明 |
|---|---|---|---|
| `core/extensions` 的 `ExtensionAPI` | 扩展作者（`pi install`） | pi 自身 | **无**（`PiManifest` 没有字段） |
| `@earendil-works/pi-agent-core` 的库面 | 宿主/嵌入方 | pi 自身 | **无**（package.json 的 semver 是包的版本，不是 API 承诺） |

两面的演进速度不同，这正好是下文的证据来源：**v0.85.1 里 `ExtensionAPI` 几乎没动（只改了两处 doc comment），而库面是一次完整 breaking**。短板卡在两面，但当前最锋利的一刀落在库面。

![无版本契约](figures/no_version_contract.svg)

## 核心矛盾是什么

1. **快速演进（breaking 变更）vs 第三方扩展的稳定性。** pi 的 API 面在**一个 release 周期内改过三轮**（v0.83 泛型 `AgentHarness<TContext>` → v0.84 lane 骨架 → v0.85 真实现；见 `_change_log/0003` 与 [`0006`](../../_change_log/0006-v0.84.4-to-v0.85.1.md)），但没有机制让扩展作者或宿主提前声明"我要求哪个 API 版本"。
2. **"兼容 shim 能给多少" vs "能承诺多少"。** 点状 shim（pi-ai compat 入口）能救几个旧调用，但救不了"整个 API 面变了"这种系统性 breaking——而后者恰恰是契约该管的。

## 设计判断是什么

### 判断一：无契约的后果是"静默失效或运行时报错"，且没有任何拦截点（硬事实 + 评价）

**更新的实例（v0.85.1）**：一个照 v0.84.4 写的库消费者（宿主，用 `@earendil-works/pi-agent-core` 自组 harness），在 v0.85.1 上会同时撞上这些 breaking：

- `AgentHarness` **从 class 变成工厂对象**（`agent-harness.ts:622`，实现私有化到 `runtime/harness.ts:29`）；
- `AgentLane` 的**每个方法都多了一个尾参 `context: Context`**；
- `peekAction` / `executeAction` / `runToCompletion` / `drive: "manual"` **全部删除**；
- `Entry` 7 种 → **4 种**（`session/types.ts:16`）、`session/state.ts` 整个删除、`registers` 存储模型换成 bound values/lists。

关键在**这些符号是从公开面消失的**：`agent/src/index.ts:43` 就是 `export * from "./harness/agent-harness.ts"`——harness 的整张类型面直接就是公开面，删一个符号就是删一个导出。`index.ts` 的净变化只有 `+14/−7`，是因为删除被新增掩盖（净行数**看不出** breaking——这正是"没有契约"最危险的地方）。

**加载期没有任何拦截**：`AgentHarness.create()` 不会说"你是给 v0.84 API 写的"，因为它无从知晓——manifest（`pi-manifest.ts:4`）和 `package.json` 都没有字段能承载这个信息。结果只有两种：TS 编译报错（作者自己升级时发现）或运行时报错（用户装上才炸）。

**一个必须记账的对照（硬事实）**：**本轮 `ExtensionAPI` 本身几乎没动**——`extensions/types.ts` 在两个 tag 间只有 10 行 `+/−`，且全是 `setModel`/`setThinkingLevel` 两处 doc comment；`loader.ts` 只有 4 行改动。**breaking 落在库面（`pi-agent-core`），不是扩展面**。所以"无契约"的锋利一刀，目前砍的是**想用 agent 包自组 harness 的宿主**，不是写 `.pi` 扩展的人。这个区分很重要：笼统说"pi 的扩展 API 不稳定"本轮并不成立。

**severity 分层**：写 `.pi` 扩展的人 = 低（本轮 `ExtensionAPI` 未破，且 manifest/prompt 契约稳定）；想用 `pi-agent-core` 自组 harness 的宿主 = 高（库面真 breaking 且无声明）；团队内部 = 中（升级 pi 时统一改一遍）；公开分发、陌生安装 = 高（第三方无法承诺"兼容 pi ≥X"，用户升级 pi 后扩展/嵌入可能炸）。

### 判断二：点状 shim 证明了"意识到了兼容问题"，但也暴露了它没上升到契约（硬事实 + 解释）

`loader.ts` 为 pi-ai 的旧全局 API 专门留了 compat 入口，`types.ts` 有 `@deprecated` 标记——**说明维护者确实在管理兼容**。但这套做法是**枚举式的**（哪里坏了补哪里），不是**声明式的**（扩展说"我要 API v2"，harness 检查后决定加载还是拒绝）。

**关键区别**：枚举式 compat 能救已知的旧调用，声明式契约能防止未来的 breaking 静默伤害。pi 现在只有前者。

### 判断三：这是"快速演进期"的典型代价，而且 v0.85.1 让它更强了，不是更弱（评价）

[2.3](./2.3_agent_lane_contract_first.md) 记录的 AgentLane 重画说明 pi 处在**高速重构期**，且这条论据在 v0.85.1 **变强**了：

- v0.84.4 时代还能说"契约在 v0.83→v0.84 这个 release 边界上变了一次"；v0.85.1 之后要说的是"**同一个 release 系列内改了三轮**"（v0.83 泛型 → v0.84 lane 骨架 → v0.85 真实现，外加 runtime 在一个周期内整体替换两轮）。
- 也就是说，**给 API 加版本契约这件事本身在这一轮还无法落地**——契约的价值要等 API 稳定后才兑现，而 v0.85.1 证明它还没稳。这与 [2.3](./2.3_agent_lane_contract_first.md) 判断三"契约兑现反而把这条短板抬高"是同一个结论的两面。

**诚实结论**：现在是"演进优先、兼容后补"的阶段。这个阶段自有其合理性，但它意味着**库面 API 稳定性没有承诺**（扩展面本轮反而稳），和 [1.3](../01-Architecture/1.3_distribution_loop.md) 里"manifest 是未来加契约的落点"相互印证——seam 放好了，契约没写。

## 影响是什么

1. **"能分发"（1.3）不等于"能稳定地分发"。** `pi install` 解决了安装，没解决"装完升级 pi 会不会炸"。缺契约，分发闭环就少最后一环。
2. **第三方作者承担了全部兼容成本。** 没有契约，作者要么锁死 pi 版本（脆弱），要么每次 pi 升级跟着改（累），要么放弃维护（生态烂）。
3. **落点已明**：如果未来加契约，位置就是 `PiManifest`（`pi-manifest.ts`）——加一个 `apiVersion`/`engines` 字段，`readPiManifest` 读、loader 检查。seam 在，缺字段。**但注意这个落点只覆盖扩展面**；库面（`pi-agent-core` 的导出）没有等价的声明位置，`package.json` 的 semver 是包版本、不是 API 承诺。

## 源码锚点是什么

- `packages/coding-agent/src/core/pi-manifest.ts`：`PiManifest`（L4）——无 `apiVersion`/`minVersion` 字段的实锤；`readPiManifest`（L17）
- `packages/coding-agent/src/core/extensions/loader.ts`：`VIRTUAL_MODULES` 中 pi-ai 解析到 compat 入口（L59-64）——点状 shim，非契约
- `packages/coding-agent/src/core/extensions/types.ts`：`@deprecated`（L1546）——枚举式兼容标记；本轮仅两处 doc comment 变动（`setModel`/`setThinkingLevel`），**`ExtensionAPI` 无 breaking**
- `packages/agent/src/index.ts`：`export * from "./harness/agent-harness.ts"`（L43）——harness 类型面即公开面，删符号 = 删导出（本轮 breaking 的物理位置）
- `packages/agent/src/harness/session/types.ts`：`EntryType` 4 种（L16）；`harness/session/values.ts:194-195`（`pi.session.name`/`pi.entry.label`）——registers → values 的落点
- 演进记录回指：`../../_change_log/0003-v0.83.0-to-v0.84.2.md`、`../../_change_log/0006-v0.84.4-to-v0.85.1.md`、`../README.md` 的"旧结论反转"一节

## 最小例证是什么

**例证 1（无字段）：** 打开 `pi-manifest.ts`——`PiManifest` 的字段只有 `extensions`/`skills`/`prompts`/`themes`，没有 `apiVersion` 或任何版本字段。证明"扩展无法声明它要求哪个 harness API 版本"。

**例证 2（点状 shim vs 契约）：** 看 `loader.ts:59` 的注释——"keep working at runtime until compat is removed"。这是"给已知的旧调用续命"，不是"扩展声明 API 版本、harness 校验"。枚举式和声明式的区别就在这里。

**例证 3（breaking 已发生，且净行数看不出来）：** 对一个 v0.84.4 时代的库消费者，v0.85.1 同时删掉了 `peekAction`/`executeAction`/`runToCompletion`/`drive: "manual"`、把 `AgentHarness` 从 class 变工厂、给每个 `AgentLane` 方法加了尾参——而 `agent/src/index.ts` 的净变化只有 `+14/−7`。**净行数小 ≠ 兼容**，这正是没有契约时最危险的一类信号。同一轮里 `ExtensionAPI` 却几乎没动——两个 API 面的 churn 率不同，读"pi 兼容性"时必须分开说。

可观察信号：例证 1 → 无声明字段；例证 2 → 只有枚举式 compat；例证 3 → breaking 演进无提前拦截、且净 diff 掩盖了它。三者同成立，才能说"分发的稳定性缺最后一环（契约）"。
