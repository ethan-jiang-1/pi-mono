## 现象是什么

pi-mono 的会话不是一个简单的消息列表，而是一个 append-only 的树形结构（硬事实）。用户可以随时从历史中的任意一点"分叉"出一个新的对话分支，在不同的分支间导航，也可以在分支之间跳转时自动生成分支摘要（硬事实）。所有这些能力都建立在一个统一的 Session tree 模型之上。

**源码位置：**
- `/packages/coding-agent/src/core/session-manager.ts`（SessionEntry 树模型、JSONL 存储实现、`buildSessionContext()`、迁移逻辑）
- `/packages/coding-agent/src/core/messages.ts`（compactionSummary / branchSummary / custom 消息类型与工厂）
- `/packages/agent/src/harness/session/`（agent 包的 session v4，lane-based，是另一套存储体系，见 3.5）

## 核心矛盾是什么

一个可导航、可分叉的对话系统必须解决三个矛盾（解释）：

1. **追加 vs 修改：** 对话历史一旦产生就不应被修改（append-only），但用户需要"回到之前的状态"的能力。不能靠删除消息来实现导航，必须在旧分支上追加新节点（解释）。

2. **存储 vs 重建：** 树形结构在磁盘上需要高效的序列化格式（JSONL），但在内存中需要支持从任意节点到 root 的路径遍历以构建 LLM 上下文（解释）。

3. **状态追踪 vs 表达力：** 对话中的状态变化（模型切换、thinking level 变更、compaction 事件）需要像消息一样被记录在树中，但它们不是 LLM 可消费的消息，需要在上下文重建时特殊处理（硬事实）。

## 实现思想是什么

### 核心数据结构

Session tree 由 `SessionEntry` 的 discriminated union 组成（session-manager.ts:144-153），每个 entry 都有 `id`、`parentId`、`timestamp`：

```typescript
type SessionEntry =
  | SessionMessageEntry       // type: "message" — 用户/助理/工具结果消息
  | ThinkingLevelChangeEntry  // type: "thinking_level_change" — 推理等级切换
  | ModelChangeEntry          // type: "model_change" — 模型切换
  | CompactionEntry           // type: "compaction" — 上下文压缩点（summary, firstKeptEntryId, tokensBefore, 可选 details/usage/fromHook；无 retainedTail）
  | BranchSummaryEntry        // type: "branch_summary" — 分支摘要（fromId, summary）
  | CustomEntry               // type: "custom" — 扩展自定义数据（不进入 LLM 上下文）
  | CustomMessageEntry        // type: "custom_message" — 扩展自定义消息（进入 LLM 上下文）
  | LabelEntry                // type: "label" — 用户标签/书签（targetId + label，label 为空即清除）
  | SessionInfoEntry          // type: "session_info" — 会话元数据（如名称）
```

注意：**没有 "leaf" entry 类型**——当前活动指针是 `SessionManager` 的内存字段 `leafId: string | null`（session-manager.ts:866），不落盘（硬事实）。`_buildIndex()` 把 leaf 重放为文件中最后一个 entry；`branch()`/`resetLeaf()` 只改内存指针，因此"导航"不产生任何磁盘写入（硬事实）。

每个 `SessionMessageEntry` 包含一个 `AgentMessage`（pi-mono 的超集消息类型，支持 `bashExecution`、`branchSummary`、`compactionSummary`、`custom` 等额外 role）。

### SessionManager 的 API

`SessionManager` 是自包含的树 + 存储实现（不实现任何外部 `SessionStorage` 接口）（硬事实），通过静态工厂构造：`create`（新会话）/ `open`（指定文件）/ `continueRecent`（最近会话）/ `inMemory`（`persist=false`，不落盘）/ `forkFrom`（跨项目 fork）。核心方法：

| 方法 | 作用 |
|------|------|
| `getBranch(fromId?)` | 从给定节点（默认 leaf）走到 root，返回 root→leaf 顺序的所有 entry |
| `buildContextEntries()` | compaction 感知的 entry 列表（渲染用） |
| `buildSessionContext()` | 重建 LLM 可消费的 `{messages, thinkingLevel, model}` |
| `getTree()` | 防御性拷贝的树结构（带解析后的 label），供 UI 导航 |
| `appendMessage(msg)` | 在 leaf 下追加一条消息节点（禁止直接追加 compactionSummary/branchSummary 消息） |
| `appendModelChange(provider, modelId)` / `appendThinkingLevelChange(level)` | 追加状态切换节点 |
| `appendCompaction(summary, firstKeptEntryId, tokensBefore, details?, fromHook?, usage?)`（session-manager.ts:1097） | 追加压缩节点（coding-agent 侧仍是 firstKeptEntryId 语义，与 agent 包 harness 的 retainedTail 不同，见 3.1）（推测） |
| `appendCustomEntry(customType, data?)` | 扩展自定义数据（不进入 LLM 上下文） |
| `appendCustomMessageEntry(customType, content, display, details?)` | 扩展自定义消息（进入 LLM 上下文） |
| `appendLabelChange(targetId, label?)` | 给某节点设置/清除标签 |
| `branch(branchFromId)` | 把 leaf 指针移到历史节点，下一次 append 形成新分支 |
| `resetLeaf()` | leaf 置 null（回到 root 之前，用于重发第一条用户消息） |
| `branchWithSummary(branchFromId, summary, ...)` | `branch()` + 追加 BranchSummaryEntry 记录被放弃路径的摘要 |
| `createBranchedSession(leafId)` | 把 root→leaf 路径抽取成新 session 文件（label entry 重建挂链） |

### buildSessionContext()：从树到线性上下文的转换

这是 Session 模型最核心的算法（解释）（session-manager.ts:461-470），分四步：`buildSessionPath`（leaf→root 反转成 root→leaf）→ `getSessionContextSettings` → `buildContextEntries` → `sessionEntryToContextMessages`。

1. **沿路径扫描**（`getSessionContextSettings`，362-377）：提取最后出现的 `thinkingLevel`（只来自 `ThinkingLevelChangeEntry`）、最后出现的 `model`（来自 `ModelChangeEntry`，或被 assistant 消息的 `provider/model` 覆盖）（硬事实）。

2. **Compaction 边界处理**（`buildContextEntries`，session-manager.ts:418-454）：取路径上**最后一个** `CompactionEntry`（硬事实），输出 = `[compaction entry]` + 从 `firstKeptEntryId` 起到 compaction 点之前的 entry + compaction 之后的所有 entry。更早的被摘要替代（硬事实）。

3. **消息提取**（`sessionEntryToContextMessages`，383-408）：`SessionMessageEntry` 原样提取（兼容旧文件的 null content 归一为 `[]`）；`CompactionEntry` → `compactionSummary` role 消息；`BranchSummaryEntry` → `branchSummary` role 消息；`CustomMessageEntry` → `custom` role 消息（在 agent 侧的 `convertToLlm` 阶段才转成 user message 发给 LLM）。

### JSONL 存储（coding-agent 层的 SessionManager）

`SessionManager` 使用 **JSONL 文件**（每行一个 JSON 对象）存储整个 session tree：

- **Header 行：** 文件第一行是 `SessionHeader`，包含 `type: "session"`、`version`（当前为 3）、`id`、`timestamp`、`cwd`、`parentSession`。文件名为 `{fileTimestamp}_{sessionId}.jsonl`。
- **Entry 行：** 后续每行是一个 `SessionEntry`。
- **惰性落盘：** `_persist()` 在出现第一条 assistant 消息之前不写文件（`hasAssistant` guard），避免空会话堆积（硬事实）；此后逐行 append。
- **Chunked 读取：** `loadEntriesFromFile()` 用 1MB buffer 分块 `readSync` + `StringDecoder` 增量解析；`readSessionHeader()` 只做有界（≤1MB）的首行扫描，供会话发现列表使用。
- **版本迁移：** 支持 v1→v2（添加 id/parentId tree 结构、`firstKeptEntryIndex`→`firstKeptEntryId`）、v2→v3（重命名 hookMessage role 为 custom）的就地迁移，迁移后整文件重写。
- **内存后端备选：** `SessionManager.inMemory()` 构造 `persist=false` 的实例，同一套 API 不落盘（测试/临时会话）。

## 在 Agent 能力面里的影响是什么

- **分支与导航：** `branch()`/`branchWithSummary()` 让用户可以在不同版本的回答之间自由切换，每次切换可以自动生成分支摘要以便后续理解；导航只改内存 leaf 指针，append-only 历史永不改写（硬事实）。
- **Compaction 是树的一部分：** CompactionEntry 不仅影响当前上下文构建，还作为树的节点存在，使得后续从 compacted 点 fork 的对话能正确理解被压缩的历史（解释）。
- **扩展的持久化通道：** `CustomEntry` 和 `CustomMessageEntry` 让扩展可以在会话树中持久化任意数据，并在会话重新加载时恢复状态。
- **重放与调试：** Append-only JSONL 格式使得会话完全可以被重放——只需从 header 开始逐行重建树结构（硬事实）。

## 最小例子是什么

```typescript
import { SessionManager } from "@earendil-works/pi-coding-agent";

// 内存后端（等价路径：SessionManager.create(cwd) 落盘到 ~/.pi/agent/sessions/）
const session = SessionManager.inMemory(process.cwd());

// 追加用户消息（append* 返回 entry id）
session.appendMessage({
  role: "user",
  content: "Write a hello world program in Python",
  timestamp: Date.now(),
});

// 追加模型响应
const msgId = session.appendMessage({
  role: "assistant",
  content: [{ type: "text", text: "I'll write a Python hello world." }],
  api: "anthropic-messages",
  provider: "anthropic",
  model: "claude-sonnet-4-5-20250929",
  usage: { input: 100, output: 50, cacheRead: 0, cacheWrite: 0, totalTokens: 150, cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 } },
  stopReason: "stop",
  timestamp: Date.now(),
});

// 追加工具调用结果
session.appendMessage({
  role: "toolResult",
  toolCallId: "tool-001",
  toolName: "write",
  content: [{ type: "text", text: "File written successfully" }],
  details: {},
  isError: false,
  timestamp: Date.now(),
});

// 追加模型切换
session.appendModelChange("openai", "gpt-5");

// 重建 LLM 上下文
const ctx = session.buildSessionContext();
// ctx.messages = [user, assistant, toolResult]
// ctx.thinkingLevel = "off"
// ctx.model = { provider: "openai", modelId: "gpt-5" }

// 导航到历史节点并记录原分支摘要
session.branchWithSummary(
  msgId,
  "Explored Python hello world alternative implementation",
);
// leaf 指针移到 msgId，BranchSummaryEntry 成为新分支的第一个 entry；
// 下一次 appendMessage 的 parentId 即 msgId，旧分支原样保留
```

这个例子展示了 Session tree 的核心操作：消息的追加、模型状态的追踪、上下文的线性重建、以及分支导航。
