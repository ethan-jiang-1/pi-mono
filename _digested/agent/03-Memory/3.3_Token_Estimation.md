# 3.3 Token Estimation: 双层估算策略

> **⚠️ v0.83.0**：`compaction.ts` 中 image token 估算因子化为 `estimateTextAndImageContentChars`，image chars 使用常量 `ESTIMATED_IMAGE_CHARS = 4800`；`Usage` 新增 `cacheWrite1h`/`reasoning` 字段。行号全部失效。

## 现象是什么

pi-mono 需要在不实际调用 LLM 的情况下估算当前上下文的 token 数量，以决定是否需要 compaction、是否会溢出。它采用一种**双层策略**：优先使用最新的 assistant 消息中 provider 上报的真实 `usage` 数据，对 usage 之后的尾部消息使用 `chars/4` 启发式估算。

**源码位置：**
- `/packages/agent/src/harness/compaction/compaction.ts`（`estimateContextTokens`、`estimateTokens`、`calculateContextTokens`）
- `/packages/ai/src/types.ts`（`Model.contextWindow`、`Model.maxTokens`、`Usage` 接口）

## 核心矛盾是什么

精确的 token 计数需要调 tokenizer，但 pi-mono 要对接二十多个 provider，每个 tokenizer 不同，且 tokenizer 库本身可能很大（不适合在浏览器或轻量级运行时加载）。另一方面，完全依赖启发式（如 `chars/4`）在长对话中误差会累积——可能低估导致 context overflow，也可能高估导致过早 compaction。

pi-mono 的选择是：信任 provider 上报的 `usage` 数据（这是真实值），只对 provider 还没见过的消息使用启发式。

## 实现思想是什么

### Usage 数据来源

每次 assistant 消息都携带 `Usage` 对象（由 provider 在响应中返回）：

```typescript
interface Usage {
  input: number;        // 输入 token（含 cache 写入）
  output: number;       // 输出 token
  cacheRead: number;    // 从 cache 读取的 token
  cacheWrite: number;   // 写入 cache 的 token
  totalTokens: number;   // 总 token
  cost: { input, output, cacheRead, cacheWrite, total };
}
```

`calculateContextTokens(usage)` 使用 `usage.totalTokens || usage.input + usage.output + usage.cacheRead + usage.cacheWrite`。`totalTokens` 由 provider 直接上报，是最准确的上下文 token 数量。

### 找到最后一个有效 usage

`getLastAssistantUsage(messages)` 从消息列表末尾向前扫描，找到最后一个 `stopReason !== "error" && stopReason !== "aborted"` 且携带 `usage` 的 assistant 消息。错误/中止的消息的 usage 不可靠（可能不完整），故排除。

### estimateContextTokens：双层估算

```typescript
function estimateContextTokens(messages: AgentMessage[]): ContextUsageEstimate
```

算法：
1. 调用 `getLastAssistantUsageInfo(messages)`，找到最后一个有效 usage 及其 index。
2. 如果找不到任何 usage（对话刚开始，还没收到过 assistant 响应）：对所有消息使用 `estimateTokens()` 启发式估算。
3. 如果找到 usage：
   - `usageTokens = calculateContextTokens(usage)`（精确值）。
   - 对 `usage.index` 之后的所有消息使用 `estimateTokens()` 启发式估算，得到 `trailingTokens`。
   - 总 tokens = `usageTokens + trailingTokens`。

返回值 `ContextUsageEstimate` 包含：
- `tokens`：总估算
- `usageTokens`：provider 上报部分
- `trailingTokens`：尾部估算部分
- `lastUsageIndex`：最后一个 usage 的 index（或 null）

### estimateTokens：chars/4 启发式

对无法使用 provider usage 的单条消息，使用 `chars/4`：

```
token ≈ ceil(string_length / 4)
```

这个公式针对英文文本，对中英文混合文本大致准确（中文字符通常 1-2 tokens，英文字符约 0.25 tokens，`/4` 是一个中和值）。

不同类型的消息的字符提取方式不同：

| 消息 role | 提取方式 |
|-----------|---------|
| `user` | 文本内容字符数 |
| `assistant` | text + thinking + toolCall(name + JSON args) 的字符数 |
| `toolResult` | content 文本 + image (固定 4800 char，约 1200 tokens) |
| `bashExecution` | command + output 字符数 |
| `branchSummary` / `compactionSummary` | summary 文本字符数 |
| `custom` | content 字符数 |

image block 被计为 4800 字符（约 1200 tokens），这是一个经验值，反映了典型截图/图片在 LLM 中的 token 等价量。

### 压缩决策中的角色

`shouldCompact(contextTokens, contextWindow, settings)`：
```typescript
return contextTokens > contextWindow - settings.reserveTokens;
```

- `contextWindow` 来自 Model 目录（`models.generated.ts`），如 `claude-sonnet-4-5-20250929` 的 `contextWindow = 200000`。
- `reserveTokens = 16384`：为压缩 prompt + LLM 摘要输出保留的预算。
- `keepRecentTokens = 20000`：压缩后保留的最近上下文 token 数。

两个保留预算的关系：
- `reserveTokens` 用于"何时触发压缩"的判断——确保有足够空间存放 compaction prompt。
- `keepRecentTokens` 用于"压缩保留多少"——决定 `findCutPoint` 中保留的尾部 token 数。

## 在 Agent 能力面里的影响是什么

- **压缩准确性：** 双层估算策略让 token 估算在大多数情况下非常接近真实值（因为最大的历史段有 provider 上报的精确 usage），压缩决策不会过早或过晚。
- **溢出预防：** `reserveTokens` 的预留确保了即使估算有偏差，也有 16384 tokens 的安全余量，足以容纳压缩 prompt 和输出。
- **模型灵活性：** 模型目录中的 `contextWindow` 和 `maxTokens` 让 token 估算不依赖于硬编码的模型参数，更新模型目录即可适配新模型。

## 最小例子是什么

```typescript
import { 
  estimateContextTokens, 
  estimateTokens, 
  shouldCompact,
  DEFAULT_COMPACTION_SETTINGS 
} from "@earendil-works/pi-agent";

// 从 model 目录获取模型参数
const model = claudeSonnet; // contextWindow = 200000, maxTokens = 32768

// 一组对话消息
const messages = [
  { role: "user", content: "Write a Python script", timestamp: 1 },
  {
    role: "assistant",
    content: [{ type: "text", text: "Here is a Python script..." }],
    usage: { input: 500, output: 1200, cacheRead: 0, cacheWrite: 500, totalTokens: 1700,
             cost: { input: 0.0015, output: 0.01, cacheRead: 0, cacheWrite: 0.001, total: 0.0125 } },
    stopReason: "stop",
    timestamp: 2,
    api: "anthropic-messages", provider: "anthropic", model: "claude-sonnet-4-5-20250929",
  },
  // 这之后还有一段对话没有 provider usage
  { role: "user", content: "Add error handling", timestamp: 3 },
];

// 双层估算
const estimate = estimateContextTokens(messages);
console.log(`总 tokens: ${estimate.tokens}`);
console.log(`  provider 上报: ${estimate.usageTokens} (index ${estimate.lastUsageIndex})`);
console.log(`  尾部估算: ${estimate.trailingTokens}`);

// 单条消息估算示例
const singleEstimate = estimateTokens({
  role: "user",
  content: "Add comprehensive error handling with retry logic and logging",
  timestamp: Date.now(),
});
console.log(`单条消息 tokens: ${singleEstimate}`); 
// 约 ceil(61/4) = 16 tokens

// 压缩决策
const needsCompaction = shouldCompact(
  estimate.tokens,
  model.contextWindow,   // 200000
  DEFAULT_COMPACTION_SETTINGS  // reserveTokens = 16384
);
// needsCompaction === estimate.tokens > 200000 - 16384
// needsCompaction === estimate.tokens > 183616
console.log(`需要压缩: ${needsCompaction}`);
```

这个例子展示了双层估算的完整链路：provider 上报的精确 usage 作为基线，尾部消息用 chars/4 补全，最终用于 compaction 决策。
