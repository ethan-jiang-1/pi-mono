# 4.3 System Prompt：从哪里来，怎么拼出来

> **⚠️ v0.83.0**：`system-prompt.ts` 仅 import style 变化（`.js`→`.ts`），无实质 API 变更。但 AgentHarness 的 systemPrompt 类型改为 `AgentHarnessSystemPrompt<TContext,...>`，函数形式不再接收 `env`。行号基本有效。
>
> **⚠️ v0.84.2**：v0.84 修复 custom system prompt 把 cwd 与后续内容拼接的 bug；AgentHarness 去泛型化后 systemPrompt 类型随之简化（见 4.1）。

## 现象是什么

pi-mono 启动后，LLM 看到的 system prompt 不是一段写死的文本，而是多层拼合的结果。不同 mode（interactive、print、RPC）可能产生不同的 system prompt；不同 model（特别是 OpenAI Codex）也会产生不同的 system prompt。

最终送到 LLM 的 system prompt 包含：
- 基础 agent prompt（你是谁、有什么工具、怎么用）
- skills 列表（`<available_skills>` XML block）
- 项目上下文（`AGENTS.md`、`CLAUDE.md` 等）
- 当前日期、工作目录、文档路径
- extensions 可能通过 `before_agent_start` hook 修改

## 核心矛盾是什么

System prompt 的构建有几个互相拉扯的力量：

1. **基础 prompt 是静态的**，但 tools/guidelines 会变（哪些工具可用？哪些 guidelines 适用？）
2. **Skills 来自文件系统**，是异步发现的，不能硬编码
3. **不同 model 需要不同的 system prompt**：大多数 model 跟普通 user message 一样处理 system prompt，但 OpenAI Codex 要求 system prompt 必须是静态的（不能有 tools、skills 等动态内容在 system prompt 中）
4. **Extensions 可能在最后一刻修改** system prompt
5. **Custom prompt 和 default prompt 走完全不同的构建路径**

## 实现思想是什么

### 两层 system prompt 构建

pi-mono 有两个 system prompt 构建点，位于不同层级：

**Layer 1 - AgentHarness 层（`packages/agent/src/harness/`）**

`AgentHarness.createTurnState()` 中的 system prompt 解析：

```typescript
let systemPrompt = "You are a helpful assistant.";  // 兜底
if (typeof this.systemPrompt === "string") {
  systemPrompt = this.systemPrompt;                   // 静态字符串
} else if (this.systemPrompt) {
  systemPrompt = await this.systemPrompt({ ... });    // 函数动态生成
}
```

`systemPrompt` 选项可以是字符串或工厂函数，接收 `{ env, session, model, thinkingLevel, activeTools, resources }`。

**Layer 2 - AgentSession 层（`packages/coding-agent/src/core/`）**

`buildSystemPrompt()` 函数是实际拼装 system prompt 的主力：

1. **基础 agent 身份**：固定文本，定义 agent 的角色和行为
2. **工具列表**：根据 `selectedTools` 和 `toolSnippets` 生成 `Available tools:` 段落。如果 read 工具可用，还会加上文档/readme/example 路径
3. **Guidelines**：根据已启用的工具，动态添加对应的 guidelines。例如有 bash 工具时加 "use bash for file system operations"；有 edit 工具时加 "use edit for precise changes"
4. **Skills 块**：如果有 skills 且 read 工具可用，调用 `formatSkillsForSystemPrompt(skills)` 生成 `<available_skills>` block
5. **项目上下文**：`<project_context>` 块包含 `AGENTS.md` 等上下文文件内容
6. **日期和 CWD**：最后加上 `Current date: 2026-05-19` 和 `Current working directory: /path/to/project`

### formatSkillsForSystemPrompt 的实现

这个函数（在 `packages/agent/src/harness/system-prompt.ts`）负责生成 skill 列表：

- 过滤掉 `disableModelInvocation === true` 的 skills（这些不会出现在 LLM 可见列表中）
- 生成 `<available_skills>` XML block，每个 skill 包含 `name`、`description`、`location` 三个字段
- 所有字段都经过 `escapeXml()` 处理（转义 `&<>"'`）
- 额外提示 LLM：相对路径应该相对于 skill 目录解析

### Custom prompt 路径的特殊性

当 `customPrompt` 被提供时，构建路径完全不同：

- 不生成默认的 agent 身份文本
- 不生成工具列表和 guidelines
- 仍然追加 context files（如果有）和 skills（如果 read 工具可用）
- 仍然追加日期和 CWD
- `appendSystemPrompt` 仍然追加

这意味着：**custom prompt 让调用方完全控制 agent 的身份和行为定义**，但上下文和技能注入不受影响。

### Model routing 对 system prompt 的影响

对于某些 model（最典型的是 OpenAI Codex），system prompt 必须是静态的，不能包含 tools 描述和 skills 列表。这是因为这些 model 的 API 做 allowlisting 时，system prompt 和 tool definitions 是分开的两套内容。

在这种场景下：
- System prompt 只包含 agent 身份和基础指令
- Tools 通过 API 的 `tools` 参数传递
- Skills 可能不放在 system prompt 中

### Extension 对 system prompt 的修改

在 AgentSession 中，构建 system prompt 后会通过 ExtensionRunner 触发 `before_agent_start` 事件。Extension handler 可以返回修改后的 system prompt：

```typescript
const extensionResult = await this._extensionRunner.emitBeforeAgentStart(
  text, images, systemPrompt, systemPromptOptions
);
if (extensionResult?.systemPrompt) {
  systemPrompt = extensionResult.systemPrompt;
}
```

这意味着 extensions 是 system prompt 的**最后修改者**。

### 指令声明的层次

System prompt 的指令存在优先级层次：

1. **AgentSession 构建的基础 prompt**（最高层，定义 agent 核心身份）
2. **Tools 带来的 guidelines**（中层，随工具动态变化）
3. **Skills 注入的领域知识**（通过 `<available_skills>` 和 skill invocation）
4. **项目上下文文件**（`AGENTS.md` 等，代表项目级别的持久化偏好）
5. **Extension 修改**（应用层，可以在最后一刻加入指令）
6. **Custom prompt**（覆盖层，完全替换基础 identity）

## 在 Agent 能力面里的影响是什么

1. **System prompt 是能力注入的主要入口**。Tools 的可用性决定了 guidelines 的内容；skills 的存在决定了 `<available_skills>` 的内容。

2. **"谁最后改谁做主"的冲突模型**。Extensions 在 `before_agent_start` 中修改 system prompt 的权力最高，但 custom prompt 在 AgentSession 层可以完全替换基础 prompt。

3. **Skills 通过 system prompt 被发现，通过 user message 被消费**。Skills 在 system prompt 中作为目录存在，在 user message 中作为内容注入。

4. **不同 mode 可能有不同的 system prompt 策略**。例如 print mode 可能不需要 `<available_skills>` 块。

## 源码锚点

- `packages/agent/src/harness/agent-harness.ts`：`createTurnState()`（L313），system prompt 解析
- `packages/agent/src/harness/system-prompt.ts`：`formatSkillsForSystemPrompt()`（L3）
- `packages/coding-agent/src/core/system-prompt.ts`：`buildSystemPrompt()`（L28），完整的系统提示词构建
- `packages/coding-agent/src/core/agent-session.ts`：system prompt 构建调用和 extension 修改
- `packages/coding-agent/src/core/skills.ts`：`formatSkillsForPrompt()`，skills 在 system prompt 中的格式化

## 最小例子是什么

```typescript
import { buildSystemPrompt } from "@earendil-works/pi-coding-agent/core";

// 1. 基础 system prompt（无 custom prompt）
const prompt = buildSystemPrompt({
  cwd: "/home/user/project",
  selectedTools: ["read", "bash", "edit", "write"],
  toolSnippets: {
    read: "Read file contents",
    bash: "Execute bash commands",
    edit: "Edit files with exact text replacement",
    write: "Write or overwrite files",
  },
  skills: [
    { name: "deploy", description: "Deploy the application", content: "...", filePath: "..." },
  ],
  contextFiles: [
    { path: "AGENTS.md", content: "Always use TypeScript strict mode." },
  ],
});

// 输出包含：
// - agent 身份
// - Available tools 段落
// - Guidelines（根据启用的工具）
// - <available_skills> XML block（如果有 skills 且 read 工具可用）
// - <project_context> 块
// - Current date 和 Current working directory

// 2. Custom prompt（完全替换基础身份）
const customPrompt = buildSystemPrompt({
  customPrompt: "You are a Python expert. Always use type hints.",
  cwd: "/home/user/project",
  skills: mySkills,
  contextFiles: myContextFiles,
});
// 不包含默认 agent 身份、工具列表、guidelines
// 仍然包含 context files、skills、日期、CWD
```
