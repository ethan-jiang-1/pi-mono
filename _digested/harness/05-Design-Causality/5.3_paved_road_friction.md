# 5.3 正确路径的摩擦差:哪里是铺装路,哪里摩擦差消失了

## 现象是什么

"做对"与"做错"在 pi 里的成本不对称,且不对称的分布不均匀。**摩擦差大的地方**:想给 pi 加能力,正确路径(写扩展)有 70+ 个可抄的运行范本、有 `npm run check` 的类型兜底(`AGENTS.md:32`)、有 entry-graph 预算防误入(`scripts/check-entry-graphs.mjs`);错误路径(往 core 塞功能)有明确的拒绝条款(`CONTRIBUTING.md:7-9`)与贡献门(见 [3.3](../03-Discipline/3.3_contribution_gate.md))。**摩擦差小的地方**:文档准确性(改错无人红)、扩展 API 的"正确组合姿势"(多段钩子怎么拼没有合同,只有范本)、"该跑哪些检查"(规则在人脑与 `AGENTS.md` 之间)。

## 核心矛盾是什么

**铺装路的铺设成本 vs 覆盖面**。每个摩擦差都要有人付费:范本靠持续维护 examples、类型兜底靠类型系统投资、门禁靠脚本。pi 把预算集中花在"资产完整性"上(5.1 判断一),参与方式的摩擦差主要靠**范本的同生命周期保真**这一招撑着——招法单一,覆盖面就有边界。

## 设计判断是什么

### 判断一:pi 的铺装路是"范本铺装",不是"门禁铺装"(解释)

正确做法的最小阻力路径在 pi 里由三类东西铺成:**可运行的范本**(examples/ 的 70+ 能力,`check` 强制其与 API 同步)、**带指向的错误消息**(如 `Agent.prompt()` 在运行中调用时直接报 "Use steer() or followUp() to queue messages",`packages/agent/src/agent.ts:374-378`——API 形状本身教学)、**类型即合同**(`AgentTool`/`AgentLoopConfig` 的 JSDoc 合同写得极其细密,`packages/agent/src/types.ts:60-104` 的逐字段合并语义)。对比 DSH 的门禁铺装(verify-* 家族、100% coverage、负例测试门禁):pi 的路更软,但**铺设成本也低一个数量级**——单维护者可负担,这正是形状因果([5.2](./5.2_shape_causality.md))允许的选择。

### 判断二:摩擦差消失的两个具体位置(硬事实 + 解释)

1. **文档层**:5.1 已证散文无保真;进一步说,散文还**制造负摩擦**——过时文档是错误写法的现成复制来源。缓解项存在但不在文档层:范本与类型。
2. **判断外置点**:DSH 把"该跑哪些检查""这算不算非平凡改动"外置成 skill/guidance;pi 对应的判断(跑 check 还是 test.sh?要不要重新生成 install-lock?)住在 `AGENTS.md` 的 Commands/Dependency 节(`:30-51`)——是** standing order 而非可调用流程**,没有对应的校准 skill。判断门槛没有被移除,也没有被拆小配工具,只是被写成了短规则([推断],可证伪:若 pi 引入 skill 化的检查流程,本条失效)。

### 判断三:负例不被测试,是范本铺装的结构性边界([框架] 借 DSH harness-idea 03 的元验证判据)

DSH 要求"门禁必须被回归证红"——铺装路本身被负例持续验证。pi 没有这层:check 红只证明代码与合同不符,不证明"合同本身挡得住错误姿势"。例:`entry-graph` 预算挡住 barrel 膨胀([3.1 判断五](../03-Discipline/3.1_core_minimal.md)),但没有机制验证"预算数值本身仍然合理"。**这不是缺陷清单,是成本结构**:元验证体系是 DSH 组合压力下的产物,pi 以 review + CI 兜底换取不建它。

## 影响是什么

1. **给贡献者/agent 的实操结论**:在 pi 里,"抄最近的范本 + 跑全量 check"是摩擦最小的正确路径;读散文定实现细节是高风险动作。
2. **给评估者的结论**:评价 pi 的 paved road 不要套 DSH 的门禁清单——pi 的铺装强度在"范本 + 类型 + 少量硬门禁",它的摩擦差设计与其生产方式自洽;真正要盯的是判断二的两个消失点是否随规模恶化。

## 源码锚点是什么

- `packages/agent/src/agent.ts:374-378`:错误消息指路的实例(判断一)
- `packages/agent/src/types.ts:60-104`:类型合同的细密程度(判断一)
- `AGENTS.md:30-51`:判断外置的现状(判断二)
- `scripts/check-entry-graphs.mjs`:硬门禁样本与预算合理性无验证(判断三)
- `CONTRIBUTING.md:7-11`:错误路径的明文拒绝

## 最小例证是什么

**例证 1(范本铺装)**:给 `examples/extensions/todo.ts` 引入一个不存在的 API 调用 → check 红;给 `docs/` 同样做 → 无反应。摩擦差分布的直接读数。
**例证 2(负摩擦)**:找一处 v0.86.x 之前写的官方文档与当前 API 对照,确认漂移仅靠人工发现(或无漂移——后者只是运气好,不是机制)。
