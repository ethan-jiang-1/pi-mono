# 3.1 Compaction: 上下文的自动压缩

> **⚠️ v0.83.0**：① `Models` 接口替代直接 `apiKey`+`headers`；② 新增 retry 支持（`completeSimpleWithRetries`）；③ `firstKeptEntryId` 变为 optional，新增 `retainedTail` 自包含 compaction；④ `SUMMARIZATION_SYSTEM_PROMPT` 文本变化。行号全部失效。

## 现象是什么

当对话持续进行数十分钟，消息历史可能达到数万 tokens。pi-mono 会在检测到上下文接近模型窗口上限时，自动将早期对话压缩为一个结构化的摘要，嵌入到后续的上下文中。这个压缩以 `CompactionEntry` 的形式记录在 Session tree 中，后续的上下文构建会从压缩点截断，只保留摘要 + 最近的对话。

**源码位置：** `/packages/agent/src/harness/compaction/compaction.ts`

## 核心矛盾是什么

对话压缩面临三个核心取舍：

1. **保留什么 vs 丢弃什么：** 早期对话的细节对后续任务可能至关重要（如"我们之前决定用 SQLite"），但全部保留会超出 context window。需要一个有信息密度的摘要格式。
2. **边界对齐：** 如果在用户消息的中间切断，模型看到的上下文是不完整的（只有 assistant 的回复和 tool 结果，没有上游的用户请求）。Cut point 必须在"合法"的位置。
3. **增量更新 vs 全新生成：** 如果之前已经有过 compaction，新 compaction 应该更新已有的摘要（而非重新生成），以保留完整的项目进度记忆。

## 实现思想是什么

### 压缩设置

```typescript
const DEFAULT_COMPACTION_SETTINGS = {
  enabled: true,
  reserveTokens: 16384,   // 为 prompt + 输出保留的 tokens
  keepRecentTokens: 20000, // 保留的最近上下文 tokens
};
```

- `reserveTokens`：压缩时，用于生成摘要的 prompt 和 LLM 输出本身也需要 tokens 配额。
- `keepRecentTokens`：压缩后保留的上下文 token 数。约 20000 tokens，足以保留最近几个完整的 turn。

### 压缩决策：何时触发

```
estimateContextTokens(messages) > model.contextWindow - reserveTokens
```

这个判断在 `shouldCompact()` 中实现。当上下文总 tokens 超过 `contextWindow - reserveTokens` 时，触发压缩。

### 寻找分割点：findCutPoint

从路径末尾向前扫描，累积 token 数，找到 `keepRecentTokens` 的分割位置。但不是所有 entry 都可以作为分割点：

**有效分割点：** user 消息、assistant 消息、bashExecution 消息、branchSummary 消息、compactionSummary 消息、customMessage、branch_summary entry、custom_message entry。

**无效分割点：** toolResult 消息（不能从工具结果开始，因为缺少上游的 user/assistant 上下文）、thinking_level_change、model_change、compaction（不能从压缩点开始一个新压缩）、custom、label、session_info、leaf。

分割点选择后，还会向后调整：如果分割点前一个是 compaction entry，停止调整；如果前一个是普通 message，也停止。这确保分割点在语义合理的边界上。

### 分回合处理（Split Turn）

当分割点落在 assistant 消息上（而非 user 消息），意味着一个回合被切断。此时 `findTurnStartIndex()` 向上查找该回合的起始（user 消息或 branch_summary），将该回合的前半部分标记为 "turn prefix"。压缩会分别处理：

1. 回合前缀（turn prefix）单独生成摘要。
2. 之前的完整历史使用标准格式（或增量更新）生成主摘要。
3. 两者合并，前缀摘要前面加上 "Turn Context (split turn)" 标注。

### 结构化摘要格式（SUMMARIZATION_PROMPT）

压缩使用标准化的六段格式：

```
## Goal
[用户想完成什么？如果有多个任务或研究方向变化，列出所有相关内容。]

## Constraints & Preferences
- [用户提到的约束、偏好或需求]
- [或 "(none)"]

## Progress
### Done
- [x] [已完成的任务/变更]

### In Progress
- [ ] [正在进行的工作]

### Blocked
- [阻塞项]

## Key Decisions
- **[决策]**: [简要理由]

## Next Steps
1. [下一步的优先级列表]

## Critical Context
- [继续工作所需的关键数据、范例或参考]
- [或 "(none)"]
```

这个格式的设计目标：让续接的 LLM 能够快速理解目标、进度、约束和下一步，而不是像通用文本摘要那样丢失结构。

### 增量更新

当存在 `previousSummary` 时，使用 `UPDATE_SUMMARIZATION_PROMPT`（而非 `SUMMARIZATION_PROMPT`）。这个 prompt 指示 LLM：
- 保留已有摘要中的所有信息。
- 添加新的进展、决策和上下文。
- 更新 Progress 部分（将 "In Progress" 移到 "Done"）。
- 保留精确的文件路径、函数名和错误消息。

这避免了反复压缩导致的信息衰减。

### compact() 的完整流程

```
prepareCompaction(pathEntries, settings)
  → 找到上一个 compaction 的位置
  → estimateContextTokens 估算当前上下文
  → findCutPoint 找到分割点
  → 提取 messagesToSummarize 和 turnPrefixMessages
  → 提取 fileOps（从 assistant tool call 中收集文件操作）

compact(preparation, model, apiKey)
  → 如果有 turnPrefixMessages：
    → 并行：generateSummary(历史) + generateTurnPrefixSummary(前缀)
    → 合并结果
  → 如果没有：
    → generateSummary(历史，可选的 previousSummary 增量更新)
  → 追加文件操作列表（readFiles, modifiedFiles）
  → 返回 CompactionResult {summary, firstKeptEntryId, tokensBefore, details}
```

### AgentSession 自动压缩

AgentSession 在 `agent_end` 后调用 `_checkCompaction()`，处理两种场景：

1. **Overflow（溢出）：** LLM 返回了 context overflow 错误 → 移除错误消息 → 执行压缩 → **自动重试**（继续原来的任务）。
2. **Threshold（阈值）：** 上下文超过阈值 → 执行压缩 → **不自动重试**（等待用户手动 continue）。

## 在 Agent 能力面里的影响是什么

- **无限对话的错觉：** Compaction 让长时间对话成为可能，而不需要用户手动管理上下文。
- **结构化的记忆：** 六段摘要格式比纯文本摘要提供了更好的"记忆索引"，后续的 LLM 调用能快速定位关键信息。
- **溢出的自动恢复：** Overflow 场景下，压缩 + 重试对用户完全透明——用户可能只看到一个短暂的"Compacting..."提示。
- **文件操作追踪：** `CompactionDetails` 记录了压缩区间内的 readFiles 和 modifiedFiles，这为后续的 compaction 提供了增量文件追踪能力。

## 最小例子是什么

```typescript
import { 
  prepareCompaction, compact, DEFAULT_COMPACTION_SETTINGS,
  estimateContextTokens, shouldCompact
} from "@earendil-works/pi-agent";

const contextWindow = 200000; // claude-sonnet-4-5
const settings = DEFAULT_COMPACTION_SETTINGS;

// 获取 session 的当前路径
const pathEntries = await session.getBranch();
const context = await session.buildContext();

// 估算当前上下文 tokens（来自 provider 上报 + 启发式）
const estimate = estimateContextTokens(context.messages);
console.log(`当前上下文: ${estimate.tokens} tokens ` +
  `(provider 上报: ${estimate.usageTokens}, 尾部估算: ${estimate.trailingTokens})`);

// 判断是否需要压缩
if (shouldCompact(estimate.tokens, contextWindow, settings)) {
  console.log("需要压缩...");
  
  // 准备压缩数据
  const prep = prepareCompaction(pathEntries, settings);
  if (!prep.ok) throw prep.error;
  if (!prep.value) return; // 不需要压缩
  
  const { firstKeptEntryId, messagesToSummarize } = prep.value;
  console.log(`压缩 ${messagesToSummarize.length} 条消息，` +
    `保留从 ${firstKeptEntryId} 开始的历史`);

  // 执行压缩
  const result = await compact(prep.value, model, apiKey);
  if (!result.ok) throw result.error;
  
  // 持久化压缩
  await session.appendCompaction(
    result.value.summary,
    result.value.firstKeptEntryId,
    result.value.tokensBefore,
    result.value.details,  // { readFiles, modifiedFiles }
  );
  
  console.log("压缩完成");
  console.log(`摘要 (前 200 字): ${result.value.summary.slice(0, 200)}...`);
}
```

这个例子展示了压缩的完整决策链路：估算 → 判断 → 准备 → 执行 → 持久化。压缩后的 CompactionEntry 被记录在 Session tree 中，后续的 `buildSessionContext` 会自动处理压缩边界。
