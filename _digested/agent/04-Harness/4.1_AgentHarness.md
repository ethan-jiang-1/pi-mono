# 4.1 AgentHarness：Agent 之上的 typed event wrapper

> **⚠️ v0.83.0**：① `AgentEvent`→`AgentSessionEvent`，事件类型移入 `harness/types.ts`；② `getApiKeyAndHeaders` 删除，auth 统一走 `Models` 接口；③ AgentHarness 新增泛型 `TContext`，工具接收 per-turn context；④ 新增 `agent/src/harness/tools/` factory 模式工具目录。行号全部失效。

## 现象是什么

`Agent` 只做最纯粹的 LLM 对话循环：接收消息列表，调用 LLM，执行 tool call，产生 `AgentSessionEvent`（v0.83.0：从 `AgentEvent` 改名）。它既不知道 session 的存在，也不管 compaction，更没有高级的 hook 机制。如果你直接用 `Agent` 做事，你得自己管理消息持久化、自己处理 context 构建、自己实现队列。

`AgentHarness` 就是解决这个问题的。它是 `Agent` 上面的第一层包装，用 typed event hooks 把 session 感知、能力注入、中断控制统一起来。

## 核心矛盾是什么

泛型 `Agent<TSchema>` 是极简的：它只有 `run()` 和 `continueRun()`，返回 `EventStream<AgentEvent, AgentMessage[]>`。它完全**不知道自己在哪个 session 里**。

但实际使用场景需要：
- 每次 turn 结束后写回 session tree（消息持久化）
- 在 LLM 请求前拦截并修改 system prompt 或工具列表
- 在执行前/后 hook tool call（权限控制、结果改写）
- 支持 steer/followUp 队列注入
- compaction 和 tree navigation 需要读取 session 历史和进入专用 phase

矛盾在于：**循环的核心逻辑不应该知道 session，但产品功能必须依赖 session。**

## 实现思想是什么

### 泛型三层设计

`AgentHarness<TSkill, TPromptTemplate, TTool>` 有三个泛型参数，分别对应外部注入的三类资源：

- `TSkill`：Skills（`SKILL.md` 文件或应用提供的专业指令）
- `TPromptTemplate`：Prompt 模板（可被 `promptFromTemplate()` 显式调用）
- `TTool`：Agent 工具（被 LLM 调用的函数）

每个类型默认为基类 `Skill`/`PromptTemplate`/`AgentTool`，可以被上层应用扩展。

### 事件系统设计

AgentHarness 有两类事件监听：

#### 1. 广播事件（subscribe）

```typescript
subscribe(listener: (event: AgentHarnessEvent) => void): () => void
```

订阅者接收**所有** AgentEvent（来自 agent loop）和 AgentHarnessOwnEvent（harness 产生的）。用于 UI 渲染、日志记录等单向通知场景。所有 listener 通过 `SUBSCRIBER_EVENT_TYPE = "*"` 这个 key 存储。

#### 2. Typed hooks（on）

```typescript
on<TType extends keyof AgentHarnessEventResultMap>(
  type: TType,
  handler: (event) => AgentHarnessEventResultMap[TType]
): () => void
```

每个事件类型有独立的 handler 集合，handler 可以返回一个结果值，多个 handler 的结果通过 last-write-wins 合并。核心 hook 事件包括：

**生命周期 hooks：**
- `before_agent_start`：prompt 发送前，可注入额外 messages 或修改 system prompt
- `context`：每次 LLM 调用前，可修改整个 messages 列表
- `before_provider_request`：provider 请求前，可修改 stream options（headers、timeout 等）
- `before_provider_payload`：payload 发往 provider 前，可修改请求体本身
- `after_provider_response`：收到 provider 响应后（通知型，不修改）

**工具 hooks：**
- `tool_call`：工具执行前，可 block（返回 `{ block: true, reason: "..." }`）阻止工具执行
- `tool_result`：工具执行后，可修改工具返回结果（content、details、isError、terminate）

**Session hooks：**
- `session_before_compact`：compaction 前，可取消或提供自定 summary
- `session_compact`：compaction 完成后（通知型）
- `session_before_tree`：tree navigation 前，可取消或提供 summary
- `session_tree`：tree navigation 完成后（通知型）

**状态变更 hooks：**
- `model_select`：模型切换后
- `thinking_level_select`：thinking level 切换后
- `resources_update`：资源（skills/promptTemplates）更新后

**控制 hooks：**
- `queue_update`：steer/followUp/nextTurn 队列变更后
- `save_point`：每次 turn 结束后，带 `hadPendingMutations` 标记
- `abort`：中断完成后
- `settled`：agent 完全空闲后（携带 `nextTurnCount`）

### 方法设计

每个公开方法遵循统一的模式：**snapshot state → hook into lifecycle → delegate to Agent loop → flush pending writes**。

`prompt(text, options?)`：
1. 检查 phase = "idle"，设置 phase = "turn"
2. `createTurnState()` snapshot 当前 session context、model、tools、resources
3. 调用 `executeTurn()` 构建实际执行流程
4. `executeTurn()` 触发 `before_agent_start` hook，允许注入 messages、修改 system prompt
5. 通过 `createLoopConfig()` 构建 `AgentLoopConfig`，把 harness hooks 挂到 agent loop 的 `beforeToolCall`/`afterToolCall`/`transformContext`/`prepareNextTurn` 等回调上
6. `createStreamFn()` 构建 streaming 函数，注入 `getApiKeyAndHeaders` 和 provider hooks
7. 调用 `runAgentLoop()` 执行
8. 通过 `handleAgentEvent()` 分发事件：`message_end` 直接写 session；`turn_end` flush pending writes 并 emit `save_point`；`agent_end` flush 并 emit `settled`
9. finally 块中 flush pending session writes 并重置 phase

`steer(text)` / `followUp(text)`：
- 只能在 phase = "turn" 时调用（idle 时报错）
- 把 UserMessage 推入 `steerQueue` / `followUpQueue`
- 通过 `getSteeringMessages` / `getFollowUpMessages` 回调，在 agent loop 的适当 drain point 被消费

`nextTurn(text)`：
- 推入 `nextTurnQueue`，在**下一次** `prompt()` 调用时作为上下文注入

`compact(customInstructions?)`：
1. 设置 phase = "compaction"（blocking）
2. 从 session 取 branch entries
3. `prepareCompaction()` 找出需要总结的消息
4. 触发 `session_before_compact` hook
5. 如果 hook 没有提供结果，则调用 compaction LLM 生成 summary
6. 写入 session，emit `session_compact` 事件

`navigateTree(targetId, options?)`：
1. 设置 phase = "branch_summary"
2. `collectEntriesForBranchSummary()` 收集两个 leaf 之间的分支差异
3. 触发 `session_before_tree` hook
4. 如果需要 summary，调用 `generateBranchSummary()`
5. 调用 `session.moveTo()` 更新分支位置

### 错误处理体系

AgentHarness 定义了一组稳定的错误类型：

- `AgentHarnessError`：通用 harness 错误，按 code 分类：`busy`、`invalid_state`、`invalid_argument`、`session`、`hook`、`auth`、`compaction`、`branch_summary`、`unknown`
- `SessionError`：session 存储层错误
- `CompactionError`：compaction 失败
- `BranchSummaryError`：branch summary 生成失败
- `ExecutionError`：shell 执行错误
- `FileError`：文件系统错误

Hook 错误处理：如果 hook handler 抛出异常，`normalizeHookError()` 将其包装为 `AgentHarnessError("hook", ...)` 并向上传播。**一个 hook 失败会导致整个操作失败**，这是有意设计的——hook 通常在权限/安全关，必须 fail-close。

### Session write 的 "pending" 机制

在 turn 执行期间，直接写 session 可能导致部分写入（如果后续失败）。因此 AgentHarness 用 `pendingSessionWrites` 队列暂存写入：
- turn 执行中 → 写入队列
- `turn_end` 事件 → flush 队列
- `agent_end` 事件 → flush 队列
- prompt() finally 块 → 无论如何 flush

### Phase 状态机

```
idle → turn → idle
idle → compaction → idle
idle → branch_summary → idle
```

- `prompt()` / `skill()` / `promptFromTemplate()` 只能在 idle 状态调用
- `steer()` / `followUp()` 只能在 turn 状态调用
- `compact()` / `navigateTree()` 只能在 idle 状态调用

## 在 Agent 能力面里的影响是什么

1. **事件是唯一的外部消费通道**。无论是 TUI 的渲染、RPC 的 JSONL 输出、还是 SDK 的回调，都通过 AgentHarness 的事件系统传递。不存在绕过事件直接读 state 的机制。

2. **Hook 系统是扩展机制的基础**。Extension system（4.4）的能力本质上就是把 extension 的 handler 注册到 AgentHarness 的 hook 上。

3. **Session 持久化是完全自动的**。只要用 AgentHarness 而不是裸 Agent，消息就会自动写入 session tree。上层不需要手动管理。

4. **Compaction 和 tree navigation 作为一等操作**。不是事后补救，而是在 harness 层直接支持。

## 最小例子是什么

```typescript
import { AgentHarness } from "@earendil-works/pi-agent-core";
import { createJsonlSession } from "@earendil-works/pi-agent-core/harness";

// 1. 创建 session
const session = createJsonlSession({ cwd: "/tmp/test", id: "demo" });

// 2. 创建 harness（不直接用 Agent）
const harness = new AgentHarness({
  env: { cwd: "/tmp/test", /* FileSystem + Shell */ },
  session,
  model: myModel,
  tools: [readTool, bashTool],
  systemPrompt: "You are a helpful assistant.",
});

// 3. 订阅所有事件（UI 渲染）
harness.subscribe((event) => {
  if (event.type === "message_update") console.log(event.assistantMessageEvent);
});

// 4. 注册 tool_call hook（权限控制）
harness.on("tool_call", ({ toolName, input }) => {
  if (toolName === "bash" && input.command?.includes("rm -rf")) {
    return { block: true, reason: "Dangerous command blocked" };
  }
});

// 5. 注册 before_agent_start hook（注入上下文）
harness.on("before_agent_start", ({ prompt, systemPrompt, resources }) => {
  return {
    systemPrompt: systemPrompt + "\nAdditional instruction: be concise.",
  };
});

// 6. 发送 prompt
const result = await harness.prompt("What files are here?");
// result 是 AssistantMessage，包含 LLM 的最终回复

// 7. 中断
await harness.abort();

// 8. 压缩
const { summary, tokensBefore } = await harness.compact();

// 9. 等待空闲
await harness.waitForIdle();
```

关键要点：**你在和 AgentHarness 交互，不是 Agent**。AgentHarness 负责把所有钩子、session 写入、事件分发串联起来，Agent 只负责最内层的 LLM 循环。
