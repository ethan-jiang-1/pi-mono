# 4.1 AgentHarness：durable drive 运行时（Harness + Lane + driveOperation）

> **⚠️ 版本史**：本文最初基于 v0.75.3 的泛型 `AgentHarness` 编写；v0.84.0 重写为零泛型的 `AgentHarness implements AgentLane` 骨架（当时操作大多 reject `HarnessNotImplemented`）；**v0.85.x–v0.86.x（WP00–WP09，见 `_change_log/0006`）把这套骨架填成完整的 durable drive 运行时**：`HarnessNotImplemented` 已删除，run/generation/tool 执行/compaction/branch summary 全部走持久化操作记录。2026-09-21 已对照 v0.86.1 复核，正文已重写至 v0.86.1 现实。
>
> **结论先行**：旧文档"AgentHarness skeleton mostly stub / 产品集成不要用 AgentHarness"的模型**已失效**。`packages/agent/src/harness/runtime/` 是一套可直接跑的持久化运行时：`Harness` 管 lanes，`Lane` 做命令仲裁与收件箱，`driveOperation()` 按 session 里记录的 operation state 逐段驱动，崩溃后可从 recovery 续跑。

## 现象是什么

`Agent`（`packages/agent/src/agent.ts`）只做最纯粹的 LLM 对话循环：收消息、调 LLM、执行 tool、吐事件。它不知道 session 的存在，不管 compaction，也没有 hook 机制。（解释）因此 Agent 之上需要一层 harness。v0.86.1 里这层就是 `harness/runtime/`：

- `packages/agent/src/harness/runtime/harness.ts:29` — `class Harness<TContext> implements AgentHarness<TContext>`：多 lane 的管理者，本身不是 lane；持有进程级 `Config`（tools/resources/streamOptions/retryPolicy/compaction/queue modes），并提供 `drive()` 等宿主控制面（`agent-harness.ts:547` 的 `AgentHarness` 接口）。
- `packages/agent/src/harness/runtime/lane.ts:221` — `class Lane<TContext> implements AgentLane`（2012 行）：单条 session 分支的运行体。lane 命令仲裁（`LaneCommand`，`runtime/types.ts:60` 附近定义、每条命令在序列化的 mutation 线上做出 effect-free decision）、inbox（steer/followUp 队列项）、watch（快照 + 增量事件）、fault handler 都在这里。`Lane` 收到操作请求后把 claim 交给 `driveOperation`（lane.ts:976）。
- `packages/agent/src/harness/runtime/drive.ts:29` — `driveOperation()`：状态机驱动器。无限循环读取 `operation.state.at`，按 13 个 family-neutral 叶子状态分派（硬事实）：`starting` → `checkpoint` → `assistant.ready`/`assistant.retry_wait`（generation，含 `assistant.effect_pending` 恢复）→ `tools`（tool placement + 执行）→ `deferred.suspended`/`deferred.effect_pending`（provider 侧延迟）→ `summary.*`（compaction/branch summary 的 structural 决策与生成）→ `navigation.ready_to_commit` → terminal；`cancel_requested` 时先走 `reconcileOperation()` 对账（drive.ts:56-59）。每个状态对应 `drive/` 下的一个模块。

## 核心矛盾是什么

老的分层矛盾仍然成立：**循环核心逻辑不知道 session，但产品功能必须依赖 session。**（解释）v0.85–0.86 的解法是把"运行中"彻底持久化（解释）：

1. **每次推进都是 durable 记录，不是内存回调。** 一个 run 从 `starting` 到 terminal 的每一步状态迁移都写成 session v4 的 guarded mutation（见 [2.5](../02-Runtime/2.5_Session_Service.md)），所以进程崩溃后 `drive/recovery.ts` 能从 `assistant.effect_pending` 等中间态恢复 generation、从 checkpoint 续跑，而不是重放整个对话。（解释）
2. **决策与效果分离。** `LaneCommand` 在 lane 的序列化 mutation 线上产出纯决策（commit + writes + materialize/events，`runtime/types.ts:60-70`），副作用经 effect gate 执行。这使同一份 operation log 既可驱动执行也可确定性审计。（解释）

## 实现思想是什么

### 1. drive/ 模块：一个状态叶子一个文件

`packages/agent/src/harness/runtime/drive/`：

- `checkpoint.ts` / `generation.ts` / `tool-placement.ts` / `tools.ts` / `response.ts` — starting、assistant 生成、tool 摆放与执行。
- `recovery.ts` — effect_pending 态的崩溃恢复（generation 与 structural 各有恢复入口）。
- `retry.ts` — 退避重试等待（预算来自 `RetryPolicy.maxAgentDelayMs`，见 [2.4](../02-Runtime/2.4_Retry_Scheduler.md)）。
- `deferred.ts` — provider 侧延迟挂起与恢复。
- `structural.ts`（1222 行）— compaction / branch summary 等 structural operation 的决策、生成与提交。
- `reconcile.ts` / `terminal.ts` — 取消对账与终态提交。

### 2. 契约面收敛

- `runtime/types.ts:18` — `SliceNotImplemented`：取代旧的 `HarnessNotImplemented`。只剩个别尚未实现的 slice（如 `watchSession`，`runtime/harness.ts:306`）会抛它；操作路径不再是全量 stub。（硬事实）
- 结果类型体系（`Result` + TaggedError，`harness/result.ts`）沿用 v0.84 设计：拒绝类（`LaneBusy`/`InvalidMessage`/`Closed` 等）是值，throw 只留给基础设施错误。
- hook 面含 `before_drive`（`agent-harness.ts:435`）：宿主可在每次 drive 推进前介入。

### 3. manual drive 控制面已删除

v0.84 文档描述的 `drive: "manual"` + `peekAction()`/`executeAction()`/`runToCompletion()` 手动步进面已随 `d9b1dae06`（remove manual drive controls）整体移除，与 v0.84.4 CHANGELOG "Removed the withdrawn manual-drive configuration" 呼应。（硬事实）确定性驱动现在由持久化 operation log 本身承担：状态就是记录，重放即审计。（解释）

### 4. 路线图

`packages/agent/docs/work-packages/00-runtime1-removal.md` … `09-lane-snapshot-settled-tools.md` 记录了 WP00–WP09 的演进（runtime1 移除、bound values/lists、atomic run acceptance、drive deadlines 移除、mutation publication、direct durable drive、session/branch/lane 分离、SQLite host ownership、named-branch streaming forks、settled tools 保留至 placement）。读 runtime 代码时按工作包索引比按 commit 更快。

### 5. 平行的实验 kernel：pico3（简记）

`harness/pico3/` 是与 `harness/runtime/` 并行的第二套实验性 harness kernel（kind-plugin 化：`pico3/harness.ts:114` 的 `class Harness<Ks>` 固定 generation/tool/postTools/collapse/job/plugin 等 built-in kinds；配套 scheduler/session/view/membrane 与 jsonl/memory 双存储实现），经 `packages/agent/package.json:21` 的 `"./experimental/pico3"` subpath 导出。它同时是 Chord service 的暴露点：`pico3/chord.ts:36-37` 的 `PicoHarnessService = defineService<Harness>("pi.harness", { local: true })` 与 `PicoConversationService`（跨进程 facet/service + replicated state 契约，实现在新包 `@earendil-works/chord`）。pico3 是实验线，产品路径仍是 `harness/runtime/`。（硬事实+定位）

## 在 Agent 能力面里的影响是什么

1. **产品集成路径不变**：TUI/RPC/SDK 继续走 coding-agent 的 `AgentSession`（`packages/coding-agent/src/core/agent-session.ts`）/ SDK（`createAgentSession()`，`packages/coding-agent/src/core/sdk.ts:175`）。runtime 线给了 upstream 一个不依赖 coding-agent 的完整 harness 实现，但消费方式（公开 exports 仍以 `./harness/session`、`./harness/runtime/reducer` 等子路径为主）还在收敛中。
2. **崩溃恢复是一等能力**：run 中途进程死亡不再丢对话——operation 记录在 session 里，重启后 recovery 从 checkpoint/effect_pending 续跑。（解释）
3. **面向接口编程**：`AgentLane`/`AgentHarness` 接口（`harness/agent-harness.ts`）仍是契约，`Harness`/`Lane` 是实现。
