# 2.5 第二条扩展轴：chord facet 插件

> 本节 2026-09-10 追加（基线 v0.85.1）。`02-Expansion/` 的四条轴（2.1-2.4）都建立在**同一条**扩展轴——`core/extensions` 的 `export default function (pi: ExtensionAPI)`——之上；本节讲 v0.85 引入的**第二条、平行的**扩展轴：`packages/chord` 的 **facet 插件**。
>
> 它**不是**前面四条轴的第五条。前面四条轴切的是"沿循环的哪个接缝、注入什么"；这条轴切的是"**同一份 feature 的代码跑在哪个进程/环境**"。详见 [`composition/10_extension_axes/10i_process_axis.md`](../../composition/10_extension_axes/10i_process_axis.md)。

## 现象是什么

v0.85.0 起 pi-mono 多了第 11 个包 `packages/chord`（"application composition runtime"，**零 Pi 依赖**，由 `packages/chord/test/boundary.test.ts` 自动守住）。它带来一套新的组合机制：**facet**。

facet 作者的典型形状不是"一个文件"，而是**一个包里几个互不相连的 bundle**：

```text
pi-example-plugin/
  src/contract.ts    service token + JSON DTO（共享，不 import 任何 host 代码）
  src/session.ts     session-worker facet（用 agent/session 代码）
  src/tui.ts         TUI facet（用 TUI 代码）
  package.json       chord.facets 的 host → entry 映射
```

**活证据**：`packages/coding-agent/examples/plugins/pi-example-plugin/`（`src/contract.ts` / `src/session.ts` / `src/tui.ts` + `package.json`）。它的 README 自述运行方式：Pi 让 Chord 发现 `src/session.ts` 与 `src/tui.ts`，把两个 entry 编进 server 侧 plugin cache，再把 TUI artifact 发给客户端。

关键否命题（`packages/agent/docs/plugins.md:57`，原文）：

> "Their shared service IDs and wire contracts connect them, **not an aggregate JavaScript object or a `definePlugin()` wrapper**."

即：**没有** `export default function (pi)`，**没有** `ExtensionAPI`，**没有**一个被所有 host 共享的"插件对象"。同一 feature 的几份代码跑在不同进程/环境里，靠 **shared service ID + wire contract** 连接。

## 核心矛盾是什么

**"一个口子"的成立前提是"一个进程、一份代码、一个对象"——而进程边界会把这个前提打掉。**

`core/extensions` 的统一注入点（[`harness/01-Architecture/1.2`](../../harness/01-Architecture/1.2_single_injection.md) 的取舍对象）之所以省认知成本，是因为"拿到 `pi`，把东西挂上去"这件事发生在一个 JS 对象上、一个进程里。但一旦：

- durable agent（真正的 `AgentHarness`）必须在 **session worker 进程**里跑，
- 而 presentation（TUI，将来还有 web）要在 **另一个进程/环境**里跑，
- 且将来还可能有独立于任何 session 的 **server 权威**（`SessionRepo`、认证、路由），

这三者就**不可能共享一个加载好的 JS 对象**。facet 的取舍是：**保留"统一 service 契约"，放弃"统一对象"**——把 feature 按 host 拆成多份代码，用 service token 与 wire contract 把它们接起来。

这也解释了 chord 的一条硬纪律：`packages/chord/PLANNING.md:37` 有一份**禁用词汇表**（Session / Harness / AgentLane / server / client / attachment / TUI / model / tool / hook / provider credential / workspace 都不许进 chord）。chord 只懂 service/facet；Pi 的语义留在 Pi 自己的适配层。

## 与 `core/extensions` 的关系：并存，不是替代

| 维度 | extension 系统（轴 2.1-2.4 的基础） | facet / plugin（第二条轴） |
|---|---|---|
| 归属 | `packages/coding-agent/src/core/extensions/`（Pi 自有） | `packages/chord`（应用中立）+ Pi 适配层 |
| 作者形状 | 单个（可 async）工厂 `export default function (pi: ExtensionAPI)` | 一个包多个 entry（`contract.ts` / `session.ts` / `tui.ts`），**运行时不互相链接** |
| 连接方式 | 一个聚合 `pi` 对象（`ExtensionFactory`，`core/extensions/types.ts:1588`） | shared service ID + wire contract |
| 运行位置 | 宿主进程，一份代码 | 按 host 拆 bundle，跑在不同进程/环境 |
| 生命周期 | 两阶段绑定：加载期注册 + 运行期回调 | facet `setup(env)` 同步声明 + `onActivate()` 异步初始化 |
| 现状 | **生产路径**；`examples/extensions/` 86 个 `.ts`/`.js` 源文件本轮零改动 | **实验路径**；只能在 repo checkout 里跑（见下） |

**"极简核 + 靠扩展长能力"这个总判断不变**——facet 不是它的反例，而是它的加强版：连最基础的 `Context` 类型都从 `chord` 外挂进来（`packages/agent/src/harness/context.ts` 整段 re-export chord 的 `Context`/`ContextKey`，该文件同时被 `pi-agent-core` 的 `./harness/context` 子路径导出）。

## 术语碰撞（必须显式声明）

"extension" 这个词在 v0.85 以后的 pi-mono 里至少有三个义项：

1. **本目录 2.1-2.4 用的义项**：一个默认导出 `export default function (pi: ExtensionAPI)` 的模块，即 `core/extensions` 的扩展。
2. **`plugins.md` 的义项**：**分发 facet 的包**。原文（`plugins.md` 鸟瞰图第 3 层）："An **extension** may distribute independent host-specific bundles containing **facets**. No aggregate extension object is loaded into all processes."
3. **`plugins.md:949` 的第三种用法**：该文档 "Open decisions" 小节首句 "Before **the extension layer** becomes normative"——这里指整个 facet 扩展层（manifest 格式、信任策略、跨进程版本偏差规则等**还没定稿**的一层），不是一个可执行对象。

**同名不同物。** 本目录（以及 `extensions/03-Patterns/3.1`）不声明义项时一律指义项 1；本节讲的是义项 2/3。

## 状态：哪些是现状、哪些是规格（引用前必须分清）

`packages/agent/docs/mobile-handoff/README.md:22` 自己立了规矩（原文）：

> "**Three units ship working code. Four are specifications.** ... Do not assume a doc describes something that exists."

按此分状态：

| 单元 | 状态 |
|---|---|
| `packages/chord`（facet / service / replicated-state / delta 运行时） | **已落地**（第 11 个包；`ServiceMode = "singleton" \| "keyed"`，`chord/src/types.ts:60`；`defineFacet` / `defineService` / `createFacetHost` / `createRemoteServiceBinding` / `replicatedState` 在 `chord/src/api.ts:66/70/19/84/88`） |
| `packages/coding-agent/examples/plugins/pi-example-plugin/` | **可运行的示例**——但只在 repo checkout 里（`PI_EXPERIMENTAL=1`），**明确不在 npm 包和 standalone binary 里** |
| `packages/agent/docs/plugins.md` | **规格**（`:3` 自述 "Design specification for the experimental facet and service architecture"），但它的抽象**与 chord 代码一致** |
| `packages/agent/docs/mobile-handoff/02-plugins/01-facets/facets.md` | **规格，且核心改动未实现**（见下） |
| `packages/agent/docs/mobile-handoff/02-plugins/02-sandbox/` | **可运行 PoC**（isolated-vm + 字符串膜，412 条断言），**不是产品** |

### 引用 `facets.md` 时必须标为规格

`facets.md:3` 自称 "Design specification. **Supersedes the facet/service model in `plugins.md` where the two disagree.**"——但**它的核心改动在 chord 里全部没有实现**：

| `facets.md` 的规格 | chord 的现状 |
|---|---|
| `ServiceMode = "singleton" \| "keyed" \| "peer"`（`facets.md:42`） | `ServiceMode = "singleton" \| "keyed"`（`chord/src/types.ts:60`）——**没有 `peer`** |
| `definePeerService()`（`facets.md:62`） | `chord` 全树**零命中**；只有 `defineService` / `defineKeyedService`（`chord/src/api.ts:70`） |
| facet 静态 `uses` / `provides` manifest（`facets.md:95-96/113-114`） | chord 没有 manifest 字段；facet 是 `{ id, setup(env) }`（`chord/src/types.ts:227`） |
| sync `construct` + async activate | chord 侧是 `setup(env)` + `onActivate()` |
| 批评 lazy facade（`facets.md:140`"disconnected lazy proxy"） | chord 保留了该设计 |

所以：**引用 `facets.md` 的一切都必须标为"规格"，不能标为"现状"。** 现状以 `packages/chord/src/` 的代码为准——`mobile-handoff/README.md` 自己立的另一条规矩："**If a doc and the code disagree, the code wins**"。

## 影响是什么

1. **"一个工厂函数"不再是全部**：它把 [`03-Patterns/3.1_one_factory.md`](../03-Patterns/3.1_one_factory.md) 的绝对化论断收窄为"凡走 `core/extensions` 的扩展"。这是本篇存在的主要理由。
2. **扩充维度多了一根切法不同的轴**："代码跑在哪个进程/环境"不能归入任何一条已有轴（详见 `composition/10_extension_axes/10i_process_axis.md`）。
3. **"极简核"的判断被加强**：`Context` 这种最基础的机制类型都外挂给了应用中立的 `chord`。
4. **但别当成可用产品**：facet 路径目前只在 repo checkout + `PI_EXPERIMENTAL=1` 下可用。v0.85.0 曾把整个 experimental 远程栈打进 npm 包（消费者一装就 import 失败，#9132），v0.85.1 已把相关依赖降为 `devDependencies` 并排除 `dist/experimental`。
5. **术语纪律**：本节之后凡本目录说"扩展"而未加限定，一律指义项 1（`core/extensions`）。

## 最小例证

**例证 1（形状不同）**：`pi-example-plugin` 有三个互不相连的 entry——`src/session.ts` 提供 remote greeting service，`src/tui.ts` 贡献 `/hello` 并调用该 service，两者之间**没有任何 import 关系**，全靠 `src/contract.ts` 里的 service token。对照 3.1 的 `hello.ts`（26 行、一个工厂、一个 `pi` 对象）：**形状完全不同**。

**例证 2（术语碰撞是真的）**：`plugins.md:57` 那句话里的 "extension" 指"分发 facet 的包"；`extensions/` 全目录里的 "extension" 指"`export default function (pi)` 的模块"。同一个词、同一个仓库、同一版文档，指两样东西。

**例证 3（规格 ≠ 现状）**：`facets.md` 说 service mode 有三种，chord 的代码说两种。照 `facets.md` 写代码会在 chord 里找不到 `definePeerService`。

可观察信号：例证 1 证明"第二条轴"是形状上可观察的事实；例证 2 证明术语限定是必需的；例证 3 证明引用规格文档前必须先对现状取证。
