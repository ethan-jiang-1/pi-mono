# 1.2 消息图：从用户输入到 LLM 可理解消息的转换链

> **⚠️ v0.83.0**：`ai/src/types.ts`(42 commits)。`Provider`→`ProviderId`、`ImagesProvider`→`ImagesProviderId`；`Usage` 新增 `cacheWrite1h`/`reasoning` 字段；`ToolResultMessage` 新增 `usage`/`addedToolNames`；`StreamFn` type 解耦。行号全部失效。

## 现象是什么

pi-mono 处理的消息有三层表示。最外层是 `AgentMessage`——一个联合类型，可以包含标准 LLM 消息（user/assistant/toolResult）和产品自定义消息（notification、artifact 等）。中间层是 `Message`——pi-ai 定义的三种标准角色（UserMessage / AssistantMessage / ToolResultMessage），LLM 协议只能理解这三种。最内层是 provider wire format——每个 provider（OpenAI、Anthropic 等）有自己的一套 JSON 格式。三层之间的转换由 `convertToLlm` 和 `transformContext` 两个钩子控制。

当你看到一个 `assistant` 消息时，它的 `content` 数组不是纯文本——可能包含 `{type: "thinking"}` 块（模型推理过程）、`{type: "toolCall"}` 块（工具调用请求）、`{type: "text"}` 块（正常输出）。每种块都有独立的流式事件类型（`text_start/delta/end`、`thinking_start/delta/end`、`toolcall_start/delta/end`），UI 层可以根据这些事件渲染不同的视觉效果。

## 核心矛盾是什么

**矛盾一：扩展性 vs 类型安全。** 如果 `AgentMessage` 只是一个固定联合类型，产品就不能添加自定义消息类型（比如 notification、artifact）。但如果把 `AgentMessage` 定义成 `any`，就失去了类型检查。pi-mono 的解决方案是 TypeScript 的 **declaration merge**：`AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`，其中 `CustomAgentMessages` 是一个空 interface，产品可以通过 `declare module` 扩展它。

**矛盾二：Agent 层可以有无穷种消息，但 LLM 只理解三种。** `convertToLlm` 钩子的存在就是因为这个矛盾——它负责把 agent 层的自定义消息要么转成 user/assistant/toolResult，要么过滤掉（返回空数组）。不做这个转换，provider 会直接报错。

**矛盾三：消息需要携带 usage 元数据，但这些数据对 LLM 不可见。** `AssistantMessage` 有一个 `usage` 字段（input/output tokens、cache read/write、cost），它还携带了 `provider`、`api`、`model`、`stopReason`、`errorMessage` 等诊断信息。这些字段不会发给 LLM（LLM 只关心 role + content），但对宿主系统（UI、计费、监控）至关重要。

## 实现思想是什么

消息类型体系分三层定义：

### 第一层：pi-ai 的基础消息类型

定义在 `packages/ai/src/types.ts`：

```
UserMessage          { role: "user", content: string | (TextContent | ImageContent)[], timestamp }
AssistantMessage     { role: "assistant", content: (TextContent | ThinkingContent | ToolCall)[], usage, stopReason, ... }
ToolResultMessage    { role: "toolResult", toolCallId, toolName, content: (TextContent | ImageContent)[], isError, details, ... }
```

其中 `AssistantMessage.content` 的三种内容块类型：

- `TextContent`：`{type: "text", text}` — 模型输出的纯文本
- `ThinkingContent`：`{type: "thinking", thinking, redacted?, thinkingSignature?}` — 推理过程（可以被 UI 折叠）
- `ToolCall`：`{type: "toolCall", id, name, arguments}` — 工具调用请求

### 第二层：pi-agent 的 AgentMessage

定义在 `packages/agent/src/types.ts`：

```typescript
export interface CustomAgentMessages {}  // 空 interface，供 declaration merge

export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];
```

`Message` 是从 pi-ai 导入的 `UserMessage | AssistantMessage | ToolResultMessage`。`CustomAgentMessages[keyof CustomAgentMessages]` 默认空 interface 时等价于 `never`——即 `AgentMessage = Message`。当应用或扩展通过 declaration merge 注入类型后，联合类型自动扩展。

### 第三层：coding-agent 的自定义消息扩展

在 `packages/coding-agent/src/core/messages.ts` 中，coding-agent 通过 declaration merge 扩展了 `CustomAgentMessages`：

```typescript
declare module "@earendil-works/pi-agent-core" {
  interface CustomAgentMessages {
    custom: CustomMessage<any>;       // 扩展产生的自定义消息
    bash: BashExecutionMessage;       // 用户直接执行的 bash 命令记录
    // ... 其他产品级消息类型
  }
}
```

这使得 `AgentMessage` 在 coding-agent 上下文中自动包含了这些自定义类型。

### 两条转换链

**链一：上下文预处理（transformContext）**

```
AgentMessage[]  --transformContext--> AgentMessage[]
```

在 LLM 调用之前，`transformContext` 在 AgentMessage 层面操作。典型用途：
- 上下文窗口管理（裁剪旧消息）
- 从外部源注入上下文
- 扩展系统通过 `context` 事件修改消息

**链二：LLM 转换（convertToLlm）**

```
AgentMessage[]  --convertToLlm--> Message[] (UserMessage | AssistantMessage | ToolResultMessage)
```

将 AgentMessage[] 转为 LLM 可理解的消息。默认实现过滤掉所有非 user/assistant/toolResult 角色的消息。coding-agent 的实现更复杂：它还需要处理 `CustomMessage` -> `UserMessage` 的转换（将扩展消息的内容注入为 user 消息）。

两条链的执行顺序（在 `streamAssistantResponse` 中）：
1. `transformContext(messages)` — AgentMessage 层预处理
2. `convertToLlm(messages)` — 转为纯 LLM 消息
3. 构建 `Context { systemPrompt, messages, tools }` 发给 streamSimple

### 消息的 usage 和诊断信息

`AssistantMessage` 携带的元数据：

```
usage: { input, output, cacheRead, cacheWrite, totalTokens, cost: { input, output, cacheRead, cacheWrite, total } }
stopReason: "stop" | "length" | "toolUse" | "error" | "aborted"
errorMessage?: string
diagnostics?: AssistantMessageDiagnostic[]
provider: Provider
api: Api
model: string
responseModel?: string
responseId?: string
```

这些字段在消息被存储到 session 文件后，可以在 UI 中渲染、用于成本统计、用于诊断模型行为。

## 在 Agent 能力面里的影响是什么

1. **Declaration merge 让消息类型可以按产品扩展。** coding-agent 加了 custom/bash 消息，未来其他嵌入 pi-mono 的产品可以加自己的消息类型（比如 artifact/notification），而不需要修改 agent 源码或使用 `any`。缺点是这是模块级全局的——不能在一个进程里对不同 session 使用不同的扩展。

2. **convertToLlm 是 Agent 的"对外接口翻译层"。** 它是唯一决定什么消息发给 LLM 的点。正确的实现可以过滤掉 UI-only 消息、把自定义消息转成 user 消息。如果实现不当（比如把 notification 消息原样传进去），LLM 会看到不合法的消息格式。

3. **transformContext 是上下文管理的注入点。** 相比 convertToLlm（发生在"外层->LLM"的边界），transformContext 发生在 AgentMessage 层，扩展系统和上下文窗口管理都在这个层面操作。两个钩子的职责分离很清晰：transformContext 用于"修改 Agent 看到的消息"，convertToLlm 用于"把 Agent 消息翻成 LLM 语言"。

4. **消息携带的 usage 信息让 cost tracking 成为可能。** 每条 assistant 消息都记录了 token 消耗和 cost，session 文件可以聚合这些数据。这对外部宿主实现自己的 billing/monitoring 很有用。

## 最小例子是什么

```typescript
import { Agent, type AgentMessage } from "@earendil-works/pi-agent-core";
import type { Message } from "@earendil-works/pi-ai";

// 自定义消息类型
interface MyNotification {
  role: "notification";
  text: string;
  timestamp: number;
}

// 通过 declaration merge 注册到 AgentMessage 联合类型
declare module "@earendil-works/pi-agent-core" {
  interface CustomAgentMessages {
    notification: MyNotification;
  }
}

const agent = new Agent({
  initialState: {
    systemPrompt: "You are helpful.",
    model: myModel,
    messages: [],
    tools: [],
  },
  // convertToLlm 过滤掉 notification 消息，LLM 不需要看到 UI 通知
  convertToLlm: (messages: AgentMessage[]): Message[] => {
    return messages.flatMap((m): Message[] => {
      if ("role" in m && m.role === "notification") {
        return [];  // 过滤掉
      }
      if (m.role === "user" || m.role === "assistant" || m.role === "toolResult") {
        return [m as Message];
      }
      return [];
    });
  },
});

// 现在 AgentMessage 类型自动包含 MyNotification：
const notification: AgentMessage = {
  role: "notification",
  text: "Loading model...",
  timestamp: Date.now(),
};
// 类型检查通过，但 convertToLlm 会过滤掉它
```

你会观察到的信号：
- 给 `agent.state.messages` 添加一个 `role: "notification"` 的消息不会导致 LLM 调用失败——`convertToLlm` 过滤了它
- 给 `agent.state.messages` 添加一个 `role: "user"` 的消息会正常被转换成 LLM 输入
- 观察 `agent.state.messages` 可以看到完整的对话历史，包括被过滤的消息（它们留在 agent 层但不到 LLM 层）
