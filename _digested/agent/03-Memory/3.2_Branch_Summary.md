## 现象是什么

当用户在 Session tree 中从当前 leaf 跳转到历史中的某个点（coding-agent 的入口是 `AgentSession.navigateTree(targetId, { summarize, customInstructions, replaceInstructions, label })`，agent-session.ts:2905；session v4 harness 定义了同名操作 `AgentHarness.navigateTree()`）时，pi-mono 会将被"遗弃"的分支内容自动总结为一个分支摘要，作为 `branch_summary` entry 落在跳转目标的位置上（解释：之所以落在跳转目标而非旧分支，是因为旧分支已被"废弃"，后面不再进入上下文；摘要必须位于新路径上才能生效）；后续构建上下文时，这个摘要会以 `branchSummary` role 的消息出现在上下文开头。这样模型就能理解"你之前在这个分支上做了什么，为什么回到了这里"。

**源码位置：** `/packages/agent/src/harness/compaction/branch-summarization.ts`

## 核心矛盾是什么

Session tree 的分支导航创造了"多路径对话历史"。当用户从 branch A 跳到 branch B，再从 B 回到 A 时，模型需要理解：

1. **在 B 上发生了什么？** 这些信息对于理解"为什么回到 A"可能至关重要（例如"在 B 上尝试了方案 X 但失败了"）。（解释：因为模型看不到 B 的原始对话，只有 A 的上下文窗口；B 的内容必须被压缩才能进入 A 的窗口。）
2. **B 上产生的工作产物**（读过的文件、改过的文件）**是否与 A 的任务相关？** 如果相关，模型需要知道。（硬事实：这些产物通过 BranchSummaryEntry.details.readFiles/modifiedFiles 传递，见 branch-summarization.ts:34-39。）
3. **摘要的预算限制：** 不能把 B 的全部对话历史塞进 A 的上下文，成本太高，信息密度太低。（硬事实：tokenBudget 通过 `(model.contextWindow || 128000) - reserveTokens` 计算，默认 reserveTokens=16384，见 branch-summarization.ts:62-79 的 GenerateBranchSummaryOptions 定义。）

## 实现思想是什么

### collectEntriesForBranchSummary

当用户执行跳转时，系统需要确定哪些 entry 需要被总结。算法（`collectEntriesForBranchSummary(session, oldLeafId, targetId)`）：

```
输入: session, oldLeafId (当前 leaf，可为 null), targetId (目标节点)
1. oldLeafId 为 null → 直接返回 { entries: [], commonAncestorId: null }
2. oldPath  = findEntriesOnBranch({ start: oldLeafId }) 的所有 entry id（Set）
   targetPath = findEntriesOnBranch({ start: targetId })
   （findEntriesOnBranch 返回顺序是 start → root，即"从目标向根"）
3. 沿 target → root 方向扫描 targetPath，第一个同时出现在 oldPath 中的 entry
   即 commonAncestorId（两条路径的最深公共祖先）
4. 从 oldLeafId 沿 parentId 向上走到 commonAncestorId，收集这条路径上的所有 entry
5. 反转顺序（使之为从旧到新的时间序）
```

结果是一个"废弃分支"上的 entry 列表（不含公共祖先本身）（解释：公共祖先是两条路径共享的部分，已经被主路径的上下文覆盖，无需重复总结）。这些 entry 被交给 `generateBranchSummary()` 生成摘要。

### prepareBranchEntries

在生成摘要前，需要将 entry 转换为 messages 并限制 token 预算：

```typescript
function prepareBranchEntries(entries: Entry[], tokenBudget = 0): BranchPreparation  // v0.84：参数是 session v4 的 Entry，不是已删除的 SessionTreeEntry
```

转换规则（`getMessageFromEntry`）：

- `MessageEntry`（role ≠ toolResult，含 user/assistant/bashExecution/custom 等）→ 原样提取 message（硬事实：getMessageFromEntry 定义于 branch-summarization.ts:112-129）
- `BranchSummaryEntry` → 创建 branchSummary message
- `CompactionEntry` → 创建 compactionSummary message
- `toolResult` → 跳过（不进入摘要上下文）（解释：toolResult 是 LLM 调用的工具输出，信息量大但价值密度低，跳过它们可以节省 token 空间给更高层的语义摘要）
- `thinking_level_change`、`model_change`、`active_tools_change`、`custom` → 跳过

预算控制：`tokenBudget` 传 0 表示不限。从最新的 entry 开始向前累积，一旦 `totalTokens + tokens` 超出预算即停止；对于 compaction/branch_summary entry，即使会超出预算，只要当前累积小于 90% 预算也会被包含（确保结构性摘要不被丢失）（解释：compaction 和 branch_summary 是结构化摘要，丢失它们会破坏上下文连续性，因此给予优先级保护）。

此外函数会先把嵌套 `branch_summary` entry 的 `details`（readFiles/modifiedFiles）并入 fileOps——这就是跨分支文件操作知识的传递通道：旧分支摘要里记录的文件清单会随下一次摘要继续累积（解释：这样即使经过多层分支跳转，文件操作信息也不会丢失，而是逐层继承到最新摘要）。

### generateBranchSummary

使用与 Compaction（3.1）同族的摘要 prompt（共用 `SUMMARIZATION_SYSTEM_PROMPT`），但是五段格式（没有 Critical Context 段）（硬事实：BRANCH_SUMMARY_PROMPT 定义于 branch-summarization.ts:178-205）：

```
## Goal
[用户在这个分支上想完成什么？]

## Constraints & Preferences
- [约束和偏好]

## Progress
### Done
- [x] [已完成]

### In Progress
- [ ] [进行中]

### Blocked
- [阻塞项]

## Key Decisions
- **[决策]**: [理由]

## Next Steps
1. [后续步骤]
```

与 Compaction 的不同：

- 分支摘要前面有一个固定的 preamble：`"The user explored a different conversation branch before returning here. Summary of that exploration:\n\n"`，这告诉模型：这是一个不同的上下文。（解释：preamble 的作用是让模型立即区分主路径内容和分支摘要，避免混淆"这是用户当前在做什么"和"这是之前在另一个分支上做的"。）
- 分支摘要使用 `maxTokens: 2048`（而非 compaction 使用 `0.8 * reserveTokens`），因为分支摘要的详细程度不需要像 compaction 那么高。（推测：2048 是硬编码值，未来可能随模型上下文能力增长而调整。）
- `tokenBudget = (model.contextWindow || 128000) - reserveTokens`（`reserveTokens` 默认 16384），确保摘要 prompt + 摘要输出不会超出上下文窗口。（硬事实：这段计算在 generateBranchSummary 中，见 branch-summarization.ts 函数体。）
- `customInstructions` 默认以 `Additional focus: ...` 附加在 prompt 后；`replaceInstructions: true` 时则整体替换默认 prompt。（硬事实：GenerateBranchSummaryOptions.replaceInstructions 在 branch-summarization.ts:62-79 中定义。）
- 没有可总结内容时直接返回 `"No content to summarize"`，不调用 LLM。（硬事实：entries 为空数组时跳过 LLM 调用，见 generateBranchSummary 开头校验。）

请求通过 `completeSimpleWithRetries` 走 `Models` 接口（不再传 `apiKey`/`headers`），支持 `RetryPolicy`/`RetryCallbacks`。（硬事实：completeSimpleWithRetries 接受 Models 接口而不是直接传 API key，v0.83 的改动。）摘要末尾与 compaction 一样追加 `<read-files>`/`<modified-files>` 标签。返回 `BranchSummaryResult { summary, usage?, readFiles, modifiedFiles }`。

### branch_summary Entry 持久化

摘要 entry 落在**跳转目标的位置**（而非旧分支上）。coding-agent 中由 `sessionManager.branchWithSummary(branchFromId, summary, details, fromHook?, usage?)`（session-manager.ts:1381-1405）写入：

```typescript
{
  type: "branch_summary",
  id: ...,
  parentId: branchFromId,       // 跳转目标（user message 目标取其父，便于重编辑）
  timestamp: ...,
  fromId: this.leafId ?? "root", // v0.84.3 起 = 跳转前的源 leaf（此前是 newLeafId ?? "root"，d711bd5f0 修正为保留源 leaf）
  summary: "总结文本...",
  details: { readFiles, modifiedFiles },
  usage: ...,
}
```

关键设计：`parentId` 指向跳转后的新 leaf 位置，而非原来废弃分支上的节点（解释：parentId 指向新路径而非旧分支，这样从目标节点向上走树时必然经过这个 branch_summary entry——这是它被注入上下文的物理基础）。这意味着从目标节点向上走树时，会经过这个 branch_summary entry。session v4 的 `BranchSummaryEntry`（session/types.ts:53-59）字段为 `{ type, fromId, summary, details?, usage? }`（parentId/seq/timestamp 由 storage 赋值），不再有 coding-agent v3 entry 上的 `fromHook` 字段。

### 在 buildSessionContext 中的使用

在 `buildSessionContext()`（session v4，context.ts）中，`branch_summary` entry 在其路径位置上被转换为一条 `branchSummary` role 的 AgentMessage。由于摘要 entry 就是跳转后新路径的第一个条目，它通常就是上下文的第一条消息。注意 `defaultContextEntryTransform` 会把最后一个 compaction 之前的所有条目（含 branch_summary）丢掉，因此"跨过一次 compaction 之后"的旧分支摘要不再进入上下文（解释：compaction 会把旧的分支摘要也压缩进 compaction 输出中，所以安全地丢弃原始 branch_summary entry 不会丢失信息）。BranchSummaryEntry 的 `details`（文件操作列表）则通过 `prepareBranchEntries` 与 compaction 的 `extractFileOperations` 参与后续的文件操作追踪。

## 在 Agent 能力面里的影响是什么

- **分支间的连续感：** 用户跳回旧分支时，模型看到的第一条消息就是"你在另一个分支上做了什么"，从而给出连续的建议。（硬事实：branch_summary entry 位于跳转目标之后的第一条，buildSessionContext 将其转为首条 branchSummary 消息。）
- **尝试-回退的工作流：** 用户尝试方案 X → 不满意 → 回到主分支 → 模型理解"方案 X 失败了"而不是从头开始。（推测：这是开发者意图——支持快速实验-回退的交互模式，但尚无用户研究数据验证实际效果。）
- **文件操作的知识传递：** BranchSummaryEntry 的 details 中记录了 readFiles 和 modifiedFiles，且会被后续的 branch summary / compaction 继续吸收，实现跨分支的文件操作累积。（硬事实：prepareBranchEntries 中的 details.fileOps 合并逻辑，见 branch-summarization.ts:132-171。）

## 最小例子是什么

```typescript
import {
  collectEntriesForBranchSummary,
  generateBranchSummary,
} from "@earendil-works/pi-agent-core";
import { createModels, type Models } from "@earendil-works/pi-ai";

const models: Models = createModels(); // getModel 是 Models 接口的方法（models.ts:170），不是顶层函数
const model = models.getModel("anthropic", "claude-sonnet-4-5")!;

// 当前在某个分支上工作，要跳回 main 分支
const oldLeafId = await session.getLeafId();  // "entry-main-branch-tip"
const targetId = "entry-original-question";    // 要跳回的点

// 收集废弃分支上需要总结的 entries
const { entries, commonAncestorId } = await collectEntriesForBranchSummary(
  session, oldLeafId, targetId
);
console.log(`需要总结 ${entries.length} 个 entry，commonAncestorId = ${commonAncestorId}`);

// 生成分支摘要（Models 接口负责 auth；不再传 apiKey/headers）
const result = await generateBranchSummary(entries, {
  models,
  model,
  signal: new AbortController().signal,
  reserveTokens: 16384,  // 默认值，可省略
  retry: { enabled: true, maxRetries: 2, baseDelayMs: 1000 },
});

if (!result.ok) {
  console.error("分支摘要生成失败:", result.error.message);
} else {
  console.log("分支摘要:", result.value.summary.slice(0, 300));
  console.log("读过的文件:", result.value.readFiles);
  console.log("修改过的文件:", result.value.modifiedFiles);
  console.log("摘要调用 usage:", result.value.usage);
}

// 执行跳转 + 持久化（coding-agent 入口）
await agentSession.navigateTree(targetId, { summarize: true });
// branch_summary entry 的 parentId = 跳转目标位置

// buildSessionContext 现在会包含 branchSummary 消息作为第一条上下文
const newContext = buildSessionContext(
  await session.findEntriesOnBranch({ order: "oldestFirst" }),
);
// newContext.messages[0].role === "branchSummary"
// newContext.messages[0].summary 以 BRANCH_SUMMARY_PREAMBLE 开头
```

这个例子展示了分支导航的完整记忆桥梁：收集废弃分支内容 → 生成结构化摘要 → 持久化为 branch_summary entry → 在新上下文中作为前缀注入。
