# 2.4 持久化：让扩充活过重启与分支

## 现象是什么

第四条扩充轴是"持久化"。一个扩展的能力如果只在内存里，`/reload`、重启、fork 之后就丢了。pi 给的答案是：**把扩展状态写进 session 本身**，而不是让扩展自己找地方存。

两条路径：

| 路径 | API | 进不进 LLM context | 用途 |
|---|---|---|---|
| 工具结果 `details` | `execute` 返回 `{ details }` | 不进（details 是给渲染/状态用的） | 工具的私有状态，随 session 走 |
| 自定义条目 | `pi.appendEntry(customType, data)` | **不**进（custom entry 不进 LLM） | 扩展的持久化数据 + 可选的 TUI 渲染 |

外加一个读回机制：`session_start` 时遍历 `ctx.sessionManager.getBranch()`，把散落的 `details` / custom entry 重建回内存状态。

## 核心矛盾是什么

**"扩展有状态"和"session 会分支"是天然冲突的。** 一个 todo 列表，如果在 fork 到旧节点后还指向"最新"的内存数组，分支后 todo 就是错的。所以状态不能存在扩展的全局变量里，必须**存进 session 的条目流里**，让"当前分支"决定"当前状态"。

`todo.ts` 的注释把这一点说透了：

> "State is stored in tool result details (not external files), which allows proper branching - when you branch, the todo state is automatically correct for that point in history."

## 扩充思路是什么

### 判断一：`details` 把"状态"藏进"历史"，分支自动正确（硬事实 + 解释）

`todo.ts` 的 todo 工具每次执行都返回 `details: { action, todos, nextId }`——**完整快照**，不是增量。重建时（`reconstructState`）从 `getBranch()` 顺序重放所有该工具的 tool result，最后一个 `details` 就是当前状态。

关键设计：**状态 = 对"当前分支"上该工具所有结果的重放**。因为 `getBranch()` 返回的是"从根到当前叶"的条目序列，fork 到任意节点后，重放那条分支上的 todo 结果，得到的 todo 就是那个历史时刻的 todo。**扩展不需要理解分支语义，只需要"每次执行存完整快照 + 启动时重放"。**

### 判断二：`appendEntry` 是"不打扰 LLM 的持久化"（硬事实）

`plan-mode/index.ts` 的 `persistState()`：

```typescript
function persistState(): void {
	pi.appendEntry("plan-mode", {
		enabled: planModeEnabled,
		todos: todoItems,
		executing: executionMode,
		toolsBeforePlanMode,
	});
}
```

`appendEntry` 写入的 custom entry **不参与 LLM context**（`docs/extensions.md` 明确），但会持久化在 session 里、且能配 `registerEntryRenderer` 在 TUI 里显示。恢复时 `session_start` 从 entries 里 `.filter(e => e.customType === "plan-mode").pop()` 拿最后一份。

**关键：** 这条路径解决的是"扩展想存状态，但不想让状态污染 LLM 上下文"的问题。工具 `details` 是"搭便车"（状态跟着 tool result 走），`appendEntry` 是"专用货位"（显式存、可选显示、永不进 context）。

### 判断三：`session_start` 是统一的"重建点"（硬事实）

几乎所有有状态的示例，都在 `session_start` 里做同一件事——遍历 `getBranch()`/`getEntries()` 重建内存：

- `todo.ts`：重放 tool result 的 `details`
- `plan-mode/`：读最后一个 `customType === "plan-mode"` entry
- `preset.ts`：读最后一个 `customType === "preset-state"` entry

这就是**持久化的完整闭环**：写（`details` / `appendEntry`）→ 存（session JSONL）→ 读（`session_start` 遍历）→ 重建（内存变量）。核提供"条目流 + 遍历 API"，扩展自己决定"存什么、怎么重建"。

### 判断四：session 树让"状态"自然获得"时间旅行"能力（解释）

因为状态是"沿分支重放"得到的，扩展状态**自动支持 fork / clone / navigateTree**：fork 到某个历史点，那条分支上的 `details`/entry 就重放出那个历史点的状态。扩展作者不需要写任何分支逻辑——**持久化的正确性由"状态存在条目流里"这个选择白送**。

这是"存进 session"和"存外部文件"的本质区别：外部文件是"全局唯一的最新值"，session 条目流是"沿时间轴的值序列"。后者天然适配 pi 的 session 树模型（见 `agent/03-Memory`）。

## 影响是什么

1. **有状态扩展的成本被压到"存快照 + 重放"**。todo 这种典型有状态工具，核心就是 `details: { todos }` + `session_start` 里一个 for 循环。
2. **分支正确性是白送的**（硬事实）。扩展不碰分支 API，就能在 fork 后得到正确状态——这是"状态进 session"这个选择的直接红利。
3. **但状态模型要作者自己设计**：存完整快照还是增量、多久存一次（`plan-mode` 每次 turn 都 `persistState`）、重建时去重还是取最后——这些是扩展的自由，也是扩展的责任。核只保证"条目流可靠、可遍历"。

## 源码/示例锚点

- `todo.ts`：`details: { todos, nextId }` 快照 + `session_start` 里 `reconstructState()` 重放（注释明说"branching automatically correct"）
- `plan-mode/index.ts`：`persistState()` 用 `appendEntry("plan-mode", ...)` + `session_start` 读回（含 resume 时重扫 `[DONE:n]` 的细节）
- `preset.ts`：`appendEntry("preset-state", { name })` + `session_start` 恢复 preset 名
- `docs/extensions.md`："State Management" 一节：`details` 持久化的官方范式

## 最小例证是什么

**例证 1（快照 + 重放）：** `todo.ts` 的 todo 工具每次执行返回**完整** `todos` 数组（不是"add 一条"增量），重建时重放该分支所有结果取最后。这是"状态正确性不依赖扩展记性"的关键——即使中间某次快照丢了，只要最后一份在，状态就全。

**例证 2（不进 context 的持久化）：** `appendEntry("plan-mode", ...)` 写出的 entry `display: false` 且不进 LLM context。这意味着 plan-mode 存了一堆"我开没开、有哪些 step"的状态，但 LLM 完全看不见这些管理数据。持久化不污染对话。

**例证 3（fork 自动正确）：** 设想 todo 有 A/B/C 三条，在"两条时" fork 出去一个分支，那条分支上的 `getBranch()` 只含 A/B 两条的快照，重放得到 2 条 todo；主干继续到 3 条，重放得到 3 条。**同一套重建代码，两条分支各得各的正确答案**——扩展一行分支逻辑都没写。

可观察信号：例证 1 证明"快照"让状态可重建；例证 2 证明持久化不污染 context；例证 3 证明"存进条目流"白送分支正确性。三者同成立，才说"持久化"是扩充的第四条轴。
