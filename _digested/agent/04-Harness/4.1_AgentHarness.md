# 4.1 AgentHarness v2：`AgentLane` 骨架与它的存储地基

> **⚠️ 版本史**：本文最初基于 v0.75.3 的泛型 `AgentHarness<TSkill, TPromptTemplate, TTool>`（typed hook wrapper）编写；v0.83 加入 `TContext`；**v0.84.0 把这套泛型设计整体删除**，重写为零泛型的 `class AgentHarness implements AgentLane` 骨架。**2026-08-17 已对照 v0.84.2 复核，正文已重写至 v0.84.2 现实。**
>
> **结论先行**：今天做产品集成不要用 `AgentHarness`——它的绝大多数操作抛 `HarnessNotImplemented`。产品级集成走 coding-agent 的 `AgentSession` / SDK（`createAgentSession()`，`packages/coding-agent/src/core/sdk.ts:171`）。这条 harness v2 线是 upstream 的在建工程：先冻结 `AgentLane` 接口契约和结果类型，再逐个填实现。

## 现象是什么

`Agent`（`packages/agent/src/agent.ts`）只做最纯粹的 LLM 对话循环：收消息列表、调 LLM、执行 tool call、吐事件。它不知道 session 的存在，不管 compaction，也没有 hook 机制。直接用 `Agent` 意味着自己管持久化、自己拼 context、自己实现 steer/followUp 队列。（解释）

因此 Agent 之上需要一层 harness——这一点从 v0.75 到 v0.84 从未变过，**变的是这层由谁来实现**：

- **产品现实**：coding-agent 的 `AgentSession`（`packages/coding-agent/src/core/agent-session.ts:305`）就是这层包装的活实现。（硬事实） 它有 `prompt()`（L1116）、`steer()`（L1343）、`followUp()`（L1363）、`compact()`（L1790）、`navigateTree()`（L2905）、`abort()`（L1550），把 session 写入、extension hook、权限拦截（`_installAgentToolHooks()`，L479）全部串起来。TUI/RPC/SDK 都建立在它上面。
- **upstream 在建工程**：`packages/agent/src/harness/agent-harness.ts`（v0.84.2 全文仅 508 行）里的 `AgentHarness implements AgentLane`（L305）是一副**新骨架**（解释）：操作面已经用 `AgentLane` 接口完整定义（L271），但当前实现大多是 stub——`prompt()`/`compact()`/`steer()` 等 22 个操作全部 reject `HarnessNotImplemented`，`create()` 遇到已有 record 的 session 直接抛 `HarnessNotImplemented("create.restore")`（L351）。（硬事实）

## 核心矛盾是什么

老的矛盾仍然成立：**循环的核心逻辑不应该知道 session，但产品功能必须依赖 session。**（解释） `Agent` 保持纯净，session 感知/权限/compaction/队列由上一层负责——`AgentSession` 一直在证明这个分层可行。

v2 引入了第二条轴线，解释了为什么 upstream 宁可先发一副空骨架：

1. **契约优先 vs 行为优先**（解释）。v0.83 的泛型 harness 边做边改（三个版本改了三次签名）。（硬事实） v2 反过来：先把"一个 lane 能被怎样操作、每种操作怎样成功/怎样被拒绝/怎样挂起恢复"用类型钉死（`AgentLane` + `Result` + `TaggedError`），实现可以慢慢填，集成方代码先稳定下来。
2. **可推断的持久化 vs 灵活的内存行为**（解释）。v2 的每个操作都要能落进 session v4 的 record log、能在 crash 后恢复或显式 suspend（`SuspendedOperation.reason: "crash" | "deferred"`），甚至能以确定性步进方式重放（`drive: "manual"` + `ActionInfo`）。这比"在事件回调里随手改状态"严格得多，所以 `AgentSession` 那套活实现不能直接搬进来，只能重写。

## 实现思想是什么

### 1. `AgentLane`：操作面即契约（`agent-harness.ts:271`）

一个 lane 是 session tree 里的一条分支。接口按功能分组：

- **发起运行**：`prompt(text, images?)` / `prompt(message | message[])`（重载）、`skill(name, additionalInstructions?)`、`promptFromTemplate(name, args?)`
- **会话维护**：`compact(options?)`、`navigateTree(targetId, options?)`（`NavigateOptions` 支持自定义 summary 指令和 label）
- **恢复与中断**：`resume()`、`abort()`（返回被中止 run 的 steer/followUp 队列内容）
- **队列**：`steer()` / `followUp()` / `nextRun()`（各自接受 text 或 message 重载）、`cancelQueued(entryId)`
- **观测**：`watch(): Promise<WatchHandle<LaneSnapshot>>`（快照 + 增量事件）、`recordUsage()`
- **空闲调度**：`waitForIdle()`、`runWhenIdle(cb)`
- **手动驱动**：`peekAction()` / `executeAction()` / `runToCompletion()`（配合 `AgentHarnessOptions.drive: "manual"`）
- **配置**：`getModel/setModel`、`getThinkingLevel/setThinkingLevel`、`getActiveTools/setActiveTools`
- **存储出口**：`readonly session: SessionTree`（session v4，见 [3.5 Session v4](../03-Memory/3.5_Session_v4.md)）

`AgentHarness` 自身还有一小批 lane 之外的多 lane/配置方法：`lane()`、`createLane()`、`lanes()`、`watchSession()`，以及 `getTools/setTools`、`getResources/setResources`、`getStreamOptions/setStreamOptions`、`getRetryPolicy`、`getCompactionSettings`、`getSteeringMode/getFollowUpMode` 等 getter/setter（L453-501）。

### 2. 结果类型体系：失败是值，不是异常

v2 用 `harness/result.ts` 的 `Result<TValue, TError>`（`ok | error` union）承载所有可预期失败，错误本体是一组 **TaggedError**（`agent-harness.ts:28-55`，工厂在 `result.ts:28`，可用 `matchError()`（`result.ts:57`）按 `_tag` 穷尽匹配）：

- **拒绝类**（调用没被接受）：`LaneBusy`、`InvalidMessage`、`UnknownSkill`、`UnknownTemplate`、`NothingToCompact`、`NothingToResume`、`UnknownTarget`、`UnknownQueueItem`、`NoActiveRun`、`NoActiveOperation`、`MissingIdentities`、`LaneExists`、`InvalidLane`、`Closed`
- 每个操作有专属拒绝 union：`RunRejected = LaneBusy | InvalidMessage | UnknownSkill | UnknownTemplate | Closed`（L105），其余见 L106-111

**结果类**（调用被接受后的结局）是 discriminated union：

- `RunOutcome`（L89）：`completed` / `aborted` / `failed`（带 `OperationError`）/ **`suspended`**（带 `DeferredHandle`——provider 侧延迟句柄，之后 `resume()` 取回）
- `CompactionOutcome`（L95）：`completed`（带 `CompactionEntry`）/ `declined` / `aborted` / `failed`——hook 可以"谢绝"一次压缩
- `NavigationOutcome`（L100）：`completed`（带 `newLeafId` 和可选 `BranchSummaryEntry`）/ `declined` / `aborted` / `failed`
- `ResumeOutcome`（L127）：三种操作 outcome 的合并（`RunOutcome`/`CompactionOutcome`/`NavigationOutcome` 共享的 `completed` 分支带 `operation` 标签）

### 3. 挂起/恢复与手动驱动：把"运行中"变成可持久化的状态

- `SuspendedOperation`（L140）描述一个被挂起的操作（硬事实）：kind（run/compaction/navigation）、`reason: "crash" | "deferred"`、原始 prompt、`missing: { tools, models }`（恢复时缺的身份）——这正是 `MissingIdentities` 拒绝类型存在的原因（解释）：恢复一个 run 需要当时用到的 tool 和 model 都还注册着。
- `ActionInfo`（L182）把 harness 的每一步执行枚举成可观察的 action：`append_entry`、`move_lane`、`set_fact`、`try_finish_run`、`finish_operation`、`consume_queue_item`、`stream_assistant`、`execute_tool`、`fetch_deferred`、`hook`、`sleep` 等（硬事实）。`peekAction()`/`executeAction()` 允许宿主逐步驱动（`drive: "manual"`），`runToCompletion()` 则一路跑完——这是为确定性重放/测试/审计设计的执行模型。（解释）
- `HarnessTool = AgentTool & { replay?: "never" | "safe" }`（L237）：工具要声明重放语义。
- hook 面收敛为 11 个 `HookName`（L198）：`before_run`、`before_resume`、`before_run_end`、`transform_context`、`before_request`、`before_payload`、`after_response`、`before_tool`、`after_tool`、`before_compaction`、`before_navigation`——比 v0.83 的事件族小得多，且通过 `HookSet.on()`（L212）注册而非泛型 event map。

### 4. 当前骨架的精确边界

构造是私有的，必须走 `AgentHarness.create()`（L347）：

```typescript
static async create(options) {
	const [record] = await options.session.findRecords({ limit: 1 });
	if (record !== undefined) throw new HarnessNotImplemented("create.restore");
	return { harness: new AgentHarness(options), suspended: [] };
}
```

只接受**空 session**（硬事实）；任何已有 record（包括上次运行留下的）都会撞上 `create.restore`。`suspended` 恒为 `[]`（硬事实）。其余边界：

- 22 个操作经 `unavailable()`（L355）reject `HarnessNotImplemented`（closed 后改抛 `HarnessClosed`）：`prompt`、`skill`、`promptFromTemplate`、`compact`、`navigateTree`、`resume`、`abort`、`steer`、`followUp`、`nextRun`、`cancelQueued`、`recordUsage`、`waitForIdle`、`runWhenIdle`、`peekAction`、`executeAction`、`runToCompletion`、`watch`、`lane`、`createLane`、`lanes`、`watchSession`
- `hooks.on` / `events.on` 由 `UnavailableRegistry`（L219）实现，直接 throw
- **已实现**：`getLeafId()`（委托私有 `durableSession`（L310），L359）、全部配置 getter/setter（`getModel/setModel` L422-426、`getThinkingLevel/setThinkingLevel` L428-432、`getActiveTools/setActiveTools` L434-439、`getTools/setTools` L455-462、`getResources/setResources`、`getStreamOptions/setStreamOptions`、`getRetryPolicy`、`getCompactionSettings`、`getSteeringMode/getFollowUpMode`——均返回防御性拷贝）、`close()`（L505）

### 5. 存储地基：session v4

`AgentHarnessOptions.session` 要求 v4 的 `Session`（`session/session.ts:102`，实现 `SessionTree`，`session/types.ts:328`），`create()` 用 `findRecords()` 探测、`getLeafId()` 直接读它。配套的 `harness/reducer.ts`（667 行）实现了 record log 的重放与损坏检测（`RecordLogCorruption`，枚举 single-writer 协议不可能产生的矛盾状态如 `multiple_open_operations`、`queue_after_abort`）——这就是"create.restore 尚未实现"背后正在铺设的恢复管道。详见 [3.5 Session v4](../03-Memory/3.5_Session_v4.md)。

### 6. v0.83 泛型设计的去向

四个泛型参数（`TContext/TSkill/TPromptTemplate/TTool`）全部移除：`Resources = AgentHarnessResources<Skill, PromptTemplate>`（L238）、`HarnessTool`（L237）、`toolContext?: object | (() => object | Promise<object>)`（L250，per-turn resolve 的零参工厂）。`AgentHarnessTool<TContext,...>` 类型本身还在 `harness/types.ts:81` 供工具 factory 使用（见 4.7），但 harness 类不再泛型化。

## 在 Agent 能力面里的影响是什么

1. **产品集成路径不变**（硬事实）：TUI/RPC/SDK 继续走 `AgentSession`。`AgentHarness` v2 当前没有任何可跑的行为，把它接进产品只会拿到 `HarnessNotImplemented`。（硬事实）
2. **面向接口编程有了正式契约**（解释）：需要 harness 语义的集成方应依赖 `AgentLane` 类型而不是 `AgentHarness` 类——upstream 承诺的是接口稳定性。
3. **错误处理范式转向**（解释）：`Result` + `TaggedError` 意味着"lane 正忙""没有可恢复的操作"这类可预期失败成为返回值，TypeScript 能强制穷尽处理；throw 只留给 `HarnessFault`/`HarnessClosed`/`HarnessNotImplemented` 这类基础设施错误（L57-82）。（硬事实）
4. **suspended 是一等结局**（解释）：长任务可以以 `suspended + DeferredHandle` 结束并在之后 resume，这为跨进程/跨重启的 agent 运行铺路（推测）——`AgentSession` 目前没有这个能力。（硬事实）

## 最小例子是什么

```typescript
import { AgentHarness, HarnessNotImplemented, HarnessClosed } from "@earendil-works/pi-agent-core";
import { Session, InMemorySessionStorage } from "@earendil-works/pi-agent-core"; // session v4

// 1. 空 session 上 create 成功
const session = new Session(new InMemorySessionStorage({ id: "demo", createdAt: 1 }));
const { harness, suspended } = await AgentHarness.create({
	session,
	models: createModels(),
	model: getBuiltinModel("google", "gemini-2.5-flash"), // 顶层 getModel 在 compat.ts（= getBuiltinModel）；providers/all.ts 直接导出 getBuiltinModel
});
// 观察到的信号：suspended === []，harness.name === "main"，
// await harness.getLeafId() === null（这是极少数已实现的方法）

// 2. 一切操作显式拒绝
await harness.prompt("hello");
// 拒绝值: { name: "HarnessNotImplemented", operation: "prompt" }
// （不是 throw，是 rejected promise；closed 后同样的调用变成 HarnessClosed 实例）

// 3. 有 record 的 session 无法打开
await session.appendRecord({ type: "operation_started", id: "run-1", lane: "main", /* ... */ });
await AgentHarness.create({ session, models, model });
// 拒绝值: { name: "HarnessNotImplemented", operation: "create.restore" }

// 4. 产品集成走这条线（不是 AgentHarness）
import { createAgentSession } from "@earendil-works/pi-coding-agent";
const { session: agentSession } = await createAgentSession({ cwd: process.cwd() });
await agentSession.prompt("What files are here?"); // 真正会跑起来的路径
```

可验证信号：第 2 步在 v0.84.2 工作树上必然得到 `operation: "prompt"` 的 `HarnessNotImplemented`（scaffold 测试 `rejects every unfinished public operation explicitly` 逐项断言了 22 个操作）；第 4 步的 `createAgentSession` 才会真的发起 LLM 调用。关键要点：**`AgentLane` 是契约，`AgentSession` 是现实，`AgentHarness` 是 upstream 承诺中的未来。**
