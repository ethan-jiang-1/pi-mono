# 5.3 正确路径的摩擦差：范本、合同与门禁

> **局部复核锚点**：`cb18c7cbc89d5becbb4ea2e490a6e7ad0e989f04`。摩擦差是研究者的分析视角，历史出处见 [方法声明](README.md)。未测量维护成本，不作数量级比较。

## 现象是什么

Pi 为扩展作者提供当前 docs、examples、类型与错误消息；为核心贡献提供范围纪律和 review 门。二者帮助用户找到可行路径，但不能将“往 core 加功能”全部称为错误路径。

来源：[扩展合同](../../../packages/coding-agent/docs/extensions.md)、[examples](../../../packages/coding-agent/examples/extensions/)、[贡献哲学](../../../CONTRIBUTING.md#philosophy)。

## 核心矛盾是什么

教学材料与机器检查解决不同问题：范本展示用法，类型限制接口，测试验证具体行为，review 判断责任与语义。任何一层都不能独立证明完整正确性；需要关注**各层覆盖什么、哪里仍需判断**，而不是给它们排一个无依据的成本等级。

## 设计判断是什么

### 1. 正确路径由范本、合同、提示与检查共同铺设

[根 tsconfig](../../../tsconfig.json#L56-L57)把多数 examples 纳入类型检查，但排除 gondolin。[Agent.prompt 的错误消息](../../../packages/agent/src/agent.ts#L374-L378)引导运行中输入使用 `steer()`/`followUp()`。[扩展事件合同](../../../packages/coding-agent/docs/extensions.md#events-and-concurrency)明确顺序和并发，不能说组合行为“完全没有合同”。

这些事实支持“Pi 帮助用户沿正确路径实现能力”的解释；不证明范本唯一可靠、维护成本低一个数量级，也不证明所有组合都有完整规范。

### 2. 文档漂移与组合语义仍是实际风险

类型检查不能验证任意 Markdown 描述的语义；范本能 typecheck 也不保证权限、资源清理或恢复正确。发现旧文档与当前 API 不符时，要回到实现和测试，而不是先判“没有漂移只是运气”。

[AGENTS](../../../AGENTS.md#commands)给检查 standing orders，[CONTRIBUTING](../../../CONTRIBUTING.md#before-submitting-a-pr)给贡献前检查要求。它们已经是判断的外置；不能因不是可调用 skill，就说判断都留在人脑。针对具体复杂流程是否需要更多辅助，应逐项评估。

### 3. 负例测试确实存在，规则覆盖与规则合理性仍要分开

[package.json](../../../package.json#L20-L27)把 runtime-deps 检查纳入 `check`；[负例测试](../../../scripts/check-runtime-deps.test.mjs#L27-L34)制造未声明依赖并断言失败，[其它负例](../../../scripts/check-runtime-deps.test.mjs#L57-L99)验证 dev-only 依赖和排除源文件的拒绝行为。根 [test:scripts](../../../package.json#L38-L39)会运行这些脚本测试，**不是说 `npm run check` 自己就运行它们**。

这直接反驳“Pi 不测试门禁负例”。但一组负例也不能证明全部门禁覆盖充分，更不能证明模块图预算的数值永远合理。**实现符合当前规则，与当前规则是否仍合适，是两个问题。** 本次没有做全门禁覆盖率审计。

## 影响是什么

1. **作者**：结合当前文档、近期范本与类型声明实现能力，按规则运行针对性检查；不要仅靠抄范本。
2. **评估者**：分别查类型、运行时合同、正反例测试、review，而不是只数脚本或示例。
3. **维护者**：新增门禁时说明拒绝哪些错误、配什么回归用例，并单独考虑预算和规则何时复核。

## 最小例证

- 一个未声明 runtime 依赖会被检查拒绝，测试还验证这种拒绝；这是“检查自身被测试”的具体证据。
- 一个扩展使用合法 API 却泄漏 watcher，可能通过类型检查；其生命周期仍需按 docs、行为测试与 review 核对。这才是范本/类型路径的真实边界。
