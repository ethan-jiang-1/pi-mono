# 4.3 System Prompt：从哪里来，怎么拼出来

> **⚠️ v0.83.0**：`system-prompt.ts` 仅 import style 变化。AgentHarness 去泛型化后 `systemPrompt` 选项简化为零参工厂（见 4.1）。
>
> **⚠️ v0.84.2**：v0.84 修复 custom system prompt 把 cwd 与后续内容拼接的 bug（custom 路径现在以 `\nCurrent working directory: ...\n` 结尾，`system-prompt.ts:69`）；v0.84 的 `buildSystemPrompt()` **不再注入日期**、guidelines 改为从工具定义聚合。2026-08-17 已对照 v0.84.2 复核，正文已修正至 v0.84.2。
>
> **⚠️ v0.84.3**（2026-08-25 核对）：条件 guideline "Use bash for file operations like ls, rg, find" 的条件从 `有 bash 且没有 grep/find/ls` 放宽为 `（有 bash 或 powershell）且没有 grep/find/ls`，三分支文本在 `core/system-prompt.ts:105-110`；tool snippet 聚合同样感知 PowerShell（`powershellToolSystemPromptContribution`）。正文 L44 的条件表述需加 `|| powershell`。

## 现象是什么

pi-mono 启动后，LLM 看到的 system prompt 不是一段写死的文本，而是多层拼合的结果。不同 mode（interactive、print、RPC）可能通过 `customPrompt`/`appendSystemPrompt` 产生不同的 system prompt。 （硬事实）

最终送到 LLM 的 system prompt 包含：
- 基础 agent prompt（你是谁、有什么工具、怎么用）
- skills 列表（`<available_skills>` XML block，需要 read 工具可用）
- 项目上下文（`AGENTS.md`、`CLAUDE.md` 等）
- 工作目录（**v0.84.2 已无日期注入**）
- extensions 可能通过 `before_agent_start` 事件修改

## 核心矛盾是什么

System prompt 的构建有几个互相拉扯的力量：

1. **基础 prompt 是静态的**，但 tools/guidelines 会变（哪些工具可用？哪些 guidelines 适用？） （解释）
2. **Skills 来自文件系统**，是运行时发现的，不能硬编码 （解释）
3. **Skills 只在 read 工具可用时才有意义**——`<available_skills>` 的消费方式是"用 read 工具读 SKILL.md"，没有 read 工具时列出目录是误导 （解释）
4. **Extensions 可能在最后一刻修改** system prompt （解释）
5. **Custom prompt 和 default prompt 走完全不同的构建路径** （硬事实）

## 实现思想是什么

### 两层 system prompt 构建

pi-mono 有两个 system prompt 构建点，位于不同层级：

**Layer 1 - AgentHarness 层（`packages/agent/src/harness/`）**

`AgentHarnessOptions.systemPrompt` 是 `string | (() => string | Promise<string>)`（`agent-harness.ts:251`）——v0.84.2 里工厂是**零参**的（v0.83 曾接收 `{ env, session, model, ... }`，去泛型化时移除）。注意这只是契约：当前 harness 骨架根本不跑 turn（见 4.1），真正的动态构建发生在下一层。 （硬事实）

**Layer 2 - AgentSession 层（`packages/coding-agent/src/core/`）**

`AgentSession._rebuildSystemPrompt()`（`agent-session.ts:1023`）收集当前状态后调用 `buildSystemPrompt()`（`core/system-prompt.ts:28`）完成拼装：

1. **基础 agent 身份**：固定文本 "You are an expert coding assistant operating inside pi..."（L121）
2. **工具列表**：`selectedTools`（默认 `["read", "bash", "edit", "write"]`，L81）中**只有提供了 snippet 的工具**才出现在 `Available tools:` 段落（L80-84），一个都没有时显示 `(none)`
3. **Guidelines**：三个来源合并去重（`addGuideline`，L89-95）——工具定义自带的 `promptGuidelines`（由 AgentSession 从 `_toolPromptGuidelines` 聚合传入，`agent-session.ts:1028-1041`）；条件 guideline "Use bash for file operations like ls, rg, find"（仅当有 bash 且**没有** grep/find/ls 工具时，L104）；固定的 "Be concise" 和 "Show file paths clearly"（L116-117）
4. **Pi 文档指引**：**无条件**（不依赖 read 工具）附上 README/docs/examples 路径和"用户问到 pi 自身时才读"的指引（L74-77、L131-138）
5. **Skills 块**：如果有 skills **且 read 工具可用**，调用 `formatSkillsForPrompt(skills)` 生成 `<available_skills>` block（L154-157）
6. **项目上下文**：`<project_context>` 块包含 `AGENTS.md` 等上下文文件内容（L145-152）
7. **CWD**：最后加上 `Current working directory: /path/to/project`（L159；v0.84.2 不再注入 `Current date`）

### Skills 格式化函数有两份

- harness 线：`formatSkillsForSystemPrompt()`（`agent/src/harness/system-prompt.ts:3`）
- 产品线（`buildSystemPrompt` 实际用的）：`formatSkillsForPrompt()`（`coding-agent/src/core/skills.ts:355`）

两者都过滤 `disableModelInvocation === true` 的 skills、生成 name/description/location 三字段的 `<available_skills>` XML、所有字段经 `escapeXml()` 转义（`&<>"'`）、提示 LLM 相对路径按 skill 目录解析。差别只在头部措辞（harness 版 "Read the full skill file..."，产品版 "Use the read tool to load a skill's file..."）。 （硬事实）

### Custom prompt 路径的特殊性

当 `customPrompt` 被提供时（`system-prompt.ts:46-72`），构建路径完全不同：

- 不生成默认的 agent 身份文本、工具列表和 guidelines
- `appendSystemPrompt` 仍然追加（L49-51）
- 仍然追加 context files 和 skills（如果有 read 工具，L54-67）
- 仍然追加 CWD，且 v0.84 修复后以 `\nCurrent working directory: ...\n` 形式结尾，不会再把 cwd 和后续拼接内容粘在一起（L69）

这意味着：**custom prompt 让调用方完全控制 agent 的身份和行为定义**，但上下文和技能注入不受影响。 （解释）

### Model routing 对 system prompt 的影响

v0.84.2 的 `buildSystemPrompt()` 是 **model 无关**的：没有任何 per-model 分支（旧版文档描述的 "OpenAI Codex 需要 static system prompt" 的特殊处理在当前代码中不存在，codex 只出现在 context window 注释和 model alias 里）。模型差异由更底层的 adapter/stream 层消化，system prompt 构建不感知模型。 （硬事实）

### Extension 对 system prompt 的修改

在 AgentSession 中，构建 system prompt 后会通过 ExtensionRunner 触发 `before_agent_start` 事件（`agent-session.ts:1233`）。Extension handler 可以返回修改后的 system prompt：

```typescript
const result = await this._extensionRunner.emitBeforeAgentStart(
  expandedText, currentImages, this._baseSystemPrompt, this._baseSystemPromptOptions
);
if (result?.systemPrompt !== undefined) {
  this._systemPromptOverride = result.systemPrompt;
  this.agent.state.systemPrompt = result.systemPrompt;
} else {
  // 回落：上一轮的 override 不跨轮残留
  this._systemPromptOverride = undefined;
  this.agent.state.systemPrompt = this._baseSystemPrompt;
}
```

这意味着 extensions 是 system prompt 的**最后修改者**，且修改只对当轮生效——下一轮没有 handler 返回时自动回到 `_baseSystemPrompt`。此外 handler 还能通过 `ctx.getSystemPrompt()` 读到"前面 handler 改过的"当前值（runner.ts:1092）。 （硬事实）

### 指令声明的层次

System prompt 的指令存在优先级层次： （解释）

1. **AgentSession 构建的基础 prompt**（最高层，定义 agent 核心身份）
2. **Tools 带来的 guidelines/snippets**（中层，随工具动态变化，`refreshTools()` 后重建）
3. **Skills 注入的领域知识**（通过 `<available_skills>` 和 skill invocation）
4. **项目上下文文件**（`AGENTS.md` 等，代表项目级别的持久化偏好）
5. **Extension 修改**（应用层，可以在最后一刻加入指令，仅当轮生效）
6. **Custom prompt**（覆盖层，完全替换基础 identity） （解释）

## 在 Agent 能力面里的影响是什么

1. **System prompt 是能力注入的主要入口**。工具的 snippet/guidelines 与 skill 列表都由"当前激活了什么"决定。 （解释）

2. **"谁最后改谁做主"的冲突模型**。Extensions 在 `before_agent_start` 中修改 system prompt 的权力最高，但 custom prompt 在 AgentSession 层可以完全替换基础 prompt；extension 的修改按轮失效，避免漂移。 （解释）

3. **Skills 通过 system prompt 被发现，通过 user message 被消费**。Skills 在 system prompt 中作为目录存在，在 user message 中作为内容注入（`/skill:name`，见 4.2）。 （硬事实）

4. **read 工具是 skills 注入的闸门**。没有 read 工具时 `<available_skills>` 整块不生成，避免给 LLM 一个无法兑现的承诺。 （硬事实）

## 源码锚点 （以下均为硬事实）

- `packages/coding-agent/src/core/system-prompt.ts`（162 行）：`buildSystemPrompt()`（L28）、custom prompt 分支（L46-72）、guidelines 聚合（L87-119）、基础身份与文档指引（L121-138）、skills/CWD 追加（L154-159）
- `packages/coding-agent/src/core/agent-session.ts`：`_rebuildSystemPrompt()`（L1023）、`emitBeforeAgentStart` 调用与 override 应用（L1233-1260）
- `packages/coding-agent/src/core/skills.ts`：`formatSkillsForPrompt()`（L335）——`buildSystemPrompt` 实际使用的 skills 格式化

## 最小例子是什么

```typescript
// buildSystemPrompt 是 coding-agent 内部函数（不在包的公开 exports 里），
// 仓库内从模块路径引用；SDK 用户通过 settings 的 system prompt / tools 配置间接影响它
import { buildSystemPrompt } from "./core/system-prompt.ts";

// 1. 基础 system prompt（无 custom prompt）
const prompt = buildSystemPrompt({
  cwd: "/home/user/project",
  selectedTools: ["read", "bash", "edit", "write"],
  toolSnippets: {
    read: "Read file contents",
    bash: "Execute bash commands",
    edit: "Edit files with exact text replacement",
    write: "Write or overwrite files",
  },
  skills: [
    { name: "deploy", description: "Deploy the application", content: "...", filePath: "..." },
  ],
  contextFiles: [
    { path: "AGENTS.md", content: "Always use TypeScript strict mode." },
  ],
});

// 输出包含：
// - agent 身份
// - Available tools 段落（只列提供了 snippet 的工具）
// - Guidelines（工具 guidelines + "Use bash for file operations..." + Be concise/Show file paths）
// - Pi 文档路径指引（无条件）
// - <available_skills> XML block（有 skills 且 selectedTools 含 read）
// - <project_context> 块
// - "Current working directory: /home/user/project"（结尾，无日期行）

// 2. Custom prompt（完全替换基础身份）
const customPrompt = buildSystemPrompt({
  customPrompt: "You are a Python expert. Always use type hints.",
  cwd: "/home/user/project",
  skills: mySkills,
  contextFiles: myContextFiles,
});
// 不包含默认 agent 身份、工具列表、guidelines、Pi 文档指引
// 仍然包含 context files、skills（若有 read）、CWD
```

可观察信号：在第 1 个例子里把 `selectedTools` 改成 `["bash", "edit", "write"]`（去掉 read），重新构建——`<available_skills>` 块会整体消失，但 "Available tools" 与文档指引仍在；这正是 read 闸门在起作用。
