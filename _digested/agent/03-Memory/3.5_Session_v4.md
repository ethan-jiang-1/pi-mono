## 现象是什么

durable 的 session 不再是"一棵 entry 树 + values 寄存器 + operation 流水"，而是**四张表 + 文档 incarnation + 严格单调 seq**（解释）：

1. **四类 record**（`StorageWrite` 联合，`types.ts:686-702`）：`conversation`（会话记录，含 ownership）、`entry`（不可变对话条目）、`task`（durable 任务，含 checkpoint/outcome）、`submission`（准入请求），外加四态 document 写（`document.create/copy/change/retire`）。（硬事实）
2. **Entry 条目**：6 个内置 kind（`entries.ts:15-34`）——`pi.user` / `pi.assistant` / `pi.system` / `pi.tool-result` / `pi.reset` / `pi.compaction`，用 `defineEntry(kind)`（`entries.ts:6`）定义并带类型守卫。`EntryRecord`（`types.ts:317`）带 `model`（进模型上下文的消息）、`data`、`head`（活跃上下文起点标记）、`edits`、`byTaskId`。（硬事实）v0.86.1 时代的 4 种 Entry（message/compaction/branch_summary/custom）与 #9548 的"model/thinking/tools 随消息携带"叙述属于旧包；durable 的 `pi.system` 是位置性 prompt/tool 变更条目。（解释）
3. **Documents**：scope 化（session/conversation/task）的 incarnation 文档，用 `defineDoc()`（`documents.ts:54`）定义——内置四个 conversation 文档：`pi.agent`（`harness/agent.ts:36`）、`pi.live`（`harness/live.ts:63`）、`pi.inbox`（`harness/inbox.ts:16`）、`pi.usage`（`harness/usage.ts:14`）。文档内容是 chord replicated state（base + delta ops），watch 经 `session/observation.ts:24` `CommittedStateSource` 桥接，监听方落后时最多缓冲 100 帧（:15 `MAX_PENDING_WATCH_FRAMES`）。（硬事实）**values 寄存器没有对应物**：名字/标签/游标这类 scalar/list 状态现在就是某个文档的字段。（解释）

全部写入共享同一个全局单调 seq（`Seq`）；每个 conversation 必有根会话 `ROOT_CONVERSATION_ID = 1`（`types.ts:39`）。（硬事实）

核心矛盾仍是**崩溃可恢复性 vs 写入简单性**：常规写是单条 commit 批次；恢复靠 task 记录重放 + open 时 reconcile（见 4.1）；后端侧靠 torn-tail 截断与事务。（解释）

## 与周边系统的关系（避免误读）

- **runtime 真实消费 session**：`harness/harness.ts:164` `HarnessImpl extends SessionImpl`——Harness 就是 session kernel 的子类，任务/提交/文档全部落在本节描述的 records 上。（硬事实）
- **guard 错误类型**（`errors.ts`）：`ReadAfterWrite`（:4，事务首个表写之后禁止再读表）、`StorageRejected`（:12，批次在任何持久化效果前被拒，Session 可安全继续）、`ConversationBusy`（:20，提交到达忙碌会话未准入）。v0.86.1 的 `SessionInvariantError` 等五个守卫错误没有对应物。（硬事实）
- **包边界**：`JsonValue`/`Op`/`replicatedState` 从 `@earendil-works/chord` 引入（`session/observation.ts:1-9`、`harness/view.ts:1`）；SQLite 后端回到 durable 包内（v0.86.1 时移出的 session-backends 包在 1.0.0 整包删除）。（硬事实）

## 后端一：memory（`storage/memory.ts`）

`storage/memory.ts:219` `class MemoryStorage implements Storage`（包根导出 `src/index.ts:99`）：全部表在内存 Map 中，`prepareCommit()`（:249）先校验（seq 严格递增、全局 ID 唯一、document 动作合法）再 apply，实现"validate-then-apply"的原子语义。（硬事实）

## 后端二：JSONL（`storage/jsonl/`，目录格式）

`storage/jsonl/storage.ts:241` `class JsonlStorage implements Storage`，便携实现（fs 经 `ExecutionEnv` 注入；Node 侧入口 `jsonl/node.ts:6` `openNodeJsonlStorage()`）。（硬事实）

- **格式**：`FORMAT_VERSION = 1`（`storage.ts:28`）——与旧包的 "JSONL format 4" 无传承关系。目录布局是**一个 `main.jsonl`（commit marker 流，:29）+ 每文档/每任务 sidecar**（`doc-<id>.jsonl` / `task-<id>.jsonl`，:100），main 行只存 marker 与各 sidecar 的写指针。（硬事实）
- **写入**：sidecar 先追加并（可选 fsync）flush，main marker 最后追加（:290-301）——marker 在，commit 才在。（硬事实）
- **torn tail**：load 时若文件末字节非 `\n`，截到最后一个 `\n`（`storage.ts:785-802` `readLines`，截断调用 :802）并继续加载有效前缀；完整行内损坏抛 `JsonlCorruptionError`。（硬事实）与旧包"丢弃残行 + 原子重写整文件"不同，1.0.0 是**就地 truncate**。（解释）
- **poison 语义**：任何写失败 → `JsonlStoragePoisonedError`（:88），存储从此拒绝服务、必须重开——宁可停也不带病写。（硬事实）
- **sidecar 回收**：空洞化后用 `<file>.reclaim` 临时文件 + `renameFile` 原子替换（:523-531）。（硬事实）
- **查询层**：`JsonlStorage` 内部持有一块 `MemoryStorage` 索引（:246）——JSONL 的 scan/query 直接复用 memory 实现的表逻辑，两后端共享同一套状态机。（硬事实）

## 后端三：SQLite（`storage/sqlite/`，1.0.0 新增）

- **异步契约**：`sqlite/database.ts:11` `SqliteExecutor`（exec/run/get/all 全 Promise，按 SQL 文本 + 位置绑定）；:35 `SqliteDatabase`（`transaction(cb)` 传事务句柄；契约要求适配器排队其他操作/事务、回调拒绝必须 ROLLBACK 后以原错误 reject，ROLLBACK 失败须换成别的错误如 AggregateError）。（硬事实）
- **Node 适配器**：`sqlite/node.ts:27` `SerialOperationQueue`（异步操作启动前先发 barrier，:43）；:76 `NodeSqliteExecutor` 持 per-connection `Map<string, StatementSync>` 语句缓存（:78）；:117 `NodeSqliteTransaction`（`BEGIN IMMEDIATE` :142，失败 `ROLLBACK` :152，回滚也失败抛 `AggregateError` :154）。`openNodeSqliteStorage()`（:205）← `openNodeSqliteDatabase()`（:180）：WAL（:190）、`synchronous=NORMAL`（:191）、autocheckpoint 可配（默认 1,000 页）、busy timeout 默认 5,000 ms；close 前 `PRAGMA wal_checkpoint(TRUNCATE)`（:167）。（硬事实）
- **存储层**：`sqlite/storage.ts:130` `SqliteStorage`——commit 走单事务（:166-178）；close 两层语义：适配器排队关闭，存储层等已放行的多查询读排干（:509-520 `closeDatabase`、:527 `admitRead` 计数）再关库。schema 用 STRICT 表 + JSON record 列，`durable_metadata.next_id` 用 TEXT 规避超安全整数（`migrations.ts:10-14`）。（硬事实）

## Fork：conversation 级 + 文档复制

1.0.0 的 fork 是**会话级操作**：`tx.forkConversation(parentId, at, options)`（`transaction.ts:289`）在可见条目 `at` 处建新会话，历史经由条目可见性（head marker + 祖先链）读到父会话前缀，不复制 entry。（硬事实）会话文档按策略复制：`session/forks.ts:26` `prepareForkDocumentCopies()` 把父会话全部持久化文档在新会话建副本——`history: "rewindable"` 的按 `asOf`（fork 点状态，forks.ts:38-47）、`"latest"` 的按 `current`（:48-57）；同一逻辑地址被选两次直接报错（:88-91）。`pi.agent` 的 `fork: "asOf"`（`harness/agent.ts:41`）即由此生效。（硬事实）

（v0.86.1 的 named-branch `ForkOptions` scope/tree 语义、streaming 两遍复制、fork 祖先校验属于旧包模型，见历史节。）（解释）

## v0.86.1 历史（pi-agent-core 旧包；文件已删除，1.0.0 未复核）

以下机制细节摘自 v0.86.1 复核版本文，其文件在当前工作树已不存在，行号无法重新核实，仅作迁移考古保留（**v0.86.1 事实，1.0.0 未复核**）：

- **`OperationState` tagged union**：`session/types.ts:316`（`OperationAt` :331、`Operation` :342），13 叶子 operation 状态机（见 4.1 历史对照表）。
