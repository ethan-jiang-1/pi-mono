# 4.1 system prompt 自报家门：教 agent 怎么查自己，而不是替 agent 背下自己

## 现象是什么

> **警示（v0.85.x–0.86.x，见 `_change_log/0006`）：本文的"每次请求头部重建 system prompt"模型已被推翻。** 自 #9548（commit `9e05370b2`）起，system prompt 是 **transcript 内一串可追加的 SystemMessage 的重放态**，不是请求级参数。下文"现象/判断"里关于"单次注入、请求头部字符串"的表述需按本节末尾的"Transcript-first 更新"重读；prompt 内容本身（自报家门、文档地图、动态聚合）的结论仍然成立。

pi 的 system prompt 第一句就自报家门（`system-prompt.ts:146-147`）：

> "You are an expert coding assistant operating inside pi, a coding agent harness."

随后是 `Available tools`（工具列表）、`Guidelines`（准则），再往后是一段**专门告诉 agent "pi 的文档在哪、什么时候读"**的指引（`system-prompt.ts:153-160`）：

> "Pi documentation (read only when the user asks about pi itself, its SDK, extensions, themes, skills, or TUI): Main documentation: ... Additional docs: ... Examples: ... When asked about: extensions (docs/extensions.md), themes (docs/themes.md), skills (docs/skills.md) ..."

它给的是**文档地图**，不是文档全文。

![system prompt 结构](figures/system_prompt_structure.svg)

## 核心矛盾是什么

1. **给 agent 多少"关于自己"的信息 vs context 窗口成本。** 30+ 篇 docs 全塞进 system prompt 会撑爆窗口；不给又让 agent 盲跑。
2. **静态描述 vs 运行时可变。** 工具集会变（`refreshTools`、扩展动态注册）、guidelines 随工具聚合。自描述不能是一段写死的文本。

## 设计判断是什么

### 判断一：自报家门是第一句，身份先于一切（硬事实）

`system-prompt.ts:146-147` 的第一句同时做了两件事：告诉 agent "你是 coding agent"，告诉它 "你在 pi 这个 harness 里"。**身份定位放在 prompt 最开头**（`preamble` section，`system-prompt.ts:142-161`），因为后面所有指令（工具、文档、项目上下文）都以"你在这个 harness 里"为前提。

### 判断二：给"文档地图"而不是"文档全文"——这是自描述最成熟的一手（硬事实 + 解释）

pi 不把 30+ 篇 docs 塞进窗口，而是放进一段**按主题映射的文档地图**：问 extensions 读 `docs/extensions.md`、问 TUI 读 `docs/tui.md`、问 SDK 读 `docs/sdk.md`。

**深意**：这解决的是矛盾 1 的"按需"——**教 agent 怎么查自己，而不是替 agent 背下自己。** agent 需要时用 read 工具按地图去读，不需要时不占窗口。这比"把全部文档塞进 prompt"省窗口，比"完全不给文档"少盲跑。折中点选得准。

### 判断三：工具列表和 guidelines 是动态聚合的，不腐化（硬事实，延伸见 4.2）

`Available tools` 只列"提供了 snippet 的工具"（`system-prompt.ts:148-151`），guidelines 从工具的 `promptGuidelines` 聚合进 `rules` section（`system-prompt.ts:81-118`、`buildSystemPromptSections` 内 `system-prompt.ts:152`；工具侧归一化在 `agent-session.ts:2840-2860`）。所以工具集变化时，prompt 里的工具列表和准则**自动跟着变**。

**这是自描述不腐化的底层机制**：pi 不手写一段"可用工具有 read/bash/edit/write"——那段话是从工具定义里长出来的。手写的会漂移，聚合的不会。完整论证在 [4.2](./4.2_tool_prompt_contract.md)。

### 判断四：自描述的边界也说得清楚（硬事实）

三处克制证明自描述不是"能多就多"：

- skills 块只在 read 或 bash 工具可用时才生成（`system-prompt.ts:165-169`，gate 取 `["read","bash"]` 中第一个被选中的）——不给 agent 一个"能看列表但读不了"的空承诺。
- 文档指引明确"resolve docs/... under Additional docs ... not the current working directory"（`system-prompt.ts:157`）——消除相对路径歧义。
- `customPrompt` 路径下默认身份/工具/guidelines/docs 全不生成（只留 `preamble`），但 context files/skills/CWD 仍追加为独立 section（`system-prompt.ts:143-144,163-173`）——调用方完全接管身份时也不丢上下文。

**深意**：自描述的成熟度不在字数，在**边界清晰**——哪些信息在什么条件下出现、相对路径怎么解析，都写进了逻辑。这是"说清楚"而不是"说得多"。

## 影响是什么

1. **对上面跑的 coding agent，pi 是一个"可自导航"的 harness。** agent 被明确告知"你是 agent、在 pi 里、有这些工具、pi 文档在这、按主题查"。这直接降低 agent 干活时的摩擦。
2. **"文档地图"模式是可复用的自描述范式**：任何 harness 都不该把全部文档塞进 prompt，而该塞一张地图 + 让文档在 read 工具够得着的地方（见 [4.3](./4.3_docs_in_package.md)）。
3. **动态聚合（判断三）是自描述不腐化的关键**，它和 [4.2](./4.2_tool_prompt_contract.md) 是同一件事的两面。

## Transcript-first 更新：system prompt 现在是重放态，不是单次注入（v0.86.0）

> **警示（v0.85.x–0.86.x，见 `_change_log/0006`）**：本节推翻旧文档里"system prompt 每次请求作为头部参数单独注入一次"的模型。

**新模型（硬事实）**：

- prompt 内容被结构化为**具名 sections**（`SystemPromptSections`，`system-prompt.ts:45-50`：`preamble`/`tools`/`rules`/`docs`/`skills`/…，非 preamble section 用同名 XML tag 包裹）。这些 sections 作为 `SystemMessage.sections` **持久化进 transcript**。
- provider 侧不再有 `context.systemPrompt`/`context.tools`。system prompt 通过重放 transcript 里的 SystemMessage 序列得出：`getCurrentSystemPrompt(messages)`（`packages/ai/src/utils/transcript.ts:99`），工具同理 `getCurrentTools()`（transcript.ts:58）。重放语义：content 追加、`sections` 按名 patch（`null` 删除）、`toolsAdded`/`toolsRemoved` 按序应用（transcript.ts:71-107）。
- mid-conversation 的工具加载/prompt 变更由 `agent-session.ts` 生成一条 SystemMessage patch 追加进 transcript：`_preparePromptAndToolLoadout()`（`agent-session.ts:1149`）对当前 transcript 重放结果与 `buildSystemPromptSections()` 做 section diff，产出 patch message 并经 `appendMessage()` 持久化；turn 之间（如 compaction 后）走 `prepareNextTurnWithContext`（`agent-session.ts:588-599`）产出同样增量，保持 cache 前缀只追加。resume 时从 transcript 声明恢复 tool loadout（`_restoreToolsFromTranscript`，`agent-session.ts:1193`）。

**两个例外（解释）**：

1. **Forced prompt 投影而非持久化**：`before_agent_start` handler 返回 `systemPrompt`（force）时，那段文本**不写 transcript**——transcript 继续保存结构化 sections；请求时由 `_installAgentForcedPromptProjection()`（`agent-session.ts:1175`，注册于 :417）用 `transformContext` 把所有 system messages 折叠成头部一条持有 forced 文本 + 当前工具的 message。即"发送但不记录"。
2. **不支持 mid-conversation system 的 API**：用 `collapseSystemMessages()`（transcript.ts:108）把整串 SystemMessage 折叠成头部一条（重放态的 system message 打头，后续 system 全部丢弃），由 `resolveTranscript()`（transcript.ts:119）按模型能力选择。

**深意**：单一注入模型下，prompt 是会话外的隐式变量，resume/branch 无法恢复"当时模型看到的是什么"；重放态下 prompt/tool 历史成为 transcript 的一等数据——可持久化、可 diff、可增量 patch，且 provider 侧只追加不改写，保住 prompt cache 前缀。这是"自描述"从"每次重建"到"状态机"的升级。

## 最小例证是什么

**例证 1（文档地图 vs 全文）：** 读 `system-prompt.ts:153-160`——它给的是 `docs/extensions.md` 这种**路径 + 主题映射**，不是 extensions.md 的正文。证明"教 agent 查"而非"替 agent 背"。

**例证 2（动态聚合）：** 把 `selectedTools` 改成 `["bash","edit","write"]`（去掉 read）再跑 `buildSystemPromptSections`——`skills` section 整块消失（gate 取 read/bash 中第一个可用），但 `tools` 和 `docs` section 仍在。证明工具列表和 skills 块是动态聚合，不是手写死文本。

**例证 3（边界清晰）：** 看 `customPrompt` 分支（`system-prompt.ts:143-144`）——默认身份/工具/guidelines/docs 不生成，但 context files/skills/CWD 仍追加。证明"自描述在什么条件下退让"也被写清楚了。

**例证 4（重放态 vs 单次注入）：** 在 mid-conversation 加载一个新工具再跑一轮——transcript 里新增一条带 `toolsAdded` 的 SystemMessage entry（`agent-session.ts:1149`），下一轮 `getCurrentTools()` 重放出包含新工具的集合。旧 session 文件（无 system message entry）回放时 `getCurrentSystemMessage()` 空返回兜底（transcript.ts:85-95），prompt 回落到请求时构造。证明 prompt 状态在 transcript 里，而不是请求参数里。

可观察信号：例证 1 → 按需自述（省窗口）；例证 2 → 动态聚合（不腐化）；例证 3 → 边界清晰（说清楚而非说得多）；例证 4 → 重放态（prompt 历史 = transcript 数据）。前三者说"prompt 内容把自己说清楚了"，例证 4 说"prompt 生命周期把自己说清楚了"——v0.86.0 后两者都成立。
