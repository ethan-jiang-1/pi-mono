# 3.5 Session v4: 会话存储（branch / values / durable operation）

> **⚠️ v0.86.1 全文重写**（2026-09-xx，本仓库工作树实测）。本文取代 v0.84.2 版描述：v0.85.x–0.86.x 期间 session 层完成了 storage/conformance/benchmark 体系重建（约 30+ commits），旧文的 "Entry 7 种 + LaneRecord 9 种 + `session/state.ts`" 模型已再次失效——`state.ts` 被删除，写入改为 **guarded mutation**（`Session.mutate()` + `MutationLine` 串行化），状态原语改为 **scalar/list values 寄存器**，operation 生命周期改为 **`OperationState` tagged union**（`session/types.ts:316`）。存储升级为 **JSONL format 4**（`jsonl/types.ts:4` `JSONL_FORMAT_VERSION = 4`），支持 legacy v3 只读打开与首写自动升级、named-branch streaming fork。（硬事实）
>
> **⚠️ v0.84.0（历史）**：v4 首次落地，取代 3.4 描述的旧 `SessionTreeEntry` 模型。

## 现象是什么

session 不再只是"一棵 entry 树"，而是三层 durable 数据 + 严格连续的单调 seq（解释）：

1. **Entry**（4 种，`session/types.ts:64`）——不可变对话树节点：`message`、`compaction`、`branch_summary`、`custom`。v0.84 时代的 `model_change` / `thinking_level_change` / `active_tools_change` 独立 entry 已不存在——model/thinking/tools 现在**随 assistant message 与 system message 携带**（#9548，见 1.1/1.2）。（硬事实）
2. **Values 寄存器**（`session/values.ts`）——session/branch/lane 级的 scalar 与 list 状态：`setValue()`/`deleteValue()`（values.ts:108/118）、`sessionName`、`branchTip(branch)`、`laneState(lane)`（:161）等具名地址。名字、标签、branch tip 游标、lane 状态都存在这里，**latest-wins 的 set 语义**（不是 append）。（硬事实）
3. **Operation 记录**——lane 归属的操作流水，其生命周期由 **`OperationState` tagged union**（`session/types.ts:316`，`OperationAt` :331、`Operation` :342）完全类型化：`starting → checkpoint → generation（assistant/tools/summary/retry-wait/effect-pending）→ deferred → navigation → terminal`。（硬事实）

三类写入共享同一个单调 seq。**Branch** 是显式具名的树投影（`Branch` 接口 `types.ts:521`），每个 session 必有 `main`；`Session`（`StorageBackedSession`，`session.ts:224`）与 `Branch` 视图都只能通过 **guarded mutation** 写入。（硬事实）

核心矛盾仍是**崩溃可恢复性 vs 写入简单性**：常规写是单行 append；恢复靠重放 + `OperationState` 状态机；torn tail、fork、legacy 升级走"临时文件 + 原子 rename 发布"。（解释）

## 与周边系统的关系（避免误读）

- **runtime 已真实消费 session**。v0.84.2 时"`AgentHarness` 是骨架"的警示已失效：`harness/runtime/` 的 durable drive（`drive.ts:29` `driveOperation()`，`drive/structural.ts` 1222 行）直接驱动持久化 operation，compaction / branch summary 是可恢复的 structural 操作（见 3.1/3.2 警示）。runtime 详见 04-Harness。（硬事实）
- **guard 错误类型**：`SessionInvariantError`（session.ts:45，内部状态不一致、禁止推进）、`SessionPendingAssistantMessageError`（:77，assistant 未 settle 前禁止推进）、`SessionInvalidBranchError`（:53）、`SessionBranchExistsError`（:66）、`SessionUnknownTargetError`（:85）。（硬事实）
- **包边界**：`JsonValue` 从 `@earendil-works/chord` 引入（`session/types.ts:10`）；SQLite backend 移出到独立的 session-backends 包；`@earendil-works/pi-agent-core/session/testing` 导出已更名为 `.../harness/session/testing`（import path breaking）。（硬事实）

## 三大接口的分工（v0.86.1 锚点）

| 接口 | 位置 | 职责 |
|------|------|------|
| `Storage` | `session/types.ts:455` | 后端契约：branch 管理、`commit(writes)`、scan/query、usage、stats |
| `Session` | `session/types.ts:530`（实现 `session.ts:224` `StorageBackedSession`） | `SessionReader` 只读 + `mutate()` guarded 写、branch 打开/创建、values 便捷方法 |
| `SessionRepo` | `session/types.ts:592` | 仓库级生命周期：`create` / `open`（含 legacy v3 只读打开）/ `list` / `delete` / `fork` |

写路径：调用方通过 `session.mutate(callback, context)`（session.ts:263）拿到 `SessionMutator`（`types.ts:517`），在回调内 commit 一批 `Write`（`EntryWrite | UsageWrite | ValueWrite | ListWrite`，types.ts:398）。同一时刻只允许一个 mutation（`MutationLine` 串行化，session.ts:239），**append 必须链到 branch 当前 tip**，否则 invariant 错误——这就是 append-only 纪律的 enforcement 点。（硬事实）

## JSONL 后端：format 4 + torn-tail 原子发布

[`session/jsonl/`](../../../packages/agent/src/harness/session/jsonl/)（codec / io / storage / repo / fork / types / legacy-v3）：

- **格式**：文件头 `v: 4`（`JSONL_FORMAT_VERSION = 4`，jsonl/types.ts:4；容器版本 `JSONL_STORAGE_VERSION = 1` :5），其后每行一个 mutation（entry / value / list / usage）。（硬事实）
- **常规写**：先 durable 后内存，写经 tail-promise 链串行化。（硬事实）
- **torn-tail 修复**：load 时只把"最后一行不完整/syntax 错误"判为 torn tail（`jsonl/storage.ts:30-34` `splitCompleteLines`、:94-109），丢弃残行并把有效前缀**原子重写**（`publishFileAtomically`，`jsonl/io.ts:81`：写临时文件 + rename）；内部行损坏直接抛 corruption。（硬事实）
- **fork**：见下节 streaming fork；同样走原子发布。（硬事实）
- **memory 后端**：`session/memory.ts` 与 `session/in-memory-storage-state.ts`（349 行，`InMemoryStorageState` :78）**共享同一套 in-memory storage 状态语义**——JSONL 与 memory 不是两份平行实现，而是同一状态机的两种持久化面。（硬事实）

## Legacy v3：发现、只读打开、首写自动升级

v0.85.x 起旧 format-3 JSONL 文件不再被拒之门外（`jsonl/legacy-v3.ts`，681 行）：

- **发现/打开**：`JsonlSessionRepo.open()` 读到 v3 header 时经 `metadataFromLegacyV3Header()`（legacy-v3.ts:165）/`normalizeLegacyV3Header()`（:184）归一化 metadata，以**只读**方式打开（repo.ts:253、:305 `isLegacyV3()`）。（硬事实）
- **升级**：首次写时原子升级为 format 4：`LegacyV3Source`（legacy-v3.ts:528）流式读取旧文件并投影为新 format 的 writes，经 fork/发布管线写入新文件再 rename 替换，并补偿 usage/commit 统计；升级发布失败有专门的原子性覆盖。（硬事实）
- **fork 来源**：legacy v3 文件可直接作为 fork source（repo.ts:313 `isLegacyV3ForkSource`，closed 文件经 format 4 投影 fork；open 中的 legacy 文件拒绝 fork）。（硬事实）
- 不支持的版本（既非 3 也非 4）直接拒绝。（硬事实）

## Fork：named-branch 语义 + streaming 两遍复制

fork 从"整树复制"变为显式 **branch-scoped** 操作（`ForkOptions`，`session/types.ts:562`，`scope: "branch" | "tree"`）：

- **branch scope 必须显式命名 branch**；`session/fork-policy.ts:8` 的 `selectBranchFork()` 沿 source branch 的 parent 祖先链验证请求的 `entryId`（缺省为 branch tip）确实在链上，`position: "before" | "at"` 决定 destination tip；不在链上直接 throw `Fork entry ... is not on source branch`。（硬事实）
- **streaming 两遍复制**（`jsonl/fork.ts`，328 行，`runJsonlFork()` :295；WP08）：第一遍扫描 source 建立轻量 index（branch 名 + 选中 entry/label，尽量少驻内存），第二遍重开 source 文件（v3 或 v4 格式均可）流式复制选中的 entries，经 `projectForkCurrentStateWrite()` 投影 values；**不再整体载入内存**，支持大文件。（硬事实）
- records/operation 流水属于源 session，不复制；目标端 seq 从 1 重编；`scope: "tree"` 复制全部 entries 与所有 branch tip。（硬事实）

## Conformance 与 benchmark

存储正确性现在由可复用的测试基建保证（`session/testing/`）：

- `testing/conformance/storage.ts` / `session-repo.ts`——按 capability 拆分的 backend conformance 套件（含 ownership、torn-tail、fork、legacy 升级矩阵），任何 `Storage`/`SessionRepo` 实现（含第三方后端）跑同一套契约。（硬事实）
- `testing/benchmark/` + `vitest.benchmark.config.ts` 的 `bench:session:*` scripts——repo lifecycle 与 fork 基准。（硬事实）
- `testing/` 还提供 `storage-decorator.ts` / `instrumented-storage.ts` / `gating-storage.ts` 用于测试注入。（硬事实）

## context 投影

`session/context.ts` 仍是无状态纯函数层：沿 branch tip → root 路径推导 `{ messages, thinkingLevel, model, activeToolNames }`（`buildSessionContext()`，context.ts:47）。截断规则与 v0.84 一致：最新的 `compaction` entry 之前的条目不进 context；`custom` entry 只有注册了 `EntryProjector`（`session/types.ts:59`）才可能进 context。新增：system message 作为 transcript 成员参与投影（#9548，见 1.2）。（硬事实）
