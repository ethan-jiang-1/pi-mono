# 4.6 Tool: Edit & Write —— 文件修改的安全机制

> **⚠️ v0.83.0**：edit/write 工具已迁移到 `agent/src/harness/tools/edit.ts` 和 `write.ts`（factory 模式）；file-mutation-queue 从全局 `Map` 改为 `WeakMap<ExecutionEnv,...>`；路径解析改为 async `resolveToolPath`。行号全部失效。

## 现象是什么

pi-mono 提供了两个文件修改工具：

- **edit**：精确的字符串替换引擎。模型给出 `oldText`（要替换的内容）和 `newText`（替换成什么），工具在文件中定位 `oldText` 并替换。支持一次调用中的多个 disjoint edits。
- **write**：创建或覆盖文件。自动创建父目录。内容可以是任意文本。

这两个工具在 TUI 中会渲染 diff 预览（edit 工具渲染在实际执行前的 preview），让用户在工具调用参数完成时就能看到将要发生的改动。

## 核心矛盾是什么

文件修改是 agent 系统中最危险的操作，因为它的副作用是**持久化的**。核心矛盾围绕以下几点：

1. **Read-then-write 一致性**：LLM 可能在"读文件"和"写文件"之间得到过时的文件内容（用户手动修改了文件，或者另一个工具修改了文件）
2. **并发修改冲突**：多个工具调用可能同时操作同一个文件（特别是在 `toolExecution: "parallel"` 模式下）
3. **Whitespace 和 BOM 处理**：LLM 不理解文件中的 BOM（字节序标记），也可能在匹配时因为换行符（CRLF vs LF）而失败
4. **匹配精度**：edit 工具的 `oldText` 必须精确匹配文件中的文本，包括缩进、空行、空白字符

## 实现思想是什么

### Edit 工具（tools/edit.ts）

**参数结构：**

```typescript
const editSchema = Type.Object({
  path: Type.String(),                           // 文件路径
  edits: Type.Array(Type.Object({
    oldText: Type.String(),                      // 要替换的精确文本
    newText: Type.String(),                      // 替换后的文本
  })),
});
```

**执行流程：**

1. `prepareEditArguments()`：处理 legacy 格式（某些模型如 Opus 4.6、GLM-5.1 把 edits 发成 JSON string 而不是 array；或者模型用 `oldText`/`newText` 顶层字段而非 `edits[]` 数组）

2. `validateEditInput()`：验证至少有一个 edit

3. **通过 file mutation queue**：`withFileMutationQueue(absolutePath, () => ...)` 确保同一个文件的操作是串行的

4. 读文件 → 检测 BOM → 统一换行为 LF → 应用 edits → 恢复换行 → 写文件

**Edits 应用算法：**

```typescript
const { baseContent, newContent } = applyEditsToNormalizedContent(
  normalizedContent,  // 已转为 LF 的文件内容
  edits,              // oldText/newText 对
  path,               // 用于错误报告
);
```

每个 `edits[].oldText` 都在**原始文件**上匹配（不是在之前 edit 的结果上）。这避免了编辑顺序带来的歧义。如果两个修改触及同一个代码块或邻近行，模型应该把它们合并成一个 edit。

**Diff 生成和渲染：**

- 预执行 diff：`computeEditsDiff()` 在工具调用参数完成后生成 preview diff。LLM 和用户都能在实际执行前看到将要发生的改动
- 执行后 diff：`generateDiffString()` 基于实际的 `baseContent` 和 `newContent` 生成统一 diff
- TUI 渲染：`renderCall()` 在参数完成时异步加载 preview；`renderResult()` 显示最终 diff

**Legacy 兼容：**

某些模型（Opus 4.6、GLM-5.1）可能使用旧格式 `{ path, oldText, newText }` 而非 `{ path, edits: [{ oldText, newText }] }`。`prepareEditArguments()` 自动转换两种格式。

**可插拔操作：**

```typescript
interface EditOperations {
  readFile: (path: string) => Promise<Buffer>;
  writeFile: (path: string, content: string) => Promise<void>;
  access: (path: string) => Promise<void>;
}
```

默认使用本地文件系统（`fs/promises`），可被 extensions 替换为远程文件操作。

### Write 工具（tools/write.ts）

**参数结构：**

```typescript
const writeSchema = Type.Object({
  path: Type.String(),
  content: Type.String(),
});
```

**执行流程：**

1. `mkdir -p` 创建父目录
2. `writeFile()` 写入内容
3. 返回写入的字节数

Write 工具比 edit 简单，因为它是全量覆盖，不涉及匹配逻辑。

**语法高亮渲染：**

Write 工具实现了增量语法高亮：

- `rebuildWriteHighlightCacheFull()`：初次高亮（前 50 行的前缀高亮 + 其余按行高亮）
- `updateWriteHighlightCacheIncremental()`：流式传入时增量更新高亮缓存
  - 只有新增部分需要高亮处理
  - 只有第一行的末尾（可能未完成）需要重新高亮
  - 后缀行每行单独高亮

这在 TUI 中提供了近乎实时的语法高亮文件预览。

**可插拔操作：**

```typescript
interface WriteOperations {
  writeFile: (path: string, content: string) => Promise<void>;
  mkdir: (dir: string) => Promise<void>;
}
```

### File Mutation Queue（file-mutation-queue.ts）

这是保证文件修改一致性的关键基础设施：

```typescript
export async function withFileMutationQueue<T>(filePath: string, fn: () => Promise<T>): Promise<T> {
  const key = getMutationQueueKey(filePath);  // 用 realpath 做 key
  const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();

  // 链式追加：等前一个完成后执行下一个
  const nextQueue = new Promise<void>((resolve) => { releaseNext = resolve; });
  const chainedQueue = currentQueue.then(() => nextQueue);
  fileMutationQueues.set(key, chainedQueue);

  await currentQueue;  // 等前一个完成
  try {
    return await fn();
  } finally {
    releaseNext();
    // 如果队列中没有新的操作，清理 entry
    if (fileMutationQueues.get(key) === chainedQueue) {
      fileMutationQueues.delete(key);
    }
  }
}
```

**设计要点：**

1. **Per-file 串行化**：同一个文件的操作被串行化。不同文件的操作可以并行。
2. **realpath 去重**：符号链接和相对路径都被解析为相同的 realpath key，防止绕过。
3. **自清理**：最后一次操作完成后从 map 中删除，防止内存泄漏。
4. **队列链式追加**：没有使用传统的 mutex/lock。新操作被追加到 promise 链上，前一个完成时自动触发下一个。

### 权限集成

Edit 和 Write 工具通过 AgentHarness 的 `beforeToolCall` hook 与权限系统集成：

```typescript
harness.on("tool_call", ({ toolName, toolCallId, input }) => {
  if (toolName === "edit" || toolName === "write") {
    // 检查文件路径是否在允许的目录内
    const resolvedPath = resolve(input.path);
    if (!resolvedPath.startsWith(allowedDir)) {
      return { block: true, reason: "Cannot modify files outside project directory" };
    }
  }
});
```

## 在 Agent 能力面里的影响是什么

1. **File Mutation Queue 保证了不会出现竞态条件**。即使在 parallel tool execution 模式下，同一文件的 edit/write 操作也是串行的。

2. **Read-then-write 不是工具的责任**。AgentHarness 的 `beforeToolCall` 和 `afterToolCall` hook 是在 LLM 层面的，工具只负责单次执行。一致性问题通过 LLM 的调用顺序来保证（LLM 应该先调用 read 再调用 edit）。

3. **Edit 的 "在原始文件上匹配" 语义减少了复杂性**。不需要处理 edit 之间的交错影响。

4. **BOM 和换行符的透明处理对 LLM 友好**。LLM 不需要理解 BOM 或换行差异。

## 最小例子是什么

```typescript
import { createEditTool, createWriteTool, withFileMutationQueue } from "@earendil-works/pi-coding-agent/core";

// 1. 创建 edit 工具
const editTool = createEditTool("/path/to/project");

// 2. LLM 调用格式
// { path: "src/main.ts", edits: [
//   { oldText: "const x = 1;", newText: "const x = 2;" },
//   { oldText: "console.log(x)", newText: "logger.info(x)" }
// ]}

// 3. 创建 write 工具
const writeTool = createWriteTool("/path/to/project");

// 4. LLM 调用格式
// { path: "src/new-file.ts", content: "export const foo = 'bar';\n" }

// 5. File mutation queue 的使用（工具内部自动使用）
await withFileMutationQueue("/path/to/project/src/main.ts", async () => {
  // 这个函数在 main.ts 的队列中串行执行
  await fs.writeFile("/path/to/project/src/main.ts", newContent);
});

// 6. 自定义 EditOperations 用于远程文件编辑
const remoteEditTool = createEditTool("/remote/project", {
  operations: {
    readFile: async (path) => Buffer.from(await sshReadFile(path)),
    writeFile: async (path, content) => await sshWriteFile(path, content),
    access: async (path) => await sshStat(path),
  },
});

// 7. 权限控制
harness.on("tool_call", ({ toolName, input }) => {
  if (toolName === "write" && input.path?.includes("../")) {
    return { block: true, reason: "Path traversal attempt blocked" };
  }
});
```

关键要点：**edit 和 write 工具通过 file mutation queue 保证同一文件的串行修改，通过 tool_call hook 暴露权限控制点，通过 BOM/换行符透明处理降低 LLM 的使用难度。**
