# 2.6 Queue Modes: 双队列并发控制

> **⚠️ v0.83.0**：AgentSession idle tracking 从 `_agentEventQueue` 改为 `_isAgentRunActive` + `_idleWaitPromise`；新增 `agent_settled` 事件。
>
> **✅ v0.84.2**：v0.84 无队列机制 breaking。2026-08-17 已对照 v0.84.2 复核，正文已修正至 v0.84.2。
>
> **⚠️ v0.85.1**（2026-09-10 核对）：队列机制本身无改动，但 **`AgentSession.isIdle` 的语义收窄**——定义从 `!this._isAgentRunActive` 变为 `!this._isAgentRunActive && !this.isCompacting`（agent-session.ts:925-927），即 **compaction / branch summary 运行期间 `isIdle` 返回 `false`**；等待者改由 `_resolveIdleWaitIfIdle()` 按 `isIdle` 判定释放，因此 `waitForIdle()` 现在也会等 compaction / branch summary。配套：`abort()` 新增 `abortCompaction()` + `abortBranchSummary()`（agent-session.ts:1619-1625）。正文与锚点表已更新。

## 现象是什么

当用户在 Agent "正在思考"或"正在执行工具"时发送新消息，pi-mono 不会直接注入该消息，也不会丢弃。它会将消息放入 steering 或 follow-up 队列，等待合适的时机（turn 边界或 agent 完成）再注入上下文（硬事实）。用户会看到一条 "busy" 提示，但也可能看到 Agent 在当前 turn 结束后自动消费排队消息（硬事实）。

**源码位置：**
- `/packages/agent/src/types.ts`（`QueueMode`、`steering`/`followUp` 相关类型定义）
- `/packages/agent/src/agent.ts`（`Agent.steer()`、`Agent.followUp()`、`PendingMessageQueue`）
- `/packages/agent/src/agent-loop.ts`（`runLoop` 中的队列消费）

## 核心矛盾是什么

Agent 运行时的并发控制面临三个相互矛盾的需求（解释）：

1. **Busy 保护：** Agent 不能同时运行两个 prompt——这会导致状态不一致（硬事实）。但用户期望在 Agent 忙碌时仍然可以"说话"（解释）。
2. **时机选择：** 用户的消息有两种语义：一种是"修正当前方向"（应在当前 turn 结束后立即注入，不等 agent 完成），另一种是"追加新任务"（应等 agent 完全停止后才注入）（解释）。这两种语义在 `PendingMessageQueue` 中分别由 steer/followUp 两个独立队列实现（硬事实：agent.ts:283-290）。
3. **批量 vs 逐个：** 如果用户连续发了多条消息，是一次性全部注入（"all"），还是一次一条地逐个处理（"one-at-a-time"）？前者快但可能混淆模型，后者慢但更可控（解释）。

## 实现思想是什么

### 双队列模型

pi-mono 使用两个独立的 `PendingMessageQueue` 实例来区分两种注入语义（解释）：

| 队列 | 方法 | 注入时机 | 消费位置 |
|------|------|---------|---------|
| steering | `Agent.steer(msg)` | 当前 turn 结束后、下一 turn 开始前 | 内层循环每次迭代末尾 poll |
| followUp | `Agent.followUp(msg)` | Agent 完成所有 turn 并停止后 | 外层循环 poll |

### PendingMessageQueue 实现

`PendingMessageQueue` 是一个带 `QueueMode` 的内存队列（agent.ts:125-159）：

```typescript
class PendingMessageQueue {
  private messages: AgentMessage[] = [];
  public mode: QueueMode;               // 运行时可改（Agent.steeringMode setter）

  enqueue(message: AgentMessage): void { this.messages.push(message); }
  hasItems(): boolean { return this.messages.length > 0; }
  clear(): void { this.messages = []; }

  drain(): AgentMessage[] {
    if (this.mode === "all") {
      // 一次性取出所有消息
      const drained = this.messages.slice();
      this.messages = [];
      return drained;
    }
    // "one-at-a-time": 只取第一条
    const first = this.messages[0];
    if (!first) return [];
    this.messages = this.messages.slice(1);
    return [first];
  }
}
```

默认模式：steering 为 `"one-at-a-time"`，followUp 也为 `"one-at-a-time"`（agent.ts:231-232）（硬事实）。这意味着默认情况下每个 turn 最多注入一条排队消息，给予模型逐条处理的空间（解释）。

### 在双层循环中的消费

回顾 2.1 中的双层循环，队列在以下位置被消费：

```
runLoop 入口：getSteeringMessages() → 初始 pending（agent-loop.ts:168）
外层 while(true):
  内层 while(hasMoreToolCalls || pendingMessages > 0):
    若有上一 turn 快照：prepareNextTurn
      → prepare 后补 poll getSteeringMessages（仅当先前 poll 为空，agent-loop.ts:194-196）
    turn_start
    注入 pendingMessages (来自 steering 或 followUp)
    streamAssistantResponse()
    executeToolCalls()
    turn_end
    shouldStopAfterTurn → true 则退出（不再 poll）
    → pendingMessages = getSteeringMessages()  // 消费 steering 队列
  → followUpMessages = getFollowUpMessages()     // 消费 followUp 队列
  → 如果有 followUp: pendingMessages = followUpMessages; continue 外层
  → 否则: break, emit agent_end
```

注意：`getSteeringMessages` 在**循环入口**、内层循环**每次迭代后**、以及 **prepareNextTurn 完成后（仅当先前 poll 为空）** 被 poll，`getFollowUpMessages` 只在**内层循环完全结束**后才被 poll（硬事实）。第三处补 poll 是 v0.84.4 加的（agent-loop.ts:194-196）：prepare 可能长时间运行（如 between-turn 压缩），期间排队的 steering 不丢；"仅当先前 poll 为空"保证 one-at-a-time 模式不会在同一 turn 投递两条消息（硬事实）。两个 getter 在 `createLoopConfig()`（agent.ts:475-482）里绑定到对应队列的 `drain()`（硬事实）。

一个防双取的细节：`Agent.continue()` 在末条消息是 assistant 时会自己 drain steering 队列并以这些消息发起新 prompt，此时传 `skipInitialSteeringPoll: true`（agent.ts:374、446-478）（硬事实），让 runLoop 的入口 poll 第一次返回空，避免同一条消息被 drain 两次（解释）。

### SingleFlight / Busy Gate

`Agent.prompt()` 和 `Agent.continue()` 都检查 `this.activeRun`（`runWithLifecycle` 也有同样的守卫）（硬事实）：

```typescript
async prompt(input: string | AgentMessage | AgentMessage[]): Promise<void> {
  if (this.activeRun) {
    throw new Error(
      "Agent is already processing a prompt. " +
      "Use steer() or followUp() to queue messages, or wait for completion."
    );
  }
  // ...
}
```

这意味着：
- 任何时候只有一个 run 在活跃（硬事实）。
- 如果 Agent 正在运行，`prompt()` 会 throw，迫使调用方使用 `steer()` 或 `followUp()`（硬事实）。
- `continue()` 在遇到最后一条消息是 `assistant` 时，会先尝试消费 steering/followUp 队列，只有在无排队消息时才 throw `"Cannot continue from message role: assistant"`（硬事实）。

### 流式交互中的特殊处理

当用户在 Agent 正在流式输出（`AgentSession.isStreaming === true`，即 `_isAgentRunActive`）时发送消息，coding-agent 层要求显式指定 `streamingBehavior`（agent-session.ts:1183-1200）（硬事实）：

```typescript
await session.prompt("Also check for outdated versions", {
  streamingBehavior: "steer",   // 或 "followUp"
});
```

- `"steer"`：走 `_queueSteer()` → `agent.steer(msg)`，当前 turn 结束后注入（硬事实）。
- `"followUp"`：走 `_queueFollowUp()` → `agent.followUp(msg)`，Agent 完全停止后注入（硬事实）。
- 不指定且正在 streaming：直接 throw（硬事实）。

`AgentSession` 同时维护文本级的影子队列（`_steeringMessages`/`_followUpMessages`），入队和消息实际被 `message_start` 消费时都会 emit `queue_update` 事件，UI 的队列渲染以此为准（硬事实）。idle 判定用 `_isAgentRunActive` + `isCompacting` + `_idleWaitPromise`（硬事实）：`_emitAgentSettled()` 在 run（含重试/compaction 续跑）结束后 emit `agent_settled`，并由 `_resolveIdleWaitIfIdle()` 在 `isIdle` 为真时 resolve 等待者（硬事实）。v0.85.1 起两个 getter 不再对称：`isStreaming` 仍只读 `_isAgentRunActive`，而 `isIdle` 收窄为 `!this._isAgentRunActive && !this.isCompacting`（agent-session.ts:925-927）——**compaction / branch summary 运行期间 `isIdle` 返回 `false`**，所以 `waitForIdle()` 会等这两者跑完（硬事实）。相应地 `abort()` 除 `abortRetry()` + `agent.abort()` 外，还会 `abortCompaction()` 与 `abortBranchSummary()`（agent-session.ts:1619-1625）（硬事实）。

## 在 Agent 能力面里的影响是什么

- **迭代式对话：** 用户可以在 Agent 执行长工具链时"中途说话"（steer），而不需要等待 Agent 完全停止。Agent 会在当前 turn 结束后读入 steering 消息（解释）。
- **批量处理控制：** `QueueMode.all` 适用于"用户粘贴了一段多行内容，可以一次性处理"；`QueueMode.one-at-a-time` 适用于"用户边看边补充，逐句处理更安全"（推测）。
- **并发安全：** SingleFlight 模式保证了 Agent 状态的完整性——不可能出现两个 prompt 同时修改 `messages` 数组（解释）。
- **流式响应中的交互：** 当模型正在流式输出时，用户消息可以排队到 followUp，等当前回答完整显示后再处理（解释）。

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent-core";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const agent = new Agent({
  streamFn: streamSimple,
  initialState: {
    model: claudeSonnet,
    tools: [readTool, writeTool, bashTool],
    systemPrompt: "You are a coding assistant.",
  },
  steeringMode: "one-at-a-time",  // 默认模式
  followUpMode: "one-at-a-time",  // 默认模式
});

// 启动第一个 prompt
agent.prompt("Write a Python script that processes CSV files")
  .catch(err => console.error(err));

// Agent 正在执行工具...此时用户发送修正指令
agent.steer({
  role: "user",
  content: "Actually, make it process JSON instead of CSV",
  timestamp: Date.now(),
});
// → 消息进入 steering 队列
// → 当前 turn 结束后 poll，注入到上下文
// → Agent 在下一个 turn 会读到 "Actually, make it process JSON"

// Agent 仍在运行，用户再发一条
agent.steer({
  role: "user",
  content: "Also add error handling",
  timestamp: Date.now(),
});
// → 因为 mode 是 "one-at-a-time"，这条消息要等再下一个 turn

// 如果尝试 prompt() 而 agent 正在运行
try {
  await agent.prompt("Add logging"); // throw!
} catch (e) {
  // "Agent is already processing a prompt"
  // 只能用 steer() 或 followUp()
}

// Agent 完成所有 tool call 后
// followUp 中的消息会触发外层循环的新一轮
agent.followUp({
  role: "user",
  content: "Now write tests for the script",
  timestamp: Date.now(),
});
await agent.continue(); // 消费 followUp 队列，继续 run

// 检查是否有排队消息
if (agent.hasQueuedMessages()) {
  console.log("还有消息等待处理");
}
```

这个例子展示了：`prompt()` 的 busy gate 保护 → `steer()` 在当前 turn 后注入 → `followUp()` 在 agent 停止后触发新一轮 → `QueueMode` 控制注入频率。
