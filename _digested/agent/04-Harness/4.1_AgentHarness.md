## 现象是什么

`Agent`（`packages/agent/src/agent.ts`）在 1.0.0 仍然只做最纯粹的 LLM 对话循环：收消息、调 LLM、执行 tool、吐事件，不知道 session 的存在。（硬事实）因此持久化执行层是独立包：`packages/durable/src/harness/`（21 个文件，v1.0.0 工作树实测）。（硬事实）

- `packages/durable/src/harness/harness.ts:407-433` — `Harness.open(storage, options, context)`：唯一入口，over 一个 `Storage` 后端打开运行时。registry 必须已含三个内置任务，否则直接抛错（:416-420）；open 失败时用非调用者的 context 关闭并重抛 open 错误（:424-429）。（硬事实）
- `harness.ts:164` — `class HarnessImpl<Tool> extends SessionImpl implements HarnessType`：Harness 是 session kernel 的扩展，加 conversation 句柄、registry、scheduler、task graph view 四件事，而不是像旧 runtime 那样自建 `Lane` 管理层。（硬事实）
- `harness.ts:82-161` — `class ConversationImpl implements Conversation`：单条对话的运行句柄——`agent()`/`configure()`（:91/:95，读写本会话的 `pi.agent`）、`submit()`（:99）、`compact()`（:103）、`reset()`（:109）、`fork()`（:140）、`abort()`（:144）、`context()`/`entries()`（:122/:126）、`viewState()`/`watch()`（:154/:158）。（硬事实）
- 每个会话自带四个内置文档（conversation scope）：`pi.agent`（`harness/agent.ts:36-44`）、`pi.live`（`harness/live.ts:63`）、`pi.inbox`（`harness/inbox.ts:16`）、`pi.usage`（`harness/usage.ts:14`），由创建钩子统一初始化（`harness.ts:354-360`）。（硬事实）

旧"运行时"叙述的去向（v0.86.x 历史，1.0.0 已删除）：

| v0.86.1（pi-agent-core） | v1.0.0（pi-durable） |
|---|---|
| `Harness` 管 lanes（`runtime/harness.ts:29`） | `Harness` 管 conversations + tasks（`harness/harness.ts:164`），lane 概念删除 |

| `driveOperation()` 状态机（`runtime/drive.ts:29`，13 个叶子状态） | 每个 task 一个持久化状态机：`GenerationTask`/`ToolTask`/`CompactionTask` 各自带 checkpoint phase（见下） |
| `drive/recovery.ts` 崩溃恢复 | `TaskScheduler.open()` reconcile：幸存 `running` 任务改回 `pending`（`harness/scheduler.ts:231-253`） |
| pico3 平行实验 kernel + chord 暴露点 | pico3 整体删除，无迁移（见下） |
| `docs/work-packages/00..09`（WP00–WP09 路线图） | agent/docs 约 39k 行内部设计文档真删除；durable 换成 `docs/spec.md`（4,601 行 normative spec）+ `docs/pico-v5-handoff.md` |

## 核心矛盾是什么

老的分层矛盾仍然成立：**循环核心逻辑不知道 session，但产品功能必须依赖 session。**（解释）1.0.0 的解法是把边界画在包级：pi-agent-core 保留无状态循环，一切持久化语义（记录、恢复、仲裁、观察）搬进 pi-durable，由它自带的 Session kernel（`session/session.ts:59` `SessionImpl`，单条 mutation 线串行化）承担。（解释）

旧 runtime 的"决策与效果分离"叙述是 v0.86.x 的；1.0.0 的等价物是：**每个任务状态迁移由 Session 变异线上的单个回调串行决定并写入**（`harness/scheduler.ts:169-172` 的 invariant 注释），而 invocation 一旦结束，它持有的 `ConversationHandle` 上所有操作先 check 再拒绝（`harness.ts:371-402` `boundConversation`）——已 admission 的持久化工作不受影响。（硬事实）

## 实现思想是什么

### 1. 从 driveOperation 到 durable task

v0.86.x 的 `driveOperation()` 是一台中央状态机，按 `operation.state.at` 逐叶推进；1.0.0 没有中央驱动器，**每个操作是一个 Task 记录**（`TaskRecord` 持久化在 session，状态含 `pending/running/waiting/completing/terminal` 与 checkpoint），checkpoint 的 `phase` 就是旧叶子状态的对应物。（解释）任务用 `defineTask()` 定义（`tasks.ts:4`），三个内置任务不可卸载（`harness/registry.ts:10` `BUILTIN_TASKS`）：

- `GenerationTask`（`harness/generation.ts:115`，名字 `pi.generation`）：checkpoint phase `prepare → request → poll/retry → tools`（checkpoint 联合定义 `generation.ts:50-90`）。prepare 阶段渲染 system prompt 与 tool loadout 并落 `pi.system` 条目；tools 阶段等待 tool 任务。（硬事实）
- `ToolTask`（`harness/tool.ts:50`）：单次工具执行。
- `CompactionTask`（`harness/compaction.ts:102`，名字 `pi.compaction`）：`select → summarize → place`；`selectCut()`（`compaction.ts:253`）按 `keepRecentTokens` 选截断点。generation 拥有的 compaction 阻塞该 generation 并直接追加摘要，conversation 拥有的经 write submission 落盘（`compaction.ts:96-99` 注释）。（硬事实）

### 2. 结构化并发：TaskScheduler 与 ownership tree

`harness/scheduler.ts:174` `class TaskScheduler`（1337 行）：任务与会话构成一棵 ownership 树（任务的父是它的 owner 任务或会话；会话的父是 owner 任务），沿树向上走决定 abort 级联、idle 范围与存活判定（`scheduler.ts:165-167`）。（硬事实）

- `abortConversation()`（`scheduler.ts:326-344`）：单次 commit 内撤回排队输入并标记该范围所有存活非后台任务，之后等 idle；`background: true` 时穿越后台边界并等待每个被标记任务。（硬事实）
- `completing` hold：任务 outcome 先以 `completing` 持有，直到它的普通 owned work 排干才终态化（`scheduler.ts:968`、`harness.ts` 无对应——这是 1.0.0 新增的中间态，取代旧 drive 的 terminal 直接提交）。（硬事实）

### 3. 崩溃恢复：open 时 reconcile

进程死亡后 task 记录还在 session 里。`Harness.open()` → `TaskScheduler.open()`（`scheduler.ts:231-253`）加载全部存活任务，把幸存 `running` 改回 `pending`（checkpoint 原样保留），再派生 abort 标记与 finalize 持有中的 outcome。（硬事实）与旧 `drive/recovery.ts` 按 effect-pending 态精细恢复不同，1.0.0 的恢复语义是**整段任务重跑**：checkpoint 让 phase 函数自己决定从哪里继续。（解释）

### 4. Extensions registry 与 per-conversation `pi.agent`（Package 21）

- 扩展定义器 `harness/define.ts`：`defineExtension`（:6-10）、`defineTool`（:13-17）、`section`（:20-26）、`hook`（:29-31）、`wrapTool`（:34-36）、`wrapSection`（:39-43）。（硬事实）
- `harness/registry.ts:73-80` `install()` 按名替换、:82-86 `uninstall()`；`createRegistry()`（:112-114）建应用自有的 registry。registry 是可变的运行时状态——Harness 打开后仍可换扩展。（硬事实）
- per-conversation agent：`pi.agent` 文档（`harness/agent.ts:36-44`）存 model/thinkingLevel/extensions/tools/instructions/cwd，`history: "rewindable"`、`fork: "asOf"`——fork 出的会话从 fork 点的 `pi.agent` 副本起步；任务拥有的新会话复制 owner 会话的 agent（`agent.ts:126-132` `createAgent`）。（硬事实）
- `resolveAgent()`（`agent.ts:147-210`）把存储态、registry 快照与 settings 组装成 `Agent`：选扩展 → 合并 tools/sections → 应用 wraps → 按 `pi.agent.tools` 过滤；wrap 抛错或改名则丢弃目标并上报（`agent.ts:234-251`）。（硬事实）

### 5. 观察面：view / task graph / events

- `harness/view.ts:25` `ConversationView`：一条会话的结构化 mount——活跃 transcript 条目 + 四个内置文档，从 commit publication 增量推进；`ConversationViews`（:71）挂到 chord 的 replicated state 上。（硬事实）
- `harness/task-graph.ts:62` `TaskGraphView`（`Harness.taskGraph()`/`watchTaskGraph()`，`harness.ts:296-302`）：全部存活任务的轻量图（`TaskGraphState` :19、`TaskGraphNode` :30），是跨会话调度/调试的只读投影。（硬事实）
- `harness/events.ts:56` `AgentEvent`、:140 `watchEvents()`：消息级事件流；`harness.ts:284-294` `usage()` 汇总全会话 `pi.usage`。（硬事实）

### 6. pico3：已删除，无迁移

`harness/pico3/**`（约 8k 源码）与 `"./experimental/pico3"` subpath 导出随 `7fd478a2e` 一并删除，没有替代实现。（硬事实）pico3 曾是 chord service 的暴露点；chord 包本身存续，pi-durable 直接消费它的 replicated state / delta 原语（`harness/view.ts:1`、`harness/task-graph.ts:1` 的 `replicatedState`/`applyImmutable` import）——即 1.0.0 里复制语义内化进 durable 的文档与 view 层，不再需要第二套 kernel 做暴露面。（解释）

### 7. 文档与路线图换血

`packages/agent/docs/`（pico、mobile-handoff、work-packages 等，约 39k 行）真删除。（硬事实）durable 的路线图记录是 `docs/pico-v5-handoff.md`（Package 14 durable task runtime :332、15 首个 chat turn :386、16 首个 tool turn :441、17 live UI :528、18 ownership :577、19 结构化并发 :606、20 compaction :681、21 extensions :825、22 lifecycle conformance :850、23 task graph :903）；normative 契约是 `docs/spec.md`（4,601 行）。读 durable 代码时按 handoff 的包索引比按 commit 快。（硬事实）

## 在 Agent 能力面里的影响是什么

1. **产品集成路径不变**：TUI/RPC/SDK 继续走 coding-agent 的 `AgentSession` / `createAgentSession()`，底层是 pi-agent-core 的 `Agent`。pi-durable 目前只被 coding-agent 的实验线消费：`src/experimental/session-worker.ts:15-16`（`Harness` + `openNodeSqliteStorage`）、`experimental/durable/`、`experimental/vacation/`、`experimental/services/`。实验面已删除的能力清单（`navigate()`/`nextRun()`/`resume()`、subagent 暴露、Transcript 分页）见 `src/experimental/services/README.md:38-47` TODO 段。（硬事实）
2. **`AgentLane`/`AgentHarness` 接口消失**：契约面现在是 pi-durable 的 `Harness`（`harness/types.ts:538`）、`Conversation`（:484）、`Session`（`types.ts:899`）、`Storage`（:993）接口。（硬事实）
3. **崩溃恢复与 durable 是一回事**：任务、提交、文档全部是持久化记录；`Harness.resume()`（`harness.ts:236-239`）恢复调度，open 时 reconcile 补齐崩溃遗留。（硬事实）
4. **三个存储后端全部公开**：memory / JSONL / SQLite（`./storage/memory`、`./storage/jsonl`[+`/node`]、`./storage/sqlite`[+`/node`]），取代 v0.86.1 时代"SQLite 在独立 session-backends 包"的布局——该包在 1.0.0 整包删除且全仓 changelog 未点名。（硬事实）

## 最小例子是什么

```typescript
// v1.0.0：运行时入口是 pi-durable 的 Harness.open()，over 一个 Storage 后端：
import { Harness, createRegistry, defineExtension } from "@earendil-works/pi-durable";
import { openNodeJsonlStorage } from "@earendil-works/pi-durable/storage/jsonl/node";

const storage = await openNodeJsonlStorage("./data", context);
const harness = await Harness.open(storage, {
  registry: createRegistry(), // 必含 Generation/Tool/Compaction 三个内置任务
  models, /* settings, env, onReport… */
}, context);

// 语义层观察（不依赖内部 API 的稳定信号）：
// - harness.root(context) 建根会话 → 创建钩子写入 pi.live/pi.inbox/pi.usage/pi.agent 四文档
// - conversation.submit() → Submissions 准入 → GenerationTask 以 pending 落盘 → scheduler 驱动
//   prepare → request → tools 各 phase，checkpoint 随 commit 持久化
// - 进程重启后 Harness.open() 把幸存 running 任务改回 pending 重跑
// - conversation.watch()/harness.watchTaskGraph() 是 chord replicated state 上的只读投影
```

关键要点：**1.0.0 里 pi-agent-core 没有 harness；`Harness`/`Conversation`/`TaskScheduler` 是 pi-durable 的现实运行时，旧 `Lane`/`driveOperation`/pico3 只在 git 历史里存在；products 路径仍走 coding-agent，durable 消费目前限于 experimental 线。**
