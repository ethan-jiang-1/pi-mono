# 5.2 形状的因果:极简核 + 深扩展口是被什么逼出来的

## 现象是什么

pi 的形状由三个互相咬合的决定构成:**极简核**(`CONTRIBUTING.md:7`:"pi's core is minimal",且"连扩展 hook 点都要审慎")、**单一深扩展口**(能力以扩展进入,[1.2](../01-Architecture/1.2_single_injection.md) 的统一注入点)、**library-first**(`README.md:15`:"the Pi agent harness project including our self extensible coding agent";SDK `createAgentSession` 是第一集成路径)。v1.0.0 又把这一形状推到底:pi-agent-core 收缩到只剩 Agent/loop/proxy/types(−105k 行),持久会话事实层移交 `packages/durable`([`_digested/README.md`](../../README.md) v1.0.0 记录)。

![压力画像如何塑形 pi](figures/shape_causality.svg)

## 核心矛盾是什么

**稳定性 vs 可组合性**。核越稳定,嵌入方越敢依赖;核越可组合,单产品内越能长出多样形态。pi 押前者,DSH 押后者——[`_faq_on_digested/06_pi_vs_dsh/answer.md`](../../../_faq_on_digested/06_pi_vs_dsh/answer.md) 已给出总论("同一个问题的两个极端答案"),本页不重做对照,只回答 pi 侧的**因果**。

## 设计判断是什么

### 判断一:形状与组合压力匹配——pi 承受的是"嵌入压力",不是"多宿主组合压力"(解释,[框架] 借用 DSH harness-idea 07 的检验维度)

DSH harness-idea 07 给过一个可迁移判据:形状的性价比由组合压力决定;多宿主、多 provider、会话级隔离、运行时装卸同时出现时,"组合一个运行时"才划算。pi 的真实压力画像不同:一个 spine、一个产品外壳(coding-agent)、一条 SDK 进程内嵌入路径(`sdk.ts:175`)、无 HTTP server 集成([`integration/`](../../integration/) 已核)——**"被别的产品当引擎嵌"不需要运行时可装卸,需要的是宿主拿到的 API 面稳定且小**。极简核正是对这种压力的形状响应:嵌入方要背的运行时越少越好。

可证伪观察:若 pi 走向多宿主(同一 runtime spine 起多棵产品树、会话级装卸扩展),现形状的成本会超过收益——[2.3](../02-Boundaries/2.3_agent_lane_contract_first.md) 记录的 AgentLane/内层 harness 反复(`pi-agent-core 有 → 移出 → durable 承接`)正是这个压力还没到位时的摇摆证据(解释)。

### 判断二:生产方式偏好"可被纪律维持的形状",而不是"可被机器证明的形状"(解释 + [推测] 标注)

pi 的工程规则(`AGENTS.md`)写得像一份给参与者的行为合同:改码必跑 check(`:32`)、不动 `models.generated.ts`、依赖变更当 review 处理(`:43` 节)、git 规则防多会话互踩(`:52` 节)。这套规则的共同点是**由 review 与 CI 兜底的文字纪律**,不是 DSH 那种为"主力是 agent"而生的机械门禁体系(`[推测]` pi 的日常开发主体构成,仓库内无第一方自述,本页不做断言;能核的只有:规则为"人与 agent 都参与"而写——`AGENTS.md` 开篇 "for both humans and agents",`README.md:24` "ask the agent to explain itself")。

在这套生产方式下,形状选择的动机可以自洽:维护者少、review 是瓶颈的仓库,最怕的是**每加一个功能都要审一遍核心 PR**——core-minimal 把核心 PR 的数量与面积同时压小,扩展面则放开到"PR 不进 core 就行"。**纪律(3.1)与形状(本页)因此互为因果**,这条因果链在 [3.1 判断一](../03-Discipline/3.1_core_minimal.md) 已立,本页补的是压力侧的"为什么值得"。

### 判断三:v1.0.0 的收缩是形状逻辑的延续,不是转向(硬事实 + 解释)

v1.0.0 把 durable/session/harness 移出 pi-agent-core(+mcp/+codemode/−session-backends,删除量首次超过新增量,[`_change_log/0007`](../../_change_log/0007-v0.86.1-to-v1.0.0.md) 已核)。按本页框架读:这是"嵌入压力"判据的再次执行——**内层会话运行时不是每个嵌入方都要背的**,收缩让 `packages/agent` 成为更纯的引擎核,把"要不要持久化"变成嵌入方的组合选择。方向与 core-minimal 完全一致。

## 影响是什么

1. **评估迁移性**:想把 pi 的形状搬到别的项目,先问自己的组合压力画像;若答案也是"嵌入型",极简核是正确响应,若不是,该学的是纪律而不是形状(与 DSH harness-idea 07 的结论句同构)。
2. **解释了 02-Boundaries 的多数"短板"为何存在**:无沙箱、无版本契约、无中心编排,都不是疏忽——它们全部位于"嵌入压力不需要"的区间([2.1](../02-Boundaries/2.1_no_sandbox.md)/[2.4](../02-Boundaries/2.4_no_version_contract.md) 从边界角度已判,本页给因果归属)。

## 最小例证是什么

**例证 1(压力画像)**:数集成路径——SDK 进程内、RPC 子进程 JSONL、TUI 终端;没有多 profile、没有运行时装卸。压力画像是"嵌入",不是"组合"。
**例证 2(收缩方向)**:对比 v0.86.1 与 v1.0.0 的 `packages/agent` 职责表([`_digested/README.md`](../../README.md) 两版):内核单调变纯。若形状逻辑变了,收缩应伴随新功能入核——没有发生。
