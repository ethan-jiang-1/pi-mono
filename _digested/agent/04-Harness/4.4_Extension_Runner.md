## 现象是什么

pi-mono 支持 extension 系统：用户或第三方可以把 TypeScript/JavaScript 文件放到特定目录，扩展会自动加载。Extension 可以注册 LLM 可调用的 tools、注册 slash commands、监听 agent 生命周期事件、注册键盘快捷键和 CLI flags、与 UI 交互、注册自定义 LLM providers。

从用户角度看：放一个 `.ts` 文件到 `.pi/extensions/`，重启或 `/reload`，新功能就生效了。（硬事实：loader.ts 的 `discoverAndLoadExtensions()` L758 扫描 `{cwd}/.pi/extensions/`）

## 核心矛盾是什么

Extension 系统面临几个矛盾：

1. **运行时隔离**：extension 是用户写的 TS 代码，可以 import npm 包。但在 Bun binary 模式下，文件系统上的 npm 包不可用——必须在编译时静态打包进 binary，然后在运行时通过 virtual modules 暴露（硬事实：`VIRTUAL_MODULES` L40-71 中的每个 key 对应一个 `_bundled*` 编译时静态 import）
2. **事件安全**：一个 extension 的 handler 崩溃不应该影响其他 extension 或宿主进程——但权限检查这类 hook 又必须 fail-close（解释：这是设计意图，体现为 `emitToolCall()` 无 try-catch vs 其他 emit 都包裹 try-catch 的差异）
3. **生命周期复杂**：extension 的 load → init → bind → event loop → shutdown 跨越多个系统组件
4. **UI 可用性未知**：extension 不知道自己运行在 TUI、RPC 还是 print mode，UI 方法可能是 no-op（硬事实：`uiContext` 初始值 `noOpUIContext` L236，`setUIContext()` L436 才注入真实实现（v0.84.4 起经 `wrapUIPromptContext` 包装））
5. **并发注册冲突**：多个 extension 可能注册同名 command、同名 shortcut、同名 tool

## 实现思想是什么

### 加载器（loader.ts）

**三步加载流程：**

1. **路径发现**：`discoverAndLoadExtensions()`（L758）从三个来源收集 extension 路径（去重）：
   - Project-local：`{cwd}/.pi/extensions/`
   - Global：`{agentDir}/extensions/`
   - Configured：显式配置的路径

2. **模块编译**：用 `jiti`（即时编译）加载 TypeScript 模块（`loadExtensionModule()` L436）
   - Node.js 模式：通过 `alias` 选项把 `@earendil-works/pi-*` 解析到 workspace 中对应包的 dist 文件
   - Bun binary 模式：通过 `virtualModules` 选项把预打包的模块直接注入，`tryNative: false` 确保 jiti 处理所有 import（L449）

3. **Factory 调用**：每个 extension 必须 `export default function(api: ExtensionAPI)`，这个函数通过 `createExtensionAPI()`（L254）拿到注册 API，注册 handlers/tools/commands/shortcuts/flags（`loadExtension()` L566）

**Virtual modules**（Bun binary 下的关键设计，L40-71）：

```typescript
const VIRTUAL_MODULES = {
  typebox: _bundledTypebox,
  "typebox/compile": _bundledTypeboxCompile,
  "typebox/value": _bundledTypeboxValue,
  "@sinclair/typebox": _bundledTypebox,        // 旧包名别名
  "@earendil-works/pi-agent-core": _bundledPiAgentCore,
  "@earendil-works/pi-tui": _bundledPiTui,
  "@earendil-works/pi-ai": _bundledPiAiCompat, // 解析到 compat 入口（旧全局 API 的超集）
  "@earendil-works/pi-coding-agent": _bundledPiCodingAgent,
  // 同时支持新旧两种 package name
  "@mariozechner/pi-agent-core": _bundledPiAgentCore,
  // ...
};
```

这些模块在编译 Bun binary 时被静态 import（保证被 bundler 包含），然后在运行时通过 virtual modules 暴露给 jiti 加载的 extension 代码。

**扩展包发现（package.json manifest）：**

`resolveExtensionEntries()`（L610）检查目录的 `package.json`。manifest 由 `readPiManifest()`（`core/pi-manifest.ts:17`，v0.86.1 重锚）解析，字段为 `pi.extensions` / `pi.skills` / `pi.prompts` / `pi.themes`：

```json
{
  "pi": {
    "extensions": ["./dist/extension.js"],
    "themes": ["./themes/dark.json"],
    "skills": ["./skills/"],
    "prompts": ["./prompts/"]
  }
}
```

没有 manifest 时回退到目录中的 `index.ts`/`index.js`。这允许 npm 包作为 extension 分发。

### 运行时（runner.ts，1236 行）

**ExtensionRunner 的生命周期：**

```
loadExtensions() → createExtensionRunner() → bindCore() → bindCommandContext() → setUIContext()
                         ↓
                    event loop（emit* 方法被调用）
                         ↓
                    invalidate() → shutdown()
```

**bindCore() 的作用（L317）：**

`bindCore(actions, contextActions, providerActions?)` 把宿主进程的实际能力绑定到 extension runtime 上：
- runtime actions：`sendMessage`、`sendUserMessage`、`appendEntry`、`setSessionName`/`getSessionName`、`setLabel`、`setModel`、`setThinkingLevel`、`getActiveTools`/`getAllTools`/`setActiveTools`/`refreshTools`、`getCommands` 等
- context actions：`getModel`、`getScopedModels`、`isIdle`、`isProjectTrusted`、`getSignal`、`abort`、`shutdown`、`getContextUsage`、`compact`、`getSystemPrompt`、`getSystemPromptOptions` 等
- provider actions：`registerProvider`、`registerNativeProvider`、`unregisterProvider`

在 `bindCore()` 之前，runtime 的这些 action 方法是加载器预置的 stub。加载阶段调用 `api.registerProvider()` 只会进 `pendingProviderRegistrations` / `pendingNativeProviderRegistrations` 队列；`bindCore()` 时逐个 flush 到 ModelRegistry（单个注册失败只 emitError，不中断 flush，L354-387），之后注册立即生效、不需要 `/reload`（L389-411）。（解释：pending 队列是加载阶段和运行阶段之间的桥梁——resolve 生命周期差异又不丢失注册）

**事件分发机制：**

ExtensionRunner 有多个 `emit*()` 方法，每个处理特定类型的事件，按 extension 加载顺序依次调用 handler：

| emit 方法 | 处理的事件 | 特殊行为 |
|---|---|---|
| `emit()`（L851） | 通用事件（除特殊事件外） | `session_before_*` 四类事件支持 `cancel` 短路 |
| `emitMessageEnd()`（L885） | `message_end` | pipeline 修改；handler 返回的 message **role 必须一致**，否则记错并跳过 |
| `emitToolCall()`（L982） | `tool_call` | `block` 结果即短路，不执行后续 handler |
| `emitToolResult()`（L927） | `tool_result` | handler 可部分覆盖 result 字段 |
| `emitContext()`（L1034） | `context` | handler 可替换整个 messages 数组（入口先 structuredClone） |
| `emitBeforeProviderRequest()`（L1066） | `before_provider_request` | handler 可改写 provider payload（pipeline） |
| `emitBeforeProviderHeaders()`（L1100） | `before_provider_headers` | handler 原地修改 headers，返回值被忽略 |
| `emitBeforeAgentStart()`（L1131） | `before_agent_start` | handler 可注入 messages 和修改 system prompt |
| `emitResourcesDiscover()`（L1197） | `resources_discover` | 收集 skill/prompt/theme 路径并附带 extensionPath |
| `emitInput()`（L1246） | `input` | transform chain，`handled` 短路，`continue` 放行 |
| `emitUserBash()`（L1005） | `user_bash` | 第一个非空结果作为 handler 结果 |

（以上行号为 v0.84.4 重锚；ui_prompt 事件不走这张表——见下文"ui prompt 包装层"。）

**ui prompt 包装层（v0.84.4 新增，#8355）：**

`setUIContext()`（L436）现在把传入的 UI context 用 `wrapUIPromptContext()`（L441-450）包一层：`select`/`confirm`/`input`/`editor`/`custom` 五个阻塞式 UI 方法各自经 `withUIPrompt(kind, title, run)`（L453-480）执行。`withUIPrompt` 用 `uiPromptDepth` 深度计数：最外层 prompt 开始时发 `ui_prompt_start`，归零时发 `ui_prompt_end`——嵌套/重叠 prompt 合并为一个外层 span。事件经 `emitUIPromptEvent()`（L482-484）用 `queueMicrotask` 异步发射，**handler 不会被 await，不阻塞 prompt 的显示与关闭**。`UIPromptKind` 与事件类型定义在 `extensions/types.ts:745-762`。

**错误隔离（以及它的一个关键例外）：**

除 `emitToolCall()` 外，所有 `emit*()` 方法的 handler 调用都包裹在 try-catch 中。如果 handler 抛出异常：
- 错误被包装为 `ExtensionError`（包含 `extensionPath`、`event`、`error`、`stack`）
- 通过 `emitError()`（L613）通知 error listeners
- 对其他 extension 没有影响（继续执行后续 handler）

**例外是 `emitToolCall()`（L1035-1053，v0.86.1 重锚；旧 L982-1003 已漂移）——它没有 try-catch，handler 异常直接向上传播。** 这是有意的 fail-close：权限检查 hook 崩溃必须阻止工具执行，而不是静默放行。（解释：设计决策——安全边界使用不同的错误模型）传播路径是 `AgentSession._installAgentToolHooks()`（`agent-session.ts:507`）里 `agent.beforeToolCall` 包装器把异常重新抛出（非 Error 值包装成 "Extension failed, blocking execution"），最终该 tool call 以错误结果收场。（v0.75 文档描述的 `AgentHarnessError("hook")` 机制已随 v0.83 泛型 harness 一起消失。）（硬事实：`agent-session.ts:507` 和 `runner.ts:1035` 的 try-catch 缺失可验证）

**Tool call 的 block/terminate 机制：**

`emitToolCall()` 中只要任何一个 handler 返回 `{ block: true }`，后续 handler 不会被调用。`ToolCallEventResult`（`extensions/types.ts:1125`）还支持 `terminate?: boolean`：blocked 且 terminate 时提示 agent 在当前 tool batch 结束后停止（agent loop 侧在 `prepareToolCall` 里把 `result.terminate` 传播出去，`agent/src/agent-loop.ts:633-638`）。要修改参数则在 handler 里原地改 `event.input`。

**Context 创建（L723）**

ExtensionRunner 通过 `createContext()` 创建 `ExtensionContext` 对象，提供给 handler 使用。Context 的属性通过 getter 懒求值，确保每次访问都拿到最新状态，且**每个 getter 都先过 `assertActive()`**（L602）——extension 失效（session 被替换、reload 等）后访问会抛出带指引的错误信息（`invalidate()` L593），防止使用 stale context：

```typescript
createContext(): ExtensionContext {
  return {
    get model() { runner.assertActive(); return getModel(); },  // 懒求值 + 失效检查
    isIdle: () => { runner.assertActive(); return runner.isIdleFn(); },
    get ui() { runner.assertActive(); return runner.uiContext; },
    // ...
  };
}
```

**UI 不可用时的处理：**

ExtensionRunner 初始化时 `uiContext` 设为 `noOpUIContext`（L235-266），所有 UI 方法都是 no-op：
- `select()` 返回 `undefined`
- `confirm()` 返回 `false`
- `input()` 返回 `undefined`
- `notify()`、`setStatus()`、`setWidget()`、`setEditorText()` 等是空函数
- `setTheme()` 返回 `{ success: false, error: "UI not available" }`

当宿主有 UI（如 interactive TUI mode）时，通过 `setUIContext(uiContext, mode)`（L436）注入真正的 UI 实现并声明运行 mode（默认 `"print"`）；`ctx.hasUI` 让 handler 自行探测。

**命令名冲突：**

`resolveRegisteredCommands()`（L603）给重名 command 分配 `name:2`、`name:3` 式的 `invocationName`，而不是静默覆盖。

### Provider 注册

Extension 可以在运行时注册自定义 LLM provider：

```typescript
api.registerProvider("my-custom-provider", {
  modelIds: ["model-a", "model-b"],
  contextWindow: 128000,
  // ... provider config
});
```

- 加载阶段的注册进入 pending 队列（见上文 bindCore）
- `bindCore()` 时 flush；此后注册立即生效（不需要 `/reload`）
- native provider（完整 `Provider` 对象）走 `registerNativeProvider()`，同样有 pending 队列

### 事件总线（EventBus）

Extension 可以通过 `api.events` 获得一个 `EventBus` 实例：

```typescript
api.events.emit("deploy:completed", { data: "hello" });
api.events.on("deploy:completed", (payload) => { ... });
```

`createEventBus()`（`core/event-bus.ts:12`）基于 Node `EventEmitter` 提供发布/订阅，用于 extension 之间以及 extension 与宿主的通信。关键行为：
- emit 同步分发；同步/异步 handler 都支持
- handler 异常被 catch 并 `console.error`，不传播
- **同一次加载的所有 extension 共享一个 bus 实例**：`loadExtensionsInternal()` 在未传入时创建一个（`loader.ts:550`），产品里由 `ResourceLoader` 持有同一个（`resource-loader.ts:257`）——所以 `api.events` 是跨 extension 的通信通道，不是每个 extension 私有的（硬事实：`loader.ts:550` 和 `resource-loader.ts:257` 的共享实例可验证）

## 在 Agent 能力面里的影响是什么

1. **Extension 是 pi-mono 最高级的能力扩展机制**。几乎任何运行时行为都可以被 extension 修改或增强。（推测：随着更多 hook 点的加入，extension 可能进一步覆盖 agent 生命周期中的更多阶段）

2. **工具（tools）不再是硬编码的**。Extension 可以注册 LLM 可调用的工具，这些工具和内置工具（bash、edit 等）同权（`getAllRegisteredTools()` 同名先到先得，L501）。（硬事实：`getAllRegisteredTools()` 的同名冲突策略是先到先得，行号 L501）

3. **事件系统的所有 hook 都暴露给 extension**。Extension 可以在 agent loop 的任何关键节点插入逻辑。

4. **Error isolation 有边界**。普通事件里一个 extension 出问题不会拖垮其他 extension；但 `tool_call`（权限关）故意 fail-close，handler 异常会阻断执行。（解释：两种错误模型服务于不同的安全需求——普通事件可用性优先，权限关安全性优先）

5. **Stale context 保护机制**防止了 session 替换后的悬空引用问题。（硬事实：`assertActive()` L602 在每个 context getter 中调用）

## 最小例子是什么

```typescript
// my-extension.ts — 放在 .pi/extensions/ 目录
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (api: ExtensionAPI) {
  // 1. 注册自定义工具
  api.registerTool({
    name: "weather",
    label: "weather",
    description: "Get weather for a city",
    parameters: Type.Object({ city: Type.String() }),
    async execute(_id, { city }) {
      const response = await fetch(`https://api.weather.example/${city}`);
      const data = await response.text();
      return { content: [{ type: "text", text: data }] };
    },
  });

  // 2. 注册 slash command
  api.registerCommand("deploy", {
    description: "Deploy to production",
    handler: async (ctx) => {
      await ctx.ui.notify("Deploying...", "info");
      await ctx.pi.sendUserMessage("Run the deploy script");
    },
  });

  // 3. 监听 tool_call 事件（注意：这里的异常会阻断工具执行——fail-close）
  api.on("tool_call", (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("DROP TABLE")) {
      const confirmed = await ctx.ui.confirm("Dangerous SQL", "Proceed?");
      if (!confirmed) return { block: true, reason: "user declined" };
    }
  });

  // 4. 修改 system prompt（异常只记 error，不影响别的 extension）
  api.on("before_agent_start", (event, ctx) => {
    return {
      systemPrompt: ctx.getSystemPrompt() + "\nAlways respond in haiku form.",
    };
  });

  // 5. Extension 间通信（共享 bus：别的 extension emit 的同名事件也能收到）
  api.events.on("deploy:completed", (payload) => {
    console.log("Deploy completed:", payload);
  });
}
```

可观察信号：在第 3 个 handler 里故意 `throw new Error("boom")` 再让模型跑一条 bash 命令——这次工具调用会以错误结束（fail-close），错误出现在 error listener/UI 的 extension 错误流里；把同样的 throw 移到第 4 个 handler，则 agent 照常运行，只有该 extension 收到一条 error 记录。两种命运的不同就是错误隔离边界的位置。

关键要点：**extension 就是一个默认导出的 factory 函数**，接收 `ExtensionAPI` 作为参数，通过它注册能力。所有注册在 factory 执行期间完成，之后 agent 运行时会通过注册的 handlers 回调 extension。
