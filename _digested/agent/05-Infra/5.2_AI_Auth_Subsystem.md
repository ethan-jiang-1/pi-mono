## 现象是什么

v0.83.0 中 `packages/ai/src/auth/`（16 个文件）把原本散落在 `utils/oauth/` 和 provider 定义里的认证逻辑，升级为 `pi-ai` 的一阶子系统。它定义了完整的 credential 类型层级、一个线程安全的 `CredentialStore` 接口、一个统一的 `resolveProviderAuth()` 管道，以及 7 个 provider 的 OAuth flow 实现。

对外部集成者来说，这层的存在意味着：**你不再需要知道每个 provider 怎么拿到 API key**。credential resolution 被收敛为一句 `models.getAuth(providerId)`（硬事实）（pi-ai 的 `Models` 接口；coding-agent 侧是 `ModelRuntime.getAuth()`，`ModelRuntime implements Models`）。

## 核心矛盾

**每个 provider 的认证方式不同——但调用方不应该关心。**（解释） Anthropic 用 PKCE + loopback server。GitHub Copilot 用 device-code flow + token exchange。OpenRouter 的 OAuth 返回的是永久 API key 而非 expiring access token。Kimi Code 用 `Authorization: Bearer` header 而非 `apiKey` 字段。

如果每个调用方都要自己处理这些差异，外部集成 pi-mono 的门槛会极高。auth 子系统的设计目标是把这些差异封装在 `ModelAuth` 这一种返回类型后面。（解释）

## 实现思想

### 类型层级

```
ModelAuth { apiKey?, headers?, baseUrl? }     ← 唯一暴露给调用方的类型
  ↑
ProviderAuth { apiKey?: ApiKeyAuth, oauth?: OAuthAuth }  ← 每个 provider 的 auth handler
  ↑
Credential { ApiKeyCredential | OAuthCredential }         ← 持久化的凭证
```

`ModelAuth` 刻意极窄——如果一种认证方式无法表达为 `apiKey` + `headers` + `baseUrl` 三个字段之一，那就不是 auth，是 provider config。（解释）

### resolveProviderAuth 管道

`resolve.ts` 导出的 `resolveProviderAuth(provider, credentials, authContext, overrides?)` 是唯一入口（硬事实）（`provider` 只需 `{ id, auth }` 形状）：

```
1. 有 override apiKey（且 provider 有 apiKey handler）？
   → 用 override 构造一次性 credential 走 resolveApiKey，跳过 store，跳过 ambient
     （overrides.env 会 overlay 到 authContext；另外可带 minOAuthValidityMs / signal）

2. 从 CredentialStore 读取已存储的凭证
   ├── OAuth + provider 有 oauth handler
   │   → resolveStoredOAuth（double-checked locking refresh）
   ├── api_key + provider 有 apiKey handler
   │   → resolveApiKey（合并 cred.env 和 overrides.env）
   └── 类型不匹配（如存了 api_key 但 provider 只有 oauth）
       → 返回 undefined

3. 没有已存储凭证 + provider 有 apiKey handler
   → resolveApiKey ambient（env var / AWS profile / ADC）
```

关键设计决策：
- **已存储凭证拥有该 provider**。一旦用户登录过，env var 等 ambient 源被完全忽略——消除"我登录了但还是用的 env var"这类 bug
- **OAuth refresh 的 double-checked locking**：先乐观读 expiry，只有 <5min 有效（`DEFAULT_OAUTH_MINIMUM_VALIDITY_MS`，override 可收紧）时才进入 `credentials.modify()`。锁内再检查一次——如果另一个请求已经 refresh 过，直接返回，避免 thundering herd。**取消语义 v1.0.3 起改变**（bde882c74）：刷新抽出为 `refreshStoredOAuthCredential()`（`auth/resolve.ts:119-155`），`signal` **只取消对 credential 锁的等待**；刷新一旦开始就跑完并持久化，仅受 15s 超时（`DEFAULT_OAUTH_REFRESH_TIMEOUT_MS`）约束。旧的 "`AbortSignal.any([signal, AbortSignal.timeout(15_000)])`" 式"signal 一并打断刷新"的描述已失效——rotation 型 provider 下那样做的后果是：provider 在刷新开始时已作废旧 refresh token，取消把新 token 一起丢掉，凭证永久损坏（下次请求 `refresh_token_invalidated`）。
- **`AuthResolutionOverrides`** 允许注入一次性 `apiKey` + `env`（+ `minOAuthValidityMs` + `signal`），完全绕过 store

### CredentialStore：per-provider 串行化

`CredentialStore` 接口：

| 方法 | 作用 |
|------|------|
| `read(providerId)` | 读凭证（可能过期）。展示/状态用。 |
| `list()` | 列出 `CredentialInfo[]`（providerId + type），不暴露 secret |
| `modify(providerId, fn)` | **唯一写路径**。串行化 read-modify-write，per provider。 |
| `delete(providerId)` | 删除凭证（logout）。与 `modify` 串行化。 |

并发模型是 per-provider 单线：`InMemoryCredentialStore` 用 promise chain 保证同一 provider 的 `modify`/`delete` 不会交错。接口文档要求支持跨进程互斥（如 file lock），使多个 pi-mono 实例不会竞态 refresh。

### OAuth 架构

**PKCE**（`pkce.ts`）：用 Web Crypto API（`crypto.getRandomValues` + `crypto.subtle.digest("SHA-256")`），跨平台（Node 20+ / 浏览器）。

**Device Code**（`device-code.ts`）：RFC 8628 兼容的轮询循环。支持 `slow_down`（GitHub 的 interval 递增）、deadline 过期、手动 abort。超时错误消息在收到过 `slow_down` 时变为时钟漂移警告（WSL/VM 常见问题）。

**Dynamic Loading**（`load.ts`）：OAuth flow 模块通过变量字符串 `import("./anthropic.ts")` 加载，bundler 无法追踪。`registerBundledOAuthFlowLoaders()` 是 Bun binary 的 escape hatch——注入静态 bundle 替代动态 import。

**Anthropic**：PKCE + `http.createServer` on `127.0.0.1:53692`。浏览器 redirect → callback server 收 code → exchange token。同时 race 一个 manual code input prompt（给 headless/remote 场景）。**v1.0.0 新增 copy-code 登录**：redirect_uri 也可用 `platform.claude.com/oauth/code/callback`（页面直接显示授权码），登录入口 select 提示 browser(默认)/copy code(headless)——见顶部横幅 ②。**v1.0.0 另有 workload identity federation**（env 驱动、SDK 做 token 交换，见横幅 ①）——provider 侧 `providers/anthropic.ts:52-71`，API 层 `api/anthropic-messages.ts:346-373`。

**OpenRouter**：类似 PKCE loopback，但 token exchange 返回**永久 API key**（`expires: MAX_SAFE_INTEGER`，`refresh: ""`）。callback server 有 `claimed` guard 防重复 claim。

**GitHub Copilot**：device-code flow。refresh 是两层 exchange：device-code access token → Copilot-specific token。登录后 enable **只有 `policyModelIds`**（未配置、catalog 已知、picker 可用的个人订阅模型，**不是"所有 Copilot models"**——v0.84.3 修正，github-copilot.ts:93-132/414-428）并 fetch model list（可用模型 = available ∪ enabled）。v0.84.3 起 rate-limit 处理走共享 `fetchWithRateLimitRetry`（尊重 `Retry-After`，带 `maxRetries`/`maxElapsedMs` 预算，定义于 `github-copilot.ts:135`），refresh 也会重取 model list。`toAuth` 返回 `baseUrl`（从 token 的 `proxy-ep` 字段派生——enterprise 用户有不同 endpoint）。

**Kimi Code**：device-code flow。refresh 有 retry logic（3 次，exponential 1s/2s/4s）for 429/5xx。401/403/invalid_grant 是 terminal——凭证标记为 dead。`toAuth` 返回 `{ headers: { Authorization: "Bearer ..." } }` 而非 `apiKey`。

## 在 Agent 能力面里的影响

- **`ModelRuntime` 是认证的核心运行时**（`packages/coding-agent/src/core/model-runtime.ts`，`implements Models`），把 models.json 装载、credential 同步、auth resolution 收进一个对象。一行 `modelRuntime.getAuth(provider)` 替代了以前的手动 `getApiKeyAndHeaders`。`ModelRegistry`（`core/model-registry.ts`）仍在，但已降级为**暴露给 extension 的同步兼容 facade**——所有方法都委托给 `ModelRuntime`，coding-agent 内部直接用后者；其 `getApiKeyAndHeaders()` 现在返回 `ResolvedRequestAuth` result，`headers` 值为 `ProviderHeaders`（`string | null`——见顶部警示）。`AuthStorage`（`core/auth-storage.ts`）仍在，角色收窄为 "auth.json 持久化的 `CredentialStore` 实现"。
- **外部集成者提供 `Models`（pi-ai，`createModels()`）或 `ModelRuntime`（coding-agent，`ModelRuntime.create({ authPath, modelsPath })`）即可**，不需要理解 OAuth flow、token refresh、PKCE。
- **并发安全是内置的**。多个请求同时触发 refresh 不会产生多次 token exchange。
- **新 provider 只需实现 `ProviderAuth`**（`login`、`refresh`、`toAuth`），PKCE/device-code 是复用工具。

## 最小例子

用 auth 子系统完成一次 credential resolution：

```ts
import {
  createModels,
  defaultProviderAuthContext,
  InMemoryCredentialStore,
} from "@earendil-works/pi-ai"; // 类型与 store 从包根导出
import { anthropicProvider } from "@earendil-works/pi-ai/providers/anthropic";

// InMemoryCredentialStore 无参构造；App 应注入自己的持久化实现
const store = new InMemoryCredentialStore();
const models = createModels({
  credentials: store, // CreateModelsOptions（**v1.4.0 `models.ts:376`**）：credentials/modelsStore/authContext
  authContext: defaultProviderAuthContext(),
});
models.setProvider(anthropicProvider());

// 解析 auth——可能是已存 OAuth credential（自动 refresh）、
// 已存 api key、或 ambient env var（如 ANTHROPIC_API_KEY）
const result = await models.getAuth("anthropic");

if (result) {
  // result.auth: ModelAuth { apiKey?, headers?, baseUrl? }
  // result.source: "ANTHROPIC_API_KEY" | "OAuth" | ...
  // 直接拿去调 API——不需要知道它来自 OAuth 还是 api key
}

// 更省事的路径：Models.streamSimple 内部自动 resolve auth（applyAuth），
// auth.baseUrl 会写回 model，header/apiKey 合并进请求 options
const stream = models.streamSimple(model, context, { reasoning: "high" });
```

注意：`resolveProviderAuth` 是 `auth/resolve.ts` 的内部入口，**没有** `@earendil-works/pi-ai/auth/resolve` 这样的包导出（pi-ai 的 exports 含 `.`、`./compat`、`./models`（v1.0.0 起）、`./providers/*`、`./api/*`、`./utils/*`（含 v1.4.0 的 `identity.ts`）、`./oauth`、`./bedrock-provider`、`./bun-oauth`）；外部代码经 `Models.getAuth()` / `ModelRuntime.getAuth()` 触发同一条管道。

可观察信号：无论 provider 用的是 OAuth（Anthropic/OpenRouter/GitHub Copilot）还是 API key（env var），`result.auth` 始终是同一个 `ModelAuth` 形状。OAuth token 在 <5min 过期时自动 refresh，调用方无感知。
