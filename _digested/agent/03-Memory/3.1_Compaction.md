## 现象是什么

当对话持续进行数十分钟，消息历史可能达到数万 tokens。pi-mono 会在检测到上下文接近模型窗口上限时，自动将早期对话压缩为一个结构化的摘要，嵌入到后续的上下文中（硬事实）。这个压缩以 `CompactionEntry` 的形式记录在 Session tree 中，且是**自包含**的：entry 上同时存有 `summary`（历史摘要）和 `retainedTail`（保留的最近消息）。后续 `buildSessionContext` 只保留最后一个 compaction entry 及其后的条目，compaction entry 被展开为一条 `compactionSummary` message + `retainedTail` 消息（硬事实）。

**源码位置：** `/packages/agent/src/harness/compaction/compaction.ts`

> 注意：`packages/coding-agent/src/core/compaction/` 还有一份仍在运行的 v3 实现（其 `CompactionResult` 仍返回 `firstKeptEntryId`、没有 `retainedTail`）。本篇以 agent 包 harness 模块（session v4 方向）为准，两份实现的分割/摘要策略同源。

## 核心矛盾是什么

对话压缩面临三个核心取舍：

1. **保留什么 vs 丢弃什么：** 早期对话的细节对后续任务可能至关重要（如"我们之前决定用 SQLite"），但全部保留会超出 context window。需要一个有信息密度的摘要格式（推测）。
2. **边界对齐：** 如果在用户消息的中间切断，模型看到的上下文是不完整的（只有 assistant 的回复和 tool 结果，没有上游的用户请求）。Cut point 必须在"合法"的位置（解释）。
3. **增量更新 vs 全新生成：** 如果之前已经有过 compaction，新 compaction 应该更新已有的摘要（而非重新生成），以保留完整的项目进度记忆（解释）。

## 实现思想是什么

### 压缩设置

```typescript
const DEFAULT_COMPACTION_SETTINGS = {
  enabled: true,
  reserveTokens: 16384,    // 为 prompt + 输出保留的 tokens
  keepRecentTokens: 20000, // 保留的最近上下文 tokens
};
```

- `reserveTokens`：压缩时，用于生成摘要的 prompt 和 LLM 输出本身也需要 tokens 配额。
- `keepRecentTokens`：压缩后保留的上下文 token 数。约 20000 tokens，足以保留最近几个完整的 turn。

### 压缩决策：何时触发

```
settings.enabled && estimateContextTokens(messages) > model.contextWindow - reserveTokens
```

这个判断在 `shouldCompact()` 中实现：`enabled` 为 false 时直接返回 false；否则当上下文总 tokens 超过 `contextWindow - reserveTokens` 时触发压缩。

### 寻找分割点：findCutPoint

从路径末尾向前扫描，累积 message entry 的 token 数（`estimateTokens`），达到 `keepRecentTokens` 后选取不早于该位置的第一个有效分割点。但不是所有 entry 都可以作为分割点：

**有效分割点：** message entry 且 role 为 user / assistant / bashExecution / branchSummary / compactionSummary / custom；以及 `branch_summary` entry（在 switch 之后单独 push）。

**无效分割点：** toolResult 消息（不能从工具结果开始，因为缺少上游的 user/assistant 上下文）、`compaction` entry（不能从压缩点开始一个新压缩）、`custom` entry。（v0.85.1：v0.84.x 时还列有 `thinking_level_change`/`model_change`/`active_tools_change` 三种 entry——它们已随 v4 Entry 收成 4 种而消失。）

分割点选择后，还会向后调整：如果分割点前一个是 compaction entry，停止调整；如果前一个是普通 message，也停止；否则把分割点继续前移。这确保分割点落在语义合理的边界上。

如果切中的不是 user 消息，`findTurnStartIndex()` 从切点向上查找该回合的起始（user 消息、bashExecution 消息或 branch_summary entry），命中则判定为 split turn。

### 分回合处理（Split Turn）

当分割点落在 assistant 消息上（而非 user 消息），意味着一个回合被切断。此时将该回合切点之前的部分标记为 "turn prefix"。压缩会分别处理：

1. 之前的完整历史先用标准格式（或增量更新）生成主摘要；没有历史时用占位文本 "No prior history."。
2. 回合前缀（turn prefix）再用 `TURN_PREFIX_SUMMARIZATION_PROMPT` 单独生成摘要（三段式：Original Request / Early Progress / Context for Suffix）。
3. 两者按顺序拼接：主摘要 + `\n\n---\n\n` + `**Turn Context (split turn):**` + 前缀摘要。

注意两步是**顺序执行**（先 history 后 turn prefix，v0.75 时代文档写的"并行"已不成立），两次 LLM 调用的 `Usage` 由 `addUsage()` 相加合并（`packages/agent/src/harness/utils/usage.ts:14`；v0.84.4 时是 `compaction.ts` 内的 `combineUsage()`，v0.85.1 移出并改名）。

### 结构化摘要格式（SUMMARIZATION_PROMPT）

压缩使用标准化的六段格式：

```
## Goal
[用户想完成什么？如果有多个任务或研究方向变化，列出所有相关内容。]

## Constraints & Preferences
- [用户提到的约束、偏好或需求]
- [或 "(none)"]

## Progress
### Done
- [x] [已完成的任务/变更]

### In Progress
- [ ] [正在进行的工作]

### Blocked
- [阻塞项]

## Key Decisions
- **[决策]**: [简要理由]

## Next Steps
1. [下一步的优先级列表]

## Critical Context
- [继续工作所需的关键数据、范例或参考]
- [或 "(none)"]
```

请求还带一个独立的 system prompt（`SUMMARIZATION_SYSTEM_PROMPT`）："You are a context summarization assistant… Do NOT continue the conversation. Do NOT respond to any questions in the conversation. ONLY output the structured summary."——防止模型把摘要任务当成对话续写。传入的 `customInstructions` 会以 `Additional focus: ...` 附加到 prompt 末尾。

输出预算：主摘要 `maxTokens = min(0.8 * reserveTokens, model.maxTokens)`；turn prefix 摘要 `maxTokens = min(0.5 * reserveTokens, model.maxTokens)`。模型支持 reasoning 且 thinkingLevel 非 off 时，请求会附带 `reasoning` 参数。

这个格式的设计目标：让续接的 LLM 能够快速理解目标、进度、约束和下一步，而不是像通用文本摘要那样丢失结构。

### 增量更新

当存在 `previousSummary` 时，使用 `UPDATE_SUMMARIZATION_PROMPT`（而非 `SUMMARIZATION_PROMPT`），并把旧摘要包在 `<previous-summary>` 标签里随请求传入。这个 prompt 指示 LLM：

- 保留已有摘要中的所有信息。
- 添加新的进展、决策和上下文。
- 更新 Progress 部分（将 "In Progress" 移到 "Done"），并基于已完成内容更新 Next Steps。
- 保留精确的文件路径、函数名和错误消息。
- 不再相关的内容允许删除。

这避免了反复压缩导致的信息衰减。

### completeSimpleWithRetries：Models 接口 + 重试

摘要请求统一走 `completeSimpleWithRetries(models, model, context, options, retry?, callbacks?)`：

- 通过 `Models` 接口调用 `models.completeSimple(...)`——auth/headers 由 Models 内部解析，调用方不再传 `apiKey`/`headers`。
- 强制 `cacheRetention: "none"`；agent 侧**总是新建** `sessionId: uuidv7()`（`createSummaryRequestOptions()`，compaction.ts:117-125，`sessionId` 在 :123；v0.84.4 时直接在 `completeSimpleWithRetries` 内，:113-114）——standalone 隔离路由。（对照：coding-agent 侧 `completeSummarization` 复用调用方 routing session：`sessionId: options.sessionId ?? uuidv7()`，`core/compaction/compaction.ts:592`，v0.84.3 起。）
- ~~v0.84.3 新增 `toolChoice: "none"`~~——**v0.84.4 撤回**（#8649/#8638）：摘要请求不再设置 `toolChoice`。对模型仍返回 `toolCall` 块的拒绝保留，且扩大到 `length` 截断：coding-agent 侧 `getSummarizationFailure(response, label)`（`core/compaction/compaction.ts:545`）对 `stopReason: "error"` 与 `"length"` 都返回失败消息，`generateSummaryWithUsage`（:715）、`generateTurnPrefixSummary`（:1000）、`generateBranchSummary`（branch-summarization.ts:357）三个调用点据此拒绝，**截断的 summary 不再被当作 checkpoint 持久化**（#7048）。
- 用 `retryAssistantCall()` 包装，支持 `RetryPolicy`（`enabled`/`maxRetries`/`baseDelayMs`，指数退避）与 `RetryCallbacks`（onRetryScheduled / onRetryAttemptStart / onRetryFinished）。

`generateSummaryWithUsage()` 返回 `{ text, usage }`（usage 是生成摘要那次 LLM 调用的真实消耗，会被记录到 CompactionEntry 上）；`generateSummary()` 是只取 text 的薄封装。

### prepareCompaction + compact() 的完整流程

```
prepareCompaction(pathEntries, settings)   // 返回 Result<CompactionPreparation | undefined>
  → 路径为空、或最后一个 entry 已是 compaction → ok(undefined)，不做压缩
  → 向前找上一个 compaction：
      previousSummary = prevCompaction.summary
      把 prevCompaction.retainedTail 重新物化为虚拟 message entries
      （id 形如 `${prev.id}:retained:${i}`），与其后的条目拼成 compactableEntries
  → tokensBefore = estimateContextTokens(buildContextEntries(pathEntries).flatMap(sessionEntryToContextMessages)).tokens
  → findCutPoint(compactableEntries, 0, end, keepRecentTokens)
  → historyEnd = isSplitTurn ? turnStartIndex : firstKeptEntryIndex
  → messagesToSummarize = [0, historyEnd)      // compaction entry 本身被跳过（已由 previousSummary 代表）
  → turnPrefixMessages = [turnStartIndex, firstKeptEntryIndex)
  → retainedTail = [firstKeptEntryIndex, end)   // 直接存进新 CompactionEntry
  → fileOps：先继承上一个 compaction 的 details(readFiles/modifiedFiles)，
    再从被摘要消息的 assistant tool call 中提取（read/write/edit，按 args.path）

compact(preparation, models, model, customInstructions, thinkingLevel, retry, callbacks, context)
  （v0.85.1 签名：signal? 的位置由尾参 context 取代；等价单请求入口是 compactWithRequest()）
  → 如果 isSplitTurn 且有 turnPrefixMessages：
    → 顺序执行 generateSummaryWithUsage(历史) → generateTurnPrefixSummary(前缀)
    → 拼接 summary，两次调用 usage 用 combineUsage() 合并
  → 否则：generateSummaryWithUsage(历史，可选 previousSummary 增量更新)
  → summary 末尾追加文件操作列表（<read-files>/<modified-files> 标签）
  → 返回 CompactResult { summary, tokensBefore, usage?, retainedTail, details? }
```

自包含设计的关键收益：上一个 compaction 的 `retainedTail` 会被重新纳入本次可压缩范围，因此连续多次压缩不会让"上次保留下来的尾部"变成永远无法压缩的死区。

### AgentSession 自动压缩

运行时集成目前仍在 coding-agent 的 `AgentSession`（`packages/coding-agent/src/core/agent-session.ts`，import 自 `core/compaction/index.ts`）：`agent_end` 之后与 prompt 提交前各调用一次 `_checkCompaction()`（agent-session.ts:2126），处理两种场景：

1. **Overflow（溢出/可恢复截断）：** LLM 返回 context overflow 错误，或输出因 length 截断且低于原始期望上限 → 从 agent 状态移除该条消息（仍留在 session 历史里）→ 执行压缩 → **自动重试**。重试只有一次（`_overflowRecoveryAttempted` 标记防止循环）；若消息 stopReason 已是 "stop"（回答已完成），压缩但不重试。
2. **Threshold（阈值）：** 上下文超过阈值 → 执行压缩 → **不自动重试**（等待用户手动 continue）。

**v0.84.4 新增第三种触发——between-turn 阈值压缩**（#8782，closes #6879）：`_compactBeforeNextAssistantResponse()`（agent-session.ts:543，挂进 `_installAgentNextTurnRefresh` 的 `prepareNextTurnWithContext` 覆盖链 :568-569）在**工具结果追加后、下一次 assistant 请求前**检查 `shouldCompact(estimateContextTokens(...))`，超阈值就在**同一 agent run 内**执行 threshold 压缩并返回压缩后的新 context（run 继续运行，不等用户 continue）。跳过条件：run 将终止（`shouldStopAfterTurn`）且无排队消息需要响应时不做检查（docs/compaction.md:37）。这依赖 v0.84.4 的 loop 时序重排——`prepareNextTurn` 只在确认循环继续后运行，final turn 不再白白触发压缩检查（见 [2.1 The Loop](../02-Runtime/2.1_The_Loop.md)）。配套：TUI 进度指示从 `agent_start` 推迟到 `turn_start`，压缩占用的时间不再显示假进度（interactive-mode.ts:2162/3197）。

session v4 侧，`AgentHarness.compact()` / `navigateTree()` 操作与 `CompactionReason`（manual/threshold/overflow）都已定义。

> **⚠️ v0.85.1 更正**：本节 v0.84.4 时写的"AgentHarness 当前仍是 scaffold（方法抛 `HarnessNotImplemented`）、`step_attempt` 与 `harness/reducer.ts` 可恢复这些操作"**已失效**。`HarnessNotImplemented` 在 v0.85.1 源码树里零命中；`AgentHarness` 已是工厂对象 `AgentHarness = { create }`，compaction/navigate 都是真实现；旧 `harness/reducer.ts`(667 行) 已删除，换成 `runtime/reducer.ts`（纯视图 fold，同名不同职能）。详见 [4.1_AgentHarness.md](../04-Harness/4.1_AgentHarness.md)（另一轮重写中）。压缩**算法**本身不受影响。

## 在 Agent 能力面里的影响是什么

- **无限对话的错觉：** Compaction 让长时间对话成为可能，而不需要用户手动管理上下文。
- **结构化的记忆：** 六段摘要格式比纯文本摘要提供了更好的"记忆索引"，后续的 LLM 调用能快速定位关键信息。
- **溢出的自动恢复：** Overflow 场景下，压缩 + 一次性重试对用户完全透明——用户可能只看到一个短暂的"Compacting..."提示。
- **文件操作追踪：** `CompactionDetails` 记录了压缩区间内的 readFiles 和 modifiedFiles，且每次 compaction 会继承上一次的 details 累积，等价于"自首次压缩以来"的文件操作账本。
- **可审计的成本：** `CompactResult.usage`（以及 entry 上的 `usage`）记录了生成摘要本身消耗的 tokens，进入 session v4 的 usage 统计（cause: "compaction"）。

## 最小例子是什么

> **⚠️ v0.85.1 提示**：下面的**压缩链路**（估算 → 判断 → 准备 → 执行 → 持久化）逐行成立，但两处 session 侧调用是 **v0.84.x 形状**，v0.85.1 已不存在：
> - `session.findEntriesOnBranch({...})` / `session.appendEntry({...}, "main")` —— 现在读路径是 `session.findEntries(query, context)` / `branch.findEntries(query, context)`，写路径是 `session.mutate(...)` 或 `branch.appendMessage(...)`，**每个读写都要传 `Context`**；
> - `buildSessionContext(pathEntries)` 现在是 **async** 且要 `(pathEntries, options | undefined, context)`（见上表）；它**不在 `pi-agent-core` 的包导出面上**（`./harness/session` 不 re-export `context.ts`），公开面可用的是 `findEntries` + `buildContextEntries` + `sessionEntryToContextMessages`（后两者同样未从包根导出）；
> - `compact()` 需要**尾参 `context`**（`signal?` 参数已被它取代）。
>
> 这三处是 session 写入面整体换模型（v0.85）的连带，不是压缩算法变化。

```typescript
import {
  buildSessionContext, compact, DEFAULT_COMPACTION_SETTINGS,
  estimateContextTokens, prepareCompaction, shouldCompact,
} from "@earendil-works/pi-agent-core";
import { createModels, type Models, uuidv7 } from "@earendil-works/pi-ai";

const models: Models = createModels(); // getModel 是 Models 接口的方法（models.ts:170），不是顶层函数 // Models 接口负责 auth 解析
const model = models.getModel("anthropic", "claude-sonnet-4-5")!; // contextWindow = 200000
const settings = DEFAULT_COMPACTION_SETTINGS;

// 获取 session 的当前路径（root → leaf 时间序，默认查询是 leaf → root，需指定 order）
const pathEntries = await session.findEntriesOnBranch({ order: "oldestFirst" });
const context = buildSessionContext(pathEntries);

// 估算当前上下文 tokens（来自 provider 上报 + 启发式）
const estimate = estimateContextTokens(context.messages);
console.log(`当前上下文: ${estimate.tokens} tokens ` +
  `(provider 上报: ${estimate.usageTokens}, 尾部估算: ${estimate.trailingTokens})`);

// 判断是否需要压缩（enabled = false 时恒为否）
if (!shouldCompact(estimate.tokens, model.contextWindow, settings)) return;

// 准备压缩数据
const prep = prepareCompaction(pathEntries, settings);
if (!prep.ok) throw prep.error;
if (!prep.value) return; // 无可压缩内容（如最后一条已是 compaction）

const { messagesToSummarize, retainedTail } = prep.value;
console.log(`压缩 ${messagesToSummarize.length} 条消息，` +
  `保留尾部 ${retainedTail.length} 条`);

// 执行压缩（v0.85.1 完整签名：customInstructions / thinkingLevel / retry / callbacks / context）
const result = await compact(prep.value, models, model);
if (!result.ok) throw result.error;

// 持久化为自包含的 CompactionEntry（parentId/seq/timestamp 由 storage 赋值）
await session.appendEntry(
  {
    type: "compaction",
    id: uuidv7(),
    summary: result.value.summary,
    tokensBefore: result.value.tokensBefore,
    retainedTail: result.value.retainedTail,
    usage: result.value.usage,
    details: result.value.details, // { readFiles, modifiedFiles }
  },
  "main",
);

console.log("压缩完成");
console.log(`摘要 (前 200 字): ${result.value.summary.slice(0, 200)}...`);
// 此后 buildSessionContext 得到的消息序列为：
// [compactionSummary, ...retainedTail, ...compaction 之后新增的条目]
```

这个例子展示了压缩的完整决策链路：估算 → 判断 → 准备 → 执行 → 持久化。压缩后的 CompactionEntry 自带 retainedTail，后续的 `buildSessionContext` 会自动展开压缩边界。
