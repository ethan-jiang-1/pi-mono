# 4.2 Skills：从文件到 prompt 的能力注入机制

> **⚠️ v0.83.0**：`skills.ts` 仅 import style 变化（`.js`→`.ts`），无实质 API 变更。
>
> **⚠️ v0.84.2**：v0.84 修复 Windows 递归 skill 加载的路径处理（`relativeEnvPath()`/`dirnameEnvPath()` 统一处理 `\\` 分隔符），无 API 变化。2026-08-17 已对照 v0.84.2 复核，正文已修正至 v0.84.2（重锚行号、更正显式调用路径与 `loadSourcedSkills` 的使用方、更正示例 import 路径）。

## 现象是什么

pi-mono 有一个 skills 系统：用户或扩展可以在特定目录放 `SKILL.md` 文件，定义专门的领域知识和操作指令。当 LLM 需要执行特定领域的任务时，它可以"调用"对应的 skill——实际上就是把 skill 的完整内容注入当前对话。

从外部看：有一个 `<available_skills>` XML block 在 system prompt 里列出所有可用 skill；有一个 `<skill name="..." location="...">` 的引用格式把 skill 内容注入用户消息。

## 核心矛盾是什么

Skills 不是普通的 prompt 指令。它们有几个特殊要求：

1. **发现（discovery）**：需要递归遍历目录找到 `SKILL.md`，但要遵守 `.gitignore`/`.ignore`/`.fdignore`
2. **解析（parsing）**：YAML frontmatter 包含元数据，body 是实际内容
3. **注入（injection）**：有两种方式——model-driven（LLM 看到 skill 列表后主动决定使用）和 direct（用户或程序显式调用）
4. **容错（resilience）**：一个 skill 文件解析失败不应该阻止其他 skill 加载或应用启动

核心矛盾：**Skills 是文件系统中的非结构化知识，但需要变成结构化的 agent 能力，而且加载过程必须鲁棒。**

## 实现思想是什么

### Skill 接口

```typescript
interface Skill {
  name: string;                    // 稳定名称，用于查找和 LLM 可见列表
  description: string;             // 简短描述，告诉 LLM 什么时候用
  content: string;                 // 完整指令内容
  filePath: string;                // SKILL.md 的绝对路径（用于 LLM 解析相对引用）
  disableModelInvocation?: boolean; // 不显示在 <available_skills> 中，只能显式调用
}
```

定义在 `harness/types.ts:46`。注意 coding-agent 有自己的平行实现 `coding-agent/src/core/skills.ts:74`（同步 `fs` 版本，`Skill` 多了 `baseDir`/`sourceInfo` 字段）——产品实际跑的是后者，harness 版本通过 `ExecutionEnv` 抽象文件系统。

### 加载流程（loadSkills）

`loadSkills(env, dirs)`（`harness/skills.ts:49`）接收一个或多个目录路径，返回 `{ skills, diagnostics }`：

1. **入口检查**：对每个目录，先 `env.fileInfo(dir)` 检查是否存在。`not_found` 直接跳过（不报错），其他错误记录为 `file_info_failed` diagnostic
2. **递归扫描**：`loadSkillsFromDirInternal()`（L103）递归遍历目录树
3. **Ignore 规则**：`addIgnoreRules()`（L177）在每个目录中查找 `.gitignore`、`.ignore`、`.fdignore`，用 `ignore` 库构建匹配器。路径前缀由 `prefixIgnorePattern()`（L225）根据相对 root dir 的位置自动处理（例如 subdir 中的 pattern 会加上 `subdir/` 前缀），并处理 `!` 取反、`\#` 转义、`/` 开头锚定
4. **Skill 文件匹配**：每个目录先在直接子项里找严格名为 `SKILL.md` 的文件，找到即加载**并立即返回**（一个目录最多产出一个 SKILL.md skill）。没有 SKILL.md 时，才把本目录其他 `.md` 文件当作 skill 加载——且仅当 `includeRootFiles` 为 true，即只有 root 目录第一层（递归调用传入 false）
5. **目录过滤**：跳过 `.` 开头的隐藏目录和 `node_modules`（L152）；第二遍扫描的子项按文件名排序
6. **符号链接处理**：`resolveKind()`（L328）先检查 `FileInfo.kind`，若是 symlink 则用 `env.canonicalPath()` 解析目标后再判断

### YAML Frontmatter 解析

`parseFrontmatter()`（L312）使用简化的 frontmatter 解析器（不依赖 gray-matter）：

1. 先把内容统一为 `\n` 换行；如果不是以 `---` 开头，整个内容就是 body
2. 找 `\n---` 分隔符，提取中间部分用 `yaml` 库的 `parse()` 解析
3. 支持的 frontmatter 字段：
   - `name`: skill 名称（如果不提供，使用父目录名）
   - `description`: 描述（**必需**，缺失或为空则 skill 不被加载，但其他 skill 不受影响）
   - `disable-model-invocation`: 不在 `<available_skills>` 中列出
4. 验证规则（`validateName()` L290 / `validateDescription()` L302）：
   - name 和父目录名不一致只报警告（`invalid_metadata` diagnostic），不阻止加载
   - name 只能包含 `[a-z0-9-]`，不能以 `-` 开头/结尾，不能有连续 `--`
   - name 最长 64 字符，description 最长 1024 字符

### 两种注入路径

**路径 A - Model-driven（LLM 自主选择）：**

`formatSkillsForSystemPrompt(skills)`（`harness/system-prompt.ts:3`）生成 `<available_skills>` XML block：

```xml
The following skills provide specialized instructions for specific tasks.
Read the full skill file when the task matches its description.
When a skill file references a relative path, resolve it against the skill directory...

<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract, merge, and convert PDF files</description>
    <location>/home/user/.pi/agent/skills/pdf-processing/SKILL.md</location>
  </skill>
</available_skills>
```

这个 block 会出现在 system prompt 中（coding-agent 侧由 `formatSkillsForPrompt()`，`core/skills.ts:335` 生成，措辞略不同："Use the read tool to load a skill's file..."）。当 LLM 判断任务匹配某个 skill 的描述时，它会通过 read 工具读 `SKILL.md` 文件。

**路径 B - Direct invocation（显式调用）：**

harness 线的辅助函数 `formatSkillInvocation(skill, additionalInstructions)`（`harness/skills.ts:38`）生成：

```xml
<skill name="pdf-processing" location="/home/.../SKILL.md">
References are relative to /home/.../skills/pdf-processing.

[skill content]
</skill>

Extract pages 1-5 from report.pdf
```

整个 XML block 作为用户消息发送给 LLM。产品里的实际入口是 TUI 的 `/skill:name [args]` 斜杠命令：`AgentSession._expandSkillCommand()`（`coding-agent/src/core/agent-session.ts:1309`）读取 SKILL.md、剥掉 frontmatter、拼出同样的 skill block 再随用户消息发出；反向解析则由 `AgentSession.parseSkillBlock()`（同文件 L129）完成，TUI 用它把这类消息渲染成可折叠的 SkillInvocation 组件。（`AgentLane` 接口上有 `skill(name, additionalInstructions?)` 方法（`agent-harness.ts:276`），但 v0.84.2 的 `AgentHarness` 骨架对它抛 `HarnessNotImplemented`，见 4.1。）

### 扩展来源的 Skills

harness 线提供 `loadSourcedSkills<TSource>()`（L83）：给每份加载结果附加调用方自定义的 `source` 标记（泛型，agent 包不解释其含义，可配 `mapSkill` 转换）。注意 **coding-agent 目前并不使用它**——产品的 extension skill 发现走 `resources_discover` 事件（runner 收集 `skillPaths + extensionPath`），再由 `resource-loader` → 自己的同步 `loadSkills()`（`core/skills.ts:387`）加载，source 语义是 `user`/`project`/`path` 三种目录来源标签。`loadSourcedSkills` 是 harness v2 线为外部 harness 构建者准备的能力。

### 诊断系统

`loadSkills()` 不会因为单个文件的加载失败而崩溃。所有失败都以 `SkillDiagnostic` 的形式返回（L19）：

```typescript
interface SkillDiagnostic {
  type: "warning";         // 目前只有 warning
  code: SkillDiagnosticCode; // file_info_failed | list_failed | read_failed | parse_failed | invalid_metadata
  message: string;
  path: string;            // 关联的文件路径
}
```

这种行为保证了一个损坏的 `SKILL.md` 不会让整个应用启动失败。（coding-agent 的同步版另外还有 `collision` 级诊断：同名 skill 按加载顺序先到先得，后到者记入 collision diagnostic。）

## 在 Agent 能力面里的影响是什么

1. **Skills 是知识注入的标准通道**。任何需要"特定领域深度知识"的场景（PDF 处理、数据库迁移、部署流程）都通过 skills 注入，而不是硬编码在 system prompt 里。

2. **模型自主调用 + 程序显式调用双路径**。模型通过 system prompt 中的 `<available_skills>` 列表知道有哪些 skills 可用；用户/程序通过 `/skill:name` 强制使用某个 skill。

3. **Skills 的 "location" 是真实文件路径**。这意味着 LLM 可以通过 read 工具访问 skill 文件的完整内容，而且 skill 内容中的相对路径引用是可解析的（block 头部显式告知了基准目录）。

4. **加载的容错性保证了稳定性**。任何一个 skill 文件的格式错误不会影响整体系统。

## 最小例子是什么

```typescript
// v0.84.2：包不再导出 "./harness" 子路径，harness 工具从主入口导入
import { loadSkills, formatSkillsForSystemPrompt, formatSkillInvocation } from "@earendil-works/pi-agent-core";

// 1. 加载 skills（容错，返回 diagnostics）
const { skills, diagnostics } = await loadSkills(env, ["/home/user/.pi/agent/skills"]);
if (diagnostics.length > 0) {
  console.warn("Skill loading warnings:", diagnostics);
}

// 2. 生成 system prompt 块
const skillBlock = formatSkillsForSystemPrompt(skills);
// 输出:
// <available_skills>
//   <skill>
//     <name>pdf-processing</name>
//     <description>...</description>
//     <location>...</location>
//   </skill>
// </available_skills>

// 3. 显式调用一个 skill（harness 辅助函数）
const mySkill = skills.find(s => s.name === "pdf-processing")!;
const prompt = formatSkillInvocation(mySkill, "Merge these files");
// 输出: "<skill name=\"pdf-processing\" location=\"...\">\nReferences are relative to ...\n\n...content...</skill>\n\nMerge these files"
// 产品里的等价操作：在 pi TUI 输入 "/skill:pdf-processing Merge these files"

// 4. 如果需要 disable model invocation（只在显式调用时可用）
const hiddenSkill = {
  name: "internal-cleanup",
  description: "Internal cleanup routines",
  content: "Remove temp files...",
  filePath: "/path/to/SKILL.md",
  disableModelInvocation: true, // 不会出现在 <available_skills> 中
};
```

可观察信号：把一个 `description` 留空的 `SKILL.md` 放进 skills 目录——它会出现在 `diagnostics`（`invalid_metadata: "description is required"`）且不出现在 `skills` 里，其余 skill 照常加载；在 pi TUI 中输入 `/` 可以看到 `skill:<name>` 自动补全项。
