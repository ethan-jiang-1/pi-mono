# 3.4 Session Tree: 以树形结构承载记忆

> **⚠️ v0.83.0**：新增 `ActiveToolsChangeEntry` session entry type；`SessionStorage` 新增 `getSessionName()`、`getSessionStats()`；`JsonlSessionCreateOptions.metadata`；RPC 新增 `get_entries`/`get_tree`。
>
> **⚠️ v0.84.0（重要）**：本文描述的 agent 包 session 模型（`SessionTreeEntry`、旧 `SessionStorage`/JSONL/in-memory repo API）已被 **v4 lane-based 模型整体取代并删除**（v0.84.0 breaking）。新的 `Entry` 7 种类型 + `LaneRecord` operation 流水 + 全局 seq 见 [3.5 Session v4](./3.5_Session_v4.md)。注意：`coding-agent` 的 `SessionManager`（本文多处引用）是独立实现，未被替换，其行为大体仍如本文所述。

## 现象是什么

pi-mono 的会话不是线性列表，而是一棵 append-only 的树。对话的每个节点（消息、模型切换、压缩事件、分支摘要）都是树中的一个 `SessionTreeEntry`。用户可以从任意历史节点"分叉"出新的对话路径，在不同分支间导航，并在导航时自动生成分支摘要。这棵树同时是"持久化格式"和"上下文重建的输入"。（解释）

**源码位置：**
- `/packages/agent/src/harness/session/session.ts`（`Session` 类的树操作方法）
- `/packages/agent/src/harness/types.ts`（`SessionTreeEntry`、`LeafEntry`、树结构定义）
- `/packages/coding-agent/src/core/session-manager.ts`（JSONL 格式的 `buildSessionContext`）

## 核心矛盾是什么

线性对话列表无法表示"用户尝试了方案 A，不满意，回到提问点尝试方案 B"的场景。如果用线性列表，方案 A 的消息要么被删除（丢失历史），要么保留（混淆模型）。树形结构可以让两个方案共存于不同分支，但带来了新的挑战：

1. **当前状态的定义：** 如果对话是一棵树，"现在在哪个位置"（leaf）成了一个需要追踪的元信息。（解释）
2. **上下文的线性重建：** LLM 需要的是线性消息列表，从树的当前 leaf 走到 root 的路径需要被转换为线性上下文。（解释）
3. **不变性与可导航性：** Append-only 保证历史不会被修改，但用户需要"回到过去"的能力——这通过导航（moveTo）+ 分支摘要来实现。（解释）

## 实现思想是什么

### 树的核心结构

```
每个 SessionTreeEntry 都有:
  - id: string          (节点唯一标识)
  - parentId: string|null  (父节点 id，root 为 null)
  - timestamp: string    (ISO 时间戳)
  - type: string         (discriminator)
```

树的"当前位置"由一个特殊的 `LeafEntry` 追踪：

```typescript
interface LeafEntry extends SessionTreeEntryBase {
  type: "leaf";
  targetId: string | null;  // 当前活动节点 id，null 表示 root 之前
}
```

每次 `moveTo(entryId)` 都会在树中追加一个新的 `LeafEntry`（通过 `setLeafId`），更新当前位置。（硬事实）

### 树的操作

**getBranch(fromId?)：** 从给定节点（默认 leaf）开始，沿 `parentId` 向上走到 root，返回路径上的所有 entry。这是树的最基本操作，所有上下文构建都依赖于它。（硬事实）

```
leaf → parent → parent → ... → root
```

**buildContext()：** 调用 `getBranch()` + `buildSessionContext()`：
1. 扫描路径，提取最后出现的 `thinkingLevel`、`model`、所有 `CompactionEntry`。
2. 如果存在 CompactionEntry，在 `firstKeptEntryId` 处截断。
3. 提取所有 MessageEntry、CustomMessageEntry、BranchSummaryEntry 的消息。
4. 返回 `{ messages: AgentMessage[], thinkingLevel: string, model: {provider, modelId} | null }`。

> ⚠️ 本节描述的 Compaction 边界逻辑是 **coding-agent `SessionManager` 的实现**（保留 `firstKeptEntryId`，无 `retainedTail`，见 3.1/3.5）；agent 包 v4 的 `buildSessionContext` 用的是 `retainedTail` 自包含模型。

**moveTo(entryId, summary?)：** 
1. 验证 `entryId` 存在于树中。
2. 调用 `setLeafId(entryId)` 更新 leaf 指针。
3. 如果提供了 `summary`，追加一个 `BranchSummaryEntry`（`parentId = entryId`，记录从旧 leaf 到 entryId 的废弃分支摘要）。

**appendMessage / appendModelChange / appendThinkingLevelChange / appendCompaction：**
所有追加操作都在当前 leaf 下创建新节点（`parentId = currentLeafId`），并自动更新 leaf 为新节点。这是 append-only 的保证——从未修改已有节点，只在树的最前端追加。（硬事实）

### Fork 机制

`SessionRepo.fork(source, options)` 创建一个从 source 会话的某个 entry 点复制出来的新会话：（硬事实）
- `options.entryId`：从哪个节点 fork。（硬事实）
- `options.position`：`"before"`（在该节点之前 fork）或 `"at"`（在该节点处 fork）。（硬事实）

Fork 实际上创建了一个全新的 JSONL 文件，复制 source 会话中从 root 到 fork 点的路径上的所有 entry。（硬事实）

### 一致性保证

1. **Append-only：** 所有写操作都追加新 entry，不修改已有 entry。这是通过 `SessionStorage.appendEntry()` 和 `SessionStorage.setLeafId()` 的接口设计强制保证的——没有 `updateEntry` 或 `deleteEntry` 方法。（硬事实）

2. **Leaf 追踪：** LeafEntry 是唯一可以被"覆盖"的东西（通过 `setLeafId`），但这本质上是追加新的 LeafEntry，旧的 LeafEntry 仍保留在树中作为历史记录。（硬事实）

3. **JSONL 不变性：** JSONL 格式天然支持 append（在文件末尾追加一行）（解释），`SessionManager` 使用 `appendFileSync` 实现写操作，确保磁盘上的 session 文件总是有效的。（硬事实）

### 上下文重建中的 Compaction 边界处理

`buildSessionContext()` 在处理 compaction 时有精密的逻辑：（硬事实）

```
如果路径中存在 CompactionEntry:
  1. 在路径中找到 compaction entry 的位置 (compactionIdx)
  2. 生成一条 compactionSummary 消息（作为上下文的第一条）
  3. 找到 firstKeptEntryId 在路径中的位置
  4. 从 firstKeptEntryId 开始，保留到 compaction entry 之前的 entry
     但跳过 compaction entry 之前的 compaction entry（嵌套 compaction）
  5. 保留 compaction entry 之后的所有 entry
```

这确保了：
- 压缩后的模型看到的是"摘要 + 压缩点之后的完整对话"。（解释）
- 如果历史上有多次 compaction（嵌套压缩），每次的 `firstKeptEntryId` 都会被正确跟踪。（解释）
- BranchSummaryEntry 也被包括在上下文中（`createBranchSummaryMessage`）。（硬事实）

## 在 Agent 能力面里的影响是什么

- **对话的持久性与可重放性：** JSONL 树形格式允许完整重放会话——读取文件，逐行解析，重构树结构，从 root 走到任意 leaf 构建上下文。（硬事实）
- **分支即历史：** 所有尝试都被保留在树中，用户可以在 "尝试方案 A" 和 "尝试方案 B" 之间自由切换，而不会丢失任何信息。（解释）
- **扩展的数据通道：** `CustomEntry` 和 `CustomMessageEntry` 让扩展可以在一等公民的层面上持久化状态，与对话历史一起被保存和加载。（解释）
- **Compaction 是树的一部分：** 压缩不是一个"全局重置"，而是在树的特定位置插入的 CompactionEntry。后续从该点 fork 的对话自动继承了压缩的上下文。（解释）

## 最小例子是什么

```typescript
// ⚠️ 本示例是 v0.83 及更早的 agent 包 session 写法；v0.84 起这些符号已删除。
// 现在的最小例子见 3.5（Session v4：InMemorySessionStorage / JsonlSessionRepo + SessionTree）与 4.1。
import { Session, SessionStorage } from "@earendil-works/pi-agent-core";

// 初始化 session
const storage = new JsonlSessionStorage("session-abc", "./sessions/session-abc.jsonl");
const session = new Session(storage);

// 追加消息 - 自动构造树节点
const userMsgId = await session.appendMessage({
  role: "user",
  content: "Write a Python script",
  timestamp: Date.now(),
});

const asstMsgId = await session.appendMessage({
  role: "assistant",
  content: [{ type: "text", text: "Here is a Python script..." }],
  api: "anthropic-messages",
  provider: "anthropic",
  model: "claude-sonnet-4-5-20250929",
  usage: { input: 500, output: 200, cacheRead: 0, cacheWrite: 0, totalTokens: 700,
           cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 } },
  stopReason: "stop",
  timestamp: Date.now(),
});

// 树结构:
// root → userMsgId → asstMsgId (leaf)

// 查看当前分支
const branch = await session.getBranch();
console.log(`从 leaf 到 root 共 ${branch.length} 个节点`);

// 导航回用户消息之前，看看另一个方向
await session.moveTo(userMsgId, {
  summary: "已尝试 Python 方案，现在考虑 JavaScript 替代方案",
});

// 树结构变为:
// root → userMsgId (leaf)
//       └→ asstMsgId
// root → userMsgId → BranchSummaryEntry(parentId=userMsgId)

// 在新 leaf 下追加新消息（开始新分支）
await session.appendMessage({
  role: "user",
  content: "Write a JavaScript script instead",
  timestamp: Date.now(),
});

// 树结构现在有两个分支:
// 分支1: root → userMsgId → asstMsgId
// 分支2: root → userMsgId → BranchSummaryEntry → newUserMsg (leaf)

// 重建上下文
const context = await session.buildContext();
// context.messages = [BranchSummary(告诉模型之前的Python探索), newUserMsg]
// context.thinkingLevel = "off"
// context.model = { provider: "anthropic", modelId: "claude-sonnet-4-5-20250929" }
```

这个例子展示了树结构的三个核心操作：消息追加（自动管理 parentId 和 leaf）、分支导航（moveTo + 分支摘要）、上下文线性重建（buildContext 将树路径展平为消息列表）。
