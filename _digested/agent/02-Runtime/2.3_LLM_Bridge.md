## 现象是什么

pi-mono 支持 Anthropic、OpenAI、Google、AWS Bedrock、DeepSeek、GitHub Copilot、OpenRouter、Groq 等三十多个 Provider，每个 Provider 的消息格式、流式协议、thinking/reasoning 参数、cache control 机制各不相同。但从 Agent Runtime 的视角看，它们全部收敛到同一个接口：`streamSimple(model, context, options) → AssistantMessageEventStream`。（硬事实）

**源码位置：**
- `/packages/ai/src/compat.ts`（顶层入口 `streamSimple`/`stream`/`completeSimple` + 全局 api-registry）
- `/packages/ai/src/api/`（各 API 协议实现模块 + `.lazy.ts` 懒加载包装）
- `/packages/ai/src/types.ts`（Model、Context、StreamOptions）
- `/packages/ai/src/models.ts`（`Models` 运行时类，auth-aware 的 `streamSimple` 方法）
- `/packages/ai/src/utils/event-stream.ts`（EventStream 通用实现）
- `/packages/ai/src/models.generated.ts`（自动生成的模型目录）

## 核心矛盾是什么

每个 Provider 的差异是多维度的：

- **API 协议不同：** Anthropic 用 Messages API（`/v1/messages`），OpenAI 用 Chat Completions（`/v1/chat/completions`）或 Responses（`/v1/responses`），Google 用 Generative AI SDK，Bedrock 用 Converse Stream。
- **Thinking/Reasoning 参数不同：** Anthropic 用 `thinking: { type: "enabled", budget_tokens: N }`，OpenAI Completions 用 `reasoning_effort`，OpenAI Responses 用 `reasoning`，DeepSeek 用 `thinking: { type: "enabled" }` 等。pi-mono 在两个包各自定义等级（注意分开说）：**ai 层** `types.ts:82` 的 `ThinkingLevel` 是 6 值（minimal/low/medium/high/xhigh/max，无 off），`types.ts:83` 的 `ModelThinkingLevel = "off" | ThinkingLevel` 补上 off 成 7 值；**agent 层**在 `types.ts:300` 独立定义自己的 7 值 `ThinkingLevel`（off…max）。两者名字相同但各自声明，别混用。（硬事实）
- **流式事件格式不同：** Anthropic 发 SSE 事件（`content_block_start/delta/stop`、`message_start/delta/stop`），OpenAI 发 `data: {"choices":[{"delta":...}]}`，Google 发 gRPC-like chunks。
- **Cache Control 机制不同：** Anthropic 用 `cache_control: { type: "ephemeral" }`，OpenAI 用 `prompt_cache_retention`。

pi-mono 需要在完全不暴露 Provider 差异的前提下，给上层（Agent Runtime）提供一个统一的、可替换的流式模型调用接口。（解释）

## 实现思想是什么

pi-ai 采用了**三层抽象**来解决 Provider 差异：（解释）

### 第一层：类型系统（`types.ts`）

定义了三个核心概念：

| 概念 | 含义 | 示例 |
|------|------|------|
| `Api` | 协议族名称（`KnownApi` 共 10 个） | `"anthropic-messages"`, `"openai-completions"`, `"openai-responses"`, `"google-generative-ai"`, `"bedrock-converse-stream"`, `"pi-messages"` … |
| `ProviderId` | 商业实体 + 网络端点 | `"anthropic"`, `"openai"`, `"deepseek"` |
| `Model<TApi>` | 具体模型，绑定到某个 Api | `{ id: "claude-sonnet-4-5-20250929", api: "anthropic-messages", provider: "anthropic", ... }` |

一个 Provider 可以提供多个 Api 协议的模型，但每个 Model 只属于一个 Api。`Model` 接口还携带 `contextWindow`、`maxTokens`、`cost`（tiered pricing）、`thinkingLevelMap`、`compat`、`samplingParams` 等元数据，这些来自自动生成的 `models.generated.ts`。

### 第二层：全局 Registry（`compat.ts`）

API 实现模块通过 `registerApiProvider()` 将自身注册到全局 `apiProviderRegistry` Map 中，key 是 Api 名称：

```typescript
registerApiProvider({
  api: "anthropic-messages",
  stream: anthropicStream,              // 接受 StreamOptions
  streamSimple: anthropicStreamSimple,  // 接受 SimpleStreamOptions
}, sourceId?);
```

compat 模块在加载时执行 `registerBuiltInApiProviders()`（compat.ts:213），把 10 个内置 API 注册进去且不覆盖已存在的自定义注册；`unregisterApiProviders(sourceId)` 供测试/扩展按来源撤销。

`streamSimple()` 的解析顺序（compat.ts:275-289）：先走 `getBuiltinProviderForModel()` 内置快路径（附带 env API key 注入 `withEnvApiKey`），否则 `resolveApiProvider(model.api)` 查注册表——未注册直接 throw `"No API provider registered for api: ..."`。这是一个**编译时类型安全**的注册模式——每个 provider 的 `stream` 函数使用泛型绑定到特定的 `TApi`（硬事实），注册时的 `wrapStream`/`wrapStreamSimple` 同时在运行时校验 `model.api` 匹配。（硬事实）

另一个入口是 `Models` 类（`models.ts`）：auth-aware 的运行时对象，`models.streamSimple(model, context, options)` 先解析 credential 再 dispatch 到 api 模块。Agent 的 `StreamFn` 契约与两者都兼容（`types.ts` 注明 "Models.streamSimple satisfies this shape"）。

### 第三层：统一事件流（`AssistantMessageEventStream`）

无论底层是什么 Provider，返回的流遵循统一的事件协议：

```
start → {partial: AssistantMessage}
  → text_start / text_delta / text_end
  → thinking_start / thinking_delta / thinking_end
  → toolcall_start / toolcall_delta / toolcall_end
→ done → {reason: "stop"|"length"|"toolUse"|"deferred", message: AssistantMessage}
  或 error → {reason: "error"|"aborted", error: AssistantMessage (stopReason="error"|"aborted")}
```

`EventStream<T, R>` 是一个通用的异步可迭代对象，内部维护一个队列 + 等待者列表。当 `push(event)` 被调用且 `isComplete(event)` 为 true 时，流终止。（硬事实）`result()` 返回一个 Promise，在流完成时 resolve 为最终结果；`AssistantMessageEventStream` 子类把 `done/error` 定为终止事件并提取最终消息（event-stream.ts:69-83）。

### SimpleStreamOptions 层

`SimpleStreamOptions`（types.ts:304-310）在 `StreamOptions`（temperature、maxTokens、signal、apiKey、transport、cacheRetention、timeoutMs、maxRetries、samplingParams 等）之上添加了 `reasoning?: ThinkingLevel`、`thinkingBudgets` 和 `deferred`（请求 provider 返回 durable handle 异步续跑）。这是 Provider 在 `streamSimple` 实现中解析为 provider 原生 thinking 参数的统一入口。

### 模型目录（`models.generated.ts`）

自动生成的模型目录包含所有已知模型的完整信息：id、name、api、provider、baseUrl、reasoning 支持、thinkingLevelMap、输入类型（text/image）、tiered 成本、contextWindow、maxTokens。它是一个大的常量对象 `MODELS`（models.generated.ts:44），第一层 key 是 provider 名，值为该 provider 各 modelId 的模型记录。（硬事实）

### HTTP 代理解析（`utils/node-http-proxy.ts`）

Provider 出站请求支持标准代理环境变量：`resolveHttpProxyUrlForTarget(targetUrl, env)` 解析 `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` 与 `NO_PROXY`（含通配符和端口匹配），返回代理 URL；SOCKS/PAC 协议不支持，会抛 `UNSUPPORTED_PROXY_PROTOCOL_MESSAGE`。（硬事实）这是 Node 端 fetch 的代理支持，不是浏览器端的代理流方案。

## 在 Agent 能力面里的影响是什么

- **Provider 无感切换：** Agent Runtime 只依赖 `StreamFn` 类型（本质上是 `typeof streamSimple`，见 `agent/src/types.ts:28-32`）。（硬事实）切换模型意味着换一个 `Model` 对象，无需改动任何 Runtime 代码。（解释）
- **Thinking 能力统一建模：** agent 层自有的 `ThinkingLevel` 从 `"off"` 到 `"max"` 共 7 个等级（agent types.ts:300，独立声明，与 ai 层的同名类型无关），被每个 Provider 的 `thinkingLevelMap` 映射为各自的实现（`null` 表示不支持），Agent 层只需要关心统一等级。（硬事实）
- **流式事件的可消费性：** `AssistantMessageEvent` 的每个事件都携带 `partial: AssistantMessage`（当时的完整消息快照），使得 UI 层不需要自己做状态重建。（解释）
- **Session-based caching：** `sessionId` 参数从 Agent 层一路传递到 Provider，Anthropic 和 OpenAI 各自利用其做 prompt caching 的 session affinity。（推测）

## 最小例子是什么

```typescript
import { streamSimple } from "@earendil-works/pi-ai/compat";

// 假设这是 claude-sonnet-4-5 模型定义（来自 models.generated.ts）
const model = {
  id: "claude-sonnet-4-5-20250929",
  name: "Claude Sonnet 4.5",
  api: "anthropic-messages" as const,
  provider: "anthropic",
  baseUrl: "https://api.anthropic.com",
  reasoning: true,
  input: ["text", "image"] as Array<"text" | "image">,
  cost: { input: 3, output: 15, cacheRead: 0.30, cacheWrite: 3.75 },
  contextWindow: 200000,
  maxTokens: 32768,
};

// 构建统一 Context
const context = {
  systemPrompt: "You are a helpful assistant.",
  messages: [
    { role: "user", content: "Hello!", timestamp: Date.now() },
  ],
};

// 流式调用 - Agent Runtime 只关心这个接口
const stream = streamSimple(model, context, {
  reasoning: "medium",   // 统一推理等级
  temperature: 0.7,
  maxTokens: 4096,
  apiKey: "sk-...",      // 或通过 getApiKey 延迟解析
  signal: abortController.signal,
  sessionId: "session-abc-123",
});

for await (const event of stream) {
  switch (event.type) {
    case "text_delta":
      process.stdout.write(event.delta); // 流式输出
      break;
    case "thinking_start":
      console.log("[思考中...]");
      break;
    case "thinking_delta":
      // 可选的思考过程展示
      break;
    case "toolcall_start":
      console.log(`[调用工具: ${event.partial.content[event.contentIndex]?.name}]`);
      break;
    case "done": {
      const msg = await stream.result();
      console.log(`消耗 ${msg.usage.totalTokens} tokens`);
      break;
    }
  }
}
```

这个例子展示了 LLM Bridge 的核心价值：上层代码只需关心 `streamSimple(model, context, options)` 这一种调用方式，所有 Provider 差异被 api-registry 和 provider 实现完全封装。
