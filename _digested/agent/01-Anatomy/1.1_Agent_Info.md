## 现象是什么

当你调用 `new Agent({...})` 创建一个 Agent 实例，或者通过 `createAgentSession()` 拿到一个 `AgentSession` 时，你拿到的不是一个简单的"发送 prompt、等待回复"的对话对象。Agent 携带了完整的执行人格：systemPrompt、model、thinkingLevel、tools、messages——以及一套覆盖 LLM 调用前后、工具执行前后、回合结束判断的钩子体系。

更关键的是，pi-mono 的 Agent **没有一个固定的角色概念**。OpenCode 有 build/plan/explore 三种 Agent 角色，每种角色预设了不同的 systemPrompt、temperature 和工具集。pi-mono 的 Agent 完全没有这个内置概念——systemPrompt 是什么、用什么工具、什么模型，全部由调用方通过 `AgentLoopConfig` 注入。Agent 只是一个"配备了所有行为出口的裸循环"。

## 核心矛盾是什么

**矛盾一：灵活性与默认行为的张力。** Agent 内核需要对外暴露足够的控制点让宿主（coding-agent 或外部 SDK 消费者）定义一切行为，但这些控制点太多了（`convertToLlm`、`transformContext`、`getApiKey`、`shouldStopAfterTurn`、`prepareNextTurn`、`getSteeringMessages`、`getFollowUpMessages`、`beforeToolCall`、`afterToolCall`……），直接使用 `packages/agent` 的学习成本很高。`coding-agent` 的 `createAgentSession()` 提供了一组合理的默认值（从 settings、模型注册表、资源加载器自动推导），解决了这个矛盾。

**矛盾二：状态可变但需要保护。** Agent 的 `state.tools` 和 `state.messages` 是公开可写的——扩展、会话管理器、UI 层都可能修改它们。但如果你让外部代码持有对内部数组的直接引用，并发修改会导致数据竞争。解决方式是 getter/setter 的 array-copy 保护：`set tools(t)` 执行 `tools = t.slice()`，`get tools()` 返回内部数组引用（读时不复制以节省性能）。

**矛盾三：单任务执行 vs 并发消息。** 当 Agent 正在 stream 时，用户可能又输入了新消息。Agent 不允许同时跑两个 prompt（`prompt()` 在 `activeRun` 存在时直接抛错），但提供了 `steer()` 和 `followUp()` 两个队列来注入中间消息。QueueMode 控制这些队列如何被消费："all" 一次排空 vs "one-at-a-time" 每次只消费一条。

## 实现思想是什么

`Agent` 类是 `packages/agent` 的核心导出，它是一个**有状态的轻量包装器**，围绕底层的 `runAgentLoop()` / `runAgentLoopContinue()` 函数构建。

设计思想可以归纳为三条：

1. **配置通过 `AgentLoopConfig` 注入，而不是通过子类化。** 所有行为差异（怎么把 AgentMessage 转成 LLM Message、要不要在某一轮后停止、怎么获取 API key、工具并行还是串行）都是配置项，不是虚方法。这保持了内核的纯净——它不知道 coding-agent、TUI 或任何具体产品的存在。

2. **事件驱动 + listener 模式。** `Agent` 内部通过 `processEvents()` 处理 agent-loop 产生的事件（`agent_start`、`turn_start`、`message_start`、`message_update`、`message_end`、`tool_execution_start`、`tool_execution_update`、`tool_execution_end`、`turn_end`、`agent_end`），先更新内部状态（`isStreaming`、`streamingMessage`、`pendingToolCalls`），然后按订阅顺序调用 listeners。`agent_end` 的 listener 执行完毕才算 run 结束，这保证了清理逻辑可以安全地观察到完整 run 状态。

3. **Steering 和 Follow-up 是两个时间维度的消息注入。** Steering 消息在每次 tool 执行完毕后检查（可以中断正在进行的工具执行循环），Follow-up 消息只在 agent 本应停止时检查。两者都使用 `PendingMessageQueue`，其 `drain()` 行为受 QueueMode 控制。

关键数据结构 `AgentState` 的字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `systemPrompt` | `string` | 每次模型请求携带的系统提示 |
| `model` | `Model<any>` | 当前使用的模型 |
| `thinkingLevel` | `ThinkingLevel` | 推理等级（off/minimal/low/medium/high/xhigh） |
| `tools` | `AgentTool<any>[]`（getter/setter 带 copy） | 可用工具列表 |
| `messages` | `AgentMessage[]`（getter/setter 带 copy） | 对话记录 |
| `isStreaming` | `boolean`（readonly） | 是否正在处理 |
| `streamingMessage` | `AgentMessage?`（readonly） | 当前流式消息的部分内容 |
| `pendingToolCalls` | `ReadonlySet<string>` | 正在执行的 tool call id |
| `errorMessage` | `string?` | 最近一次失败的 assistant turn 的错误信息 |

`AgentLoopConfig` 扩展自 `SimpleStreamOptions`（来自 pi-ai），额外加了大量钩子：

- **`convertToLlm`**（必填）：`AgentMessage[] -> Message[]`，把自定义消息转成 LLM 能理解的 user/assistant/toolResult 消息
- **`transformContext`**（可选）：`AgentMessage[] -> AgentMessage[]`，在 convertToLlm 之前执行，用于上下文窗口管理
- **`getApiKey`**（可选）：每次 LLM 调用时动态获取 API key（支持短期 token）
- **`shouldStopAfterTurn`**（可选）：回合结束后判断是否应停止
- **`prepareNextTurn`**（可选）：回合结束后返回下一轮的新 context/model/thinkingLevel
- **`getSteeringMessages`**（可选）：返回 steering 消息，在工具执行完成后注入
- **`getFollowUpMessages`**（可选）：返回 follow-up 消息，在 agent 本应停止时注入
- **`toolExecution`**（可选）：`"sequential" | "parallel"`，默认 `"parallel"`
- **`beforeToolCall`**（可选）：工具执行前，可 block
- **`afterToolCall`**（可选）：工具执行后，可修改 result

Agent 的公开 API 很简洁：

| 方法 | 说明 |
|---|---|
| `prompt(text)` 或 `prompt(messages)` | 启动新的 agent run（不能在有 activeRun 时调用） |
| `steer(message)` | 在工具执行完成后注入 steering 消息 |
| `followUp(message)` | 在 agent 本应停止时注入 follow-up 消息 |
| `abort()` | 中断当前 run |
| `subscribe(listener)` | 订阅 AgentEvent，返回取消订阅函数 |
| `waitForIdle()` | 等待当前 run 完全结束（包括 agent_end listeners） |
| `reset()` | 清除对话状态和队列 |
| `state`（getter） | 访问当前 AgentState |

## 在 Agent 能力面里的影响是什么

1. **Agent 角色不是内置的。** 不管是"代码编写 agent"还是"只读分析 agent"，都靠调用方配置 systemPrompt + tools 来选择，Agent 内核不区分角色。这让 pi-mono 的 Agent 更容易被嵌入任意场景——不需要对抗内置的角色假设。

2. **所有行为点都暴露为配置钩子。** 外部宿主可以在 LLM 调用前修改消息（`transformContext`）、在 token 过期时刷新 API key（`getApiKey`）、在特定条件下主动停止（`shouldStopAfterTurn`）、在工具执行前后做权限检查或结果改写——所有这些都不需要 fork 或 monkey-patch agent 源码。

3. **Steering 和 Follow-up 提供了两阶段异步消息注入。** 这让宿主可以实现"用户在中途插话"（steering）和"任务完成后自动追加下一步"（follow-up）两种交互模式，而不需要自己管理消息队列的并发。

4. **QueueMode 控制排队行为。** `"all"` 适合批量处理场景（一次性把所有排队消息注入），`"one-at-a-time"` 适合交互式场景（每次只处理一条，保留其他消息给后续轮次）。默认 steering 和 follow-up 都用 `"one-at-a-time"`。

## 最小例子是什么

```typescript
import { Agent } from "@earendil-works/pi-agent-core";

// 创建一个 Agent，只配置最少的必要项
const agent = new Agent({
  initialState: {
    systemPrompt: "You are a helpful assistant. Answer concisely.",
    model: myModel,  // 来自 pi-ai 的 Model<any>
    thinkingLevel: "off",
    tools: [],  // 无工具
  },
  convertToLlm: (msgs) => msgs.filter(m =>
    m.role === "user" || m.role === "assistant" || m.role === "toolResult"
  ),
});

// 订阅事件观察运行状态
agent.subscribe((event) => {
  if (event.type === "agent_start") console.log("Agent started");
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);  // 流式输出
  }
  if (event.type === "agent_end") console.log("\nAgent done, messages:", event.messages.length);
});

// 发送 prompt
await agent.prompt("What is 2+2?");
await agent.waitForIdle();  // 等待完全结束

// 你会观察到：
// - "Agent started" 日志
// - 流式输出的文本
// - "Agent done, messages: X" 日志
// - agent.state.messages 包含完整的 user + assistant 消息对
```

要模拟 steering 消息的注入：

```typescript
// 在 agent 运行过程中（比如在 event listener 里）：
agent.steer({ role: "user", content: [{ type: "text", text: "Also explain your reasoning." }], timestamp: Date.now() });
// 当前 turn 结束后，这条 steering 消息会被注入，agent 会继续产生新的 assistant 回复
```
