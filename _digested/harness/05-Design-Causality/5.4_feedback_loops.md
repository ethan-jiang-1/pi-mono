# 5.4 反馈三环:失败信号如何流动,pi 如何从失败里学

## 现象是什么

借 DSH harness-idea 09 的三环框架检验 pi:**轮内环**(环境事实 → 模型可见信号的塑形)、**会话环**(反馈 → 持久账本 → 投影/恢复)、**元环**(harness 自身的失败 → 规则回写)。三环在 pi 里都有明确的对应物,且分权立场与 DSH 相同——**harness 报告,模型/人裁决**。

![pi 的反馈三环](figures/feedback_three_loops.svg)

## 核心矛盾是什么

反馈链路的普遍张力:信号要**保真**(截断/摘要不丢关键事实)与**预算**(上下文有限)冲突;恢复要**可用**与**诚实**(不伪造已知结果)冲突。pi 在两个冲突上的选择都偏向后者,代价由模型与用户承担。

## 设计判断是什么

### 判断一:轮内环——失败是带旗标的普通结果,重试是模型的动作(硬事实)

pi 的工具结算合同把失败钉成三种模型可见形状:工具 throw/被 block/校验失败 → `isError: true` 的工具结果,循环不断(`packages/agent/src/agent-loop.ts:806-809,841-847`);上游请求失败 → stopReason `error`/`aborted` 的 assistant 消息,由 StreamFn 合同强制"不得 throw"(`packages/agent/src/types.ts:27-37`);截断响应的全部工具调用 → 一律判失败并要求重发(`agent-loop.ts:478-503`)。**没有 harness 侧重试**:重试与否是模型读着结果自己决定的下一个动作。与 DSH 的差异只在形状(DSH 用标记文本,pi 用 isError 旗标),分权立场一致。

### 判断二:会话环——事实先行,派生状态重放重建,恢复不伪造(硬事实 + 解释)

持久账本是 append-only JSONL 树(`session-manager.ts:977-986`);扩展的编排状态(todo/plan)存进工具结果 details 与 custom entry,**恢复时从账本重放重建**而非单独持久化副本(`todo.ts:114-133`、`plan-mode/index.ts:339-389`)。恢复的诚实性:进行中的 run 不复活,内存队列不还原([01](../../orchestration/01-loop.md) 边界节)——"重启后你得到的是事实,不是伪装的连续性"。compaction 是这套账本的预算机制(机制归 [`agent/03-Memory/`](../../agent/03-Memory/)),它在路径解析层工作(`session-manager.ts:517`),不改写历史。

### 判断三:元环——学习发生在仓库文本与检查脚本里,`AGENTS.md` 是回写产物(硬事实 + 解释)

pi 没有会话记忆回注;慢反馈的出口是**改规则与改脚本**。`AGENTS.md` 里多条规则读起来就是事故回写:全量 vitest 禁令的原因写明 "e2e tests that activate when endpoint/auth env vars are present"(`AGENTS.md:34`——一次"环境变量在场的 e2e 意外激活"被固化成了流程规则);lockfile 门禁与 install-lock 的生命周期脚本 allowlist(`:43-51` 节,install-lock 自 v1.0.1 起取代已删除的 npm-shrinkwrap,机制不变)是供应链教训的制度化;`npm run check` 全输出不截尾的要求(`:32`)同理。**与 DSH 元环的差别在封印强度**:DSH 的回写被 doc-sync 门禁与元验证把关,pi 的回写(AGENTS.md 修订、新 check 脚本)靠 review 与使用者自觉——回写本身无机器强制,这与 5.1 判断一的系统层边界一致。

### 判断四:三环共用的分权点——裁决权在人/模型,机械权在 loop(解释)

轮内环:是否重试、是否放弃,模型裁决;`beforeToolCall` 只在宿主真正拥有权限的地方拦截(块/早停,`types.ts:60-74`)。会话环:分支、恢复、批准(plan-mode 的 ui.select),人裁决。元环:规则采纳,维护者裁决。**pi 没有任何一处由 harness 自动"替你决定怎么办"**——这是与 DSH 同构、且比 DSH 更彻底的立场(DSH 至少在 goal 生命周期与基础设施失败处收走裁决权;pi 内核连长目标生命周期都不提供)。

## 影响是什么

1. **故障排查路径**:pi 出问题先分环——模型反复失败看轮内环信号(isError 文本质量);状态诡异看会话环(账本 vs 派生状态是否一致);同类事故反复出现,问元环缺了哪条规则/脚本。
2. **对 DSH 借鉴者的提醒**:pi 证明三环立场可以用极低的机器化成本维持;省下的是门禁体系,承担的是回写与文档的漂移风险(5.1/5.3 已判)。

## 源码锚点是什么

- `packages/agent/src/agent-loop.ts:806-809,841-847,478-503`:失败的三种塑形(判断一)
- `packages/agent/src/types.ts:27-37,60-74`:StreamFn 合同与宿主拦截权(判断一/四)
- `packages/coding-agent/src/core/session-manager.ts:977-986,517`:账本与路径解析(判断二)
- `AGENTS.md:32-51`:元环回写的文本证据(判断三)
- `packages/agent/src/agent.ts:374-378`:API 指路式反馈(判断一)

## 最小例证是什么

**例证 1(轮内环)**:构造一个 throw 的工具调用 → 观察 loop 收到 isError 结果并继续,而非中断。
**例证 2(元环)**:读 `AGENTS.md:34` 的禁令原文——规则的"事故成因"就写在规则里,这是回写产物的直接形态;对照:仓库内不存在"该规则曾被验证挡住回归"的负例记录(判断三的边界)。
